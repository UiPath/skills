## `trigger_detail.json` — what it captures and why

### Node type
`uipath.connector.trigger.uipath-microsoft-outlook365.email-received`  
This is the curated Outlook connector trigger; `registry search outlook trigger` resolves to this key.

### Top-level `--detail` fields

| Field | Value | Notes |
|---|---|---|
| `connectionId` | `<OUTLOOK_CONNECTION_ID>` | UUID from `uip is connections list 'uipath-microsoft-outlook365' --all-folders`. Must be a live connection ping-verified before `node configure`. |
| `folderKey` | `<ORCHESTRATOR_FOLDER_KEY>` | Orchestrator folder the connection lives in — required by the CLI for binding generation. |
| `eventMode` | `"polling"` | Outlook email-received is a polling trigger. If `registry get` returns `"webhooks"` on your tenant, change this field — the connector determines the mode, not the author. |
| `objectName` | *(omitted)* | Curated triggers bake the object name into the manifest; passing it would be ignored or cause an error. |

### `eventParameters`

```json
"eventParameters": { "parentFolderId": "<RESOLVED_INBOX_FOLDER_ID>" }
```

`parentFolderId` is the Outlook mail-folder parameter (the watched mailbox folder — typically your Inbox). It's a **reference field** that must be resolved with:

```bash
uip is resources run list 'uipath-microsoft-outlook365' 'MailFolder' \
  --connection-id <connectionId> --output json
```

Look for `displayName: "Inbox"` (or whichever folder you want) and use its `id` value. Never copy this ID from another flow — reference IDs are connection-scoped.

### `filter` — AND-combined, structured tree (not a string)

```json
{
  "groupOperator": 0,   ← 0 = AND, 1 = OR
  "index": 0,
  "filters": [
    { "id": "from",    "operator": "Equals",   "value": { "value": "abc@xyz.com", "rawString": "\"abc@xyz.com\"", "isLiteral": true } },
    { "id": "subject", "operator": "Contains", "value": { "value": "good day",    "rawString": "\"good day\"",    "isLiteral": true } }
  ]
}
```

- `groupOperator: 0` (AND) — **both** conditions must be true for the trigger to fire.
- `id: "from"` / `operator: "Equals"` — exact sender match against `abc@xyz.com`.
- `id: "subject"` / `operator: "Contains"` — substring match for `good day` in the subject.
- Each leaf value is wrapped in the `WorkflowValue` object (`value` + `rawString` + `isLiteral: true`) as required by the CLI — a bare string would be rejected.
- **`filterExpression` is deliberately absent** — it's a CLI output, not an input. Passing it directly causes a validation error (MST-8802).
