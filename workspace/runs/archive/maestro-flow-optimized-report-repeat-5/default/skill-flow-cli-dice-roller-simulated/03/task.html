### CLI-owned nodes → `uip maestro flow node add` + `node configure`
These are nodes whose `inputs.detail` field is a special `=jsonString:essentialConfiguration` envelope that the validator **rejects if hand-authored**. They must go through the CLI:
- Connector activities (`uipath.connector.<key>.<op>`)
- Connector triggers (`uipath.connector.trigger.<key>.<trigger>`)
- Managed HTTP (`core.action.http.v2`)

### User-owned nodes → direct `Edit` / `Write` on the `.flow` file
Everything else is intentionally authored as JSON directly:
- Triggers (`core.trigger.manual`)
- Control flow (`core.control.end`, `core.logic.decision`, loops, etc.)
- Logic nodes — **including `core.action.script`**

Both nodes in this flow (`core.action.script` and `core.control.end`) fall squarely in the user-owned category. There is no `uip maestro flow node add` path for them — or rather, if there were edge/node add CLI subcommands for user-owned types, using them would be going *against* the prescribed pattern.

## What a CLI-heavy flow would look like

If your dice roller had called, say, a Slack connector to *post* the result, that Slack node (`uipath.connector.slack.post-message`) would be CLI-owned. You'd see:

```bash
uip maestro flow node add DiceRoller.flow uipath.connector.slack.post-message --label "Post result to Slack"
uip maestro flow node configure DiceRoller.flow <nodeId> --detail '{"channel":"#general","text":"=js:$vars.rollDice.output.message"}'
```

That's exactly where the CLI commands are warranted — not for a simple script node.

So: **right tool, right node type**. If you'd like to extend the flow with a connector (e.g. post the roll to Slack or Teams), that's where the CLI-driven path would kick in.
