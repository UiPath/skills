The process structure, variables, script task, and diagram are complete and pass

## CLI-owned enrichment blockers

The following items **must** be resolved via the CLI before this project can be
packaged, uploaded, or run.  None of them can be hand-authored.

### 1. Slack connection ID (`Binding_SlackConn`)

**Blocker:** The `uipath:binding` element for `Binding_SlackConn` has an empty
`default=""` value.  Without a real connection ID, the IS node has no connection
to execute against.

**Resolution:**

```
uip is connections list  (with the all-folders flag)
```

Find the Slack connection entry.  Copy its `Id` value, then replace the
empty `default` in the `uipath:binding` element with that ID.

---

### 2. Connector operation metadata (activity, connectorKey, folderKey, method, path)

**Blocker:** The five IS context fields — `activity`, `connectorKey`,
`folderKey`, `method`, and `path` — are either empty or set to the sentinel
string `DRAFT_PENDING_CLI_ENRICHMENT`.  The sentinel satisfies the structural
validator but is not a real operation name; the process will fail at runtime.

**Resolution:**

```
uip maestro bpmn registry get Intsvc.ActivityExecution \
    (with the connection-id and object-name arguments)
```

Pass the connection ID found in step 1 and the desired Slack object name
(for example: `chat` for the chat-message operations).  The CLI response
returns an `ISEnrichment` block containing the live `connectorKey`,
`folderKey`, `method`, `path`, and the real operation name to put in
`activity`.  Replace all five context-field values in the BPMN with the
values from that block.

---

### 3. Dynamic body schema (request inputs for the Slack operation)

**Blocker:** The `body` CDATA for `Task_SendSlack` is `{}`.  Real Slack
operations require specific input fields (for example `channel` and `text`
for a message post).  These fields and their types come from the dynamic
connector schema generated by the enrichment step above.

**Resolution:**  After step 2, extract the input-schema fields from the
`ISEnrichment` response and populate the `body` CDATA JSON object with the
actual field names and their expression values (referencing process variables
via `=vars.Var_DigestText`, etc.).

---

### 4. Generated output schema (`Var_SlackResult`)

**Blocker:** `Var_SlackResult` is declared as `type="object"` with no inner
schema.  The concrete output field names come from the connector schema
generated by enrichment.

**Resolution:**  After enrichment, update the output mapping `source` path
if a specific field is needed (e.g. `source="=result.response.ts"` for the
Slack message timestamp).

---

### 5. `bindings_v2.json` — empty `resources` array

**Blocker:** `bindings_v2.json` was scaffolded with `"resources": []`.  For
a project that contains an `Intsvc.ActivityExecution` node, the CLI pack step
must populate this array with the live connection resource entry.

**Resolution:**  After steps 1–4, run:

```
uip maestro bpmn pack  (or the equivalent package command)
```

The pack command reads the connection binding and generates the complete
`resources` array.  **Do not hand-edit this file.**

---

### 6. Package metadata (`entry-points.json`, `operate.json`, `package-descriptor.json`)

**Blocker:** The five scaffolded metadata files (`project.uiproj`,
`operate.json`, `entry-points.json`, `bindings_v2.json`,
`package-descriptor.json`) were generated from the BPMN source by
`scaffold_metadata.py`.  They are structurally correct but are not the
authoritative CLI-generated artifacts required for upload.

**Resolution:**  Run the pack command after all enrichment blockers above
are resolved.  The pack command regenerates all five files with the correct
hashes, connection-resource entries, and dependency metadata.
