# UiPath IXP Document Extraction Assistant

Skill for UiPath IXP projects: create projects, upload documents, review predictions, improve extraction, and publish or deploy models.

## When to Use This Skill

Use for standalone IXP work: create/upload/label/review/confirm documents; improve extraction scores, prompts, or field instructions; publish/manage model versions; deploy, upgrade, or list deployments (`deployments create` / `upgrade` / `list`); import taxonomy; or retrieve taxonomy at a trained version (`deployments get-taxonomy <project-name> --version <N>`).

## When NOT to Use This Skill — defer to uipath-maestro-flow

For models, extractors, nodes, or any adding, wiring, referencing, or other work in a `.flow`/Maestro flow, STOP and invoke `uipath-maestro-flow` following its commands. Do not answer from this skill; this overrides Critical Rule 1.

**Inbound handoff exception:** if `uipath-maestro-flow` delegates because supplied documents have no published extractor, do the IXP work here: use the supplied Orchestrator folder without re-asking, create the project, deploy a trained version to that folder ([Deployment Guide](references/deployment-guide.md), including its no-folder exit), report deployment, and hand control back. Do not wire or edit the flow.

## Critical Rules

1. **Verify `uip ixp` syntax before running a command.** Use a targeted lookup in [CLI Reference](references/cli-reference.md), copy exact subcommand/options, and never guess. If unavailable, report that no documented CLI path exists; do not improvise, use curl, call REST APIs, or explore source. Flow/Maestro registry questions defer to `uipath-maestro-flow` — see *When NOT to Use This Skill* above.
2. Run workflows end-to-end automatically; never ask the user to perform individual steps.
3. Always use `--output json` when parsing CLI output.
4. Work in `/tmp/ixp/<project-name>/`; at workflow start run `mkdir -p /tmp/ixp/<project-name>/{docs,taxonomies,payloads}`. Reuse `docs/` and `taxonomies/` — do not re-download documents already present; never reuse `payloads/`. `docs/` contains downloaded `<document-id>.pdf`, `.png`, … files; `taxonomies/` contains `v1.json`, `v2.json`, … snapshots; `payloads/` contains one-shot JSON request files (Rule 5). Do not use the Write tool for `/tmp/ixp/` paths because Windows resolves them elsewhere.
5. Pass JSON options as files, never inline JSON or use `"$(cat ...)"`. Write and pass a new file in the **same command** with `--updates-file <path>`, `--fields-file <path>`, or `--choices-file <path>`. Bash: `cat > /tmp/ixp/<project-name>/payloads/field_updates.json << 'EOF' ... EOF` then `uip ixp fields update-prompts <project-name> --updates-file /tmp/ixp/<project-name>/payloads/field_updates.json`. PowerShell: `Set-Content -Encoding utf8 -Path <file> -Value @'` … `'@` then the same `uip` call; without `-Encoding utf8`, Windows PowerShell corrupts non-ASCII text. Never pass an unwritten or earlier file: it may contain stale names or occurrence indices.
6. Never use `UID` as a variable name; it is readonly. Use `DOC_ID`, `DOCUMENT_ID`, etc.
7. Always use project `Name`, never `Title`. `project list` has both; commands require the lowercase `Name` slug with UUID and `-ixp` suffix.
8. Review each predicted field, not whole documents; confirm only correct fields and judge by taxonomy type, not literal page text. `Date` reads `YYYY-MM-DDTHH:MM:SSZ` (date-only uses `T00:00:00Z`); `Monetary Quantity` reads `<amount> <ISO-4217 code>`. Equivalent normalized values are **CONFIRMED**; do not reformat, calculate conversions, or script checks. Full mapping: [CLI Reference § Normalized output formats](references/cli-reference.md#normalized-output-formats). **Normalization changes only how a value is written — never what it means** (separators, trailing zeros, currency code vs symbol, date layout, century expansion); numeric magnitude must remain unchanged. A wrong magnitude remains wrong (page `£7,300.00` predicted as `£730.00` is a wrong value, not a normalization). A prediction disagreeing with the document remains UNANNOTATED and is never fixed: wrong answer/source, garbled characters (`MSIÓÓÓ601020/` for `MSI0601020`), digit/decimal error, flipped boolean, or wrong inferred/computed number. Without `--group`, `--fields` applies to every occurrence; see Rule 12.
   Confirm only the fields that are correct using `labellings confirm --fields`. **Judge a prediction by its taxonomy data type, not by the page's literal text** — a date-only page value comes back at `T00:00:00Z` (page `21-JUN-22` → `2022-06-21T00:00:00Z`), `Monetary Quantity` as `<amount> <ISO-4217 code>` (page `114.91` → `114.91 AUD`). Same value in normalized form is **CONFIRMED**.
9. Do not manually extract values. All labelling uses IXP predictions through `labellings confirm`; never substitute user-, prompt-, hint-, or agent-supplied values or commands — even when handed the right value or the command to write it; that is manual extraction, no matter how it is framed.
10. You are reviewer, not extractor: for each document compare predictions with the document and view it using one full `Read` without `pages` (native text and image for digital/scanned documents; no PDF tools). Confirm correct fields, skip wrong ones, and improve low-F1 fields by improving the prompt.
11. Mark missing only when IXP predicted no value and the field is genuinely absent. Check `get-predictions` first; never use missing to override a wrong prediction. Use `labellings mark-missing --fields <ids>`. `confirm --fields` marks an empty predicted value missing; use it in the review batch. `mark-missing` is additionally needed for a field absent from current predictions, such as stale annotation after model/taxonomy change, or a standalone mark.
12. For repeatable groups, confirm per occurrence when validation differs. Plain `confirm --fields <id>` confirms every occurrence. `get-predictions` supplies explicit 0-based `Occurrence`, scoped to that read (Rule 17). If all are correct use plain form; otherwise use `--group <name> --occurrence <N>` for one, or `--group <name> --updates-file <path>` for several atomically; `--occurrence <N>` equals a one-entry updates file. Copy the group's `Name` verbatim from `get-predictions`; never assemble it. Without `--fields`, confirm every predicted field in the occurrence; with it, only those. See [CLI Reference](references/cli-reference.md#labellings).
13. `confirm` is additive and never un-confirms. `confirm`/`mark-missing` retain existing annotations; use `unconfirm` to roll back. `--occurrence 0` on an already-labelled table yields "row 0 confirmed AND everything previously confirmed stays confirmed" — NOT "only row 0".
14. F1 measures prediction-versus-confirmed-label agreement, not document truth; blind confirmation can make a wrong value score 1.00. Sanity-check every value first. Per-document no-`--fields` confirmation is valid after reviewing all fields. If the user explicitly says every prediction in named documents was reviewed and correct, accept that and confirm without re-reviewing, but still pin the version (Rule 18). Never run `confirm` without a document-id. See [Label Documents Guide](references/label-documents-guide.md) §2d.
15. Ambiguous entity reference: ask, never guess. Projects (Titles), groups, fields, and data types share user-facing names. Before `update-title`, `rename`, `delete`, or `change-type`, resolve entity kind. If a name matches multiple kinds in context, `projects list`, or taxonomy, stop and list every candidate and kind; do not mutate one or several. If interactive questioning is unavailable, surface the question through the task channel and stop.
   If the name matches more than one kind — in the user's own context or in `projects list` / taxonomy output — STOP and ask which one, explicitly listing every matching candidate and its kind. Do NOT pick one, and do NOT mutate several candidates "to cover all cases".
16. Reuse built-in data types: `Exact Text`, `Inferred Text`, `Number`, `Date`, `Monetary Quantity`, `Boolean` (authoritative `entity_defs` from `projects get-taxonomy`). Before `data-types add` or choosing `--type`, reuse a matching default, such as `Monetary Quantity` for currency, never a hand-rolled clone (`Currency Amount`). Add custom type only when no default covers it, such as project-specific `Choice` or a concept needing tailored instructions; never add one only to reformat. Mapping: [CLI Reference § Default data types](references/cli-reference.md#default-data-types).
17. `Occurrence` belongs to the read that produced it. `get-predictions` lists annotated occurrences first, then unannotated; confirming one moves it to occurrence 0 and renumbers the rest while preserving values/page location. Put all per-occurrence targets in one `--updates-file` call. If sequential calls are unavoidable, rerun `get-predictions` after each and relocate rows by field values, never old indices. Only fully unannotated/annotated documents read in document order. Report rows by value ("the freight-surcharge line"), not index.
18. Confirm the reviewed version with `--model-version`: use the read's `ModelVersion` as `confirm -m <N>`. If retraining changed it, confirmation is rejected with `PredictionVersionChangedError`; reread, re-review, and confirm the new version. User-supplied review is no exception: pin the named `ModelVersion` or run one `get-predictions` to capture it; a version-only read is not a re-review.
19. `DeploymentName` differs from `DeploymentTitle`; `create` never repoints. `deployments create --title` sets free-form `DeploymentTitle`; runtime resolves `DeploymentName`, a slugged title plus unpredictable per-deployment suffix. Read it from the create response or `deployments list`; never construct it. `create` only adds. Repoint with `deployments upgrade <project-name> <deployment-name>` using `DeploymentName`, not title (title gives `404`), and run `deployments list` before every upgrade. Upgrading changes the version received by every runtime caller of that folder/name; confirm intent for shared folders. See [CLI Reference § Deployments](references/cli-reference.md#deployments).
20. `get-metrics` defaults to LATEST, not LIVE. Resolve first: for performing/production use live (`list-models` tag `live`; otherwise highest `Models[]` with `Pinned: true`; otherwise latest); for an improvement baseline use latest because edits retrain that model ([Improve Prompts Guide § 1a](references/improve-prompts-guide.md#1a-get-baseline-metrics)). Pass `--model-version <N>` and state the reported version.
21. Compare metrics by `FieldId`, report by `Name`. `Fields[]` includes `FieldGroup`, `FieldId`, and `Name`; do not fetch taxonomy. Names are unique only within groups; duplicate names must be shown as `<FieldGroup> / <Name>`. Join versions by `FieldId`, never `Name`, and report the current version's name. See [CLI Reference § `get-metrics`](references/cli-reference.md#projects).
22. Never switch projects without being asked. Resolve the instructed project's `Name` once and pass it everywhere. If you were not asked to, do not modify or continue the task on another project, however similar it looks. Diagnostic reads of another project are allowed; moving the task requires explicit approval. If you can't ask, report the blocker and stop; never report another project's results as this task's.
23. Never change an existing taxonomy by importing one. Import merges by name, cannot rename/remove, and overwrites same-name instructions. Use `projects import-taxonomy` only for a project with no taxonomy; use `groups`/`fields`/`data-types` and `projects update-prompt` for changes. `groups delete` + `groups add` is not replacement. If unsupported, report and route in-product ([Unsupported Capabilities](#unsupported-capabilities)); never substitute import, even when asked for one directly. Full mechanics: [CLI Reference § `import-taxonomy`](references/cli-reference.md#projects).

## Quick Start

1. Run `uip ixp projects list --output json`.
2. Create with [Project Setup Guide](references/project-setup-guide.md); improve with [Improve Prompts Guide](references/improve-prompts-guide.md); label with [Label Documents Guide](references/label-documents-guide.md).
3. For a folder-callable model: `projects create` → `list-models` → `deployments create --folder-key`; neither labelling nor `publish` is required. See [Deployment Guide](references/deployment-guide.md).

For supplied or copied taxonomy, use `--skip-taxonomy` and `import-taxonomy` (Project Setup Option B). Import never edits a nonempty taxonomy (Rule 23).

## Task Navigation

- **Create/upload:** New project or upload to a new project uses [Project Setup Guide](references/project-setup-guide.md). Existing uploads use `uip ixp documents upload <project-name> <file> --output json`, one file per call. See [CLI Reference § Uploading documents](references/cli-reference.md#uploading-documents-to-an-existing-project).
- **Taxonomy:** Supplied/copied taxonomy uses Option B: `--skip-taxonomy` + `import-taxonomy`; export with `projects get-taxonomy`. **The target's taxonomy must be empty** — check the target with `projects get-taxonomy`; if `label_groups` is nonempty, use targeted `groups`/`fields`/`data-types`. Rename/edit/restructure/replace uses targeted commands and `projects update-prompt`, never `import-taxonomy` or `groups delete` + `groups add`.
- **Review/improve:** Use [Label Documents Guide](references/label-documents-guide.md) and [Improve Prompts Guide](references/improve-prompts-guide.md).
- **Publish:** `uip ixp projects publish <project-name> --output json`; add `--tag <live\|staging>`. Publishes latest, untagged unless tagged; see [cli-reference](references/cli-reference.md) for `--model-version`/`--description`. **Publishing does not deploy the model to an Orchestrator folder** — publish pins the version, and `--tag` moves the `live`/`staging` tag, which selects the version the DU framework serves (including to DU activities that call through it). Folder-resolving callers (Maestro Flow among them) see only `deployments create`. Do not chain deployment unless requested.
- **Rollback/restore:** `uip ixp projects publish <project-name> --model-version <N> --output json`; list versions with `uip ixp projects list-models <project-name> --output json`.
- **Unpublish/tag:** `uip ixp projects unpublish <project-name> --model-version <N> --output json` (`--model-version` required; removes publication, not training; find published versions via `list-models` (`Pinned: true`)); use `publish` to change live. Remove a tag only with `uip ixp projects untag <project-name> --tag <live\|staging> --output json`; do not `unpublish` or re-`publish` to clear it (`unpublish` removes publication, not the tag; `publish` without `--tag` leaves the existing tag untouched). `publish --tag staging` switches live→staging.
- **Deploy:** `uip ixp deployments create <project-name> --version <N> --folder-key <guid> [--title <title>] --output json`. `--version` comes from `list-models`; `--folder-key` from `uip or folders list --output json`; both required. Resolve named folders through that list; ask only if no folder was identified. Default title is project name minus `-ixp`; create never repoints (a title already deployed in that folder on a different version gives `409`; use upgrade); read `DeploymentName` from response. See [cli-reference § Deployments](references/cli-reference.md#deployments).
- **Upgrade/list:** `uip ixp deployments upgrade <project-name> <deployment-name> --version <N> --folder-key <guid> --output json`; use `DeploymentName` from `deployments list`, not title (`404`), confirm shared-folder intent, and target a version in `projects list-models`. It is not rollback. List with `uip ixp deployments list <project-name> --output json`; it returns `DeploymentName`, `DeploymentTitle`, `ModelVersion`, `FolderKey`, `DeployedAt`, or `[]`, and must precede upgrade. See [cli-reference § create vs upgrade](references/cli-reference.md#create-vs-upgrade).
- **Metrics:** `uip ixp projects get-metrics <project-name> --model-version <N> --output json`; always specify version, resolving live first when requested. For performing/F1, resolve the live version with `uip ixp projects list-models <project-name> --output json` per Rule 20, then run `uip ixp projects get-metrics <project-name> --model-version <live-version> --output json`. If `Data` is `{ Metrics: null }`, or `Result: Failure` with `ErrorCode: not_found` (no trained model, such as no confirmed labellings), report no metrics and stop. Otherwise report version, `TrainedTime`, `ProjectScore`/`ProjectScoreQuality`, each `FieldGroups[]` F1/Precision/Recall, and `Fields[]` lowest F1 first with F1, Precision, Recall, `Annotations`, and `ErrorRate` (= errors/`Annotations`, not `1 - Precision`). Ignore `Quality` labels ([Improve Prompts Guide § What get-metrics returns](references/improve-prompts-guide.md#what-get-metrics-returns-and-which-values-decide)); name/join by Rule 21. State numbers plainly; no "good enough" judgement unless asked; route low scores to [Improve Prompts Guide](references/improve-prompts-guide.md). Answer from these calls only — no ad-hoc discovery (Rule 1).
- **Projects/model:** List with `uip ixp projects list --output json`. Configure with `uip ixp projects configure-model <project-name> [options] --output json`. Read model/pre-processing with `uip ixp projects get-taxonomy <project-name> --output json`; read `Data.dataset._model_config`: `model_version` is the `--model` value (for example `gemini_2_5_flash`), and invert `input_config` to `none`/`table_mini`/`table` (`null` means unconfigured; report project default, not `none`). There is no `get-model-config`; `configure-model` is read-modify-write and must not be called for reading. Do not use `list-models.ModelName` (`gemini_ixp` labeller family). See [CLI Reference § Reading the current model and pre-processing](references/cli-reference.md#reading-the-current-model-and-pre-processing).
- **Delete:** `uip ixp projects delete <project-name> -y --output json`; permanent, irreversible, removes documents, taxonomy, models; `-y/--yes` required and CLI never prompts. Delete document with `uip ixp documents delete <project-name> <document-id> -y --output json`; irreversible and retrains; find a filename's `DocumentId` using `documents list` and `Filename`.
- **Taxonomy entities:** Groups: `uip ixp groups {add,delete,rename} <project-name> --name <name> ... --output json`; `groups add` requires `--instructions` and `--fields-file <path>` containing all new fields in one array; do not add one-by-one. `fields add` is for an existing group; delete requires `-y/--yes`. Data types: `uip ixp data-types {add,update-instructions,rename,delete} <project-name> --name <name> ... --output json`; `add` requires `--kind` (`text/date/money/number/boolean/choice`) and `--instructions`; `--input-value` is required only for `text` and `choice`, rejected for others; delete requires `-y/--yes` and breaks referencing fields. Reuse defaults (Rule 16). Fields: `uip ixp fields {add,delete,rename,change-type} <project-name> --group <name> --field <name> ... --output json`; delete requires `-y/--yes`; `change-type` deletes annotations and also requires it. See [CLI Reference § Groups](references/cli-reference.md#groups), [CLI Reference § Data Types](references/cli-reference.md#data-types), and [CLI Reference § Fields](references/cli-reference.md#fields).
- **Move field:** No move command. Read `type` and `instructions` with `projects get-taxonomy`; `fields add` to target, then `fields delete <source> -y`. Add first; both groups must exist. Never import edited taxonomy: import merges and duplicates the field. The recreated field has a new `field_id`, so labels do not follow; say this before starting. See [CLI Reference § Moving a field](references/cli-reference.md#moving-a-field-to-a-different-field-group).
- **Labeling:** Mark missing with `uip ixp labellings mark-missing <project-name> <document-id> --fields <ids> --output json` only when genuinely absent and IXP predicted nothing; empty predictions can instead be listed in `confirm --fields` (Rule 11). Unconfirm with `uip ixp labellings unconfirm <project-name> <document-id> --fields <ids> --output json`; it rolls back `confirm`/`mark-missing`, retaining other annotations. `--fields` alone affects all occurrences; target occurrences with `--group` plus `--occurrence <N>` or `--updates-file <path>`. Confirm one occurrence with `uip ixp labellings confirm <project-name> <document-id> --group <name> --occurrence <N> [--fields <ids>] --output json`; index is 0-based from latest `get-predictions`, without `--fields` confirms all predicted fields, otherwise only listed fields; other occurrences remain. Batch with `--updates-file <path>`; confirmation renumbers. Unconfirm one occurrence with `uip ixp labellings unconfirm <project-name> <document-id> --group <name> --occurrence <N> [--fields <ids>] --output json`; without fields unconfirm all annotated fields in that occurrence. Re-read first because confirmed rows sort first; use updates file for several.
- **`--fields` format:** pass all IDs as one comma-separated value — `--fields "a7c3e9105f2b4d86,b2f8a01c7d3e6940"` — never space-separated; this applies to `confirm`, `unconfirm` and `mark-missing`.
- **Prompts:** Overall prompt: `uip ixp projects update-prompt <project-name> --prompt "<text>" --output json`; it replaces taxonomy-wide instructions and differs from `fields update-prompts` and `groups update-prompts`.
- **Describe project:** In order: (1) `uip ixp projects get <project-name> --output json` for `Title`/`Name`; (2) `list-models` for live/published trained version and `TrainedTime` (the trained version, not the configured extraction model — for that see **Projects/model** above); (3) `uip ixp projects get-taxonomy <project-name> --output json` for counts under `Data.dataset.label_groups` and `Data.dataset.entity_defs`. Do not page `documents list` or read deployment bindings; its `Data` is `{ Documents, Total, Offset, Limit }`, with `Total` the count. Fold in performance (**Metrics** above) only if asked. Answer only from these calls.

## Unsupported Capabilities

These requests fall outside the skill: recognise the request, reply with the standard response, route the user. Do not enter discovery (`uip --help`, grep, source reading); follow Rule 1.

| User request | Standard response |
|---|---|
| Create a model/project | If documents, taxonomy, or a blank project are supplied/requested, use [Project Setup Guide](references/project-setup-guide.md). Otherwise: “I work on existing IXP projects rather than creating them from scratch. Create one in-product: https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/managing-projects — then I can label, review, and improve it.” |
| Upload/add documents | If a project is named/in context, upload using **Create/upload** in Task Navigation. Otherwise: “Name an existing project and I'll upload it — or upload in-product (e.g. for a new project): https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/building-and-deploying-models.” |
| Push to environment/tenant; deploy to staging/production | If the user names an Orchestrator folder (e.g. one literally called `Production`), it is supported: use folder deployment (**Deploy** in Task Navigation). Otherwise: “IXP has no environment or cross-tenant deploy target — a deployment is a (folder, version) pair inside one tenant.” Explain that `projects publish --tag staging\|live` moves the tag the DU framework (and DU activities calling through it) resolve — for those consumers that IS the staging/live switch; it creates no folder deployment. |
| Access/share/roles/permissions | “Access, roles, and permissions are managed in-product, not through this skill: https://docs.uipath.com/ixp/automation-cloud/latest/overview/managing-access.” |
| Use model in automation/workflow/agent/process | “Consuming a published model inside an automation is an authoring task outside this skill. See https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/building-and-consuming-a-workflow.” |
| Mine emails/communications | “Communications Mining is a separate IXP capability this skill doesn't cover (this skill is document extraction). See https://docs.uipath.com/ixp/automation-cloud/latest/cm-user-guide/introduction-to-uipath-communication-mining.” |
| Monitor deployment/runtime throughput/incidents | “Runtime/operational monitoring of a deployed model lives in Orchestrator, not this skill: https://docs.uipath.com/orchestrator/automation-cloud/latest/user-guide/about-monitoring. For design-time scores use `get-metrics` (see **Metrics** in Task Navigation).” |
| Replace/overwrite/import over existing taxonomy | “IXP has no replace-the-taxonomy operation — importing over an existing taxonomy merges into it and duplicates. I can apply the differences one by one with the targeted commands, or import the file into a **new** project if you want it clean (the existing project's documents and labels stay where they are).” List differences and let the user choose. |
| Edit Choice values | “The CLI can rename a data type, change its instructions (`data-types update-instructions`), or delete it — but it can't add or remove the **values** of an existing Choice data type. Do that by hand in-product on the Manage Taxonomy page: https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/managing-projects — then continue here.” |
| Read/add business rules | “The CLI can't read or update validation (business) rules. View or edit them by hand in-product on the Manage Taxonomy page — then continue here.” |
