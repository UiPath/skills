# UiPath IXP Document Extraction Assistant

Skill for standalone UiPath IXP projects: create projects, upload/review documents, improve extraction, manage versions, and deploy models.

## When to Use This Skill

Use for standalone IXP project creation; document upload; training a document extraction model; document labeling, review, or confirmation; extraction, score, prompt, or field-instruction improvement; model publishing/version management; deployment creation, upgrade, or listing; taxonomy import; or trained-version taxonomy retrieval (`deployments get-taxonomy <project-name> --version <N>`).

## When NOT to Use This Skill — defer to uipath-maestro-flow

This skill does not cover IxP/document-extraction models, extractors, or nodes available to a `.flow`/Maestro flow; adding, wiring, or referencing an IxP node inside a flow; or any `.flow`/Maestro-flow work. STOP, re-activate `uipath-maestro-flow`, and follow its commands; do not answer from this skill. This overrides Critical Rule 1.

**Inbound handoff exception:** If `uipath-maestro-flow` supplies documents with no published extractor, do the IXP work here despite flow context: use the supplied Orchestrator folder without re-asking, create the project, deploy a trained version to that folder ([Deployment Guide](references/deployment-guide.md), including its exit when no folder arrived), report the deployment, and hand control back. Do not wire or edit the flow.

## Critical Rules

1. **Verify `uip ixp` syntax before running a command** — use a targeted lookup in [CLI Reference](references/cli-reference.md), copy exact subcommand/options, and never guess. If undocumented, report that this skill has no documented CLI path; do not improvise. Never use curl, direct REST APIs, or source exploration. (Exception: defer flow/Maestro registry questions to `uipath-maestro-flow` — see *When NOT to Use This Skill* above.)
2. **Run workflows end-to-end automatically** — do NOT ask the user to do individual steps.
3. **Always use `--output json`** when parsing CLI output programmatically.
4. **Use `/tmp/ixp/<project-name>/` as the working directory with this structure:**
   ```
   /tmp/ixp/<project-name>/
   ├── docs/         # Document files (<document-id>.pdf, .png, …) — downloaded once, reused across sessions
   ├── taxonomies/   # Taxonomy snapshots (v1.json, v2.json, …) — new version after each update-prompts
   └── payloads/     # One-shot JSON request files (Rule 5) — never reused
   ```
   At workflow start run `mkdir -p /tmp/ixp/<project-name>/{docs,taxonomies,payloads}`. Reuse existing `docs/` and `taxonomies/`, never re-download them, never reuse `payloads/`, and never use the Write tool for `/tmp/ixp/` paths (Windows resolves it elsewhere).
5. **Pass JSON options as files** — never inline the JSON or use `"$(cat ...)"`: Windows cmd/PowerShell strip the quotes inside it. Write the JSON to a file and pass it with `--updates-file <path>`, `--fields-file <path>`, or `--choices-file <path>` in the **same command**. Never pass a file you didn't write in that command: any earlier file, from this session or a previous one, holds stale names or occurrence indices. Bash: `cat > /tmp/ixp/<project-name>/payloads/field_updates.json << 'EOF' ... EOF` then `uip ixp fields update-prompts <project-name> --updates-file /tmp/ixp/<project-name>/payloads/field_updates.json`. PowerShell: `Set-Content -Encoding utf8 -Path <file> -Value @'` … `'@`, then the same `uip` call; without `-Encoding utf8`, Windows PowerShell writes ANSI and corrupts non-ASCII text.
6. **Never use `UID` as a variable name** — it is readonly. Use `DOC_ID`, `DOCUMENT_ID`, etc.
7. **Always use the project `Name`, never the `Title`** — `project list` exposes both: `Name` (e.g., `my_invoices-f1afa9ef-ixp`) is the lowercase slug with UUID and `-ixp` suffix; `Title` (e.g., `My_Invoices`) is display text; commands require `Name`.
8. **Review at field level, not document level** — review each predicted field by taxonomy data type, not literal page formatting: `Date` is `YYYY-MM-DDTHH:MM:SSZ` (date-only: `T00:00:00Z`); `Monetary Quantity` is `<amount> <ISO-4217 code>`; normalized equivalents are **CONFIRMED**, never reformatted, converted, or script-checked. See [CLI Reference § Normalized output formats](references/cli-reference.md#normalized-output-formats). Normalization changes representation, not meaning (separators, trailing zeros, currency code vs symbol, date layout, century expansion); number magnitude must remain unchanged — page `£7,300.00` predicted as `£730.00` changed the magnitude, so it is a wrong value, not a normalization. A mismatch, wrong source, garbling, digit/decimal error, wrong boolean, or wrong inferred/computed number is **UNANNOTATED**, never fixed. Without `--group`, `--fields` applies to every occurrence (Rule 12).
9. **Do NOT manually extract values** — label only through IXP predictions with `labellings confirm`; never substitute a user-, prompt-, hint-, or self-supplied value — even when handed the right value or the command to write it; that is manual extraction, however it is framed.
10. **You are the reviewer, not the extractor** — view each document with one full `Read` without `pages` (text and image work for digital/scanned documents); do not install PDF tools. Confirm correct fields with `labellings confirm --fields`, skip wrong ones, and improve low-F1 prompts.
11. **Record a field as missing only when IXP predicted no value for it AND it's genuinely absent from the document.** Check `get-predictions` first — never mark a field missing to override a *wrong* predicted value; leave that field unannotated. `labellings mark-missing --fields <ids>` handles a genuinely missing field, including one absent from current predictions; `confirm --fields` marks an empty predicted value missing. Include empty fields in a review confirm batch; use `mark-missing` only for a standalone mark or a field absent from predictions.
12. **For repeatable field groups, confirm per-occurrence when validation differs across extractions** — plain `confirm --fields <id>` confirms that field in every occurrence. If validation differs, use the explicit 0-based `Occurrence` from the same `get-predictions`: `--group <name> --occurrence <N>` confirms one; `--group <name> --updates-file <path>` confirms several atomically; `--occurrence <N>` equals a one-entry updates file. `--group` is the group's `Name` copied **verbatim** from `get-predictions` (e.g. `"Line Items"`) — never a name you assembled yourself. Without `--fields`, every predicted field in the occurrence is confirmed; with it, only those. Unselected occurrences retain annotations. See [CLI Reference](references/cli-reference.md#labellings).
13. **`confirm` is additive — it never un-confirms.** `confirm` and `mark-missing` retain existing annotations: `--occurrence 0` on an already-labelled table yields "row 0 confirmed AND everything previously confirmed stays confirmed" — NOT "only row 0". Use `unconfirm` to roll one back.
14. **F1 reflects confirmed labels, not document truth — never blind-confirm.** F1/`ProjectScore` measure prediction-versus-confirmed-label agreement, not truth; blind-confirming a wrong value can produce 1.00. Before confirming, sanity-check every value against the document; a perfect score (F1 or `ProjectScore`) is not evidence the values are correct. Per-document confirm without `--fields` is valid after reviewing all fields. If the user explicitly says every predicted field in named documents was reviewed and correct, accept that and confirm without re-reviewing, but still pin the version (Rule 18). Never confirm without a document-id. See [Label Documents Guide](references/label-documents-guide.md) §2d.
15. **Ambiguous entity reference → ask, never guess.** Resolve entity kind before any mutation (`update-title`, `rename`, `delete`, `change-type`): projects (Titles), groups, fields, and data types can share names. If a name matches multiple kinds in context or output, stop and ask while listing every candidate and kind; never pick one, and never mutate several candidates "to cover all cases". If interactive questioning is unavailable, surface the question through the task channel and stop.
16. **Reuse the built-in data types before adding new ones.** `Exact Text`, `Inferred Text`, `Number`, `Date`, `Monetary Quantity`, `Boolean`; `projects get-taxonomy` `entity_defs` is authoritative. Before `data-types add` or picking a field's `--type`, reuse a matching default — e.g. `Monetary Quantity` for a currency amount, never a hand-rolled clone (`Currency Amount`). Add a custom type only when no default fits, never for formatting. See [CLI Reference § Default data types](references/cli-reference.md#default-data-types).
17. **`Occurrence` is scoped to the read that produced it — re-read predictions after every per-occurrence write.** Predictions list annotated occurrences first; confirming one moves it to `Occurrence` 0 and renumbers the rest while retaining values and page location. Batch targets in one `--updates-file`; if sequential calls are unavoidable, rerun `get-predictions` and relocate rows by field values, never old indices. Only wholly unannotated or wholly annotated documents remain in document order. Report rows by value, not index.
18. **Confirm against the version you reviewed — pass `--model-version`.** Always pass the reviewed `ModelVersion` as `confirm -m <N>` because confirmation retrains. If it changed, confirmation is rejected with `PredictionVersionChangedError`; re-read, re-review, and confirm against the new version. User-supplied reviews are no exception: pin the named version or run one `get-predictions` to capture it (a version-only read is not a re-review).
19. **`DeploymentName` ≠ `DeploymentTitle`, and `create` never repoints.** `deployments create --title` sets the free-form title, while runtime uses a slugged title plus an unpredictable per-deployment suffix. Read `DeploymentName` from create or list; never construct it. `create` only adds. Before every `upgrade`, run `deployments list`; use `deployments upgrade <project-name> <deployment-name>` with `DeploymentName`, not title (`404`). Upgrading changes the version received by every runtime caller of that folder/name; confirm intent for shared folders. See [CLI Reference § Deployments](references/cli-reference.md#deployments).
20. **`get-metrics` defaults to LATEST, not LIVE — always name the version you report.** For production/performance resolve live first (`list-models` tag `live`, else highest `Pinned: true`, else latest); for an improvement baseline use latest trained because edits retrain it ([Improve Prompts Guide § 1a](references/improve-prompts-guide.md#1a-get-baseline-metrics)). Then pass `--model-version <N>` and state the reported version.
21. **Compare metrics fields on `FieldId`, report them by `Name`.** `Fields[]` already contains `FieldGroup`, `FieldId`, and `Name`, so do not fetch taxonomy. Repeated names use `<FieldGroup> / <Name>` in replies, tables, and file `name` values, even when the requested schema asks only for the field's name. Join versions by `FieldId`, not name, and report the current version's name. See [CLI Reference § `get-metrics`](references/cli-reference.md#projects).
22. **Never switch projects without being asked. Always work on the project you were instructed to work with.** Resolve `Name` once and use it for every command. If you were not asked to, do not modify or continue the task on another project, however similar it looks to yours. Reading another project to diagnose is fine; moving the task to it needs the user's explicit go-ahead. Never report another project's results as this task's. If permission to ask is unavailable, report the blocker and stop.
23. **Never change a taxonomy by importing one** — import merges by name and overwrites same-name instructions; it cannot rename/remove. Use `projects import-taxonomy` only for a project with no taxonomy, typically after `--skip-taxonomy`. Modify existing content with `groups`, `fields`, `data-types`, and `projects update-prompt`; `groups delete` + `groups add` is not replacement. If unsupported, report and route via [Unsupported Capabilities](#unsupported-capabilities) — never substitute an import, even when asked for one directly. See [CLI Reference § `import-taxonomy`](references/cli-reference.md#projects).

## Quick Start

1. Run `uip ixp projects list --output json`.
2. Follow [Project Setup Guide](references/project-setup-guide.md) for creation, [Improve Prompts Guide](references/improve-prompts-guide.md) for improvement, or [Label Documents Guide](references/label-documents-guide.md) for labeling.
3. For runtime deployment, run `projects create` → `list-models` → `deployments create --folder-key`; labeling and `publish` are not required. See [Deployment Guide](references/deployment-guide.md).

For supplied or copied taxonomy, use `--skip-taxonomy` and `import-taxonomy` (Option B in the Project Setup guide) only after ensuring the target is empty; import never edits existing content (Rule 23).

## Task Navigation

- **"Create an IXP project" / "Upload documents to a new project":** Follow [Project Setup Guide](references/project-setup-guide.md); new projects combine uploads and taxonomy. For existing projects, see the "Upload a document" entry below.
- **"Import this taxonomy" / provides a taxonomy file / "give this project the same taxonomy as another project":** Use Option B in [Project Setup Guide](references/project-setup-guide.md): `--skip-taxonomy` + `import-taxonomy`; for a copy, export the source project with `projects get-taxonomy` first. Check target `get-taxonomy`; if `label_groups` is non-empty, use targeted calls instead (Rule 23).
- **"Rename / edit / restructure the taxonomy" / "replace the taxonomy with this file" / "edit the taxonomy JSON":** Use targeted groups/fields/data-types commands plus `projects update-prompt`; never import or delete+add groups. Route unsupported requests to [Unsupported Capabilities](#unsupported-capabilities).
- **"Label documents" / "Review predictions":** Follow [Label Documents Guide](references/label-documents-guide.md).
- **"Improve scores" / "Fix prompts" / "Improve F1":** Follow [Improve Prompts Guide](references/improve-prompts-guide.md).
- **"Publish the model" / "Tag as live":** `uip ixp projects publish <project-name> --output json` — publishes the latest version, untagged. Add `--tag <live|staging>` only to also tag it. See [cli-reference](references/cli-reference.md) for `--model-version`/`--description`. Publishing does not deploy to a folder; do not chain deployment unless requested. Tags select the DU framework version, including DU activities.
- **"Roll back to a previous version" / "Restore version N":** `uip ixp projects publish <project-name> --model-version <N> --output json`; obtain versions with `uip ixp projects list-models <project-name> --output json`.
- **"Unpublish a model" / "Take a model out of production":** `uip ixp projects unpublish <project-name> --model-version <N> --output json`; version is required; find published versions via `list-models` (`Pinned: true`). To change live, publish another version.
- **"Remove the live/staging tag" / "Untag a version":** `uip ixp projects untag <project-name> --tag <live|staging> --output json`. This is the only tag-removal operation; do NOT `unpublish` or re-`publish` to clear it (`unpublish` removes publication, not the tag; `publish` without `--tag` leaves the existing tag untouched). To switch live→staging, publish `--tag staging`.
- **"Deploy this model to a folder" / "make it callable at runtime" / "deploy version N":** `uip ixp deployments create <project-name> --version <N> --folder-key <guid> [--title <title>] --output json`. Resolve a named folder with `uip or folders list --output json`; ask only if no folder was identified. `--version` and `--folder-key` are required; title defaults to project name minus `-ixp`. `create` never repoints an existing deployment — a `409` means use `upgrade` (next entry). Read `DeploymentName` from the response; it is never the title or the project name. See [cli-reference § Deployments](references/cli-reference.md#deployments).
- **"Move a deployment to another version" / "upgrade the deployed model" / "that folder is serving an old version":** `uip ixp deployments upgrade <project-name> <deployment-name> --version <N> --folder-key <guid> --output json`; use `DeploymentName` from `deployments list`, not title (`404`), and confirm shared-folder impact. Target must appear in `projects list-models`; this is not rollback. See [cli-reference § create vs upgrade](references/cli-reference.md#create-vs-upgrade).
- **"Where is this model deployed?" / "list deployments" / "which folder or version is live at runtime":** `uip ixp deployments list <project-name> --output json`; fields are `DeploymentName`, `DeploymentTitle`, `ModelVersion`, `FolderKey`, `DeployedAt`; never-deployed is `[]`. This is the reliable source of `DeploymentName`.
- **"Show metrics" / "What are the scores?":** `uip ixp projects get-metrics <project-name> --model-version <N> --output json`; always name the version (latest ≠ live; see Rule 20); get the live version from `list-models` first (see "How is this project performing?"). See [CLI Reference § `get-metrics`](references/cli-reference.md#projects) and Rule 21.
- **"List projects":** `uip ixp projects list --output json`.
- **"Configure the model":** `uip ixp projects configure-model <project-name> [options] --output json`.
- **"What model / pre-processing does this project use?" / "Query the model settings":** Run `uip ixp projects get-taxonomy <project-name> --output json`; read `Data.dataset._model_config`: `model_version` is the `--model` value and invert `input_config` to `none`/`table_mini`/`table`; `null` means project default, not `none`. There is no `get-model-config`; `configure-model` is read-modify-write and must not be used to read. Do not use `list-models` `ModelName` (`gemini_ixp` is the labeller family). See [CLI Reference § Reading the current model and pre-processing](references/cli-reference.md#reading-the-current-model-and-pre-processing).
- **"Delete a project" / "Remove this project":** `uip ixp projects delete <project-name> -y --output json`; permanent, irreversible, and removes documents, taxonomy, and trained models. Requires `-y/--yes` (the CLI never prompts).
- **"Upload a document" / "Add documents to an existing project":** `uip ixp documents upload <project-name> <file> --output json`; one file per call, loop for multiple. See [CLI Reference § Uploading documents](references/cli-reference.md#uploading-documents-to-an-existing-project).
- **"Delete a document" / "Remove a document":** `uip ixp documents delete <project-name> <document-id> -y --output json`; irreversible and retrains. `-y/--yes` is required (the CLI never prompts). For filename, find `DocumentId` with `documents list` (`Filename` is original name).
- **"Add / delete / rename a field group":** `uip ixp groups {add,delete,rename} <project-name> --name <name> ... --output json`; see [CLI Reference § Groups](references/cli-reference.md#groups). `groups add` requires `--instructions` and one `--fields-file <path>` containing all new fields; do not add individually. Delete requires `-y/--yes`.
- **"Add / edit / rename / delete a data type":** `uip ixp data-types {add,update-instructions,rename,delete} <project-name> --name <name> ... --output json`; see [CLI Reference § Data Types](references/cli-reference.md#data-types). `add` requires `--kind` (`text/date/money/number/boolean/choice`) and `--instructions`; `--input-value` is required only for `text` and `choice`, rejected for others. Delete requires `-y/--yes` and breaks referencing fields. Reuse a default data type before adding a custom one (Rule 16).
- **"Add / delete / rename / retype a field":** `uip ixp fields {add,delete,rename,change-type} <project-name> --group <name> --field <name> ... --output json`; see [CLI Reference § Fields](references/cli-reference.md#fields). Delete requires `-y/--yes`; `change-type` deletes annotations and also requires it.
- **"Move a field to another group" / "this field belongs under X":** No move command. Read `type` and `instructions` with `projects get-taxonomy`; `fields add` to the existing target group, then `fields delete <source> -y`. Move only after both groups exist; add first. This is irreversible: new `field_id`, labels do not follow; say so before starting. Never edit taxonomy and import, which duplicates the field. See [CLI Reference § Moving a field](references/cli-reference.md#moving-a-field-to-a-different-field-group).
- **"Mark a field as missing for a document":** `uip ixp labellings mark-missing <project-name> <document-id> --fields <ids> --output json`; only when genuinely absent and IXP predicted nothing. Empty predictions can instead be listed in `confirm --fields`.
- **"Undo / unconfirm a wrong confirmation":** `uip ixp labellings unconfirm <project-name> <document-id> --fields <ids> --output json`; rolls back an earlier `confirm` or `mark-missing` for the listed fields; `confirm` cannot undo. Without group, shared IDs across repeatable occurrences are removed from all; use `--group` plus `--occurrence <N>` or `--updates-file <path>` for selected occurrences.
- **"Confirm one line item / extraction" / "Confirm only this occurrence":** `uip ixp labellings confirm <project-name> <document-id> --group <name> --occurrence <N> [--fields <ids>] --output json`; use the 0-based index from latest predictions. Without fields confirms all predicted fields; otherwise only listed; other occurrences stay unchanged. Batch several with `--updates-file <path>` and follow Rules 12/17.
- **"Unconfirm one line item / extraction" / "Roll back only this occurrence":** `uip ixp labellings unconfirm <project-name> <document-id> --group <name> --occurrence <N> [--fields <ids>] --output json`; re-read first because annotated rows sort first. Without fields unconfirms every annotated field in that occurrence; otherwise only listed. Use `--updates-file <path>` for several.
- **"Set overall extraction instructions" / "Update project prompt":** `uip ixp projects update-prompt <project-name> --prompt "<text>" --output json`; replaces taxonomy-wide instructions and differs from `fields update-prompts` and `groups update-prompts`.
- **"How is this project performing?" / "What's the F1?":** Resolve live with `uip ixp projects list-models <project-name> --output json`, then run `uip ixp projects get-metrics <project-name> --model-version <live-version> --output json`. If `Data` is `{ Metrics: null }` the model isn't validated yet — report that and stop. If result is `Result: Failure` with `ErrorCode: not_found`, report no metrics yet and stop. Otherwise report in order: (1) version + `TrainedTime`; (2) overall `ProjectScore`/`ProjectScoreQuality`; (3) `FieldGroups[]` F1/Precision/Recall; (4) `Fields[]` lowest F1 first with F1, Precision, Recall, `Annotations`, and `ErrorRate` (= errors/`Annotations`, not `1 - Precision`). Ignore `Quality` labels ([Improve Prompts Guide § What get-metrics returns](references/improve-prompts-guide.md#what-get-metrics-returns-and-which-values-decide)). State numbers plainly; no "good enough" judgement unless asked; route low scores to [Improve Prompts Guide](references/improve-prompts-guide.md). Answer from these calls only — no ad-hoc discovery (Rule 1); follow Rules 20/21.
- **"Describe this project" / "What's in it?":** In order: `uip ixp projects get <project-name> --output json` for `Title`/`Name`; `list-models` for live/published trained version + `TrainedTime`; `uip ixp projects get-taxonomy <project-name> --output json` for counts under `Data.dataset.label_groups` and `Data.dataset.entity_defs` (snake_case). Fold in performance only if asked. Do not page `documents list` (its `Data` is `{ Documents, Total, Offset, Limit }`; use `Total` for a count) or read deployments. Answer from these calls only (Rule 1).

## Unsupported Capabilities

Do not enter discovery (`uip --help`, grep, source reading); follow Rule 1 and these responses.

| User request | Standard response |
|---|---|
| Create model/project | If documents, taxonomy, or a blank project was supplied/requested, use [Project Setup Guide](references/project-setup-guide.md). Otherwise: "I work on existing IXP projects rather than creating them from scratch. Create one in-product: https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/managing-projects — then I can label, review, and improve it." |
| Upload/add documents | If a project is named/in context, supported: see the "Upload a document" entry in Task Navigation. Otherwise: "Name an existing project and I'll upload it — or upload in-product (e.g. for a new project): https://docs.uipath.com/ixp/automation-cloud/latest/user-guide/building-and-deploying-models." |
| Push to environment/tenant; deploy to staging/production | If the request names an Orchestrator folder (e.g. one literally called `Production`), use the "Deploy this model to a folder" entry in [Task Navigation](#task-navigation). Otherwise: "IXP has no environment or cross-tenant deploy target — a deployment is a (folder, version) pair inside one tenant." Note `projects publish --tag staging\|live` moves the tag the DU framework (and DU activities calling through it) resolve — for those consumers that IS the staging/live switch; it creates no folder deployment. |
| "Give X access" / "share this project" / "change roles or permissions" | "Access, roles, and permissions are managed in-product, not through this skill: https://docs.uipath.com/ixp/automation-cloud/latest/overview/managing-access." |
