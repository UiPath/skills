# UiPath Test Assistant

Manage UiPath Test Manager projects, requirements (including AI test-case generation, evaluation, and obsolete-case search), test cases, sets, executions, logs, defects, attachments, results, custom fields, performance scenarios, labels, and persona-tailored reports.

## Use For

Test Manager CRUD; CI runs of every test in uploaded packages; execution analysis, coverage, regression trends, failure rates, go/no-go summaries; failed-run triage; flaky-versus-regression analysis; failure evidence; load-testing automated cases and diagnosis; and shareable QA-engineer, developer, or release-manager reports.

## Concepts and CLI

Requirements define scope; test cases define scenarios and may contain **teststeps**; sets group cases; executions come from set/case runs. Testcase logs record cases in executions and provide navigation; test-step logs record steps; testcase-log assertions are assertion steps. Requirement AI uses descriptions and attachments to propose cases, improve requirements, or flag obsolete linked cases; each is a background job with an activity id. Defects are raised from one testcase log and synced to the project tracker.

Performance scenarios load-test automated cases. Load groups specify case, Orchestrator package/folder, and profile (virtual users, ramp-up, peak, ramp-down). Dry runs check operation; performance runs apply load and consume tenant licence.

External Playwright packages are uploaded suites. Ingestion creates one testcase per Playwright test, without a link step, and labels each `PW_Tag_*`, `PW_Project_*`, `PW_Suite_*`, and `PW_File_*`; they run on serverless cloud runtimes: [references/playwright-first-mile-guide.md](references/playwright-first-mile-guide.md).

Use `uip tm`; discover syntax with `uip tm --help` and `uip tm <command> <subcommand> --help`. **Always pass `--output json` to every `uip` command; all commands below require it.** For file values, pass `"$(cat <FILE>)"`; never retype read content.

## Commands

### Projects, folders, and requirements

- Projects: `uip tm project list --filter <NAME_OR_KEY>`; `project create --name <PROJECT_NAME> --project-key <PROJECT_KEY>`; `project update --project-key <PROJECT_KEY> --name <PROJECT_NAME>`; `project delete --project-key <PROJECT_KEY>`; `project set-default-folder --project-key <PROJECT_KEY> --folder-key <FOLDER_KEY>`; `project clear-default-folder --project-key <PROJECT_KEY>`; `project owners list --project-key <PROJECT_KEY> [<PROJECT_KEY> ...]`.
- Default project: one per tenant for runs without a project. `project list`, `create`, and `update` carry `IsDefault`. Inspect with `uip tm project list --limit 1 --output json` without `--filter`: `Data[0]` is default only when `IsDefault` is `true`; otherwise report “no default visible” (tenant may have none or login may lack access). `uip tm project get-default --output json` returns it and **creates one when absent** (`Default Project`, key `TMDP`, opened to Everyone); run only when needed, never merely to inspect. **New work with no project named goes to the default project.** When the user asks to create test cases, test sets or requirements, or to run a package, and names no project, run `get-default`, use its `ProjectKey`, and tell the user the work went into that project (name and key). For existing items, ask for the project (Quick Start step 2). <!-- Intended: get-default may create the tenant's default without asking; the agent then says which project it used. --> `uip tm project update --project-key <PROJECT_KEY> --set-default --output json` makes an existing project the default and requires `TM.Administration` or tenant administration; access is unchanged, so an inaccessible default makes `get-default` return `permission_denied`. There is no `project create --set-default`. For `permission_denied` from either command, report `Message` and `Instructions` and stop (Rule 10).
- Permissions: `uip tm project-permissions get` returns `Data.Permissions` (the permission names the **caller** holds on that project) and `Data.Count`; it requires `Project.Read`, so success includes that permission (`Count >= 1`); no access is 403 or 404, never successful empty data. Only `get` is exposed.
- Settings: `uip tm project settings get --project-key <PROJECT_KEY>` reads time zone, execution-name format, step cap, default folder, and governance. `project settings update --project-key <PROJECT_KEY> [--time-zone <IANA_NAME>] [--execution-name-format <TEMPLATE>]` writes only the first two. See [references/project-settings-guide.md](references/project-settings-guide.md).
- Folders: `uip or folders list -n <name> --all --output json` lists all visible folders.
- Requirements: `uip tm requirements list --project-key <PROJECT_KEY>` with optional `--test-case-id <UUID>` (use this, never `list-testcase-ids` per requirement), `--filter`, `--labels`, `--requirement-ids`, `--limit`, `--offset`; `list-by-test-execution --project-key <PROJECT_KEY> --execution-id <uuid>`; `get --project-key <PROJECT_KEY> (--requirement-id <uuid> | --requirement-key <key>)`; `create --project-key <PROJECT_KEY> --name <name>`; `update --project-key <PROJECT_KEY> --requirement-id <uuid>` with name and/or description (at least one); `delete --project-key <PROJECT_KEY> --requirement-ids <uuid...>`; `export --project-key <PROJECT_KEY> --output-file <path>` (`.xlsx`); `list-testcase-ids --project-key <PROJECT_KEY> --requirement-id <uuid>`; `testcases --project-key <PROJECT_KEY> --requirement-id <uuid> (--add-testcase-ids <uuid...> | --remove-testcase-ids <uuid...>)`. UUID/key selectors and add/remove selectors are mutually exclusive.
- Migration: `uip tm project export` → `uip tm project import` (`.tmh`); jobs `uip tm migration get|list|download`; schemas `uip tm migration schemas list|download`. These take minutes: pass `--wait` (export also `--output-file`); otherwise get a job id for `migration get`, never start another to poll. Automation is included unless `--exclude automation`; governance, project config (Test Cloud only, otherwise 403), and prompts require `--include`. Sets travel only as `.tmh`; cases/requirements may also export to Excel (`testcases export`, `requirements export`). Ask format/purpose when “export these” is unspecified. Before import ask existing versus new project (`--create-project`); if key is taken ask for `--new-project-key`.

### AI on requirements

`uip tm requirements generate-testcases`, `uip tm requirements evaluate`, and `uip tm requirements find-obsolete-testcases` each start a background job returning `ActivityId`. **Each start spends AI units: start once, then reuse `--activity-id <ACTIVITY_ID>` to wait, show, create, unlink, or delete; never restart to retry.** Use `--timeout 540` and a 600 s shell limit. Scenarios, `Score`, `ConfidenceLevel`, and outcomes: [references/requirement-ai-guide.md](references/requirement-ai-guide.md).

### Test cases

- CRUD: `uip tm testcases create --project-key <PROJECT_KEY> --name <TEST_CASE_NAME>`; `list --project-key <PROJECT_KEY>` optionally `--filter <text>` (name/key **PREFIX**, not substring); `update --project-key <PROJECT_KEY> --test-case-key <TEST_CASE_KEY> --name <TEST_CASE_NAME>` updates name, description, precondition, or postcondition and requires at least one field; `delete --project-key <PROJECT_KEY> --test-case-key <TEST_CASE_KEY>`.
- Automation: `link-automation --project-key <PROJECT_KEY> --test-case-key <TEST_CASE_KEY> --folder-key <FOLDER_KEY> --package-name <PACKAGE_NAME> --test-name <TEST_NAME>`; optional `--entry-point-id <PACKAGE_ENTRY_POINT_ID>` from `list-automations`, overriding `--test-name`. `unlink-automation --project-key <PROJECT_KEY> --test-case-key <TEST_CASE_KEY>`; `list-automations --project-key <PROJECT_KEY> --folder-key <FOLDER_KEY>` optionally `--package-name <PACKAGE_NAME>`, returning `PackageEntryPointId`; `list-testsets --project-key <PROJECT_KEY> --test-case-key <TEST_CASE_KEY>`.
- Inventory/copy/bulk: “Which sets include cases labelled X” uses one `list-testsets --labels X`, not a case loop; it shows explicit assignments only, not sets that pull a case in by a dynamic label; say so. `clone` returns `Accepted` without a key, copies asynchronously with steps last; find it using `list --filter` from `Instructions`, never clone to check/retry, and list after a 5xx because a copy may exist. Labels, documents, requirements, and parameters copy only with `--include`. `bulk-create --file` accepts a JSON array of `{"name", "labels": [...], "steps": [{"description", "expectedResult"}]}`; names are nonunique, so reruns duplicate; pass `--skip-existing` when some names may already exist. File error exit 3 creates nothing; later-batch failure leaves earlier creations; report and ask before rerun. `KeysResolved: false` still means created. `list --automated` excludes Playwright-linked cases. A 403 on `group-by` (licence or feature off): stop and tell the user.
- Steps: `uip tm testcases steps list --project-key <PROJECT_KEY> --test-case-id <TEST_CASE_ID>` (UUID, not `--test-case-key`); `steps get --project-key <PROJECT_KEY> --step-id <UUID>`; `steps add --project-key <PROJECT_KEY> --test-case-id <UUID> --description <text>` or repeated `--step '<json>'` (mutually exclusive; JSON mode is **not atomic**, earlier steps persist); `steps update --project-key <PROJECT_KEY> --step-id <UUID>` updates passed fields; `steps move --project-key <PROJECT_KEY> --step-id <UUID> --target-position <n>` (0-based); `steps delete --project-key <PROJECT_KEY> --step-id <UUID> --yes`.
- Results/runs: `list-result-history --project-key <PROJECT_KEY> --test-case-id <TEST_CASE_ID>` supports `--only-failed`, `--filter`, `--limit`, `--offset`. `run --project-key <PROJECT_KEY> --test-case-id <TEST_CASE_ID> --name <EXECUTION_NAME> --execution-type <manual|automated|none|mixed>` starts one or more space-separated testcase UUIDs; optional `--async`, `--folder-key`, `--robot-user-key`, `--machine-key`.
- Membership: `uip tm testcases add --test-set-key <TEST_SET_KEY> (--test-case-keys <KEY1> <KEY2> … | --labels <Label1> <Label2> …)` (mutually exclusive, variadic); keys allow comma form (`DEMO:1,DEMO:2`), labels do not (`--labels A,B` is one label). Labels are OR, exact, case-insensitive; quote spaces. Without `--dynamic`, labels create a one-time snapshot. `uip tm testcases remove --test-set-key <TEST_SET_KEY> --test-case-keys <KEY1,KEY2,...>` removes static links; it succeeds but does nothing for a testcase included only by a dynamic label — change its labels or the set's dynamic labels instead.
- Dynamic membership: `uip tm testcases add --test-set-key <TEST_SET_KEY> --labels <Label1> <Label2> … --dynamic` stores OR/exact/case-insensitive labels, follows later labels, merges existing labels (maximum 30), retains static links, and returns `DynamicLabels` and `MatchedTestCases`; `--limit` and `--test-case-keys` are rejected. `uip tm testcases remove --test-set-key <TEST_SET_KEY> --dynamic [--labels <Label1> …] --yes` removes named/all labels and returns `Result` `Removed`, `Cleared`, or `NotSet`; unavailable for externally linked sets. Use dynamic for label-tracking suites, otherwise snapshot. If `uip tm testcases add --help` lists no `--dynamic`, use non-dynamic labels and rerun when labels change.
- Parameters (`uip tm testcases parameters`): use `--default-value`, not `--value`. Names are unique per case and exact case-insensitive (`User name` ≠ `Username`); check `list --search` and exact `Name`; empty means absent, not a Rule 4/10 stop. Ask confirmation for near matches. **An existing parameter is never changed by an "add" request**, even when the request gives a different value: never run `update` for it; single add reports existence and asks another name; Adding to several test cases: skip it, leave its value, and list it as skipped. Changing a missing name: ask before creating it. A rename onto a name in use is refused; report it. Confirm deletes (Rule 5). `delete` may return `Success` with no action; report `Data.Passed`/`Data.Failed`. For multiple cases, list each, add only missing names, and summarize added/skipped per case.
- IDs: use `--test-case-id <UUID>` for `run`, `steps list`, `steps add`, `list-result-history`, and `testcaselog start`/`finish`; obtain from `testcases list` (`Id`) or the just-opened run's logs (see Execution lifecycle). Use singular `--test-case-key <PROJECT_KEY:NUMBER>` for `update`, `delete`, automation, and `list-testsets`; plural `--test-case-keys <KEY1,KEY2,...>` for set bulk membership. Use `--step-id <UUID>` for step commands except `list`/`add`, from `steps list` (`Id`).

### Test sets and executions

- Sets: `uip tm testsets create --project-key <PROJECT_KEY> --name <TEST_SET_NAME>` optionally `--dynamic-labels <Label1> …` (returns `DynamicLabels`, `MatchedTestCases`); `list --project-key <PROJECT_KEY>` optionally `--filter`, `--folder-key`, `--include-last-execution`; `update --test-set-key <TEST_SET_KEY> --name <TEST_SET_NAME>`; `delete --test-set-key <TEST_SET_KEY>`; `list-testcases --project-key <PROJECT_KEY> --test-set-key <TEST_SET_KEY>` (static plus dynamic, `AssignmentType`: `Static|Dynamic|Both`); `get-dynamic-assignment --project-key <PROJECT_KEY> --test-set-key <TEST_SET_KEY>` returns `DynamicLabels` (`[]` when none) and `MatchedTestCases`.
- Run/probe: `uip tm testsets run --test-set-key <TEST_SET_KEY>` returns execution id; optional `--execution-type <automated|manual|mixed|none>` (default `automated`), `--input-path <FILE>`, and Playwright `--playwright-project <name>`. `playwright-context --test-set-key <TEST_SET_KEY>` returns `IsPlaywright`, available, and selected projects. Keys are `PROJECT_KEY:NUMBER`; membership uses `testcases add/remove`, not set verbs. Playwright needs support and a CLI with external-package commands; one case-sensitive `playwright.config` name per execution, selection persists; all cases must come from one package; unknown names fail listing valid ones. Probe first and branch on `IsPlaywright`. See [references/playwright-first-mile-guide.md](references/playwright-first-mile-guide.md).
- Configuration: `get`, `clone`, `set-execution-order`, `settings get`, `settings set`, `assign-user`, `set-folder`, `set-robot`, `set-execution-target`, `autoselect-packages`, `group-by`, and `list --labels`. `clone` waits and returns `TestSetKey`; `--no-wait` returns `Accepted` without key. Timeout is failure: stop and never reclone. Names may repeat, so choose a unique copy name. Folder, robot, packages, enforce flag, and order are not copied. Read `list-testcases` before `set-execution-order`; include every assigned case; order applies only after `settings set --enforce-execution-order`. Only enforce is writable; stop-on-failure, coverage, video, remote control, and Autopilot are read-only — say so. Name options (`--folder-path`, `--robot-name`, `--assignee-email`) resolve in Orchestrator. A 403 there, or on `set-execution-target`/`group-by` (licence or feature off): stop and tell the user. `autoselect-packages` saves nothing.
- Executions: `uip tm executions list --project-key <PROJECT_KEY>` supports `--test-set-id <UUID>`, `--filter`, `--status`, `--execution-type`, `--execution-finished-interval`, `--limit`, `--offset`; `list-filtered --project-key <PROJECT_KEY>` supports those except `--filter`, plus `--updated-by`, `--labels`, `--test-execution-ids`, `--sort-by`, and uses `--search` for names. Use `list` for one test set or project; use `list-filtered` for labels, several execution IDs, custom ordering, or `--updated-by`. Lower-case filter enums (other casing is rejected): `--status <pending|running|cancelling|finished|cancelled>`, `--execution-type <manual|automated|none|mixed|autonomous>`, `--execution-finished-interval <lastHour|lastDay|lastWeek|last15Days|last30Days>`. Responses capitalize `Status`; do not reuse response values as filters.
- `get-stats --execution-id <EXECUTION_ID> --project-key <PROJECT_KEY>` aggregates pass/fail/none; `report get` also summarizes completed runs, while list rows do not. `run --execution-id <EXECUTION_ID> --execution-type <TYPE>` reruns, optionally `--test-case-log-ids <UUID...>` (space-separated) and `--async`; `retry --execution-id <EXECUTION_ID>` retries failures, optionally `--project-key`, `--test-set-key`, `--execution-type`; `testcaselogs list --execution-id <EXECUTION_ID> --project-key <PROJECT_KEY>` lists logs with `--only-failed`, `--filter`, `--limit`, `--offset`. Use `uip tm testcases run` for testcase UUIDs, `uip tm testsets run` for a test-set key, and `uip tm executions run` to rerun an execution.

### Execution lifecycle

Open a manual run with `uip tm testsets run --test-set-key <KEY> --execution-type manual` (`Data.ExecutionId`; no `executions create`), resolve case IDs from `uip tm executions testcaselogs list --execution-id <ID>`, then `testcaselog start`/`finish`. **A manual run self-closes when its last log finishes** — `executions finish` is the force-close for a run left with logs open, not the normal last step. `set-reporting-date` requires a closed run (`ExecutionFinished`, not `Status`). Manual/automated distinctions, filtered reads, all `cancel`/`delete`/`finish`/`export`/`set-reporting-date` caveats, and exit contracts: [references/executions-guide.md](references/executions-guide.md); discover flags/enums with `-h`.

### Test set schedules

Verbs: `uip tm schedules create|update|list|next-runs|enable|disable|delete`. `list` is the only read; recover values there before `update`, which replaces the **whole** definition (pass every flag you want kept) and cannot change enabled state (use `enable`/`disable`). `delete` and `--all` require `--yes`. `--cron` has 6 or 7 fields beginning with seconds, not Unix cron; daily 02:00 is `0 0 2 1/1 * ? *`; five fields are refused. `--cron-details` recurrence JSON is required for every recurrence type. `--start-time`/`--disable-time` are wall-clock `YYYY-MM-DDTHH:mm` in `--timezone`; seconds and `Z` are refused. Pass `next-runs` ids printed by `list`; bad ids return 200 with an empty list. See [references/schedules-guide.md](references/schedules-guide.md).

### Run an uploaded package (CI)

`uip tm run --type package --package-name <PACKAGE_NAME> --package-version <VERSION> --folder-path <FOLDER_PATH> --project-key <PROJECT_KEY> --output json` runs every test in an uploaded package, retries failures with `--max-retries <N>`, and writes a report. Pack/upload with `uip rpa pack` / `uip or packages upload`. Without a project, run `uip tm project get-default --output json` and use `ProjectKey` (see Default project). Obtain versions with `uip or packages versions <PACKAGE_NAME> --folder-path <FOLDER_PATH> --output json`: app version `1.0` selects latest `1.0.x`; exact versions must be latest patches; older versions exit 3 with nothing created. Under a CI limit pass `--timeout <SECONDS>` below it (default 7200); a killed step leaves no report. Exit 1 with `RunPackageTestsFailed` or `RunPackageCancelled` is a test result: report per Rule 10(d). Exit 4 is timeout; execution may continue and `Data.OutputPath` is partial with unfinished tests skipped; report timeout and never count skipped as passed. Other nonzero exits stop (Rule 10). Undeclared `--input-path` names appear in `Data.IgnoredInputs`; tell the user.

### Logs, reports, attachments, and results

- Start/finish: `uip tm testcaselog start --project-key <PROJECT_KEY> --execution-id <EXECUTION_ID> --test-case-id <TEST_CASE_ID>` optionally `--run-id <NUMBER>`. Finish with `finish --project-key <PROJECT_KEY> --execution-id <EXECUTION_ID> --test-case-id <TEST_CASE_ID> --result <None|Passed|Failed|Restricted> --has-error <true|false> --executed-by <EMAIL>`; all three flags are required; this records the result — how a manual run's case is marked `Failed`. **`--executed-by` takes an email but is validated non-empty then discarded** — the stored `ExecutedBy` is the authenticated caller, so never tell the user a result was attributed to whoever they named. Optional `--detail-link <URL>`, `--run-id`, `--is-post-condition-met`, `--step-logs <json>`, or `--step-logs-file <path>`. Start requires an existing execution; open one with `uip tm testcases run … --execution-type manual` or `testsets run … --execution-type manual`. <!-- Verified 2026-10-12, CLI 1.205.0 on alpha. -->
- Record manual step results on finish (`--step-logs`/`--step-logs-file`): start returns testcase-log `Id` and creates one step log per step. Read with `uip tm teststeplog list --project-key <PROJECT_KEY> --test-case-log-id <TEST_CASE_LOG_ID> --output json`; pass each back as `{"id":"<STEP_LOG_ID>","testCaseLogId":"<TEST_CASE_LOG_ID>","result":"Passed","comment":"<text>","hasError":false}`. Match by `id`, not `testStepId`; unknown ids are ignored; only `result`, `comment`, `hasError`, `hasAttachment` persist.
- Read/correct: `testcaselog list` supports `--results`/`--statuses`/`--labels`/`--search`/`--assignees` but no date/execution filter; narrow runs with `executions testcaselogs list`. `get --test-case-log-id <ID>` optionally `--include-assertions`; `latest --test-case-ids <ID...>` returns newest per case. A result is overridden only when populated `Result` and `OriginalResult` differ; empty `OriginalResult` means not overridden. Use `override create|update|delete|get`; create requires `--result` and `--reason`. Assign with `assign --assignee-email <EMAIL>` or `--assignee-id <IDP_UUID>`. See [references/testcaselog-guide.md](references/testcaselog-guide.md).
- Assertions/robot/steps: `uip tm testcaselog list-assertions --project-key <PROJECT_KEY> --test-case-log-id <TEST_CASE_LOG_ID>`; `render-assertions` returns them as markdown; `get-robot-logs` (expiring link or `--output-file`); `uip tm teststeplog list --project-key <PROJECT_KEY> --test-case-log-id <TEST_CASE_LOG_ID>`.
- Reports/files: `uip tm report get --execution-id <EXECUTION_ID> (--project-key <KEY> | --test-set-key <KEY>)`; exactly one project identifier is required, and execution-only exits with `Provide --project-key or --test-set-key`. `uip tm attachment download --execution-id <EXECUTION_ID>`; `attachment upload --object-id <UUID> --object-type <type> --file <path>` (for example `testCaseLog`); `uip tm result download --execution-id <EXECUTION_ID>` downloads JUnit XML, optionally `--project-key`, `--test-set-key`, `--result-path <DIR>`.
- Attachments: `uip tm attachment` upload returns `AttachmentId`. Find the parent with `list --test-case-keys` / `--requirement-keys`, select by `FileName`, then use `AttachmentId`; no match or duplicate asks. `list` shows only `userBased` unless `--source` is `orchestrator`, `studio`, or `taskCapture`; keys that don't resolve come back under `Unresolved` beside the rest — name them; unknown `--object-ids` gives `AttachmentCount: 0`. `--object-type` is the parent object's type, not the file's; a wrong one can still succeed. `download --attachment-id` writes server name in current folder unless `--result-path`/`--output-file`, never replaces files; on `already exists`, stop and ask; use `--overwrite` only when requested. `update` only renames with `--file-name`. `--all` is one page per call; follow `Pagination`. Confirm deletes (Rule 5).
- Exports: `uip tm testcases export` produces `.xlsx` (`--test-case-ids`, otherwise whole project); `uip tm report export` exports execution reports with `--execution-id --format excel|pdf|junit`, or selected result PDFs with `--test-case-log-ids` (two or more become one `.zip`). When the user wants the file, pass `--wait --output-file <path>`; without `--wait`, poll `uip tm export-jobs get --job-id` while `Initiated`/`InProgress`, stop on `Failed`/`Cancelled`, then `attachment download --attachment-id <AttachmentId>` as `Instructions` prints; never start the same export twice. Existing output files are refused before start; ask and use `--overwrite` only when told. `export-jobs get` requires the starting project (otherwise 404). JUnit off on the tenant (`feature is not enabled`) or a 403 on result PDFs (licence): report it, don't retry.

### Playwright pack

`uip tm pack --project-path <dir> --type playwright --project-key <PROJECT_KEY> --name <PackageName> --package-version <ver> -o <out-dir>` creates a `.nupkg`; lockfile and `@playwright/test` required. Version is NuGet/SemVer-style with three/four numeric parts and optional prerelease/build suffix (`1.0.0`, `1.0.0.0`, `1.0.1-beta.1`); `1.0` and nonnumeric values are rejected. `--project-key` enables automatic ingestion; `--no-create-test-cases` skips it; `--dry-run` previews. Upload with `uip or packages upload <nupkg>`. Packing is offline/no auth. Pipeline: [references/playwright-first-mile-guide.md](references/playwright-first-mile-guide.md).

### Defects

`uip tm defects` supports `create | list | get | update | delete | get-external-issue | get-related | attachments list|download`; raise from failed results, update status/priority/tracker link, and trace. Defects are UUID-only; find `DefectId` in `executions testcaselogs list`. Before any call read [references/defects-guide.md](references/defects-guide.md); `update`/`delete` often take 10–40 s and require a shell limit of at least 120 s.

### Wait and user

`uip tm wait --execution-id <EXECUTION_ID>` waits for terminal state; optional `--project-key`, `--test-set-key`, `--timeout <SECONDS>`. `uip tm user get` returns the authenticated profile.

### Custom fields

Project-scoped definitions attach to Requirement/TestCase/TestSet, with per-object `label` and `value` rows via `uip tm customfield …`. Full scopes, `--object-type`/`--data-type` enums (`Requirement|TestCase|TestSet`, `Text|Label`), `--values` JSON semantics, and label/value verbs: [references/custom-fields-guide.md](references/custom-fields-guide.md).

### Object labels

Use `uip tm objectlabel …` on `Requirement`, `TestCase`, `TestSet`, `TestExecution`, or `TestCaseLog`. Avoid label-id/object-id confusion and `--remove-other-labels` deleting hidden internal labels: [references/object-labels-guide.md](references/object-labels-guide.md).

### Performance (load) testing

1. Find an automated case with `testcases list`, then folder/package with `testcases list-automations`.
2. Create with `uip tm perf-scenario create --project-key <PROJECT_KEY> --name <NAME>`, then `perf-scenario load-groups add --scenario-key <SCENARIO_KEY> --test-case-key <TEST_CASE_KEY> --folder-key <FOLDER_KEY> --package-name <PACKAGE_NAME>`. `add` ignores profile flags and resets to 20 virtual users; update with `perf-scenario load-groups update --load-group-id <LOAD_GROUP_ID> --project-key <PROJECT_KEY> --virtual-users <N>` using the returned id.
3. `perf-scenario execute --scenario-key <SCENARIO_KEY> --wait` performs a dry run. A full run requires a passing `list-dry-run-reports` result and licence units from `licenses get`.
4. Run `perf-scenario execute --scenario-key <SCENARIO_KEY> --execution-type performanceTesting --wait`; inspect each group with `load-groups list --execution-id <EXECUTION_ID>`, then `results get` or `report generate`.

`get`, `delete`, `execute`, and `list-dry-run-reports` take only `--scenario-key` (for example `CLAIM:7441`); `--project-key` is unknown. `create`, `list`, `stop`, and `licenses get` take `--project-key`; licenses fails without it, though any project returns the same tenant value. `load-groups update`/`remove` use the scenario load-group id from `get` or `add`; `load-groups get`, `jobs list`, `robot-logs list`, `http-errors`, `automation-errors`, and `transaction-metrics` use the load-group execution id from `load-groups list --execution-id <EXECUTION_ID>`; mixing them returns 404 `not_found`. `licenses get` returns tenant-wide `RemainingVirtualUserUnits` and may lag 4 hours. Full runs consume virtual users × 1 (API), 10 (Chrome/Edge), or 100 (other targets); dry runs consume none. If units are short, stop and tell the user. Triage failures with `robot-logs list --load-group-id <ID> --level Error` and `jobs list --load-group-id <ID>`; feature/permission 403 stops under Rule 10. `delete --scenario-key <SCENARIO_KEY> --yes` permanently removes scenario/groups, keeps past executions (they become unlinked), and does not stop active executions; run `stop` first.

## Critical Rules

1. **Always check login first:** run `uip login status --output json` before any Test Manager operation. If unauthenticated, run `uip login`.
2. **Always pass `--output json`** to every `uip` command, without exception.
3. **Cap retries at 3** for any failing `uip` command. After three failures, stop and report the error; never use direct REST APIs.
4. An empty list stops and informs the user rather than proceeding with a null key. Exception: empty `tm testcases list --filter` may be a prefix miss; use Rule 8's prefix fallback and stop only if it also finds nothing. Empty filtered project or customfield lookups are real empty results and stop normally.
5. **Confirm before delete:** confirm the target resource key unless the user already authorized that exact delete. Every delete requires `--yes` or `-y`; omission exits without deleting.
6. For a required folder key, use `uip or folders list -n <folder-name> --all --output json` when the user named the folder; when choosing one yourself, omit `--all` to list only member folders. Run `/uipath-platform` for folder-management details.
7. **Discover before assuming:** never guess automation names, folder keys, project IDs, or testcase keys; run the matching list first, such as `uip tm testcases list-automations` or `uip or folders list -n <folder-name> --all`.
8. **Narrow named-entity list calls server-side:** when given a name, key, label, or tag, inspect `uip tm <resource> list --help` or `uip or <resource> list --help` for its narrowing flag and use it. Never list all then filter client-side; this applies to every entity across `uip tm` and `uip or`, and result filters too: failed-run logs use `executions testcaselogs list --only-failed`; case failures use `testcases list-result-history --only-failed`. Exception: `tm testcases list --filter` is prefix matching. If a mid-name term returns zero, retry with a broader contextual prefix; relist without `--filter` only if no workable prefix exists, walking every page (Rule 11) before concluding absence.
9. **Default-folder recovery:** `uip tm testcases run` and `uip tm testsets run` require a project default folder. Attempt the run first. Only when failure text exactly includes `"Message": "HTTP 400: Please assign folder to project level before executing testcases."` and `errorCode: itemNotFound`, run `uip tm project set-default-folder --project-key <PROJECT_KEY> --folder-key <FOLDER_KEY> --output json`, then retry once. Get keys with `uip or folders list -n <folder-name> --all --output json`. Do not interpret other errors as missing folders: an unusable default gives opaque `HTTP 5xx`; a nonexistent folder key gives `"HTTP 400: Internal Server Error."` with `errorCode: unknown`. Both stop under Rule 10. Never overwrite a working default folder; an arbitrary folder may be rejected and break later runs. This is the only named run exception to Rule 10; all other run failures stop.
10. **Any `uip` failure or ambiguity stops and asks the user:** this includes command errors, malformed output, unclear flags/values, multiple matches, missing identifiers, and unexpected schemas. Never fall back to REST. Exceptions are exact expected outcomes plus one fixable mistake: (a) Rule 9's missing-folder error; (b) `uip tm wait` exit 2 with `Timed out after <N>s waiting for execution '<EXECUTION_ID>'. Last status: <status>.` means bounded timeout worked—report non-finish and continue; `Polling failed/interrupted/aborted ...` and exit 1 are real failures; (c) requirement AI exit 2 with `ErrorCode: timeout` means the job continues—resume with the `--activity-id … --wait` command named in `Instructions`, never start another; (d) package-run exit 1 with `"Code": "RunPackageTestsFailed"` or `"RunPackageCancelled"` and `"ErrorCode": "execution_failed"` means finished failed/no tests or cancelled—report `Data` (counts, `OutputPath`, `ExecutionUrl`) and do not retry; (e) `ValidationError` for a passed flag (`unknown option`, `missing required option`) permits reading `<command> --help`, fixing flags, and one rerun (counts toward Rule 3); a second usage error on the same command stops. Every other failure stops.
11. **Walk pages before concluding absence:** list responses contain only `Data`, with no total/cursor/has-more. A page exactly equal to `--limit` (default 50) may continue; when the item you need is not on it, raise `--offset` by page size until a short page. Maximum `--limit` is 100; above it fails with `HTTP 400 … Page size cannot be greater than 100.` For lists without `--limit`/`--offset`, such as `tm testcases list`, use narrowing flags (Rule 8).

## Quick Start

1. Verify auth: run `uip login status --output json`; if unauthenticated, run `uip login`. If needed set tenant with `uip login tenant set <TENANT_NAME> --output json`. Run `/uipath-platform` for authentication details.
2. Before any Test Manager call ask for project name/key, except unnamed new work, which uses the default project (see Default project). For multiple projects collect all names/keys in one prompt. Resolve with `uip tm project list --filter <NAME_OR_KEY> --output json`; zero matches stop and ask; multiple matches present candidates and ask; reuse confirmed `PROJECT_KEY`.
3. As needed: `uip tm testsets list --project-key <PROJECT_KEY> --filter <TEST_SET_NAME_OR_KEY> --output json`; `uip tm testsets list-testcases --project-key <PROJECT_KEY> --test-set-key <TEST_SET_KEY> --output json`; `uip tm executions list --project-key <PROJECT_KEY> --test-set-id <TEST_SET_ID> --limit 100 --output json`; `uip tm executions testcaselogs list --execution-id <EXECUTION_ID> --project-key <PROJECT_KEY> --output json` (red run: add `--only-failed`, then `testcases list-result-history --test-case-id <TEST_CASE_ID> --only-failed`; see [references/failure-triage-guide.md](references/failure-triage-guide.md)); `uip tm testcaselog list-assertions --project-key <PROJECT_KEY> --test-case-log-id <TEST_CASE_LOG_ID> --output json`; `uip tm teststeplog list --project-key <PROJECT_KEY> --test-case-log-id <TEST_CASE_LOG_ID> --output json`.

## Troubleshooting

For `401 Unauthorized` on a REST API, run `uip login` to re-authenticate. For unexpected command failure, first verify `uip tm <command> --help`, then `uip login status --output json`; Rule 10 controls whether to proceed.

## Anti-patterns

- **Do not proceed if authentication fails:** all Test Manager API calls require a valid bearer token; fail fast rather than causing later 401s.
- **Do not guess command names:** verb-noun composites are required; bare verbs do not exist. Confirm with `uip tm <resource> --help --output json`.
- **Do not hand-build a package run:** use `uip tm run --type package`, not `link-package` → `testsets create` → `testcases add` → `testsets run` → `wait` → `result download`.
- **Do not run `project get-default` to see which project is default:** it creates one, open to Everyone, when none exists; inspect the first `project list` row.
- **Do not `link-automation` Playwright test cases:** ingestion links them automatically; manual linking is only for Studio/RPA.
