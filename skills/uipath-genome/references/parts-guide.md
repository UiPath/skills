# Parts Guide — work in parts, through subagents or forks, and resuming

Work too large for one context runs in parts. The agent that plans the parts is the **orchestrator**: it fixes the shared decisions, writes the brief, runs the parts through subagents where the host has them or builds them itself one after another, checks each part's return against the disk, and assembles the result. The brief, the ledgers, the read plans and the returns below are the same either way; they are what a part, a new agent or a resumed session works from. What extraction's parts add: [extraction-parts-guide.md](extraction-parts-guide.md); a build's: [execution-parts-guide.md](execution-parts-guide.md).

1. **The orchestrator fixes the shared decisions before fan-out** — every decision two parts would otherwise take differently — and writes them into the brief. Each mode's parts guide lists them.
2. **One brief, written before the first part starts,** in the working folder: absolute paths, the shared decisions, the reads, the return contract, the part table with each part's state, and a numbered **Rulings** section. Every orchestrator decision taken during the run takes the next ruling number, is written before the part that builds on it starts, and overrides the brief's text above it; it reaches every later part through the brief, never only through one agent's prompt. A ruling that changes what a running part writes is also sent to that part with its number, and the part applies it to its own files; where the host cannot reach a running part, the orchestrator applies it once the part has returned. Either way the orchestrator edits no file a part still owns (item 7). Every agent is pointed at the brief and the guides instead of receiving the rules inline.
3. **A ledger per part, written through.** Every item assigned to the part carries its state, written in the turn the work lands, and the ledger opens with a `Resume` block naming the next item. A resumed part — after a pause, a compaction or in a new session — reads the brief with its rulings, its ledger and what it has written; it takes from a compaction summary only the work after the last row and confirms it on disk, re-runs its read plan, since a summary carries none of the reads it made, and continues at the next item. A part that ends before finishing returns its unfinished items. Before relaunching or resuming a part, the orchestrator reconciles its ledger with the disk and assigns only unfinished work.
4. **Every part reads by plan, in at most three turns** ([SKILL.md § Read Plans](../SKILL.md)). The plan is written before the part starts and a subagent's prompt carries it, so the part's first turn needs nothing read before it: every file the part reads, whole or by named sections, with the line count of each whole-read file above the single-read limit, so its ranges go out in turn 1. A read stops at the harness's single-read limit, so a file the plan reads whole above that limit is read as consecutive line ranges in the same turn. Another part's ledger is not read; what a part needs of another part's work reaches it through the brief.
5. **A fork starts with its owner's whole context and resends it on every turn**, so when the owner forks decides both what the fork knows and what each of its turns costs.
   - **When.** Fork once the shared reads are done and the shared decisions are written down, before the owner reads any one fork's material or writes a file. Forked before the shared reads, every fork pays them again or works without them; forked after, every fork carries the other forks' material and the owner's own output on every turn.
   - **After a compaction.** A context rebuilt from a compaction summary holds none of the mandatory reads: the owner re-runs them before it forks.
   - **Fork or fresh subagent.** Fork when most of the owner's context is what each fork needs; otherwise a fresh subagent with its own read plan (item 4) carries less. Each fork adds the inherited context to every one of its turns, so the number of forks trades the part's time against its token use.
   - **What a fork does.** It reads its own material, writes only its assigned files and runs none of the owner's shared operations (item 7). It returns the report its mode's return contract lists for its files.
   - **Review before accepting.** A fork's return is a claim. The owner reviews each fork's files against the material they were written from before building on them, and sends a defect back to the fork that wrote it or fixes it itself; a fork whose files were only spot-checked has not been reviewed.
6. **A part returns a verdict, never a retelling, and the return is a claim; the disk is the result.** The return accounts for each item and contract its mode's return contract lists, so it can be checked against the disk. Before accepting a part — a subagent's, a fork's, or one resumed after a compaction — the orchestrator checks it mechanically: the files the return names exist with the counts it gives, and every assigned item appears done or among the unfinished ones. A defect such a check finds goes back to the part that owns it, with the evidence.
7. **What parts share has one owner at a time** — a part or the orchestrator. Ownership passes only once the previous owner has stopped: a subagent that receives a message after its final report resumes and acts again, so before the next part starts on what the previous one owned, the orchestrator confirms that the previous part's agent is idle with no unread message. A fix goes to a part only while no later part has taken its files: the message reopens it, it owns them again, and its new report passes the check of item 6. Once ownership has passed, a note goes to the current owner or into the brief as a ruling (item 2), never to the earlier part. Only the owner edits a shared file and runs a shared operation.
8. **Parts run at most four at once, on a smaller model in a build and on the orchestrator's model in an extraction, unless the Subagents question says otherwise.** Where the host lets the orchestrator choose a subagent's model, both modes ask before the first part starts: "Which model do the parts run on, and how many parts run at once?" The options: a smaller model of the orchestrator's family, at most four parts at once; the smaller model, as many parts at once as the mode's parts guide lets run in parallel; the orchestrator's model, at most four parts at once. A build recommends the first, an extraction the last. A request that names the model or the cap answers it. In a build the smaller model suffices: the brief, the read plan and the return contract hold the part to the work, and validate, build and the orchestrator's check of the return against the disk (item 6) catch what it gets wrong, so the larger model's tokens go to the orchestrator's decisions and checks. In an extraction a part's reading becomes the genome's text, which no validate or build checks, and a value misread there is built as behaviour ([extracted-genome-guide.md § Source values](extracted-genome-guide.md)). Four is the cap because each running part adds its own stream of model calls and, in a build, its project's authoring host and CLI processes on the same machine, and its return waits for the orchestrator's check before anything builds on it. A fork runs on its owner's model and is not a part (item 5), so it does not count against the cap.

## Anti-patterns

1. **A part reading file by file.** Reads in the order files name each other, one per turn; whole reads of what a part needs only by section; another part's ledger; a read plan that gives every part the reads of all parts. Each read is replayed on every later turn of the part (items 3, 4).
2. **A fork that runs a shared operation or edits a shared file, a fork made from a context already full of the other forks' material, or a fork's files accepted after a spot-check** — two agents rewrite one file, every fork pays for material it never uses, and a dropped rule ships unreviewed (items 5, 7).
