# Parts Guide — work in parts, through subagents, and resuming

Work too large for one context runs in parts. The agent that plans the parts is the **orchestrator**: it fixes the shared decisions, writes the brief, runs the parts through subagents where the host has them or builds them itself one after another, checks each part's return against the disk, and assembles the result. The brief, the ledgers, the read plans and the returns below are the same either way; they are what a part, a new agent or a resumed session works from. What extraction's parts add: [extraction-parts-guide.md](extraction-parts-guide.md); a build's: [execution-parts-guide.md](execution-parts-guide.md).

1. **The orchestrator fixes the shared decisions before fan-out** — every decision two parts would otherwise take differently — and writes them into the brief. Each mode's parts guide lists them.
2. **One brief, written before the first part starts,** in the working folder: absolute paths, the shared decisions, the reads, the return contract, the part table with each part's state, and a numbered **Rulings** section. Every orchestrator decision taken during the run takes the next ruling number, is written before the part that builds on it starts, and overrides the brief's text above it; it reaches every later part through the brief, never only through one agent's prompt. A ruling that changes what a running part writes is also sent to that part with its number, and the part applies it to its own files; where the host cannot reach a running part, the orchestrator applies it once the part has returned. Either way the orchestrator edits no file a part still owns (item 6). Every agent is pointed at the brief and the guides instead of receiving the rules inline.
3. **A ledger per part, written through.** Every item assigned to the part carries its state, written in the turn the work lands, and the ledger opens with a `Resume` block naming the next item. A resumed part — after a pause, a compaction or in a new session — reads the brief with its rulings, its ledger and what it has written; it takes from a compaction summary only the work after the last row and confirms it on disk, re-runs its read plan, since a summary carries none of the reads it made, and continues at the next item. A part that ends before finishing returns its unfinished items. Before relaunching or resuming a part, the orchestrator reconciles its ledger with the disk and assigns only unfinished work.
4. **Every part reads by plan, in at most three turns** ([SKILL.md § Read Plans](../SKILL.md)). A part run through a subagent starts fresh, never as a fork of the orchestrator or of another part: a fork starts with its parent's whole context and resends it on every turn. The plan is written before the part starts and a subagent's prompt carries it, so the part's first turn needs nothing read before it: every file the part reads, whole or by named sections, with the line count of each whole-read file above the single-read limit, so its ranges go out in turn 1. A read stops at the harness's single-read limit, so a file the plan reads whole above that limit is read as consecutive line ranges in the same turn. Another part's ledger is not read; what a part needs of another part's work reaches it through the brief.
5. **A part returns a verdict, never a retelling, and the return is a claim; the disk is the result.** The return accounts for each item and contract its mode's return contract lists, so it can be checked against the disk. Before accepting a part — a subagent's or one resumed after a compaction — the orchestrator checks it mechanically: the files the return names exist with the counts it gives, and every assigned item appears done or among the unfinished ones. A defect such a check finds goes back to the part that owns it, with the evidence.
6. **What parts share has one owner at a time** — a part or the orchestrator. Ownership passes only once the previous owner has stopped: a subagent that receives a message after its final report resumes and acts again, so before the next part starts on what the previous one owned, the orchestrator confirms that the previous part's agent is idle with no unread message. A fix goes to a part only while no later part has taken its files: the message reopens it, it owns them again, and its new report passes the check of item 5. Once ownership has passed, a note goes to the current owner or into the brief as a ruling (item 2), never to the earlier part. Only the owner edits a shared file and runs a shared operation.
7. **A simple or medium build runs in one session; otherwise parts run at most two at once, on a smaller model in a build and on the orchestrator's model in an extraction — unless the Subagents question says otherwise.**
   - **The question.** Each mode asks its Subagents question before the first part starts ([extraction-guide.md](extraction-guide.md) Step 1, [execution-guide.md § 1.3](execution-guide.md)), with these options: a smaller model of the orchestrator's family, at most two parts at once; the smaller model, as many parts at once as the mode's parts guide lets run in parallel; the orchestrator's model, at most two parts at once. A build adds a fourth option, no subagents: the orchestrator builds every part itself, one after another, in its own session, the ledgers and progress kept as for any part. A build recommends no subagents when the genome's Complexity is simple or medium (a process genome's own level, [genome-format-guide.md § Complexity](genome-format-guide.md)) — such a build fits one context, and built there it skips each part's read turns, ledger and report and the orchestrator's check of each return, so it costs about what parts cost and finishes sooner — and the first option when it is complex; an extraction recommends the last. A request that names the model or the cap answers it.
   - **Review in one session.** Each part the orchestrator builds itself still gets an independent review: a background agent on the smaller model reads the part's files against the material they were written from and runs the check of a return (item 5), and writes only its findings, to a file in the working folder. The orchestrator does not wait for it: it goes on with the next part, and at each part boundary reads the findings that have arrived and fixes them in the reviewed files. It waits — the bounded wait of item 8 — only where a part is about to build on a reviewed part's files, or the project is about to be packed, and that review has not returned.
   - **The model and the cap.** In a build the smaller model suffices: the brief, the read plan and the return contract hold the part to the work, and validate, build and the orchestrator's check of the return against the disk (item 5) catch what it gets wrong, so the larger model's tokens go to the orchestrator's decisions and checks. In an extraction a part's reading becomes the genome's text, which no validate or build checks, and a value misread there is built as behaviour ([extracted-genome-guide.md § Source values](extracted-genome-guide.md)). Two is the cap because each running part spends the host's usage limit with its own stream of model calls. Parts that spend the limit before its window resets leave every running context idle past the prompt cache's lifetime, and the resume rewrites each of those contexts in full (item 8), so the new window goes to rebuilding caches; fewer parts at once spend the limit more slowly and leave fewer contexts to rewrite. Each running part also adds, in a build, its project's authoring host and CLI processes on the same machine, and its return waits for the orchestrator's check before anything builds on it.
8. **Every agent's context grows only by what it acts on, and stays cached while it waits.** Every turn resends the whole context, so a command's output is paid again on every later turn, and the host's prompt cache lapses after a few idle minutes (five on the Claude API), so the call after a longer pause rewrites the whole context at many times the price of reading it.
   - **Output.** A script the run writes prints one line per failure and a summary line, with the details in a file in the working folder; a listing, search or log longer than about 150 lines goes to a file, and the agent reads the lines it needs.
   - **Waits.** Every call returns within about four minutes, so the next one still finds its context cached. A command that runs longer goes to the background, and so does every part the orchestrator launches. Whoever waits — a part on its command, the orchestrator on its parts — repeats one bounded wait, a shell call that returns when the awaited report or output file exists or after about four minutes (`sh -c 'i=0; until [ -f "<REPORT_PATH>" ] || [ $i -ge 15 ]; do sleep 15; i=$((i+1)); done'`), until the file is there. The call's own time limit is set above that wait: a call past the shell tool's limit is cut off or moved to the background. Ending the turn to await a notice — the part's completion or a file watcher's event — or launching a part in the foreground, leaves the context idle for as long as the part runs, and the call after it rewrites the whole context; a poll rereads the cached context at a small fraction of that price. A part does not wait on an agent it launched to review its own files; the orchestrator launches the review once the part has returned.
   - **Looks.** Every look at the disk the next step needs — a file's arguments, a link count, a folder listing, a package's contents, the lines around an edit point — goes out with the other looks of that step, in one message or one shell chain, never one look per turn. In a build, a project's first part writes one status script, which every part of the project runs to see, for all its workflow files at once, the arguments, the files each invokes and the targets still unlinked; a part opens a workflow file only to edit it or to copy from it.

## Anti-patterns

1. **A part reading file by file.** Reads in the order files name each other, one per turn; whole reads of what a part needs only by section; another part's ledger; a read plan that gives every part the reads of all parts. Each read is replayed on every later turn of the part (items 3, 4).
