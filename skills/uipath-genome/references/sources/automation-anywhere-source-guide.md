# Automation Anywhere Source Guide

Framework facts for extracting a genome from an Automation Anywhere **Automation 360** bot export — bots authored in Automation 360 (a Control Room "Export bots" package with a `manifest.json`) and bots migrated from Enterprise 11 by the Bot Migration wizard. Follows [source-framework-contract.md](source-framework-contract.md); pipeline: [extraction-guide.md](../extraction-guide.md); generic rules pointed to below are not restated here. Observations come from two production exports of one customer: nineteen migrated bots driving an Oracle Forms application from a mailbox intake, and thirty-nine native bots driving the same application from a REST intake and a SQL Server process database.

Export = a folder tree mirroring the Control Room repository: `Bots/My Tasks/<folders>/<BotName>` and `Bots/My MetaBots/<folders>/<BotName>` hold one **extension-less JSON document per bot**; `<BotName>Metadata/` folders hold the recorder's screenshots; `MyDocs/` (or `My Docs/`) holds files the bots read through `repository:///` URIs; a Control Room export adds `manifest.json` beside the `Automation Anywhere/` tree. Bot documents are small (tens to hundreds of kilobytes) but a bot line holds a base64 blob per captured UI object and the same twenty- to hundred-variable dictionary on every sub-bot call, so read them through the bundled inventory script, never raw:

```bash
# Extract mode — read the export from a scratch folder
python3 <SKILL_DIR>/scripts/a360-export-inventory.py profile "<EXPORT_DIR>" --out "<WORK_DIR>"
python3 <SKILL_DIR>/scripts/a360-export-inventory.py cards   "<EXPORT_DIR>" --out "<WORK_DIR>"
python3 <SKILL_DIR>/scripts/a360-export-inventory.py dump    "<EXPORT_DIR>" "<BOT_NAME>" --compact   # one bot, line by line; drop --compact to see disabled subtrees in full
python3 <SKILL_DIR>/scripts/a360-export-inventory.py targets "<EXPORT_DIR>" --out "<WORK_DIR>"   # windows + captured controls with decoded properties and the action applied
python3 <SKILL_DIR>/scripts/a360-export-inventory.py data    "<EXPORT_DIR>" --out "<WORK_DIR>"   # bot inventory with call edges + data sources, for the step-map check
# Execute mode (migration preflight) — derive the catalogs into the build's working folder
python3 <SKILL_DIR>/scripts/a360-export-inventory.py targets "<EXPORT_DIR>" --out "<BUILD_DIR>/migration/source"
python3 <SKILL_DIR>/scripts/a360-export-inventory.py data    "<EXPORT_DIR>" --out "<BUILD_DIR>/migration/source"
python3 <SKILL_DIR>/scripts/genome-step-map.py "<GENOME.md>" --processes "<BUILD_DIR>/migration/source/a360-process-data.json" --recordsets "<BUILD_DIR>/migration/source/a360-data-sources.json" --out "<BUILD_DIR>/migration/source"
```

`profile` writes identity, manifest cross-check, packages, folders, command vocabulary, per-bot summary, call graph, roots, credential references, windows, capture counts, application launches, API calls and DLL functions, stored procedures, mail, database and file commands, evidence density and migration plumbing; `cards` one compact card per bot (description, inputs, outputs, callers, callees in order with the **real parameters** — bindings that are not a same-named pass-through — windows, captures, conditions, loops, database, API, keystrokes, error handling, evidence); `dump` one bot in editor order with every attribute rendered (`--compact` folds disabled subtrees to one line, folds same-named pass-through bindings of a sub-bot call to a count, renders a call to a **logger bot** as a log line, and shortens log, delay and message-box lines). A logger bot is a bot made only of log, flow, string and file commands with at least one log line and no sub-bot call; `profile` names them and every catalog flags them — their calls are the run's own logging, never steps. Read profile and cards in full; dump every bot the genome covers — compact first, full only where a folded subtree matters. `targets` writes the UI target catalog (`a360-targets.json` + `.md`: window variables, captured controls with decoded object properties, keystroke commands — § UI Target Locators); `data` the bot inventory (`a360-process-data.json`, a **list** with id, path, folder, inputs, outputs, call edges with their argument bindings) and the data sources the bots read and write (`a360-data-sources.json` + `.md` — § Test Data). Which mode reads what, and why nothing is written beside the genome: [genome-format-guide.md § Source Map](../genome-format-guide.md) and [source-migration-guide.md § Migration preflight](../source-migration-guide.md).

Automation 360 exports carry no numeric object ids: a bot is identified by its repository path, and names repeat across folders (`Main` in two projects, a MetaBot logic and the task that calls it named alike). The script derives a stable six-digit id from the path (CRC-32 folded into 100000–999999; the same export yields the same ids) so Source Map rows carry `` `Name` (id) `` and `genome-step-map.py` resolves them.

## Detection

| Signal | Meaning |
|---|---|
| Folder containing `Bots/` whose files are extension-less JSON documents with top-level `nodes`, `variables`, `packages` (and `triggers`, `breakpoints`, `properties`, `migrationJournalReviewIds`, `workItemTemplateName`) | Automation 360 Control Room export. Multi-component: a repository folder holds a **root task bot plus the sub-bots it runs**, so the export is a **process genome** whose components are the bot groups of § Component Detection. |
| `Bots/My MetaBots/…` folders | Enterprise 11 MetaBots converted by the Bot Migration: their logic blocks are now ordinary bots, each still one reusable UI capability |
| `Bots/My Tasks/…` folders | Task bots (v11 `.atmx` converted, or authored in Automation 360) |
| `<BotName>Metadata/` beside a bot, full of `*.png` | Recorder screenshots (`screenshotMetadataPath` / `thumbnailMetadataPath` inside capture and region values); evidence of what was captured, never logic |
| `migrationJournalReviewIds` non-empty, `LegacyAutomation` package, variables named `m-*` / `M-*` / `Loop-*` / `Error-*`, `Prompt-Assignment`, `my-list-variable` | Bot Migration output: the bot was converted from Enterprise 11 (§ Framework Pitfalls) |
| `manifest.json` beside the `Automation Anywhere/` tree: `files[] {path, contentType (application/vnd.aa.taskbot, image/png), scannedDependencies[], manualDependencies[], metadataForFile, excluded, description, author}`, `packages[]` | A Control Room **bot export** package (native Automation 360 bots, or a mix): the file list is the export's identity, `scannedDependencies` are the enabled Run Task targets the Control Room found (`profile` § MANIFEST cross-checks them against the bots' own edges), `metadataForFile` ties each screenshot to its bot; `excluded: true` marks a bot the exporter left out. Absent on Bot Migration output |
| Empty `migrationJournalReviewIds`, no `LegacyAutomation` package, a first `Step` block titled `Comment Section` with `Description :`, `Author :`, `Created Date :` comments, variables prefixed `v` / `i` / `c` (value, input, constant), `Step.step` sections naming each phase | Native Automation 360 authoring; the section titles and `Description :` comment are the author's narration and the best wording source |
| `$@AAE_EnvironmentType$` or `$System:AAControlRoom$` compared to `dev` / `uat` | Environment switch: the bot picks connection strings, URLs and credentials by the Control Room it runs on → Configuration Question "which environment" and one asset per Orchestrator folder |
| `packages[].version` | Package build dates identify the Automation 360 release the export was taken from (e.g. `Recorder 2.16.0-20231101-…`) — the version the Source Map states |
| `properties.automationPriority`, `properties.botCodeVersion` | Run priority and the bot's own edit version; identity only |
| `MyDocs/*.xml`, `MyDocs/*.xlsx` | Configuration files the bots read through `repository:///` paths; the only run-time data present in the export |

A single bot file with no `runTask` command is one **component** (component genome). An export missing `Bots/` but holding the JSON documents in one folder is still an export; the repository paths are then the file names, flagged `*[Inferred]*`.

## Inventory and Exclusions

| Pattern | Contents | Use |
|---|---|---|
| `Bots/**/<Bot>` (no extension, JSON) | One bot: `variables[]`, `nodes[]` (tree with `children` and `branches`), `packages[]`, `properties`, `triggers[]` | Steps, control flow, call graph, interface, targets |
| `nodes[].variables` … `variables[]` fields `name`, `type` (STRING, NUMBER, BOOLEAN, LIST, DICTIONARY, RECORD, DATETIME, WINDOW), `subtype`, `input`, `output`, `readOnly`, `defaultValue` | Bot interface (`input`/`output` flags) and constants (`readOnly`, literal defaults); WINDOW variables carry the recorded window (`window.name` title with `*` wildcards, `window.class`, `window.path` executable) | Interface, Target Applications, target catalog |
| `<Bot>Metadata/*.png` | Recorder screenshots of captured controls and screen-change regions | Evidence only; never read for logic |
| `MyDocs/`, `My Docs/` | Configuration XML and workbooks addressed by `repository:///Automation Anywhere/Bots/…` URIs | Configuration Questions defaults; data sources |
| `triggers[]` | Bot-level triggers (empty in exports of scheduled bots — schedules live in the Control Room, not the export) | Deployment note |

Excluded from logic: nodes with `disabled: true` **and their whole subtree** (the editor shows them greyed; the runtime skips them — `dump --compact` folds them to one line); `Comment` nodes whose text is a separator (`====`, `----`, `||||`) or a migration placeholder (`Please enter the commands to handle errors.`, `EndIf`, `Please enter the conditional commands here.`); `MessageBox` nodes (debugging left-overs — in a production export they are almost all disabled; an enabled one is a pitfall, § Framework Pitfalls); `LegacyAutomation.getKeystrokesDelay` (computes the delay the following keystroke command uses); `Delay.delay` (timing → Error Handling wording, never a step); `LogToFile.logToFile` (the run's own log — § Evidence; its **message text** is the author's step narration and is read for wording); `Screen.captureDesktop` (screenshot on error — § Evidence); `String.assign` of a `m-string-start-in-path*` variable (migration plumbing that feeds the next command's path); `.LegacyAutomation:parseVariableOperation` re-assignments of the variable just assigned (a no-op the migration inserted after every assignment); `TaskBot.runTask` of a **logger bot** (the run's own logging — the message binding is the narration, read it like a `logToFile` line); `Credential.assignToCV` (moves a vault credential into a variable for the capture that types it — credential plumbing, the vault reference is what counts); `String.replace` of `$System:AATaskName$` with a path regex (the bot computing its own name for the log); `System.systemInformation USERNAME` (the runner's identity); `Application.runApp taskkill.exe` (§ Step vocabulary); `Database.connect` / `disconnect` pairs around every procedure call (session plumbing — the procedure is the step); `Number.assignToNumber` of fixed delays.

## Component Detection

Automation 360 has one artifact type: the bot. Components come from the **repository folders and the call graph**, not from file types:

| Construct | Component type | Skill | Rationale |
|---|---|---|---|
| The root task bot (never called by an enabled `runTask`) plus the task bots in its folder that only it and its siblings call (initialisation, mail intake, data filtering, navigation, notification, cleanup) | One **RPA process** (REFramework-style: initialise → get work → process → report) | `uipath-rpa` (Process project) | One deployable unit in Automation 360 (the root is what the Control Room schedules); the sub-bots are its phases, not products of their own |
| A `My MetaBots/<Product>/<MetaBot>` folder: the logic blocks of one migrated MetaBot (login, navigate, search, change a value, read a popup, read a title) | One **UI library** for that application | `uipath-rpa` (Library project, one public workflow per logic bot) | A MetaBot is Automation Anywhere's reusable application library; its logics are invoked from several task bots with a fixed argument set (the MetaBot input/output variables) |
| A `Reusable_Components` (or `Common`, `Shared`) folder of bots called from several processes' roots — application launchers, shared exception loggers | One **common library** | `uipath-rpa` (Library project) | The customer maintains it as shared code; other processes of the export or of the tenant depend on it |
| **Copies of a MetaBot kept in the process folder**: generic application bots (`Inputing_LARA_Credentials`, `ChangeDept`, `GenericPushButtons`, `0_Common_Screen_Navigation_*`, popup handlers) whose disabled `runTask` commands still point at `My MetaBots/<Customer>/Reusable Component/<MetaBot>/…` | One **UI library** for the application, the same one the customer's other processes use | `uipath-rpa` (Library project) | The bots were copied out of the MetaBot into the process; the dead calls prove the origin. The process's own business screens (a booking screen, a charges screen) stay in the process even when they are task bots beside the copies — their rules are the process's, only their popups, toolbar and navigation come from the library *[Inferred]* |
| A **logger bot** (log-level filter writing one line per call; § Evidence) | Not a component | — | Evidence policy of the process that calls it |
| `DLL.Open` + `DLL.RunCSharpDLL_V1` (a C# assembly loaded from a configured path, one function called with typed parameters) | A **coded step** of the calling component | `uipath-rpa` (coded workflow or Invoke Code inside the process project) | The assembly is not in the export; the genome states the function's contract (inputs, output, side effects) and flags the logic `*[Inferred]*` for the rebuild |
| `Rest.restPost` / `restGet` chains (token, data, acknowledgement) inside a task bot | HTTP steps of the calling component | `uipath-rpa` (the intake is one phase of the root bot); `uipath-api-workflow` only when the calls stand alone with no UI or file work around them ([skill-mapping-guide.md](../skill-mapping-guide.md) decision tree 5) | |
| Bots reachable only through **disabled** `runTask` commands, or referenced by a path no file in the export matches | Dead calls / unresolved | Source Map only | Superseded copies (`ToDataFilter` vs `TODataFilterTask`, `sub_Handling_Wavier` vs `sub_Handling_Wavier_V1`) or bots outside the export (the MetaBot originals) |
| `triggers[]` with an event or schedule trigger | Entry point of the process component | Deployment → triggers | Rare in exports; the Control Room schedule is the usual trigger and is not exported |

Every construct maps to `uipath-rpa`: Automation 360 has no flow, agent or API-workflow equivalents in an export; a `runTask` chain is workflow invocation, not orchestration. When a root does nothing but call other roots each with its own schedule, consider one process per root and a coordinating Flow `*[Inferred]*`.

## Signals — Bot

`profile` and `cards` surface these; `dump` shows them per line. Line numbers are the editor's (every node including `else`, `elseIf`, `catch`, `finally` branches counts one line) — the `Error-LineNumber` a catch block logs refers to them.

### Step vocabulary → behaviour

| Command | Genome wording |
|---|---|
| `TaskBot.runTask` | Invoke sub-bot (call-graph edge; in a UiPath process, invoke workflow; across components, invoke the library workflow) |
| `If` family with a variable condition | "If {variable in business terms} {is / is not / contains / exceeds} {value}, then …; otherwise …" ([genome-format-guide.md § Business Rules](../genome-format-guide.md)); `INCLUDE` = contains, `NOTINCLUDE` = does not contain, `EQ` with `matchCase` = is exactly |
| `If windowExists` / `windowTitleExists`, `Wait.waitForWindow` | "If the {dialog or window} appears within N seconds, …" — optional dialog handling |
| `If fileExists` / `folderDoesNotExists` | Pre-condition on the file system ("create the folder when missing") |
| `Loop times` ending in `break` on success | "Retry up to N times" — Error Handling |
| `Loop times` over a count read from a query, each iteration fetching the next pending row | "For each pending {record} …" — the work-item loop |

### Value syntax

`$name$` a variable; `$name{key}$` a dictionary or record field (`$Loop-Email-Response-1{emailSubject}$`, `$Loop-Files-1{extension}$`); `$name[0]$` a list element or a record column by index; `$name.Package:function$` a value transform (`.String:toNumber`, `.Number:toString`, `.String:uppercase`, `.LegacyAutomation:getIncrementedNumber`, `.LegacyAutomation:getCellByIndexOrName("SenderEmail")`); `$@Name$` a Control Room **global value** (`$@AABasePath$`, `$@AAE_EmailSettings_host$`); `$System:Name$` a system variable (`AATaskName`, `Year`, `Month`, `Day`, `Hour`, `Minute`, `Second`, `AATaskExecutor`). A STRING value carries `expression` when it references variables and `string` when literal; read `expression` first. `FILE` values are `file://<path>` or `repository:///Automation Anywhere/Bots/<path>`; `%20` and `%3B` are URL-encoded. CREDENTIAL values are references (`lockerName` / `name` / `attributeName`), never secrets. Literal values are the defaults for Configuration Questions. Never copy a literal assigned into a variable whose name contains `password`, `pwd`, `secret` or `token`: bots carry such literals (pitfall 9) and the inventory script redacts them.

Oracle Forms specifics the LARA bots instantiate: the application is a Java applet launched from a browser page through Java Web Start (`jp2launcher.exe`, frames `SunAwtFrame`, dialogs `SunAwtDialog`), the browser only hosts the launch page; Forms alerts are internal dialogs whose message is the accessible name of a `Client` object (`Error LARA-…`, `Question …`, `Information …`, `Forms …`, `ALERT …` — the first word is the alert class the bots branch on); grids are rows of identically named text fields distinguished by accessibility index or path suffix; the status bar is a `StaticText` (`FRM-40301: Query caused no records to be retrieved`, `FRM-40212: Invalid value for field …`) and the record indicator another (`Record: 1/5`, `Record: 1/?` before the query fetched every row); the menu is a tree of `Level 1` / `Level 2` / `Level 0` captions; buttons carry their mnemonic (`Search alt S`, `Connect As alt C`, `Auto Freight alt A`); a screen's title is the accessible name of its canvas (`Consignment Booking`, `Charges`) read after every navigation.

## Target Resolution

1. **Window variable → application.** Every UI command names a WINDOW variable; its `window.path` executable and `window.class` give the application (`jp2launcher.exe` + `SunAwtFrame` = Java Web Start application, `javaw.exe` + `#32770` = a Java runtime dialog, `msedge.exe` + `Chrome_WidgetWin_1` = Microsoft Edge, `iexplore.exe` + `IEFrame` = Internet Explorer, `OUTLOOK.EXE` + `rctrl_renwnd32` = Outlook desktop, `Explorer.EXE` + `CabinetWClass` = a File Explorer window, `CredentialUIBroker.exe` = the Windows credential prompt). The `window.name` is the title with `*` wildcards; the business application's name is the title's stable word (`LARA*`, `fulfillmentSCE*`). A window variable with empty `path` and `class` was never captured against a live window — title only.
2. **URL variables** (`LARA_DEV_URL`, `LARA_QA_URL`, `LARA_PROD_URL`, `openbrowser.url`) → Configuration Question "Which environment URL?" with the host as default; the values live in the configuration workbook, not the export, so the default is the variable's role unless a literal is present (a frame `src` in a capture — `http://lara-11g.<tenant>/LHP_appli.html` — gives the host).
3. **Mail server.** `emailConnect serverType=EWS` with `exchangeService`, OAuth `clientIdInteractive` / `tenantIdInteractive` = Exchange Online (Microsoft 365) through EWS; `EMAIL_SERVER` + `protocol IMAP` + `serverHost` = the named IMAP host; a browser login to `outlook.office365.com` / `login.microsoftonline.com` / a corporate identity provider page is the same mailbox reached through Outlook on the web to prime the OAuth token → Target Application "Exchange Online mailbox" plus a Configuration Question on the authentication method.
4. **OLEDB connection strings** → Excel workbooks (Target Application "Excel workbooks (via OLEDB)"); `Data Source=` names the file variable.
5. **`runApp` / `taskkill` executables** are the applications above; `taskkill` never creates a Target Application row on its own.
6. **Shared folders** (UNC paths in literals: `\\server\share\…`) → Platform Dependencies (a storage bucket or the kept network share), never a Target Application.
7. Global values `$@AAE_EmailSettings_*$` are Control Room email settings → Configuration Questions; `$@AABasePath$` is the runner's local repository root (migration path resolution) and disappears in UiPath; `$@AA_LocalMachinePath$` (with a `#UserName#` placeholder), `$@AAE_SQLConnectionString$` (a template with a `##DATABASE##` placeholder), `$@CleanUpTaskConfigFilePath$`, `$@AAE_EnvironmentType$` are deployment settings → text assets.
8. **REST URIs** live in configuration variables (`$vConfig_Generate_Token$`, `$vConfig_Input_API$`, `$vConfig_Acknowledgement_API$` with a `{messageId}` placeholder); the literal test URLs in disabled commands give the host of the test environment → Target Application "<vendor> API" named after the host and path, one credential asset per environment for the client credentials.
9. **`Chrome_WidgetWin_1` + `*.pdf*` title** = an Edge tab showing a PDF (the application's report viewer); the UI Automation read of its `Address and search bar` is "the URL of the PDF" → a browser Get URL, then a download.
10. **A C# DLL** (`DLL.Open` path from configuration) is not an application: it is code of the process → Build With rationale names it a coded step.

## Call Graph Rules

1. Edge = enabled `TaskBot.runTask` whose `taskbotFile` resolves to a bot in the export. Order edges by editor line. A disabled `runTask` is a dead call (Source Map); an unresolved path is an external or deleted bot (Source Map, "unresolved").
2. Roots = bots never referenced by an enabled edge. Leaves = bots with no outgoing enabled edge. One root is the process entry; several roots in one folder are several processes or one process plus superseded copies — decide by the folder's other bots and the migration journal, flag `*[Inferred]*`.
3. Depth-first from the root; siblings in editor order; a `runTask` inside a loop or a condition inherits that step's rule ("for each pending record, invoke …", "when login fails, invoke …").
4. **The same sub-bot called from many places is one step of the callee's component and a reference in each caller's step**: a notification bot called eighteen times is one "Send notification" workflow; the callers' steps say which notification they send. Never one workflow step per call site.
5. Argument bindings: `taskbotInput` keys are the callee's `input` variables; a key bound to the same-named caller variable is state pass-through, a key bound to a literal or another variable is a real parameter (`vTempProcessName="AutoCompTo"`, `strDept="$StrCompanyCode$"`). `taskbotOutput` and the node's `returnTo` map (`{ExceptionReason: $ExceptionReason$, …}`) are the outputs the caller reads. The Interface of a library component lists the parameters the callers actually bind, not every flagged variable.
6. Recursion is impossible (a bot cannot run itself); a `times` loop around a `runTask` is a retry (Error Handling), not a call-graph cycle.
7. MetaBot logic bots call each other (`LoginLARA` → `GetWindowTitle`, `GetErrorPopupText`); these are edges inside the library component and become invoked workflows of the same library.
8. **Logger bots are not edges of the workflow.** `profile` lists them; `cards` counts their calls separately and `dump --compact` renders each call as a log line. A component's step count never includes them.
9. **A sub-bot that ends itself** (`TaskBot.stopTask` after setting the error variables) returns to the caller like a normal return; the caller's `if $vErrorStatus$` decides. Word the sub-bot's stop as "the step ends with {error}" inside the caller's step, never as a process stop.
10. **Variants of one bot** (`_V1` / `_V2`, `_Japan`) are one workflow: diff them (`dump --compact` of both) and record the difference — a logout timer and relaunch added in V2, a different credential and mailbox URL in the Japan copy — as an argument or a Configuration Question, and the older copy as a Source Map row of the same step (called only by the session check).
11. **A result-set loop that assigns every row to the same variables** keeps the last row (`Process_Controller` reading "the detail row to process"); word it as "take the row the procedure returns" and flag the last-row behaviour.

## Expression Translation

Conditions are structured, not expressions: `{variable} {operator} {value}` with `EqualsTo` / `EQ` = "is", `DoesNotEqualTo` / `NEQ` = "is not", `INCLUDE` = "contains", `NOTINCLUDE` = "does not contain", `GreaterThan` / `GT` / `GreaterThanOrEqualTo` / `GTE` / `LT` / `LTE` = "exceeds" / "is at least" / "is less than" / "is at most", `matchCase: true` = "exactly". Several conditions on one `If` are joined by its `operator` (AND / OR); a native bot nests them as groups (`groupAttribute` / `operatorAttribute`) which `dump` renders with parentheses — keep the parentheses in the wording ("(contains `error` and not `Question`) or contains `LARA-009763`"). A `WHILE` loop's condition reads "until {condition is false}"; `dateVariable` compares a date field to a fixed date ("on or after 11 June 2024"); `fileDate … Days=5` reads "modified within the last 5 days"; `tableRowCondition GT 0` reads "when the table has rows". Arithmetic hides in `Number.assignToNumber input="<base>+$row$"` (a row offset) and in a minute difference (`$end$-$start$`, a timeout). Variable transforms in values (`$x.String:toNumber$`) carry no business meaning; `$Loop-Files-1{extension}$ EqualsTo "xlsx"` reads "the file is an Excel workbook". String flags stored as text (`"TRUE"` / `"FALSE"` in STRING variables) are booleans. Translate with the table in [genome-format-guide.md § Business Rules](../genome-format-guide.md). The SQL in `sqlQuery` / `insertUpdateDelete` is a business filter or a write-back: translate `WHERE [Transport Status] IN ('Started','Sent','Generated')` as "whose transport status is Started, Sent or Generated"; keep column names as field names in the genome (they are the data schema, not code).

## UI Target Locators

Every `Recorder.capture` (and every capture used as a condition) carries its recognition data inline — there is no object repository in an Automation 360 export. `targets` decodes it into one normalized record per capture (`a360-targets.json`): `technology` (`JAVA`, `HTML`, `MS_ACTIVE_ACCESSIBILITY`, `MS_UI_AUTOMATION`), `controlType` (`TEXTBOX`, `PASSWORD_TEXT`, `BUTTON`, `LABEL`, `CLIENT`), `criteria` (only the properties the author **enabled** for matching, `name → value`, values may be variable expressions), `object` (the decoded blob: accessible `name`, numeric `role`, `description`, `className`, `id`, the accessibility `path` of child indexes, bounds, the recorder's `attributes` list), `window` (the resolved WINDOW variable: title, class, executable), `action`, `value` (redacted for password fields), `credential`, `screenshots` (the PNG names under `<Bot>Metadata/`), `line`, `disabled`. Keystroke commands and window operations are listed per bot with their window. Formats and per-property translation: [automation-anywhere-selectors-guide.md](automation-anywhere-selectors-guide.md). Extraction records only counts (captures per technology and control type, how many disabled, how many located by position only) in the Source Map; execution derives the catalog at migration preflight and turns it into Object Repository targets ([source-migration-guide.md](../source-migration-guide.md)).

Several captures usually target the **same control** (the recorder attached a fresh capture each time the author recaptured after a run-time error — the disabled twin sits one line above the live one): collapse by window + criteria + object name at execution ([source-migration-guide.md § Object Repository identity](../source-migration-guide.md)). A control whose only enabled criteria are `Path` / `Index` is positional (low confidence, live capture owed); one whose `Index` is a variable is a row of a grid (§ Composite actions).

| Intake workbooks (mail attachments, sheet named `*TO_STATUS_REP*`) and the work-list workbooks the process creates (`<input>_TOSuccessList.xlsx`: `SLNO`, `TONumber`, `Status`, `Date`, `Reason`) | The transactional data and its schema | `query` sources (SELECT / INSERT / UPDATE columns) → Interface row schema |
| CREDENTIAL references | Accounts (§ Platform Resources); passwords never present as values | `mailbox` source names the account reference |
| Literals in disabled test commands (a recipient address in a disabled `sendMail`, a test transport-order number as a variable default, a test API host, client id and scope in a disabled `restPost`) | Test values the author used | Configuration Questions defaults, marked as test values; tokens and secrets among them are redacted (pitfall 18) |
| A **database-held configuration** (`Database.store` of a configuration procedure, rows `Name` / `Path` assigned to same-named variables) | Every process constant: folders, delays, browser and version, mail lists, API URLs and scope, query texts, sender bot ids, waiver folder | Not in the export — the key list is in the bot; each key is a Configuration Question with no default unless a literal gives one |
| Stored-procedure result sets and parameters (`stored-procedure` sources: parameters in / out, export file) | The transactional schema: which columns a step reads (`Department_Code`, `BookingReference`, `IsCustomerProfile`) and writes back | `stored-procedure` and `query` sources → Interface outputs and Handoffs data |
| `api-endpoint` sources (method, URI variable, header and form parameter names, vault references, response variable) | The API contract of the intake | Handoffs row for the API |
| `csv-file`, `text-file`, `pdf-file`, `download`, `dll-function`, `script`, `credential`, `mailbox-send` sources | Files the process reads or writes, the helper function call, the external scripts, the vault credentials assigned to variables, the mail sends with their account and recipients | Interface outputs, Platform Dependencies, Source Map |

`a360-process-data.json` is the process inventory `genome-step-map.py` consumes (`[{id, name, recordset: null, loggerBot, calls: [{calleeId, recordset: null}]}]` plus path, folder, inputs, outputs, screenshot and log counts, argument bindings); `a360-data-sources.json` is its recordset list (`[{id, name, kind, usedBy}]`, kinds `config-file`, `workbook`, `database-connection`, `query`, `stored-procedure`, `api-endpoint`, `dll-file`, `dll-function`, `csv-file`, `text-file`, `pdf-file`, `download`, `json-file`, `xml-file`, `xml-node`, `script`, `credential`, `mailbox`, `mailbox-folder`, `mailbox-send`, `folder`, `file-operation`, `log-file`, `screenshot-file`; ids derived from `kind|name` the same way as bot ids). Commands inside a disabled subtree are not sources: the script propagates a node's `disabled` flag to its whole subtree before counting. Rules: the runner-number branches (`BOT_SCALE_SEQUENCE` 1 / 2 / 3) are one data dimension (account per runner), never three steps; a `readStatus` that differs between the branches (`UNREAD` in two, `ALL` in the third) is a source quirk to carry over and flag, not to correct silently; template placeholders `{0}`, `{1}`, `{2}`, `{3}` and the order they are filled in are the notification's data contract.

## Provenance the Source Map must carry, and the inventory shape

Export identity: the export root path, the Control Room repository root the paths start with (`Automation Anywhere/Bots`), the bot count, the package versions that date the export (`profile` § PACKAGES), whether bots carry migration journal ids (Enterprise 11 origin) or native `Created Date` headers, whether a `manifest.json` is present (its file count by content type and whether its scanned dependencies match the bots' enabled edges — `profile` § MANIFEST), and the data files present under `MyDocs/`. Source object identity: `` `BotName` (id) `` with the id from `profile` / `cards` / `data` (CRC-32 of the repository path), because bot names repeat across folders and a moved copy keeps its path. Per workflow step: the bots the step was built from and, for a library workflow, the callers; the editor line ranges when one bot yields several steps (`dump` line numbers). Checkpoints (for test components only; a process export has none unless the bots assert). Inventory counts: bots, lines (enabled / disabled), window variables, captures (enabled / disabled, per technology), keystroke commands, credential references, data sources, dead calls, unresolved callees.

## Evidence

Automation 360 bots log to a text file on almost every step (`LogToFile.logToFile` is 13% of all lines in a typical migrated export) and take a desktop screenshot in catch blocks and on business errors (`Screen.captureDesktop`, named `<Screen>Error_<timestamp>.png` under the process's `Screenshots` folder). That is the blanket evidence policy of [extraction-guide.md](../extraction-guide.md) Step 3: `profile` § EVIDENCE AND NOISE and `cards` report log and screenshot counts per bot — state the policy once per component (log lines become the robot's own logging at the same points; a screenshot per handled error becomes screenshot-on-failure attached to the job), never one activity per log line. `MessageBox` commands are the author's debugging (107 of 109 disabled in the migrated export — but 112 of 288 **enabled** in the native export, echoing configuration, credentials and intermediate values); an enabled `MessageBox` blocks an unattended run and is an Error Handling finding (state the count once, in Error Handling § Global), not evidence. A **logger bot** (`Sub_Logger`: inputs message, level, file path, name, extension, task name; a level filter `ALL` / `TRACE` / `DEBUG` / `INFO` / `ERROR` / `NONE`; one CSV line `datetime,level,task,message` per call; the message convention `<LEVEL> -> <text>`) is the native equivalent of the migrated bots' direct log lines: `profile` and `cards` count its calls per bot; the genome states the level names and the line format once as the evidence policy and the rebuild maps them to the robot's log levels. Native bots also keep a second, per-bot text log (`AddlLog_<d>_<m>_<yyyy>.txt` under the runner's Documents) with `At <line>;<variables>` lines — the author's trace, useful for wording, never a step. Metadata PNGs are the recorder's captures of each control at design time: useful to an executor deriving a target (the screenshot shows the widget), never a run-time artifact.

**Checkpoints for the Source Map.** A process export asserts nothing formally; the checks it does make are business decisions (a popup text read and compared, a count queried) and belong to Business Rules. When a bot is a test (it only reads and compares), its GETPROPERTY-and-compare pairs are the checkpoints: record them as `line — asserts — expected — screenshot taken?`.

## Framework Pitfalls

1. **Disabled code is everywhere and looks like logic.** A fifth of all lines in a migrated export is disabled: whole `Step` blocks of the pre-migration Internet Explorer flow, the recapture twins of controls, the v11 credential comments, the IMAP connection commands replaced by OAuth. Read `dump --compact` (disabled subtrees folded) for the behaviour and the full dump only to understand history; put the superseded flow in the Source Map as dead code.
2. **Bot Migration plumbing is not behaviour.** Variables `m-string-start-in-path*` (a path staged for the next command), `M-Logic-Return-Dict-*` (a MetaBot's returned variables as a dictionary), `M-IsBotExecutedSuccessfully` and `M-Error-Description-Default-Val` (the `finally` / `throw` idiom marking the run Failed; the default value is empty), `Loop-Counter-*`, `Loop-Dataset-Column*`, `Loop-Files-*`, `Loop-Email-Response-*`, `Prompt-Assignment` (`Test-Value`), `my-list-variable`, the `.LegacyAutomation:parseVariableOperation` re-assignment after every assignment, `.LegacyAutomation:getAbsolutePath($@AABasePath$)` around every path. `profile` § MIGRATION PLUMBING counts them per bot. None of it enters the genome.
3. **Every variable is flagged input and output.** Migrated task bots declare 50–90 in/out variables and pass them all on every `runTask`; the real interface is the handful the callee reads or writes. Derive it from the body and from the bindings that carry a literal or a differently named variable.
4. **Empty error text means success.** Sub-bots return an error reason built from `Error-Description`, whose migration default is empty; a caller that tests the returned text for a word (`INCLUDE "Completed"`) can never see it and takes the failure branch. Carry the caller's rule as written, flag it `*[Inferred]*` as a suspected defect, and word the intended behaviour ("an empty error reason means the update succeeded").
5. **N identical branches per runner.** A `BOT_SCALE_SEQUENCE`-style switch repeats a 300-line block per bot runner, differing only in the credential and in accidental drift (one branch reads all mail instead of unread mail, one parses the company code with an extra step, one moves mail without filtering by subject and sender). Extract one step with the account as a parameter and list the drift as source quirks.
6. **`taskkill` is cleanup, not an application.** Migrated bots force-close Java, Edge, Excel and Outlook before and after work; word it once under Error Handling / cleanup.
7. **Positional Java locators.** Oracle Forms controls are matched by accessibility `Path` (`1|1|2|1|1|1|1|1|1|3|1|1|1|1|1|5`) and `Index`; the same control appears with `-1|…` and `1|…` paths in its recaptured twins and identical `Name`s repeat per grid row. `Name` + `Role` are the reusable identity; `Path` / `Index` are position ([automation-anywhere-selectors-guide.md § Java](automation-anywhere-selectors-guide.md)).
8. **Window variables are snapshots.** A WINDOW variable records the handle, size and the Java runtime's executable path of the capture session (`jre1.8.0_281`, `jre7`, `jre1.8.0_331` across bots); only title wildcard, class and executable *name* carry over. Titles differ by browser generation (`LARA*` for the applet frame, `LARA*- Microsoft Edge` for the launch tab, `fulfillmentSCE` for the login frame).
9. **Plaintext secrets.** A literal typed into a password field or assigned into a password-named variable (`StrLaraPassword`) is a secret in the export. The inventory script redacts the value wherever it appears; the genome names the credential asset and the report says the export contains a plaintext password without repeating it. Test recipient addresses and a runner's personal user name in disabled test commands are personal data — configuration values, not defaults to keep.
10. **Sheet names read through a formula.** `SetCell` `=MID(CELL("filename",A2),…)` into a spare cell followed by `GetSingleCell` is the v11 idiom for "read the active sheet's name"; it also **writes into the customer's input file** (cell M2). Word the intent (find the sheet whose name contains `TO_STATUS_REP`) and note the side effect.
11. **Excel through OLEDB.** `Database.*` commands with an ACE OLEDB connection string are workbook reads and writes; `[Sheet$]` is a sheet, the SQL is the filter or the write-back. `dosaveData` on `disconnect` is meaningless for a workbook. IMEX and HDR flags in the connection string are Configuration Question material (`CONNECTIONSTRING` itself is a config value with a `FileName` placeholder).
12. **`continueOnError` plus a string flag.** Callers run sub-bots with `continueOnError: true` and then test a `blnIsTaskError` string (`"TRUE"`) the sub-bot set, calling a shared exception logger and `stopTask`. That is the process's exception routing: one Error Handling § Global entry, not a rule per call site.
13. **Comments drift.** Section comments (`START: Email processing.`, `END: Download Attachment File`) are copy-pasted around unrelated calls; log messages are the reliable narration. Descriptions of MetaBot logics ("Metabot logic to …") are accurate.
14. **The launch page and the application are different windows and technologies.** A browser tab (HTML: click the `LARA` button in the `mainFrame` frame) starts a Java Web Start applet (JAVA: everything after); Java's own dialogs (`Security Warning`, `Java Update Needed`) are Win32 (MSAA) windows of `javaw.exe` / `jp2launcher.exe`; Edge's toolbar is UI Automation. One business step (open LARA) spans four technologies and three windows — the Target Applications table names the application once, the selectors guide maps each technology.
15. **Native bots pass 40–100 variables on every call.** A controller declares every setting as in / out and binds all of them by name on each `runTask` (`in{+55 pass-through}` in the compact dump). The real interface is the handful of bindings that carry a literal or a differently named variable (`cards` lists them as "real parameters passed"); the same-named ones are shared state. Never write a library Interface from the flags.
16. **`Database.store` is a stored procedure, not a "store".** The `query` attribute holds the procedure name, the session names are usually the procedure names too (`susp_Getting_…`), and one procedure call replaces what a migrated bot did with a dozen workbook commands. The result set drives the next loop; output parameters (`InputOutput`) come back through the node's `returnTo` map. Read the procedure's parameter names as the data contract; the procedure body is not in the export.
17. **The database is the work list and the run controller.** Master / detail tables, a per-runner hand-out procedure, a master-validation procedure returning `<flag>#<instruction>`, login tracking, notification trackers, templates. Word the protocol values (`Success`, `stop`, `delete`, `apierror`, `Stop`) and their effects; do not invent a queue — offer it as a Configuration Question.
18. **Secrets hide in disabled test commands and in configuration rows.** A disabled `restGet` carried a literal bearer token (a JWT) in its `Authorization` header and a disabled `restPost` a literal client id and secret; the database configuration carries `LARAUserName` / `LARAPassword` rows that the bots read and echo in a message box while the vault credential is what they type. The inventory script redacts JWTs, bearer / basic literals and every value of a `passw` / `pwd` / `secret` / `token` / `api key` attribute wherever they appear; the genome names the credential assets, reports that the export contains such literals, and never repeats them. A functional mailbox address (`GBS.…@`, `tyo.…@`) is a configuration value, not a secret.
19. **Copies of a MetaBot inside the process folder.** Native exports of a customer with MetaBot-era libraries carry the generic application bots as task bots beside the process (`Inputing_LARA_Credentials`, `ChangeDept`, `GenericPushButtons`, `ModuleToWaitForScreen`, `0_Common_Screen_Navigation_V1` / `_V2`); disabled `runTask` commands still pointing at `My MetaBots/…/Reusable Component/…` reveal the origin. They are the UI library (§ Component Detection), and the same bots appear in the sibling process's export under the MetaBot folder — one library serves both genomes.
20. **Bot variants.** `_V1` / `_V2` pairs (the session check still calls V1, the process calls V2), a `_Japan` copy of the mailbox sign-in differing only in the credential and the mailbox URL, a `_SingleBot` copy of the notification bot without the template step. Diff them; one workflow with an argument.
21. **Status strings drift.** Error flags are `STRING`s holding `TRUE` / `FALSE` — and `FASLE` on reset lines, `""` after a reset, `Fail` from one library bot, `true` in lower case from another; callers test `NEQ "TRUE"`, `INCLUDE "FALSE"`, `EQ "FALSE"`, `NOTINCLUDE "TRUE"` interchangeably. Translate every test to "when the step reported an error" and list the spellings once as a source quirk; a catch that sets the flag to `FALSE` (the waiver insert) hides its own failure — flag it.
22. **Enabled message boxes in production bots.** Native bots keep debugging message boxes enabled (`vConfig_… <> $value$`, `Step 1 :` dumps, popup echoes): 112 in the reference native export, 10 in the session check alone. Each would block an unattended run; count them in the Source Map inventory and state the finding once in Error Handling § Global.
23. **Positional Java locators dominate native captures.** 140 of 426 enabled controls in the native export are located by `Path` (plus `Top`, the y-coordinate) only; grid cells and tree rows use a `Path` whose last segment is a counter; the same field is captured under two path variants (`…|2|1|1|198` / `…|1|1|1|198`) in a try / catch pair. `Name` + `Role` are the reusable identity; the toolbar dispatcher's sixteen buttons are all positional ([automation-anywhere-selectors-guide.md § Java](automation-anywhere-selectors-guide.md)).
24. **Environment detection through Control Room values.** `$@AAE_EnvironmentType$` / `$System:AAControlRoom$` compared to `dev` / `uat` select connection strings, URLs and the API credential (`_UAT` locker); a hardcoded server-address replacement in the connection string (`10.5.102.20,1443` → `10.5.116.6,1450`) is a migration left-over to report as a Configuration Question default.
25. **`taskkill excel.exe` before every OLEDB read** and `usp_Kill_SleepingConnection` before the work loop are the source's workaround for leaked handles; word them once under cleanup, never as steps.
26. **Regional variants send from another mailbox.** The Japanese invoice email is sent from a second functional mailbox with a second credential and a hard-coded copy recipient; the plain-text copy of every notification is sent from a sibling process's mailbox (`Export_ECC/…`). Each account is its own credential asset ([genome-format-guide.md § Platform Dependencies](../genome-format-guide.md)); the cross-process mailbox is a source quirk to report.
