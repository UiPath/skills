# Test Execution Guide — test components at build

A genome with test components adds to [execution-guide.md](execution-guide.md) the test cases' shape and data and, for a suite extracted with its checkpoints, the parity with the source's results.

## Test cases

**Test components** follow the owning skill's testing guidance for shape and registration (Given-When-Then, data sources, test-case registration in the project manifest). Genome-specific rules on top: each case's data source is where § Test data keeps its data set; a source loop over data rows becomes the data source's variations with an execute-flag skip gate inside the case; constants live in the test project's configuration ([genome-format-guide.md § Interface](genome-format-guide.md); [execution-guide.md § 1.3](execution-guide.md), Test project template); checkpoints and captures are verify activities (§ Result parity rules 2–3); the case's own checkpoints and the checks the genome's rebuild text adds are its verifies, so a case whose criterion sits in the steps it calls ends with no verify of its own; every case records a one-line result the business consumer can read.

## Rules

1. **Migrate test data from the data catalog by default.** Seed records and variation files are filled from it by a scripted, reviewable mapping from source columns to the entity's rows or test-case arguments, never by hand (§ Test data). Generated placeholder rows are a temporary state, not a deliverable.
2. **A variation file's argument set is frozen during data migration.** Mappings place source values onto the test cases' existing arguments; a value with no argument goes to the project's configuration or argument defaults and is listed as `unmapped`. Source row counts and execution flags replace generated ones. Never widen a test case's argument set to fit the source layout.

## Result parity — making a UiPath run comparable with the source's

Whether a migrated suite reproduces the source's results is decided by whoever can compare runs — against a fresh source run when the source still executes, or against the last result log the export carries when it does not. That comparison is not the skill's job, nor is verifying the outcome. The skill's job is to make it possible: the built automation asserts at the source's checkpoints, names each assertion and its evidence by what it checks, and ships a mapping table saying which UiPath assertion and which artifact stand for each source checkpoint. The table is **static** — derived from the workflows before any run — one per test case, `parity/<TestCase>.md` in the hand-off folder ([execution-guide.md § 3.3](execution-guide.md)):

| # | Source checkpoint | Expected | UiPath assertion | Evidence | Compare |
|---|---|---|---|---|---|
| 12 | step 12 (id 4471) — verify requisition status after submit | `Successfully Completed` | Verify Expression With Operator `Requisition status after submit`, Equality, on the status cell's text read after "Click Submit" | the assertion's screenshot; log `Requisition status: expected Successfully Completed, got Successfully Completed` | equals |
| 19 | step 19 (id 4488) — screen capture after the position opened | position page shown | Verify Expression on True `Position page after OK` after "Click OK" | the assertion's screenshot | present |
| — | none | — | pick acceptance: `VerifyOptions` Appears on "Type Location", target: the field's value display | none | added |

Rules:

1. **Every source checkpoint has a row.** A checkpoint is a source step that asserts something (verify, compare, visible, cell check, a row search whose miss fails the step), a step the source's result log records as a check, or a capture the source took where the state was meant to be inspected; the source guide's § Evidence says which of its step kinds count. A check whose failure the source logs as a pass or ignores is not a checkpoint, a check inside a loop asserts on every pass, and a check on one branch asserts only on that branch. Extraction lists them per workflow step in the Source Map's Checkpoints row ([extracted-genome-guide.md § Source Map](extracted-genome-guide.md)). No checkpoint list, no parity.
2. **Every row names the UiPath construct that asserts the same thing:** the verify activity the owning skill's testing guidance gives for that kind of check — for a value on screen, the verify that wraps the read — with the source's operator and case rule under the testing package's comparison rules (the normal case), or a Check activity where the source branched ([ui-verification-guide.md](ui-verification-guide.md)). The verify sits at the checkpoint's source point, in When or in a workflow the case invokes, and stops the case where the source's failure ends it; the case's Then holds the final success criterion the case's own steps check, or only its result line when the steps it calls carry the checks. A custom check — a comparison in code and a throw, a Check activity and a log line — records no assertion, so its row is `not asserted`. A checkpoint with no counterpart is a row marked `not asserted` with the reason; the report counts them.
3. **Evidence per checkpoint, named by what it checks.** Test Manager stores two texts of each checkpoint's verify, and its reader has neither the genome nor the export: the title says what is checked in the business's words (`Requisition status after submit`), unique within its workflow file, and the message format shows what was checked with the expected and the observed value (`Requisition status: expected Successfully Completed, got {…}`). Neither text carries a source id, a step number or a checkpoint prefix; its component's checkpoint map (rule 6) ties each title to its source checkpoint. The verify logs that message itself, at Info on pass and at Error on fail, so a run's log reads row by row against the table, which gives each title its source checkpoint, and through it against the source's result log, with no log line of the build's own. The failure screenshot is on for every verify. A failure that is no assertion — an element not found, a throw after a restart ceiling — has no verify to take it: the Test Automation Framework template's TryCatch records it as a failed assertion with its screenshot, and the cleanup after it, such as closing the application, is the template's teardown hook (the owning skill's testing guidance). Without the template, each case wraps its Given, When and Then in the TryCatch the template uses, since Given opens the applications and prepares the data, with its cleanup in both the Catch and the Finally. The success screenshot is on only where the source captured at that point — a capture right after the checkpoint is that checkpoint's screenshot — so the rebuild captures where the source did and nowhere else. A source capture that is no checkpoint is a verify on True titled by what the screen shows (`Position page after OK`), in the checkpoint map like a checkpoint's, its success screenshot on: the screenshot reaches the result as a checkpoint's does — evidence, not a parity row — and it never fails where the source checked nothing. A verify's screenshot covers what the testing package captures, not the source's capture mode (the owning skill's testing guidance): where the source captured one window or one element, the checkpoint's Evidence cell and the report say what the screenshot covers instead. The verify properties behind these texts: the owning skill's testing guidance. A library whose steps hold checkpoints or captures depends on the testing package.
4. **The compare rule is the source's own criteria** carried over — equals, contains, present, absent, count — never tightened or loosened.
5. **Assertions the source never had are rows marked `added`:** the pattern verifications [ui-target-migration-guide.md § Composite interactions](ui-target-migration-guide.md) requires (pick acceptance the source did not verify) and the checks the genome's rebuild text states. A build adds none of its own. They do not count toward parity; they are listed so the reviewer sees the difference.
6. **Generated, not typed.** Each component whose workflows hold a checkpoint's or a capture's verify has a checkpoint map, `checkpoints/<component>.md` in the hand-off folder, written with the component — a row in the turn its verify is written — and kept current with it: one row per source checkpoint or capture the component asserts, in the source's order. Columns `Source id | Workflow | Verify title`: the id the genome's Checkpoints row or step table gives it, the workflow file holding its verify, and the verify's title. The parity table is produced by the executor's own script from the genome's Checkpoints rows of the case and of every step it calls, joined through the maps with the workflows' verify titles: a listed checkpoint with no map row, or whose mapped title its workflow no longer carries, is `not asserted`, and a mapped verify is never `added`. It needs no run, and is regenerated after every change. A table maintained by hand drifts from the project within one edit. The parity table's columns, its counts line (`source checkpoints N, asserted N, not asserted N, added N`) and the map's columns are the schema every executor writes, so tables from different runs and executors read alike; the script lives in the build's `migration/` folder and writes the tables into the hand-off folder.

The completion report states, per test case: source checkpoints, asserted, not asserted (with reasons), added, and where the tables are. It does not claim parity — only a comparison of runs can make that statement, and it belongs to the reviewer who holds a source result.

## Test data — pipeline

**The rebuild keeps a data set where the source kept it.** A data set the source reads from a store outside its project — a test-management database's recordsets, a database table — is edited by its owners without a release, read when each run starts, and may be written by the run itself. One the project ships as files (variation files, fixtures, a sheet in the repository) changes only with the project. The first becomes records of the project's test-data entity (§ Data kept in a store), the second a variation file per test case (§ Data shipped with the project). The source guide's § Test Data says where its data lives; an authored genome keeps its data where the description puts it, in project files otherwise.

| Step | Output |
|---|---|
| 1. Decode the data catalog | data sets as named rows (schema = layout variables, in column order); per data set the root that runs with it, the calls that bind it (mode, filter) and the steps that write it |
| 2. Per data set, decide its home and the mapping | store: its data-set name and its records in the project's test-data entity, the row key per column; files: per data file its source data sets and rows, per argument its source variable (with transform when needed), join, constant, lookup into another data set, or default |
| 3. Check coverage, then migrate | every column or argument has a rule, credentials refused, rows rewritten, coverage report per data set or file (migrated / kept / missing) |
| 4. Rebuild the project | data is not compiled; rebuild once to catch argument or field drift |

Report per project: rows and cells migrated, values kept at defaults and why, source values with no counterpart (and where they went), source quirks carried over (typos, wrong-field values, historical worker names, stale run dates). Historical run dates and worker names must be refreshed before a run on a live tenant; say so in the report.

### Data kept in a store

1. **All of a test project's data sets live in its one test-data entity**, one record per source row, in the shape the owning skill's testing guidance gives (data-set name, row order, the row as JSON). A data set's name is the source's, unless another data set of the project shares it: sources reuse a name across schemas (the source's layout, table or sheet) — a case's own data set and the item set its calls bind often share the case's name — and each data set sharing a name is then qualified by its schema's name. A data-set name is a contract once a test case binds it and is never renamed; the report lists data-set name → source schema and data set. The row's keys are the source's columns as written. Every value is text: a typed value changes it as the source held it (a decimal loses its scale, a date its format), and a source that types its values into screens as text keeps parity only as text — a step that needs a number or a date converts it through the project's parse helper, under the source's format. A credential column becomes `<Column>Asset`, holding the asset name ([source-migration-guide.md § Credentials](source-migration-guide.md)).
2. **Every data set the build uses is loaded, and only those** — a root's own, one a call binds, one a call picks by name at run time, one the run writes — so a data set several cases share is one set of records, as in the source. A data set no root and no call binds is left out and listed in the report with its source id.
3. **The entity exists in the connected tenant before a workflow that uses it is written**, as the Data Fabric scaffolding answer decides ([execution-guide.md § 1.3](execution-guide.md)), and is installed into the project before the UI automation package is (errata, Tools). An entity deleted or renamed in the tenant drops its type at the next install into a project, so every workflow using it stops compiling: the entity's name and its fields are a contract. Carry the entity through the install, one workflow that uses it, validate, build and a local run before the other workflows are written against it.
4. **Seed:** the records as JSON, in files of at most the batch the record insert accepts, generated by script from the data catalog with credential columns holding asset names. They are the baseline a re-seed restores and another environment loads, so they are handed over beside the open-items file, never in the project, where a file ships in the package ([open-items-guide.md](open-items-guide.md) rule 4). The build loads them as the owning skill's testing guidance states.
5. **A root's data set is its test case's data source.** The case binds to the entity filtered on the data set's name — a data-driven cluster on any of its members' names — and every matching record is one variation, read when the run starts, so a record added or edited later runs with no republish. How the binding is written, and its limits: the owning skill's testing guidance. The argument has no default, so no copy of the data stays in the project. Three things the source did differently are reported, not rebuilt:
   - a data set with no rows today: the case shows Failed without running until a record matches (an open item);
   - more rows than the data source returns: the rows beyond it never run (a gap);
   - rows that depend on one another through run-wide variables or the application's state, because the source ran every row in one session: each record runs as its own job. A dependency through a data set the run writes is kept, since that data set is in the entity.
6. **A call that binds a data set queries the entity before the invoke**, on the data set's name, in row order, as the owning skill's testing guidance states; the call's own filter — criteria on the row's columns, with values from the caller's variables when the call starts — runs on the parsed rows with the source's comparison rule exactly (equals or contains, its case rule). The query, the parse and the filter are one helper workflow of the project, invoked at each call site. The callee then runs once per matching row in row order, each pass a step of the same test:

   | Mode | Rebuild |
   |---|---|
   | Read | the query and the loop |
   | Read and update | after each pass, an update of that record whose row holds the columns the callee wrote |
   | Append | a loop that creates a record from the callee's outputs — the data set's name, the next row order, the outputs as the row — until the callee exits |
   | Clear and append | the data set's records deleted first, then append |

   No record matches → the call does what the source guide says the source does; a skipped call is no invoke and a Warn log line naming the callee, the data set and the criteria with their values, in the source's wording where the source logs the no-match itself. A no-match in today's data is a fact the genome states, not a source defect: the call keeps its query, so a record that matches later runs the callee with no change.
7. **A data set the run writes is written to the entity as the source writes it:** a clear deletes its records, an append creates the next row order, a read by position queries by row order and keeps a cursor, and a save-now or reload command builds nothing, since every write is stored at once. A write whose semantics the source guide leaves open is unresolved and asked.
8. **Isolation.** Tests that write a shared data set do not run in parallel, or write under a data-set name per run — the source's own idiom when it builds the name from the date or the user.

### Data shipped with the project

Each data-driven test case gets one variation file in the owning skill's format, filled by the scripted mapping (rule 1) from its source data sets. Recurring transforms: organisation-with-manager strings (`Org (Manager)` → org, manager), On/Off → boolean, country → region code, dates normalised, placeholder markers (`^`) → empty, user name → credential asset name and tenant URL.

**When the source row is wider than the analyzer's argument cap.** A data-driven test case binds its variation file to its arguments **by name**, so the column set and the argument set are one set: a row of thirty source columns is a case with thirty arguments, and the workflow-analyzer rule that caps arguments (`ST-DBP-002`, Error severity, so it fails analyze and pack but not validate) is breached by the data, not by the authoring. The cap is a default best practice written for hand-authored workflows; no project setting changes it — rule settings live in the user's analyzer configuration or a governance policy — and the pack command's governance-file option is accepted and then ignored. Resolve it in this order, and never by the last two:

1. Drop columns the case never reads — a variation column with no `row:` reference is dead weight, and trimming them is free.
2. Move values that are **environment**, not scenario, into the project's configuration (asset names, tenant URLs) — rule 2's normal route.
3. Still over: accept the finding. Record it as an accepted analyzer error with the reason, pack that project with the rule ignored (the analyze and pack commands' ignored-rules option, which a tenant governance policy overrides), and list the findings verbatim in the report ([execution-guide.md § 1.5](execution-guide.md) item 1 — decide with the user and record the decision). The analyzer runs first without the option so the findings are captured. Every later pack needs the same option, or a policy that disables the rule: an open item.
4. **Not** by dropping source data to fit, and **not** by moving per-scenario values into configuration — either one makes the case stop testing what the source tested, which is the whole point of the migration.

## Anti-patterns

1. Authoring test rows from genome defaults when the Source Map names a reachable export (rule 1).
2. Widening a test case's argument set to fit the source layout instead of mapping onto the existing arguments and configuration defaults (rule 2).
3. Reporting a test migration done without the result parity table, or with a hand-typed table; evidence the checkpoint map does not tie to its source checkpoint is not comparable evidence; a source id or checkpoint prefix in a verify's title or message reads as noise to everyone without the export (§ Result parity rules 3 and 6).
4. Dropping source data, or moving per-scenario values into configuration, to get a data-driven test case under the argument cap (§ Test data).
5. Copying a data set the source kept in a store into variation files or argument defaults, typing its columns, or reporting a filter that matches no row today as a source defect (§ Test data, Data kept in a store).
6. Asserting a test project's checkpoint with `VerifyOptions`, or with a Check activity and a log line, or attaching its evidence through a screenshot workflow of the build's own ([ui-verification-guide.md](ui-verification-guide.md), § Result parity rule 3).
