# Transactional Execution Guide — the transactional shape at build

A genome whose Transactional Shape is not the stub (§ Shape Rules) adds three things to [execution-guide.md](execution-guide.md): the split questions, the projects their answers materialise, and the REFramework surfaces each consumer project is built on. The behaviour the genome states is owed whatever the answers.

## Shape Rules

What the genome's Transactional Shape section states, as the build reads it; this guide's rules cite them by number. Whether the automation iterates over **units of work** — items that succeed, fail, are retried and are tracked independently of one another — and, when it does, how the work is handled today and how it could be divided at build. UiPath realises per-item work with the **REFramework** (Robotic Enterprise Framework): a state machine that opens the applications once, takes one item at a time, classifies each item's outcome, retries system failures, records every item's status, closes the applications at the end, and reads its settings from a configuration workbook plus Orchestrator assets. A **flow** is one kind of item handed from the steps or component that produce it to the steps or component that consume it, independently of any other item; the children an item expands into are levels of that item, not a flow of their own. The section **describes**, per flow (`### Flow N`, listed on the `Flows:` line): the unit of work and its alternatives (`Unit of work:`, `Alternative units of work:`), the `| Aspect | As-is |` table (Produced by, Consumed by, Item store, Coordination, Item kinds, Step groups), the outcomes table, the Split options table (`Unit of work | Option | Requires | Changes against as-is`), and the Evidence, Configuration and Traceability lines; a component genome inside a process carries its `Role:` line and `Split options: per the process genome, Flow N.` It **asserts no split, no store, no template and no unit** — those are the split questions' answers (§ Split questions) — except a split the agreed SDD or the user's request already chose, which the flow's `Decided:` line records. The behaviour written in Business Rules, Error Handling and Acceptance Criteria is owed whatever the user chooses.

1. **Applicability.** A unit of work is a discrete item that can succeed, fail, be retried and be tracked independently of the others, and the automation iterates over such items; each flow is tested on its own, and the section carries the stub only when no flow passes. **Component types that are never consumers** (they may still be producers): a library, a test-case group, a Flow, BPMN process or Case — as a coordinator or working its items itself, its per-item lifecycle is its own runtime's — an agent, an API workflow, a coded app, a function.
2. **Roles are described, never assigned.** "Produced by" and "Consumed by" name the steps — and, in a process genome, the components — that create and take items today. A consumer is an RPA process (`uipath-rpa`); the types rule 1 lists never are. `dispatcher` and `performer` name the projects a chosen split materialises, never what the genome claims the rebuild is.
3. **The item store follows the split.** The As-is row says where items and their state live today; each option needs the store this rule gives it. This rule is the options' one definition: the Split options table names an option by its letter and writes only what this flow requires and changes. **Option A keeps the items in the job**: one job takes its items end-to-end on one runner — the REFramework's direct mode, or a plain loop over an in-process list — and needs no Orchestrator queue. **Options B and C keep them in an Orchestrator queue**, which items need whenever they are shared across jobs — several runners, retries or postponements across runs, another process reading them after the run — with exactly **one queue per unit of work**, which any number of producers and consumers, and any number of runners of each, share. **C keeps both roles in one process**: one entry point and one trigger, every job produces behind a once-guard and then consumes, and every runner runs the same process — the shape of a source that runs one process on several robots and guards its population with a lock or a ledger. **B separates them** into processes with their own triggers, which the roles need when their cadences, machines, credentials or owners differ; a producer entry point with its own trigger is a producer process, so two entry points of one project are B, never C.
   A source's own coordination stores — a parent queue, a populate ledger, a lock, a tag join — are facts of the Coordination row; they are carried into a build only when the chosen split still needs them and the user keeps them (§ Split questions). **Per-item state a queue cannot hold.** An Orchestrator queue item carries specific content fixed when it is added, a progress text while it is in progress and output data written when it completes; none of them changes once the item is final, and a fetch selects by reference alone. Where the As-is keeps state beyond that — values written after the item is added that a later attempt, run or process reads; a hand-out filtered on anything but the reference; a change to an item after it is final; the outcomes of children worked inside their parent's transaction (rule 11) — B and C need a **record store** beside the queue: one record per item, keyed by the item's reference, holding that state, while the queue keeps hand-out, lock, attempts, postponement and outcome. State the queue can hold stays in it: a value fixed at add in the specific content, a value only the held attempt uses in its progress and output, a hand-out by item kind, one kind per item fixed at add, as one queue per kind. The As-is names the state and its readers; the Requires cells of B and C name the record store.
   A source that keeps its work list in a **database the process owns** (hand-out per runner, per-item status written back, operators reading the tables) already has a shared store: the As-is says so, the Requires and Changes cells of B and C can keep that database as the store or as the record store, and the build offers it in the store question rather than imposing a queue.
4. **Outcomes classify the rules and handlers already written; they never restate them.** Three rows always, a fourth only under the condition at the end of this rule: **Success**; **Business exception** — the Business Rules that reject an item (missing or wrong data, a rule the item fails): no retry, the item is recorded with the reason, the run continues; **System exception** — every other failure (application unavailable, element not found, timeout): the applications are closed and reopened, the item is retried the configured number of times, then recorded as failed with the reason, and the run stops after the configured number of consecutive system exceptions. Rules and handlers are named by step ("Step 7 rules: duplicate, no open PO"). A source's own per-item results — approved, rejected, skipped, routed to a person — are not outcome rows: the result of a completed item is the Success row, and every result a rule decides is a Business exception naming that rule by step. In an extracted genome this row states the source's own recovery and its two counts, 0 and 1 included, never the framework's defaults: "not retried (0×); the run stops after 1" is built as written. An authored genome asks the counts as Configuration Questions `(constant; default: retried 2×; stop after 3 consecutive)`. A fourth row, **Postponed**, exists only when the source or the description puts an item back for a later attempt without counting it as a failure. Its When names the rule by step; its Effect states the postpone time and the limit: in a queue store the item returns to the queue with a postpone time and its attempt count untouched, in an in-process store it is written back as pending; past the limit it is a business exception. Postponement never replaces the system-exception retry, and a run that waits between polls is not postponing items.
5. **Once per run, per item, at the end.** Every Workflow step of a consumer belongs to exactly one group, named by step number in the As-is Step groups row: once per run (open and sign in to the applications, read configuration and reference data, read the source when the store is in-process and the source is complete at the start), per item (the business steps), at the end (close the applications, write the summary or report). A producer's steps are never in the consumer's once-per-run group: they are the Produced by row's own steps. In a chain the steps that create the downstream flow's items are **per-item** steps of the upstream flow's consumer, named in both flows' blocks (rule 13).
6. **Configuration: split, do not repeat.** The settings and constants are the ones [genome-reading-guide.md § Configuration Questions](genome-reading-guide.md) marks; the section names which apply to the flow's consumer and states that its assets in Platform Dependencies are read at start, except each credential or Secret asset, read where its secret is used. A secret is never a configuration value ([genome-reading-guide.md § Platform Dependencies](genome-reading-guide.md)).
7. **Traceability: what is recorded per item, and where.** The reference, the outcome and its reason — as the queue item's status, progress and output when the store is a queue; as a write-back column, a result file or a reporting queue when it is not; a screenshot on every system exception; one run summary (items taken, succeeded, business exceptions, failed). These are what a reporting step or a digest reads; a reporting component reads them, never the consumer's log.
8. **Split options and evidence replace any verdict.** Options A, B and C are listed whenever a unit of work exists — once for the unit of work and once for every Alternative unit of work — each with its requirements and its changes against as-is; an option the evidence excludes is still listed, with the reason in its Requires cell. Two things are never options: **the number of runners**, a deployment setting of each resulting process (A runs on one runner per job; several runners mean B or C), and **several producers or several consumers**, sub-choices of B the build asks when the As-is shows several independent sources or several item kinds. The cells state facts in this automation's terms and never rank the options; the Evidence line carries facts only. The build prepares its recommended option from the As-is, the Evidence line and this derivation table:

   | Signal in the source or the description | Split options it enables or excludes |
   |---|---|
   | One job works items end-to-end, nothing else touches them, a rerun is harmless | A viable |
   | Several robots run the same process on the same items; an item must survive a run failure; a postponement or retry crosses runs | A excluded; B and C viable — C while both roles share cadence, machines, credentials and owner |
   | Another process reads the items after the run (a report, an audit, an operator view) | A excluded unless the job writes a per-item record the reader can use; B and C keep the items where the reader finds them |
   | Population and consumption have different natural cadences (an export published once a day, files dropped all day), or need different machines, credentials or owners | B favoured; C excluded |
   | Several independent sources feed the items | B with one producer per source, or A or C reading every source in its producer steps |
   | Item kinds need different applications or machines, or different attempt limits or SLAs | B with one consumer per kind and one queue per kind; otherwise one consumer with a route step |
   | The source guards population with a lock or a ledger | evidence that several identical jobs ran the process, which is C's shape; C keeps a once-guard in its place (a unique reference the queue refuses twice, or the kept ledger); B with one producer job removes the need for it |
   | Work happens once per parent when its children are final (a summary, a report, a close-out per file or mail) | at the child unit: every option names how that work learns its children are final (rule 11); at the parent unit: it is the transaction's last step |

   When the flow's producer and consumer are **different genome components**, B is their as-is, A means the two components' roles in one process and C the two components' roles in one process that keeps the queue between them: the build materialises one project for both, records it in the completion report, and leaves the genome's Components table unchanged.
9. **Levels.** The process genome carries the `Flows:` line and one full block per flow. A component genome inside a process carries one block per flow it takes part in — its `Role:` line, the As-is rows that concern the role, and `Split options: per the process genome, Flow N.` — or the stub with the reason. A standalone component genome carries every block in full. **A flow with one side outside the genome** — items handed to a queue another process works, or taken from one another process fills — carries `Split options: none — the consumer is outside this genome: {what takes the items}.` (or `the producer is outside this genome: …`) in place of the Split options table: the build cannot divide roles it does not build.
11. **Several levels of items are one unit of work.** A source whose items expand into children (a record into its line items, a file into its rows, a mail into its attachments) has one candidate level per generation; one is the unit of work and the other an Alternative unit of work. Whether a level is folded at build — children produced up front, several robots on one parent's children, the parent's fate derived from its children instead of kept as an item — is a build decision recorded in the completion report (§ REFramework at build). The Split options rows state the consequence per level: at the child level, how the parent's end-of-parent work learns that its children are final — a parent item on its own queue postponed until they are, a reporting step over the children's records with a guard against sending twice, the consumer that finishes the last child — and what that costs with several runners; at the parent level, that this work is the transaction's last step, that the children are worked inside the transaction, and what a parent retry redoes (only the unfinished children, when the children's state survives the retry).
13. **Chains.** When the consumer of Flow N produces the items of Flow N+1, the downstream item carries the upstream reference, so traceability follows an item end-to-end, and who creates it decides the rest. **The automation creates it:** creating it is a per-item step of the upstream item, and its failure is a system exception of the upstream item — retried with it, so the downstream reference must make a second creation a duplicate the store refuses (derive it from the upstream reference); the upstream item succeeds only when its downstream item exists. **A person creates it** (a review or approval between the stages): the upstream item succeeds when it is handed to that person, and the downstream reference is the upstream reference itself. Each flow's Split options are its own; taking option A or C for two adjacent flows puts their components' roles in one process — under A the intermediate store gone only when the downstream work can run inside the upstream transaction, under C the intermediate queue kept.

## Split questions

Asked once per **flow** of the Transactional Shape (its `### Flow N` blocks, in the order of the `Flows:` line), after the genome questions and before any scaffolding question, because the project list depends on every flow's answers. In a refactor they follow the refactor questions and are asked only for the flows whose consumer's target is an RPA process ([refactor-guide.md § Refactor questions](refactor-guide.md) rule 4). A component that takes part in several flows is resolved once, after all its flows are answered (§ Projects from the split answers). Every option is concrete; the first is **prepared from the genome** — the As-is table, the Evidence line and the derivation table of § Shape Rules rule 8 — and marked "(Recommended)"; the As-is option is the recommendation when the evidence favours nothing else. Questions whose condition does not hold are not asked. Each is worded as [configuration-questions-guide.md](configuration-questions-guide.md) rules 2–2b state, a flow by its unit of work (`the flow over each invoice`), never by its number.

| Topic | Question | Options (first = Recommended, prepared from the genome) |
|---|---|---|
| Unit of work | Which item is the transaction? | the genome's unit of work; each Alternative unit of work, with its fit condition and the Requires and Changes cells of its Split option rows quoted. When the unit is the child of a container that has its own rejections or end-of-parent work (a mail and its rows, a folder and its files), each option says where that work runs: at the child unit in the item fetch, outside the framework's handling of an item's outcome; at the container unit inside the transaction, its children a loop there |
| Split | How are the producer and consumer roles divided? | the genome's Split option rows **for the unit just chosen** — A (one process, both roles, no queue), B (a producer process and a consumer process) or C (one process, both roles, with a queue), the one the Evidence favours first (as-is when nothing favours another), each with its Requires and Changes cells; an excluded option shown last with its reason. The number of runners is not asked here: it is a deployment setting of each resulting process (Triggers) |
| Producers *(As-is names several sources)* | One producer for every source, or one per source? | one producer with every source (as-is); one producer per source, each with its own trigger, in one project; one producer per source as separate components |
| Consumers *(As-is names several item kinds)* | One consumer for every kind, or one per kind? | one consumer with a route step (as-is); one consumer per kind with one queue per kind; one consumer per kind sharing one queue by a reference convention — flagged fragile |
| Item store | Where do the items live? | B and C: one Orchestrator queue per unit of work (under C filled and worked by the same process), plus, where the option's Requires cell names one, the record store beside it — a Data Fabric entity, or the source's database the process owns (§ Shape Rules rule 3); A: in-process list read once per run (one runner) — no queue; the source's own database when the As-is names one the process owns (§ Shape Rules rule 3); one queue per unit of work **plus** the source's coordination stores kept (parent queue, ledger, lock) — offered only with the reason the genome's Coordination row gives |
| Template | Build each consumer project on the REFramework template? | REFramework in the mode the store implies — queue for a queue store, direct for an in-process store, and under C the producer steps in its initialisation behind the once-guard (Recommended); plain project — the per-item loop, outcomes, retries and per-item records authored from the genome's Error Handling and Transactional Shape |
| Shared steps *(B chosen; or two components' genomes describe behaviour that [genome-reading-guide.md § Two Levels](genome-reading-guide.md) rule 6 gives a library component the genome lacks — asked once, not per flow)* | The steps several projects need — configuration, guards, logging, run setup and cleanup, the mail client, the error mail — are duplicated or shared? | duplicated in each project (Recommended below about five steps); a common non-UI library component the executor creates, named in the report; under B also: kept in the consumer only, the producer re-implements the minimum it needs |
| Triggers and runners | How does each resulting project start, and on how many runners? | B producer: time trigger at the as-is cadence, one runner; B consumer: queue trigger with a robot cap (Recommended) or a time trigger on the robot pool; A: one time trigger, one runner; C: one time trigger at the as-is cadence on the as-is runner count, the once-guard making a later runner's population a no-op; manual start for replays — recorded for Deployment and the open-items file; the build creates no trigger |

Rules:

1. The split questions are asked once per flow of every Transactional Shape that is not the stub — the genome decides no split except on a `Decided:` line (below), so the questions are never skipped because the As-is "seemed clear". A component that is not an RPA process cannot consume (§ Shape Rules rule 2); a genome whose As-is names one has a defect: report it and do not ask. The answers are recorded under `Scaffolding`, one line per flow, as `Split: Flow <N> (<components>) — <A|B|C> — unit <item>; producers <n> (<sources>); consumers <m> (<kinds>); runners <producer n, consumer m>; store <one queue per unit [+ record store <entity or table>] | in-process | queues + kept coordination stores: …>; template <REFramework <queue|direct> | plain> per consumer project; shared steps <duplicated | library <name> | consumer only>; triggers <…>`. A "plain" template answer changes the project template, never the behaviour owed: every outcome, retry, postponement and per-item record the genome states is still built. A flow with a `Decided:` line — a split the agreed SDD or the user's request already chose — lists that option alone: its Unit of work and Split questions are answered, never asked or confirmed, and recorded `(from the SDD)` or `(from the request)` as the line's source says; the completion report lists them. A user who wants another option sends the genome back to `uipath-planner` as an edit, since the other options were never described.
2. Autonomous runs ([configuration-questions-guide.md](configuration-questions-guide.md)): for the split questions the default, for every flow, is the flow's `Decided:` option and unit when it has one; otherwise the As-is option with the genome's unit of work — B with a queue store when the As-is runs the producer and the consumer as separate processes or entry points; C with a queue store when one process both produces and consumes and shares its items across robots, runs or a later reader; A with an in-process store otherwise — its implied template, the record store its Requires cell names, and the As-is runner count.

## Projects from the split answers

**Resolve the split answers** (§ Split questions, one per flow) before creating anything:

- **Per flow first.** Each flow's answer says, for its producer and consumer: one process holding both roles, without a queue (A) or with one (C), or a producer process and a consumer process (B). For a flow inside one component, A and C keep one project and B splits it (below). For a flow between two genome components, B is one project per component (as-is) and A or C materialises **one project holding both components' roles** (under C with the queue between them kept), listed in the report's Files table under both components.
- **Then per component, across its flows.** A component in several flows takes the union of what its flows imply: a chain component that is the consumer of Flow 1 and the producer of Flow 2 hosts the Flow 1 consumer and creates the Flow 2 items inside its per-item steps (never in a once-per-run surface); a component that consumes two flows gets one consumer entry point, and one REFramework consumer project, per flow it consumes. Answers that pull a component two ways — Flow 1 merging it with its upstream component while Flow 2 splits the same component into producer and consumer projects, or two merges that chain three components into one project — are shown to the user with the resulting project list and confirmed before anything is created.

- Option A: the project the flow lands in — the component's own, or the one project of a merged pair above — keeps an in-process store and no queue; the producer's steps run inside the one job before its items are taken.
- Option C: the project the flow lands in, as under A, has one entry point and one trigger, and the unit-of-work queue declared as a solution resource as under B; every job runs the producer steps first behind a **once-guard** — the unique reference the queue refuses twice, or the source's ledger when the user kept it — and then takes items from the queue, so any number of runners can start the same process without producing twice.
- Option B: one genome component **materialises as several processes** — several projects, or one project whose producer and consumer entry points are each published as their own process when the As-is already has that shape — named after the component and the role — `<Component>.Dispatcher`, `<Component>.Performer`, or `<Component>.Dispatcher.<Source>` / `<Component>.Performer.<Kind>` — each created through the owning skill with that component's scaffolding answers. The genome's Components table is **not** edited; the report's Files table lists the materialised projects under their genome component with the split option that produced them.
- The store answer decides the solution resources: one Orchestrator queue per unit of work (or per consumer kind) declared with the attempt limits and the unique-reference rule the Outcomes table and the Reference rule imply, unique references always when a record store keys its records by them; a record store in Data Fabric is an entity created per the Data Fabric answer ([configuration-questions-guide.md](configuration-questions-guide.md)); a source coordination store (parent queue, ledger, lock) is declared only when the user kept it.
- A common library chosen under "Shared steps" is created as a library project and packed first ([execution-guide.md § 1.5](execution-guide.md) items 2 and 8).

**REFramework chosen** for a consumer project: create it from the REFramework template through the owning skill's project-creation step and its template-selection rules (it searches the template feed and never silently picks a Marketplace template), with the same scaffolding answers. The template's own files — the state-machine entry point, the configuration loader, the item fetch and status surfaces, retry, close and kill, screenshot — are the framework's: keep them and configure them per § REFramework at build. Never scaffold a blank project and hand-write a state machine, and never rewrite a framework file from memory.

## Groups and surfaces

Groups are planned per **materialised project**: a consumer project lists the surface each of its steps lands on — once per run → initialisation, per item → the per-item process, at the end → close — taken from the As-is Step groups row of the genome's Transactional Shape; a producer's steps go to the producer project or entry point, never to a consumer's initialisation; shared once-per-run steps go where the Shared steps answer put them.

## REFramework at build

Build each consumer project chosen for the REFramework on the template's surfaces per the owning skill's REFramework guidance, never from memory:

1. **Mode from the store answer.** A queue store: the queue named for the unit of work is wired where the template takes it (the owning skill's queue-driven mode) and the template's item fetch and status surfaces stay as shipped, apart from a record store's writes and fetch (item 1a); queue retries own the per-transaction retry, so the framework's own retry count is 0 and the source's in-phase retries (close the application, sign in again, retry the phase) stay inside the phase workflow. An in-process store (option A, the owning skill's tabular mode): a source complete at the start of the run is read once in the initialisation surface; a source the run polls until an end time (a mailbox, a drop folder) is polled by the item fetch, whose waits between polls follow the owning skill's stop-signal rule for waits inside the item fetch. The item fetch returns the next row or file, and nothing when the source is exhausted or the run ends; the status surface writes back where the Traceability line says instead of updating a queue item.
1a. **Record store.** Where the store answer adds one, each record carries the item's reference, the state the As-is keeps beyond the queue, the item's status and postpone time, and one sort key in the queue's hand-out order (items with a deadline first, then priority, then deadline, then age), since a query sorts by one field. Labels a fetch filters on (tags) are one text field, each enclosed in a delimiter and matched with it, since a text query's contains matches any substring; a matching rule of the source that the query cannot apply (case, wildcards) is finished in code. Every write goes to the record before the queue — the producer's before the add, each postponement, outcome and value a later attempt, run or process reads before the queue changes — so a failed record write fails the transaction and the queue's retry repeats it; a change to a final item writes the record alone. A fetch by reference alone stays the template's. A fetch on any other filter queries the record store for the first few candidates past their postpone time in sort-key order, shuffles those few so runners do not contend, and takes each from the queue by its exact reference until one is taken; a candidate another job took, postponed or finished is a miss, not an error, and when every candidate misses the fetch queries once more without them, then returns no item. A listing on such a filter reads the record store alone and takes nothing. The queue's lock is the only lock: a record says what to take, never who holds it. The initialisation surface first writes the final status of every record whose item is final, which a job that ended between its two writes leaves behind.
1b. **Children in the record store.** With a record store, children worked inside their parent's transaction (§ Shape Rules rule 11) are records of their own, keyed by the parent's reference and their own. The transaction reads its parent's children in their order, and each child carries its outcome and an attempt count, limited by the outcomes table's retry count, which replaces the queue's retry for a child. One job holds a parent at a time, so a child still in progress when its parent is taken belongs to an earlier attempt and is retaken, counted as an attempt. The parent completes only when no child is new, in progress or still within its attempts.
2. **Steps.** Consumer once-per-run steps into the application-open surface; per-item steps into the per-item process surface; at-the-end steps into the close surface. A Workflow step is a unit of the genome, not a file: the owning skill's rule for when a workflow file is worth writing decides the files, so a step of a few activities stays inline in its surface or in the workflow of the step it serves. **Where a producer's steps go follows the split**: A — the initialisation surface reads the source into the in-process list (item 1); C — the initialisation surface runs them once per job, before the first item fetch, behind the once-guard, and a failure there ends the job before any item is taken and is never retried as a transaction; B — never in the consumer: they are the producer entry point or project.
2a. **Applications.** Beside the at-the-end steps the close surface holds, the close and kill surfaces cover every application the project opens — its Target Applications and the applications its libraries launch — as the owning skill's checklist asks: an application is not a step, so no step mapping brings it there. The source's force-closes, which an extracted genome words as cleanup, name the processes. Where the source reuses an application a previous run left open, the framework's kill at the first initialisation changes that behaviour: keeping or dropping it is a decision recorded with its reason and reported as a deviation.
3. **Outcomes.** Every rule the outcomes table lists as a business exception is thrown as a business-rule exception carrying the genome's reason wording; everything else propagates as a system exception; a Postponed row becomes the queue postponement (or the pending write-back) with its limit; the retry and consecutive-failure counts go into the constants, from the outcomes table or from the Configuration Answers when the genome asks them. When the genome's system-exception outcome is retries **inside** the step (a re-logon count, a write attempt count) followed by a run stop, the framework's per-item retry is 0 and its consecutive-failure limit 1: the framework must neither multiply the in-step retries nor repeat a posting the step may already have made; with a queue store the queue's attempt limit is the only cross-run retry. Outcomes of the level above the item — a folder or a mail rejected before any row of it has been taken — have no transaction item yet: they are handled where the item fetch takes that container, recorded with their reason and reply as the genome says, and the fetch moves on; they are not thrown as a transaction's business exception. A stop decided outside the per-item surface (in the fetch, in the status surface) carries its reason to the end state so the job ends faulted. So does a failure of the close surface's own steps (the final mail, the clean-up) where the source's end fails the run: the framework only logs a failure there (the owning skill's End Process guidance), so the reason is set before those steps run, and each of them is contained so the others still run.
4. **Configuration.** Settings and constants from the Configuration Answers per the section's split, where the Settings store answer puts them; the Orchestrator assets from Platform Dependencies and from the settings that answer makes assets, wired as the owning skill's REFramework guide states for the template's configuration file; no secret in the configuration file. A setting the source addresses by number (a row of its configuration table) keeps that number in the configuration file, so it traces back to the source, and is read through one named member defined where the settings load: no workflow reads a setting by its number, and the guards ([configuration-questions-guide.md](configuration-questions-guide.md) rule 8) name the same members.
4a. **State.** The run's settings, identity and reference data are one object the initialisation surface fills and no later workflow writes; an item's values travel on the transaction item or as arguments of the workflows that use them, and a workflow that changes a value takes it as an in/out argument. One mutable object handed to every workflow hides which step writes what.
5. **Traceability.** The per-item record carries the outcome reason where the Traceability line says (queue status, progress and output; or the write-back); the template's screenshot on system exception stays.
6. **Coordination.** Source coordination the user did **not** keep (a parent queue, a ledger, a lock) is realised as what the split makes it: de-duplication on the unit-of-work queue, a derived parent view, a single producer job; what the user kept is built as declared. Under C the once-guard is the kept ledger when the user kept it, otherwise the unique-reference add on the unit-of-work queue. A kept ledger guards only when its queue refuses a second item of one reference, so it is declared with unique references, a deviation from the source's queue: without them, two runners that start together both find no ledger item and both populate. A failed ledger item still refuses its reference, so a failed population runs again only through that item's retry. Every add a guard or a derived reference (§ Shape Rules rule 13) relies on catches the duplicate-reference refusal the add raises, which the add-item activity's doc names, and goes on — a later runner to consume, a retried item past the add; any other failure propagates. Every such realisation is a deviation from the As-is and is listed in [completion-report-guide.md](completion-report-guide.md).
7. **Checklist.** The owning skill's REFramework customisation checklist is worked through in full before the group is reported complete, and the group report lists every item as done or not applicable with the reason; no global exception handler is added.

The framework's own files are configured, not authored, and are not workflow steps in the group report.

**Alternative unit of work chosen** (§ Split questions): re-derive the As-is and the outcomes at that granularity before item 1. The unit-of-work line and the producer's reference rule take the alternative's item and reference; the steps that iterated over the genome's unit of work become a loop inside the per-item group; a rejection of one former item is recorded in the new item's outcome reason and does not end the item, unless a Business Rule rejects the whole; the outcomes table is re-read at the new level. Record the unit under `Scaffolding` and report it in [completion-report-guide.md](completion-report-guide.md) as a deviation from the As-is, with its reason. The genome is not edited ([execution-guide.md § Anti-patterns](execution-guide.md) 6).

**Verify the group** ([execution-guide.md § 2.2](execution-guide.md) step 3): when a consumer project is built on the REFramework, the group also reports the customisation checklist complete and, where the owning skill offers a local run, drives one synthetic item through each exit — success, business exception, system exception retried, system exception stopping the run — and reports each exit as passed, failed with the observed behaviour, or not runnable; a failed exit blocks the group from being reported complete.

## Anti-patterns

1. **A shape asserted in the genome or chosen silently at build.** Skipping a split question because the As-is seemed clear; folding a producer's steps into the consumer's initialisation state outside option C, or under C without the once-guard; carrying a source's parent queue, ledger or lock into the build because the source had it, without the user having kept it; two queues for one unit of work, or one queue for two units; materialising projects the report does not tie to the split option that produced them; wrapping a linear flow in a state machine; scaffolding a blank project and hand-writing the state machine or its plumbing; adding a Global Exception Handler to a framework project; writing a secret into a configuration sheet; or reporting a framework group complete without the customisation checklist and the exits it exercised (§ Split questions, § Projects from the split answers, § REFramework at build).
