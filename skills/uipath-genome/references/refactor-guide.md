# Refactor Guide — rebuild a UiPath automation from its genome

A genome extracted from a UiPath source is built only to refactor that automation, and one extracted from another framework is refactored when the request asks for it instead of a migration that keeps the source's shape: every component is re-authored, never copied, on the UiPath product and framework the refactor answers choose, while the source keeps running until the switch. The genome is the behavioural contract; this guide adds to [execution-guide.md](execution-guide.md) the refactor questions, the refactor plan, the characterization tests, the run modes and the comparison, and the cutover.

## The contract

1. **Kept:** every rule, outcome, wait, retry and attempt count, every message, mail and log text word for word — a log line in the log the target keeps, wherever that is — the schedule and its time zone, and every output the source leaves — the records, files, mails, messages, tags and statuses it writes, with their names, fields, recipients and formats. Readers outside the export can depend on any output, so none is reshaped or dropped because nothing in the export reads it. A date the source takes from the clock keeps the source's clock: a rebuild that starts at another hour or in another time zone computes the date the source's run would have used.
2. **Changed only with a reason**, and each change is a row of the refactor plan (§ Refactor plan) or a record of the source-to-target trace ([migration-trace-guide.md](migration-trace-guide.md)):
   - a source defect, as the genome's defect index says the rebuild follows ([extracted-genome-guide.md § Source Defects](extracted-genome-guide.md));
   - a user ruling written in the genome;
   - a refactor answer (§ Refactor questions);
   - a platform limit the build meets, recorded with the finding;
   - a change of how that leaves every output the same: one read where the source read once per item, a check the source repeated now made once, duplicated branches merged, a hand-written guard replaced by the platform's own (a lock on running jobs by a queue's unique reference), dead code, unused dependencies and the source's workarounds for its own platform dropped.
3. **A behaviour the genome leaves to the user** — an evident intent only the step's purpose shows, an open question — keeps the source's behaviour until the user rules ([extracted-genome-guide.md § Source Defects](extracted-genome-guide.md)).
4. **Retries and re-runs are safe.** A write the rebuild retries, or that a second run of the same inputs would make again, first checks whether it already went through, so a retry never repeats it; where the source repeated it, that is a plan difference with this reason. The reads and checks a run's writes depend on run before its first write, so a failed read stops the run with nothing half done. Where that puts time between the read that decides a write and the write — reads batched at the start, items queued for later — the item is read again just before its write, and one changed meanwhile is left alone and reported.
5. **Carried over from a UiPath source, not re-derived:** the Object Repository and inline targets ([uipath-source-guide.md § UI Target Locators](uipath-source-guide.md)), the data files and test variations, the project's activity defaults as the new project's settings when the target is an RPA project, the libraries the source consumes, installed as packages, and the configuration of each connector activity — connector, object, operation, fields — from which the rebuild authors the same call where the build cannot resolve it from a live connection. From another framework's source, the UI targets, test data and credentials migrate, and each kind of source step is built, as [source-migration-guide.md](source-migration-guide.md) states; its rule that the rebuild keeps the source's names and shape gives way to § Refactor plan.

## Refactor questions

Asked after the genome questions and before the split questions ([execution-guide.md § 1.3](execution-guide.md)): the target of each component decides which split and scaffolding questions apply. Options are prepared from the genome — its steps, Transactional Shape and Handoffs — and from the Source Map's deployed-state and runtime rows ([uipath-source-guide.md § Provenance](uipath-source-guide.md)):

| Topic | Question | Options (first = Recommended) |
|---|---|---|
| Retire *(an entry point the runtime row shows with no run in its window)* | Rebuild `<entry point>` or retire it? | Rebuild (Recommended): a window with no run does not show the entry point is unused, since a quarterly, year-end or on-demand run can fall outside it; retire, when its owner confirms it is no longer used: nothing is built for it, and its removal is a cutover step |
| Fold *(a component that learns from another component's output what that component already knew — a mail it parses, a file or table it re-reads; a component started only by another's items that no longer need a queue once the reads are batched (§ Choosing the target rule 2); two components that run on one schedule over the same data)* | Fold `<reader>` into `<writer>`? | Fold (Recommended): the reader's steps run inside the writer's run, on the data the writer already holds; the reader's trigger, its parsing and the handoff go, its outputs stay; keep both |
| Target *(every component kept)* | Which UiPath product runs `<component>`? | The options of § Choosing the target, the Recommended one first, each with what the steps need from it |
| Rulings *(each source defect whose Rebuild follows cell leaves the choice to the user, and each evident intent the genome marks `*[Inferred]*`; code that can never run is dropped by the contract, never put to a ruling)* | `<the defect in a few words>`: keep the source's behaviour, or `<the evident intent>`? | The intent (Recommended when it changes only how a run counts, logs, retries or recovers — a wrong count, a retry that repeats a write, a fault that hides what the run did or stops the other items); the source's behaviour (Recommended when the intent would change a business outcome — what is written, to whom, for which item — or would send a mail or message the source never sent: that is the owner's to decide) |
| Run modes | Build a shadow mode and a write-test mode (§ Run modes)? | Both (Recommended when the automation writes to a system of record or reaches people, and no test environment holds data like production's); a dry-run switch only, which reads and writes nothing; neither |
| Run record | How does a run report what it did? | A run record and a failure alert (Recommended when the source's runs can skip items or fail without notice): each run's start, end, status and counts, and each item skipped or failed with its business key and reason, in a store the owner reads, plus a mail to the owner when a run fails; the logs only |
| Connections *(a connection the deployed state shows signed in as a person)* | Which identity does `<connection>` sign in as in the rebuild? | A service account of the same connector that the deployed state shows the source already using elsewhere (Recommended when there is one: a person's account makes every write look like that person's and stops the run when the person leaves); the source's identity; a service account the user names. The identity decides who appears as the author of every write and which fields and records the run can read, so a changed identity's access is checked before the first live run (§ Cutover) |

Rules:

1. The answers are recorded under `Refactor` in the Configuration Answers, one line per component: `<component> — <retired | folded into <component> | <target>> — modes <both | dry run | none> — run record <yes | no> — connections <kept | <service account>> — rulings <defect: intent | source>, …`. A ruling becomes a plan difference (§ Refactor plan) and is offered as a genome edit in the completion report ([editing-guide.md](editing-guide.md), "Fix this defect in the rebuild"), so the genome states the contract the rebuild follows.
2. Unattended runs take the Recommended option of every refactor question, as [execution-guide.md § 1.3](execution-guide.md) takes every default.
3. A retired component, and a folded one, gets no project. A folded component's steps are planned in the writer's groups, after the writer's steps whose data they use; the handoff between the two is not built, and every output the folded component left is still written.
4. The split questions are asked only for the components whose target is an RPA process: any other target works its items in its own loop, and every outcome the Transactional Shape lists is still owed — each item retried and reported on its own, one item's failure never ending the others.

## Choosing the target

The target is chosen per component in two moves. First each step is typed with [skill-mapping-guide.md § Decision Tree for Ambiguous Steps](skill-mapping-guide.md), which places every kind of step on the UiPath product that runs it — screens and machine-local work, connector and HTTP calls, document extraction, decision tables, judgment, deterministic code, a person's task, coordination, a user screen, shared data. Then the component gets one host, the product that runs all its steps: a host keeps as steps the calls it makes and uses within one run — an RPA process calls connectors, document models, an LLM, an agent or a published automation; an API workflow calls connectors and other API workflows; a coordinator calls them all as its nodes — so a component whose steps type to several products is still one host unless its coordination needs a coordinator (the tree's coordination row). The Recommended host is the simplest that holds every step:

| The component's steps | Recommended host |
|---|---|
| Any step on a screen or on what only a robot's machine reaches | RPA process, Portable unless an activity the steps need exists only for Windows; the other typed steps become its activities and calls |
| Connector and HTTP calls only, in a short run of few steps | API workflow |
| Connector and HTTP calls only, in a long run, with waits, or with many steps whose every run must be inspectable step by step | Maestro flow |
| Items worked one by one, each retried and reported on its own after the reads are batched (rule 2) | an RPA process that consumes the queue — the only component kind that consumes ([transactional-shape-guide.md](transactional-shape-guide.md) rule 2) — doing the queue work itself (taking items, setting their status) and starting each item's connector and HTTP work as an API workflow, so only the queue work needs a robot |
| Coordination one host cannot hold: a person's task or a wait of days between automations, events or timers, parallel branches | Maestro flow, BPMN process or case, as the tree's coordination row distinguishes them, with each automation it calls a component of its own |
| A threshold, eligibility or routing table, a document-extraction model, judgment no rule decides, code several components call | a component of its own beside the host — decision table, extraction model, agent, function — only when the business maintains it apart, it is trained, or several components call it; otherwise a step of the host |

1. **A product is chosen for the shape, never as an upgrade.** A Maestro coordinator, an agent, a function or a queue is the Recommended option only when the steps need what it adds. A UiPath source's own product is always an option; a Windows project's other option is the same project kind on Portable.
2. **Batch before counting items.** A per-item fan-out the source built because it read one item at a time — a queue item per row, then a remote lookup per item — is counted again after the reads are batched: one query for all rows, matched in memory, asking only for the items whose state can lead to an action — the filters the decision applies moved into the query, none narrower than the rules. When what is left per item is a few writes a run, the target works them in its own loop, and the queue goes; when the items still need retries across runs, parallel workers or per-item status that people read, the queue stays. This rule decides the split question's default in a refactor, before the autonomous default of [transactional-execution-guide.md § Split questions](transactional-execution-guide.md) rule 2.
3. **Coordination is replaced, not copied or dropped.** For each lock on running jobs, second pass over the same items or ledger the source built, the plan names what it protects against and what it costs: a lock that ends a run when another is running drops the work of every event that arrives meanwhile, and a second pass repeats every read to catch data that changed mid-run. The target keeps the protection by its own means — a queue item per unit of work with a unique reference, so every event adds its work and duplicates are refused; a fresh read of each item before its writes — and the source's mechanism is kept only with the reason the target's means cannot hold. A coordinator replaces the queues and triggers between the automations it coordinates — it starts each one and waits for its result — so it is judged on what the whole chain needs (how the chain starts, its waits, its human tasks, its retries), never on whether it can take the source's queue items or start on the source's queue triggers.
4. **Check the target before recommending it.** Each connector operation, trigger and limit the steps rely on — how the target is started (time, queue, event), how it reads its configuration (assets, inputs), what it can call (another process, a queue), its run-time limit — is confirmed through the target's owning skill: its SKILL.md and its discovery commands (a connector registry, an activity listing). For every operation the registry does not list, the generic HTTP route is checked before the operation is called unconfirmed: the operation is confirmed when the target's owning skill documents an HTTP step that calls the vendor's API through the connector's connection and the vendor's API documentation has the call (a workbook read through the vendor's API where the connector lists no read operation) — a documentation check, needing no live call. A tenant or a connection the run cannot reach is no evidence against a target. A capability none of these confirms makes that target a later option, the gap named in its label.
5. **Probe what decides the shape before the plan fixes it.** A behaviour the target's documentation leaves open and the choice turns on — whether a queue refuses a reference again once its item succeeded, whether a trigger can start that kind of project, the answer shape of a call — is tried in a throwaway project outside the build, and the result goes into the plan's Decisions. A probe that needs a tenant runs only in a folder of its own that the user allows for it; without one, the plan takes the behaviour the documentation states, lists it under Not proven with the design the build falls back to when it is wrong, and names the probe as a cutover step before the shadow run. A capability found missing during the build changes the plan: the plan records the finding, the new target or the workaround, and why.
6. **An event trigger stays an event trigger.** A component the source starts on a system's event keeps that event, read from the genome's Deployment and, for a UiPath source, its deployed state ([uipath-source-guide.md § Deployed State](uipath-source-guide.md)); the target is one that the event can start, directly or through a component that it starts.

## Refactor plan

Written to `migration/refactor-plan.md` once the questions are answered and before any project is created, and read by every group:

1. **Decisions:** the refactor answer line of each component (§ Refactor questions rule 1), then the projects the answers materialise, with the target's reason. Where the answers change the genome's Build With, Components or Handoffs rows, the build follows the plan: projects are created ([execution-guide.md § 1.4](execution-guide.md)), groups planned (§ 2.1), built through the target's owning skill (§ 2.2) and wired (§ 2.3) from the plan's projects and the handoffs it keeps, and the genome stays as written.
2. **Differences:** one row per output the rebuild produces differently from the source — `# | Source | Rebuild | Reason` — the reason one of the contract's (a defect with its index row, a ruling with its date, an answer, a platform limit with its finding, a retry made safe). A change of how that leaves every output the same is a trace record, not a row of this table.
3. **Kept outputs:** each store, file, mail, message and tag the source writes and the rebuild writes the same way, with its name and fields or recipients: the list the comparison and the characterization tests check.
4. **Not proven until it runs:** each assumption the offline build cannot prove — a connector's answer shape, a trigger's input, a limit, an identity's access — with the run that first shows it (the first shadow run, the write test, the first live run) and what the rebuild does when it is wrong. Groups add the assumptions they meet.

The build names its own steps and groups them for the target — a refactor, not a migration — each display name saying what the step does in the business's words, and keeps every text a person or another system reads as the source spells it. Its source-to-target trace follows [migration-trace-guide.md](migration-trace-guide.md); records cite the plan rows, folds, retirements and how-changes they implement.

## Characterization

The source's behaviour is pinned in tests before the rebuild's logic exists, so the rebuild proves that it changed the internals and kept the outcomes:

1. **Before a group builds a step's logic, it builds that step's characterization tests:** fixed inputs and the outcome the source produces from them, for every rule and branch of the step and every acceptance criterion it serves. They are written in the owning skill's test facility — test cases an RPA project runs locally, the evaluation rows of an API workflow or a flow — under that skill's rules for when they run (a run that needs the user's consent or a tenant waits for it), and the logic the target runs as code (a script step, a coded workflow) is also checked offline by the run's own check, so a build with no tenant still runs its characterization.
2. **Texts are compared with the source's own.** Each mail, message and log line the rebuild writes is checked against its text in the source workflow, spacing and punctuation included, with the values the test supplies.
3. **A plan difference is a test of the rebuild's behaviour** that names its row; every other test expects the source's outcome.
4. **Recorded runs are replayed when the user has them** — job logs with the items each run handled and what it did, the records a run wrote: the rebuild's decisions on those inputs equal the source's, except the plan's differences.
5. **The source is not run to make expectations** against production systems; its outcomes come from its workflows, the genome and the recorded runs.

The results — tests per step, passed, and the plan rows they cover — go in the completion report.

## Run modes

Built when the Run modes answer asks for them, in every component that writes:

1. **One required setting, `mode`:** `shadow`, `write-test` or `live`, with no default; a missing or unknown value stops the run before its first read, naming the setting.
2. **Reads run in every mode; writes run only in live mode** — every record, file, mail, message, tag and status the run writes, in the source's systems and in its own stores — except in write-test mode, which writes for one item only: one the source would write the same way in the same run, its mails only to the test recipient the configuration names.
3. **In shadow mode each write a live run would make is recorded instead**, as a would-do record in a store the rebuild owns: the run, the item's key, the action and what it would write — fields, recipients, subject, text. The run writes nothing else.
4. **The shadow keeps its own done-marks** where the source marks its work done in a system both read (a tag, a status, a record) and the shadow cannot run before every source run that writes the mark — a source started on events, many times a day. It records its marks in its store and reads each item as it would be had the source not run, so the source's marks do not hide the work the shadow must decide. A shadow that runs before each source run reads the systems as they stand.
5. **The shadow sees the source's inputs:** it runs just before the source's run, with the date and time window the source's run uses.
6. **The comparison is a read-only check built and tested with the rebuild:** given one source run — its job logs, the records and mails it left — and the shadow's would-do records for the same inputs, it lists each item as the same, different as expected (citing the plan row), or to look at, and prints the counts per run.

The stores the run record, the would-do records and the shadow's marks need are platform resources the rebuild adds: Platform Dependencies of the plan's Decisions, created per the Data Fabric answer ([execution-guide.md § 1.3](execution-guide.md)) or listed in the open items.

## Cutover

The refactor's open-items file for the solution ([open-items-guide.md](open-items-guide.md)) ends with a `## Cutover` section, after Triggers, in the same voice — one step per checkbox, for the engineer:

1. **Shadow run** — when modes were built: deploy in shadow mode into a folder of its own, its trigger before the source's; run the comparison after each run until a set number of runs (the user's, five by default) shows nothing to look at.
2. **Write test** — when write-test mode was built: one run in write-test mode; read back every write, including the identity it was written as. A second item the run must fail or skip proves the failure path's writes too — a failed status, an error mail.
3. **Access check** — when a connection changes identity: one read of every field and record the steps read and write, on that connection, before the first live run.
4. **Switch,** in one change window: the source's triggers disabled and its pending, running and suspended jobs finished or stopped before the rebuild's triggers are enabled — a disabled trigger starts no new job but leaves those running, and two implementations writing at once can repeat or interleave each other's writes; `mode` set to `live` when modes were built; after every deploy or upgrade, every trigger (enabled or not, its input, the identity it runs as) and every connection binding read back.
5. **Rollback:** the criteria (a failed run, a difference to look at, an outcome missing) and the steps — the rebuild's triggers off and its jobs finished or stopped, then the source's back on; the source's processes stay deployed until retirement.
6. **Hypercare:** the first live runs compared with the runtime baseline of the Source Map.
7. **Retirement:** the source's processes and triggers, the retired and folded components, and each queue, asset and connection that neither the rebuild nor another automation uses (for a UiPath source, the deployed state's other processes); a queue once it holds no open item.

## Done

Beyond [execution-guide.md](execution-guide.md)'s list, a refactor is done when the refactor plan is written, every step's characterization tests run with their results in the report, the run modes and the comparison are built where the answer asked for them, and the Cutover section is written. The completion report adds one line: `Refactor: <component → target | folded into X | retired>, …; plan migration/refactor-plan.md (<n> differences, <m> unproven); characterization <passed>/<total>; modes <both | dry run | none>; comparison <built | not built>`.

## Anti-patterns

1. **Copying a source workflow into the rebuild**, or porting it activity by activity: a refactor re-authors each component from the genome.
2. **Choosing a target by preference** — a flow or an agent because it is newer, a queue because the source had one — or without checking the capabilities the steps rely on (§ Choosing the target).
3. **A changed output with no plan row**, an output dropped because nothing in the export reads it, or a defect fixed that the genome says the rebuild keeps (§ The contract).
4. **A shadow that writes, or that decides from the source's done-marks** (§ Run modes).
5. **Logic built before its characterization tests**, or tests whose expected values come from the rebuild instead of the source (§ Characterization).
