# Composite Interactions Guide — one source step, several UiPath activities

Part of the UI target migration of [ui-target-migration-guide.md](ui-target-migration-guide.md); the § Object Repository identity, § Element Scope and § Verifying targets pointers below are that guide's.


Test frameworks package multi-step interactions into one parameterised step: type-ahead pick, menu path, option list, find-row-then-act, keystrokes to the focused element. The genome substep carries the interaction contract ([genome-reading-guide.md § Workflow](genome-reading-guide.md)); the source guide's composite-actions table names the source actions and dictates wording; this section fixes how execution builds them. **Rule: build the pattern, never the nearest single activity.** Each naive mapping below validates, runs, and does the wrong thing: type-ahead as "type, then click the first popup entry", a custom list as a native select, a two-level menu as one click. This is the most expensive class of migration defect, because none of it shows up as an error — the project builds, the run completes, and the automation exercised nothing.

**Derived elements.** The catalog holds only the anchor control (input, menu root, table); the popup entries, menu items, option rows and matched cells the source clicked were never learned and must be derived. A derived element's selector is its tag and the matched text, with its semantic description — never an identifier the source did not record for it ([selector-translation-guide.md](selector-translation-guide.md) rule 13). Which attribute carries the matched text is the three-case test of [selector-translation-web-guide.md § Rule 5](selector-translation-web-guide.md) (form-ish tag → synthesised `aaname`; text leaf → `aaname` + `isleaf='1'`; container → `visibleinnertext` matched exactly); the tag is the one the node's role in the pattern implies, never a guessed `DIV` — a derived element has no recorded tag to draw on, so it is the one case where the role's implied tag is the best evidence there is (rule 14). Where the catalog does not say which node is which, the target is tag-only with the semantic description and owes a live pass (rule 13).

Before building any UI group of an extracted genome, read the per-control `actions` in the derived target catalog and the substep wording, classify every UI step against this table, and read the owning skill's control-interaction guidance for the classified controls (option lists, date inputs, tables) as it mandates. Which patterns become workflows of their own follows the owning skill's rule on the groups it extracts; one that does is parametrised by field label and value (§ Object Repository identity rule 3), and the steps invoke it. A helper that pages through a list or grid to find what it acts on starts each call from the first page, or restores the page it found: otherwise a call that ends on another page, a miss the step tolerates included, starts the next call there. A row that builds a single activity — keystrokes, a coordinate click, set state, set versus type — is that activity at each call site, with its keys or state chosen at build time. Node roles named below (wrapper, label, form item, acting leaf, value display, popup list, popup entry) and their concrete shapes: [selector-translation-guide.md](selector-translation-guide.md) rule 16 and, on the web, [selector-translation-web-guide.md § Rule 16](selector-translation-web-guide.md).

| **Type-ahead pick** — type text, suggestion list appears, pick the entry matching a caption rule, optional confirm key | type + click "first item" (positional container element); type + Enter without checking what was accepted; **verifying on the option's text leaf**, which also exists in the still-open list and passes before anything was accepted | 1. Type the value into the field's *acting leaf* — the labelled input, never the widget wrapper — with key-event input (never set-value: the list opens only on key events). 2. Confirm as the source did (Enter) or pick: the entry is the popup's text leaf, scoped to the *popup labelled with the field*, caption as a selector variable under the source's criteria (contains / equals / nth). 3. Verify on the acting activity's `VerifyOptions` (`Appears`) against the field's **value display scoped to the field** ([ui-verification-guide.md](ui-verification-guide.md)) — the source's own verification becomes this acceptance check. The typed text is gone once the prompt accepts, so Type Into's target-less Auto/Expected-text verify does not apply to a prompt. 4. When the source itself had a fallback (Enter failed → click the entry), keep it as a Check with the click in the not-found branch; the verify still belongs on the acting activities | popup entry (scoped to the labelled popup) and value display (scoped to the field) — one pair per widget type, parametrised by field label and value, or one pair per field; low confidence until seen live, `derived from <anchor control>` |
| **Option list** — choose an item by caption rule from a list, dropdown or combo | `SelectItem` on a custom (div/li/span) widget; positional `idx` on the item; verifying on the option text | Whether the control takes Select Item, and its `items`, come from the application notes' structures ([live-application-guide.md § Exploring](live-application-guide.md)), where exploration probed it as the owning skill's select-item guidance prescribes: read its `items`, and tried a select where `items` was empty. If the control takes Select Item, use `SelectItem` with the source's caption under the source's criterion: the caption for Is Equal To, `*value*` for Contains, `value*` for Starts With, where that guidance says the control takes a pattern. If the source ignores case, select the entry of `items` that matches; where `items` stays empty, select the caption as the application spells it and record the deviation. If the control does not take Select Item (custom lists expose `selecteditem` but not `items`), click the combobox open (the acting leaf, inside the form item pinned by its label), click the option under the *list labelled with the field*, and verify the field's displayed selection, scoped to the field. For a list the notes do not settle, a source step that selects from a combo or list box is `SelectItem` at its call site under the same rules, and a source that clicked the list open and then an entry keeps those two clicks; each such list is a row of the live checks, and a list the healing pass finds not taking Select Item gets the click-to-open form, noted per list. A numeric index in the source is positional: keep it as an index on the option element and flag it | option entry (scoped to the labelled list), displayed selection; medium when the source caption is literal, low when variable-bound |
| **Segmented date entry** — source clicked a date field off-centre (its first segment) and typed the whole date | Type Into on the widget wrapper with the source's click offset; a bare-tag Check afterwards | Target the first segment by the field's label (only the first segment carries it), or scope on the form item (§ Element Scope) and type into each segment with the segment's expected text as the verify. Follow the owning skill's date-input guidance for the rendered format, `EmptyFieldMode` None and auto-advance. Verify against the widget's rendered value (a hidden "current value is …" leaf, or the segments) — never a bare `tag='DIV'` | month/day/year segments under the field's form item; medium |
| **Menu / tree path** — `A\|B\|C` from a menu root, levels revealed by hover or click | one click on the root, or on the leaf caption anywhere on the page | One click (or hover, as the application notes record) per level, each re-resolving its target after the previous level rendered; levels are separate activities, never one target with the leaf text. Each revealed level is usually a *new popup of the same type*, and a label can repeat across groups of one level, so a level entry is scoped to its own popup (the newest one) or to its group header, never matched page-wide by text. The last level gets a verify (the page or dialog the leaf opens). A desktop tree or tab control that takes `SelectItem` (settled as for an option list) selects a node by its caption, not by its path: a level whose caption is unique in the control is that select, any other stays a click. Menu roots that appear in several source windows reuse one element | one element per level (text leaf under its own popup); medium for the root (mapped), low for levels |
| **Table row by content** — find the row whose cell(s) match, then click, read, type or verify in that row | store a row number and index into the table with it; assume the grid's markup without looking | Never carry a row integer. Choose the cell shape per [selector-translation-guide.md](selector-translation-guide.md) rule 8 from the one cell's attribute listing the application notes record for the grid (table attributes → row-anchored `TD` by `rowName`/`colName`; absent → row container pinned by exact text, cell as its descendant; key text repeated in its column → pin the row by the discriminating value); a grid the notes do not cover takes rule 8's offline shape and a row of the live checks. Alternatively extract the table, filter in code, then act through the pinned row. `Last` = last matching row. Multi-criteria finds and-combine the cell matches. Source "popup rendered as table" (suggestion popups) is an option pick, not a table op | matched cell (anchor), target cell in the same row; medium |
| **Table cell** — act on the cell at (row rule, column caption or number) | absolute `tableRow`/`tableCol` | Column by header caption (`colName='{caption}*'` where the application notes record it exposed; otherwise a row of the live checks, and the healing pass, which can anchor the cell to its header, decides), row by content rule from the preceding find; a literal row number in the source is positional and stays flagged; double-click and follow-up keystroke preserved. A prompt inside a cell (typed value + Enter) is a type-ahead pick inside the cell | header cell, target cell; medium |
| **Read cell / row count / control text** | Get Text on the table element | Get Text or Get Attribute on the row-anchored cell after previewing what it extracts (owning skill's get-text guidance); row count via table extraction or a rows attribute, a row of the live checks until the notes or the healing pass confirm it | as table cell |
| **Collect matching elements** — the source gathers every element a locator matches (a find-all) and reads or acts on them by position | Find Elements with no target and the source's locator as its filter | Find Elements on the container the elements sit in (list, table, panel), its own element, with the children filtered by what they share, as the activity doc's targeting and filter rules prescribe. A missing container then fails the step, so an empty result means nothing to find. Elements the source reads in groups by position keep that arithmetic. Where an empty result is a valid business answer, a filter that matches nothing passes every run: a run row of the live checks tests the step on a record that has elements (§ Verifying targets) | container and the child filter; low until seen live |
| **Keystrokes** — keys sent to the window or the focused element | Keyboard Shortcuts to the page body; a Delay; a key after a focus move aimed at the element focus left | The first key targets the preceding step's element (Type Into with special-key tokens after typing; Keyboard Shortcuts otherwise). After a key that moves focus (Tab, a menu arrow, a key that opens a window), the next key targets the element focus moved to when the source names it, and otherwise has no target: Keyboard Shortcuts and Type Into without a target act on the element that has focus. One activity per chord the source sent; a source's bring-to-front is `ActivateBefore`; a click on the same element is the fallback when the source had one. Page-scrolling keys are dropped (UiPath scrolls the target into view); a browser refresh is the browser navigation activity; only keys the source sent | none; the preceding step's element, or no target after a focus move |
| **Coordinate click** — click at pointer position or screen x/y | Click with an offset on the page | Identify the intended element from surrounding steps (dismiss a popup, focus the page, an unmapped button) and target it; semantic description; flag `*[Inferred]*` in the report | derived element; low |
| **Set state** — ensure checkbox/radio state | Click | Check/Uncheck with the state (idempotent); radio click plus verify selected | none |
| **Input-method hint** — source switched to key-event input for the fields that follow | ignored | Carry into the affected activities' input mode (key events / hardware, per the owning skill's input-methods guidance); the type-ahead pattern needs it | none |
| **Set versus type** — the source either set a field's value (its previous content replaced, no key events) or typed key by key after the current content (optionally with a delay between keys) | one Type Into default for both | Setting → the field is emptied first and the value entered; key events only where the page reacts to keys (a type-ahead, an input mask). Typing → key events, the field **not** emptied, the source's delay between keys kept. The source guide's step vocabulary says which source call is which | none |

Every derived element is named `derived from <anchor control> — <pattern>` in its description, labelled `INFERRED (low)` unless the table says medium, and listed first in the live checks (§ Verifying targets). The description names which attributes came from the source control; if it has to say an attribute was "taken from" another control, that attribute does not belong in the selector. Source match criteria carry over unchanged ([selector-translation-guide.md](selector-translation-guide.md) rule 2); confidence tiers and targeting method (strict selectors, a caption reached by a `<nav>` path, anchors only from a live capture, a semantic step only where the user asks for one) are rule 12 there, the semantic description rule 11 — a derived element with no control of its own stays **low**. Every type-ahead and menu-path step is a run row of the live checks, exercised by the first live run; a step that "passes" by clicking the wrong entry is the failure mode this section prevents, so the verify sub-step of each pattern is mandatory, not optional.

**Actions without a control** map to target-less activities, not to invented elements. Each keeps its window-level scope from the catalog.

- **Open a browser at a URL:** the application card opens it, at the URL on its Object Repository screen. Not Start Process: the card starts the browser with flags that keep a minimised or covered window taking input and that suppress the first-run, search-engine and profile-picker prompts and the debugger banner.
- **Start a desktop application:** the application card opens it, with the file path, arguments and working directory on its screen. A path the source does not record stays empty, a row of the live checks; until it is set, the card only attaches.
- **Force-close a process:** Kill Process.
- **Maximise, activate or close a window:** Window Operations inside a card attached to a window-level screen (a screen with no elements).
- **Desktop screenshot on error:** Take Screenshot with no target.
- **"The dialog appears within N seconds":** the first activity that targets the dialog, with N as its timeout. Add a Check App State on the dialog's captured button or on the window-level screen only where the source branched on the dialog or no later step acts on it ([ui-verification-guide.md](ui-verification-guide.md)).

The owning skill's CLI makes a first definition only from a live node; the seeds and the seed-and-mutate procedure the offline migration builds every definition with: [offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md).
