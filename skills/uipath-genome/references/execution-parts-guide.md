# Execution Parts Guide — large groups in parts, ledgers and resuming

A large group is built in parts (item 1a), under [parts-guide.md](parts-guide.md): the orchestrator, the brief and its rulings, the ledgers, read plans, forks and returns are stated there. This guide holds what a build adds.

1. **A project has one owner at a time** — a subagent or the orchestrator, handed on as [parts-guide.md](parts-guide.md) item 7 states; test-component groups sharing a project run sequentially, or in parallel under item 1c, each writing only its own test cases, their data files and its component's checkpoint map, and returning the manifest registrations they need, which the owner applies. Only the owner runs the project's shared operations — Object Repository registration and linking, build, pack, package installs, host restarts — and edits its shared files: the workflows that route to or invoke several steps' files, the manifest, the configuration file, a code file several workflows use, the ledger, the progress file, the target spec, the Object Repository registry, the link table and the project's live checks. The owner may have disjoint files authored in parallel (item 1c). Whoever builds a part performs the owning skill's contract ([execution-guide.md § 2.2](execution-guide.md) step 2) and reports the reads it performed.
1a. **Keep a project ledger with a skeleton before the first workflow, in two files** — the ledger of [parts-guide.md](parts-guide.md) item 3, for a project. Both live in the working folder outside every project. The **contract** (`<Project>.md`) opens with the skeleton, written by the first part after its reads: workflow file list and each file's argument names, directions and types; configuration keys; Object Repository screen and element names; the split into parts, which assigns every workflow file to exactly one part, with each part's source objects, its estimate (below) and the activity kinds it will use. The same part writes an argument-only stub of every file the skeleton lists, so every invoke validates before its callee is written. Decisions with reasons and source object and line, open questions and the orchestrator's rulings follow it. Later work agrees with these contracts; a change is a decision naming the affected items. The **progress file** (`<Project>-progress.md`) tracks every planned item's written, validated and linked status (not applicable where appropriate), with plans and counts, such as derived elements and why each is needed.

    Read the contract whole before the first project action; assemble the group report from both files at the end, never leave an empty report skeleton as the record of progress.

    **Size parts by the context they fill.** Since every call resends a part's whole context ([parts-guide.md](parts-guide.md) item 9), a part that grows large slows, compacts and degrades the model that runs it, while every split repeats a read set and adds the orchestrator's launches and checks. Estimate each candidate part before planning it: its read set once its reads are done, plus its growth per line built times the lines its steps are built from — in a migration its source objects' lines in the rendering the build reads them from, otherwise its steps' genome text. Split only where the estimated peak passes the ceiling — about 600k tokens, or the context at which the host compacts when that comes sooner — and at a boundary few contracts cross. Until the first authoring parts have returned, start from a read set of about 200k tokens and, for steps read from the inventory script's dump, about 300 tokens per dump line; then re-plan the later parts as a ruling from their contexts, where the host records them: the read set is the context at about the tenth call, the growth is the peak before any compaction, less the read set, divided by the lines built.

    **A source object stays in one part.** One part builds every file of a source object, so it reads the object once and reviews every built branch against it in source order. The estimate decides how many source objects a part takes, never whether one is divided. An object whose own estimate passes the ceiling is a part by itself, which authors every file of the object itself and may run past the ceiling and compact, carried across by its progress written through (item 4) and its read plan re-run after the compaction ([parts-guide.md](parts-guide.md) item 3).

    **The order of work.** A migration opens with the source-fact tables, one part per component, beside exploration on a reachable application; then the target specs, one part per component, derived with exploration's notes; then, on a reachable application, the contract probe ([live-application-guide.md § Contract probe](live-application-guide.md)); then the libraries. Each set runs in parallel, except that a library starts after the libraries it depends on ([execution-guide.md § 1.5](execution-guide.md) item 7), and that the work which drives the application — exploration, the contract probe, the live healing pass — runs in one agent at a time: the application is shared, with one owner at a time ([parts-guide.md](parts-guide.md) item 7). A migrated process project's work then runs in this order, within parts and across them — a phase is never a reason for a part of its own: its configuration and framework surfaces with the once-per-run and end-of-run steps, and the skeleton with its stubs; the per-item steps, their files linked at the end of each part or wave (item 3a); on a reachable application, once every project's UI steps are linked, the live healing pass, run by the project's owner because its fixes replace elements through the run's target tool (item 1); then verification, the gate, the framework exits and the acceptance verdicts. Each part opens with its read plan (item 1b), which starts with the brief and the ledger contract. Parts of one project run one after another, except where they author in parallel under item 1c; independent projects may run in parallel.
1b. **Every part reads by plan (item 6), in the three turns of [parts-guide.md](parts-guide.md) item 4.** Turn 2's discovery covers every activity kind the skeleton lists for the part, with the listing of each package's per-activity doc folder — a class name is not a doc file name — and a search of those docs for the component and type docs they link, which a per-activity doc requires read with it; turn 3 reads the per-activity docs, the docs they link and the shapes that discovery returned. The part report names every mandated read the plan omitted and every read that missed.

    ```
    Read plan — part B1 (steps 10–11 and the Object Repository, UI)
      Turn 1  whole:    run brief; ledger contract; execution-parts-guide; component genome; owning skill's rule files,
                        cards and UI guides (its two-step reads split across turns 1 and 2); source-migration-guide;
                        offline guide
              headings: source-fact table; selector-translation-guide; pack source and selectors guides; owning skill's catalogs
      Turn 2  sections: source facts § Configuration, § Step 10, § Step 11, § shared, § Deviations;
                        selector-translation-guide and its SAP GUI guide; pack § Composite actions,
                        § Realised at execution, selectors § SAP GUI; catalog sections matching the part's activity kinds
              discovery for the part's activity kinds (skeleton)
      Turn 3  per-activity docs, the docs they link, and shapes; references the turn-2 reads route to
    ```

    Read by section: the source-fact table (configuration, the part's steps, the sections shared by every step, deviations), the framework pack's guides (the constructs the part builds), the owning skill's catalogs. A long ledger contract is a whole read above the single-read limit. An earlier part's workflows are known from the skeleton: open one only to edit or copy it, find the edit point with a search that prints the surrounding lines, and read that region. Another project's contract reaches the part through the brief: a library's packed surface, a shared helper's arguments. A targeted lookup for a detail the source-fact table leaves open (item 6) is not part of the plan: it runs before the file that needs it is written. A source-fact part writes the dumps of all its source objects with one command loop and reads them in one message.
1c. **Authoring in parallel inside one project** — by forks of the owner, or by parts with read plans of their own, as [parts-guide.md](parts-guide.md) item 5 decides — runs under five conditions:
    1. **Stubs first.** Parallel authors start once the skeleton and its stubs (item 1a) are written and validate.
    2. **Disjoint files.** An author writes only the files the skeleton assigns it and its own files in the working folder — its progress file and report, and its link-table rows, target-spec additions and live-checks rows, which the owner merges at the wave's end (item 3a). A helper the skeleton does not list is claimed before it is written: the author appends a row — the file, its arguments and the author — to the project's helper registry (item 6), reads the registry again, and writes the helper only if its row is the first for that file; otherwise it invokes the helper the first row names. The registry is the one file every author of a wave writes, and only by appending: a rewrite drops the rows others added since it was read.
    3. **Shared operations and files stay with the owner** (item 1): the agent that started the wave — the part that forks, or the orchestrator that launches the parts — until the wave's end has passed (item 3a). An author edits a shared file only where the brief assigns it that file by name, and validates only its own files.
    4. **Contracts change through the owner.** An author changes no declared argument's name, direction or type. It requests the change in its report with the callers it knows; the owner rules on it, naming each caller and its author, and the callee and its callers change only after that ruling, each by its current owner ([parts-guide.md](parts-guide.md) items 2 and 7), and are validated.
    5. **Waves.** The authors started together form a wave; the next wave starts once this one's end (item 3a) has passed.

    Forks follow [parts-guide.md](parts-guide.md) item 5; in a build the shared reads are the brief, the ledger contract and the owning skill's mandatory reads for what the forks author, and the shared decisions in the ledger are each fork's files with their arguments, the helpers they call, and the shared-file edits the owner makes; the owner forks before it reads any one fork's step material or authors a file. A fork reads its own steps' material — their source-fact sections, source objects and target-spec entries — validates its files per file, and returns the report of item 7 for its files. The owner reviews each fork's files against the source-fact sections and source defects of its steps before it registers and links them.
2. One authoring host serves all agents of a project: every CLI call carries the project directory; a busy or locked host is retried once after a pause; the owner's per-file mutations (validate, link, register) run sequentially inside one shell call per batch, following the owning skill's turn-batching guidance, while parallel authors validate their own files beside them (item 1c).
3. Object Repository linking follows the owning skill's target-attachment guidance (screen first, then elements; never two link commands on one file at once) and the ordering and verification rules in [ui-target-migration-guide.md § UI targets](ui-target-migration-guide.md) — link last, size batches by payload, check the file. The executor only orders the work.
3a. **Link and build at the end of every part and every wave, never once after the last.** A build stops at validation errors before it runs any analyzer rule, and an unset target that a UI activity needs is one: while any file is unlinked, the build reports no analyzer error in any file, so an error in the first files surfaces only once the last is linked, after later files have repeated it and the parts that wrote them have handed them on. A stub holds no UI activity, so once the files written so far are linked the build passes validation and runs the analyzer. Before the next part or wave starts — for a wave, once each of its authors is accepted (item 7) — the project's owner:
    1. merges the authors' link-table rows, target-spec additions and live-checks rows into the project's;
    2. registers and links the accepted files with the run's target tool (item 3);
    3. builds the project, sends each error to the owner of its file ([parts-guide.md](parts-guide.md) item 7) for a fix in place, and builds again until the build passes;
    4. checks by hand, against each callee's arguments, the calls the build passes unchecked: a missing In argument (the owning skill's build guidance) and a call that passes its arguments as one dictionary.
4. **Progress is written through** ([parts-guide.md](parts-guide.md) item 3), so a part resumes after a compaction, a pause or in a new session. No signal precedes a compaction, so the progress file stays at most one item behind the work: an item's row is written in the turn its validate result arrives, batched with the next item's first call, never at the end of the part. The file opens with a `Resume` block rewritten with each row: the current part, the last item and its gate result, the next item, the files changed since their last validate, and the work in flight (an Object Repository or link batch, a scratch copy, a host restart owed). Beside the brief, `run-progress.md` lists every part of every project with its state, its report and its read plan, and the next parts in order; the orchestrator updates it at each part boundary. A pause is taken at the next clean boundary: the operation in hand is finished (a link batch recounted in its file, a written file validated), nothing new starts, and the Resume block and the run progress are written. To resume, read the run progress, the brief with its rulings, the ledger contract and the current part's Resume block and rows — a part that starts fresh does not read the progress file. Confirming a compaction summary's work on disk is validating again every file changed since its last validate and recounting a link batch in its file; the read plan a resumed part re-runs includes the owning skill's mandatory reads.
5. Solution-level mutations (project registration, resources) are done by the orchestrator alone, after the parts that touch the projects finish. Creating a project inside the solution folder registers it, so a part's scratch or probe project is created outside that folder.
5a. **A builder deletes nothing**, and the brief and every part's prompt say so: no delete command (`rm`, `git clean` or the shell's own); the one removal allowed is a single file named exactly. Anything else goes to the orchestrator.
6. **One run brief, written before the first part starts** ([parts-guide.md](parts-guide.md) item 2). The orchestrator writes a single brief file in the build's working folder outside every project (the `migration/` folder of [source-migration-guide.md § What the executor records](source-migration-guide.md) when the run is a migration): absolute paths (build folder, working folder, export, local feed), the authoring mode ([execution-guide.md § 2.2](execution-guide.md) step 2, verbatim), the run's behavioural contracts (Object Repository rules, the cross-project Interface, verification verdicts), the source-fact table ([source-migration-guide.md § Migration preflight](source-migration-guide.md) step 4), each component's target spec from that preflight, the link table, each project's Object Repository registry and the run's target tool once it exists ([ui-target-migration-guide.md § UI targets](ui-target-migration-guide.md)), each project's ledger paths and, where its parts author in parallel, its helper registry path (item 1c), the report path and format, the configuration answers, the libraries' packed surfaces once they exist, the environment workarounds the run finds (CLI environment variables, path quirks), and the numbered **Rulings** section, where every orchestrator decision lands — a contract question between a library and its consumers, a source-fact deviation, an interface change, a guard list. Each part's read plan is written into the run progress (item 4) and lists, in the turns of item 1b: the brief, its ledger contract and source-fact sections, parts-guide.md and this guide whole (the owner rule, forking, progress written through and the report the part owes), the owning skill's mandatory reads for what the part authors (UI reads only for a part that writes UI activities), the migration reads of [SKILL.md § Source Frameworks](../SKILL.md) for what the part writes, never cut to sections, the application notes of the applications a UI part's steps act on ([live-application-guide.md § Exploring](live-application-guide.md)), [live-application-guide.md](live-application-guide.md) whole for a part that drives the application, and the genome and pack sections the part's steps use. A group takes literals, counts, waits, flags and log texts from its steps' source-fact sections before it writes. For a missing detail, use the source guide's targeted lookup (`raw --lines` / `--find` where supported) and record the finding with its source object and line in the ledger. A whole-bot dump is only for a step the table does not cover at all. A skill's post-build context files are not written into a project — they would ship in the package. Reports, mapping files and scratch output go to the paths the brief names, never inside a project folder — a file inside a project ships in its package, and a `migration/` or `reports/` folder found inside a project is moved out before packing.
7. **A part's report** ([parts-guide.md](parts-guide.md) item 6) accounts for each contract per step and per file: for each step, every source defect the genome states for it ([extracted-genome-guide.md § Source Defects](extracted-genome-guide.md) — the process genome's index, or the step itself) and what was built for each; the step's source log points kept and its waits taken from the source; for each file, its validate result and its link count, or its link rows where the owner links it; for each file it authored, its review line, `<file>: reviewed against <source object and lines, or genome steps>; fixes: <list or none>` — the review is a second read, once the file validates, of every built branch against its source in source order, checking each source value of [extracted-genome-guide.md § Source values](extracted-genome-guide.md) the branch builds and each argument or state key it reads or writes; a script that checks literals for presence does not replace it, and a file with no source object of its own, such as a pattern helper, is reviewed against the source steps it stands for, named in its line; the forks the owner ran, each with its files, or none and the reason (item 1c); the live-checks rows it wrote; as a project's last part, the verdict of each acceptance criterion of that project ([execution-guide.md § 3.1](execution-guide.md)); and the scripts and inline commands the part ran, none of which wrote a workflow. The mechanical check before a part is accepted covers the packed surface with `uip rpa packages inspect`, the Object Repository identities and element count against the target spec and the Object Repository registry, every element's description and label, and its semantic step only where the user asked for one ([ui-target-migration-guide.md](ui-target-migration-guide.md) rule 2), every element and step the live checks owe a row for ([ui-target-migration-guide.md § Verifying targets](ui-target-migration-guide.md)), reconciling reuse, parametrisation and derived elements with the ledger, a search of the workflows for literal `idx=` values, a search of their names and texts, and of the elements' descriptions, for the citations [execution-guide.md § 2.2](execution-guide.md) rules out in each, the comparison literals and operators against the source export, the validate result re-run, the project build of item 3a, for a part that links its own files (per-file validate runs no analyzer rule, the owning skill's build guidance), a search of the working folder's scripts and of the inline commands the report lists for any that write `.xaml` or `.cs` into a project. The check also compares the reads the report lists with the part's read plan in the run progress, and the activity kinds its files use — XAML element names and coded activity calls — with the report's list of kinds, each with its default XAML fetched and its per-activity doc read ([execution-guide.md § 2.2](execution-guide.md) step 2); it finds a review line for every file the part authored, and compares three of the part's built branches with what they were built from, chosen among conditions with a case rule, loop bounds and waits. A mandated read missing or listed as omitted, or a kind missing from the list or listed without both, sends the part back to make the read, re-check every file it wrote against it, validate again what it changes, and report the reads and the changes; a missing review line, or one compared branch that differs from what it was built from, sends it back to redo the review of every file it authored.

## Anti-patterns

1. **Building a large group without a skeleton, a ledger and progress written through.** A compaction then loses the contracts, the decisions and every item the progress file never recorded; a part resumed from the summary instead of its read plan authors without the owning skill's reads, and mandatory reads and source dumps are paid twice (items 1a, 4).
2. **A part reading the build's files whole that it needs by section or not at all** — catalogs, the progress file, an earlier part's workflows, another project's ledger — beside the reads [parts-guide.md](parts-guide.md) anti-pattern 1 names (items 1a, 1b, 6).
