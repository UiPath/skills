# Execution Parts Guide — large groups in parts, ledgers and resuming

A large group is built in parts (item 1a), under [parts-guide.md](parts-guide.md): the orchestrator, the brief and its rulings, the ledgers, read plans and returns are stated there. This guide holds what a build adds.

1. **A project has one owner at a time** — a subagent or the orchestrator, handed on as [parts-guide.md](parts-guide.md) item 6 states; test-component groups sharing a project run sequentially, or in parallel under item 1c, each writing only its own test cases, their data files and its component's checkpoint map, and returning the manifest registrations they need, which the owner applies. Only the owner runs the project's shared operations — Object Repository registration and linking, build, pack, package installs, host restarts — and edits its shared files: the workflows that route to or invoke several steps' files, the manifest, the configuration file, a code file several workflows use, the ledger, the progress file, the target spec, the Object Repository registry, the link table and the project's live checks. The orchestrator may have disjoint files authored in parallel (item 1c). Whoever builds a part performs the owning skill's contract ([execution-guide.md § 2.2](execution-guide.md) step 2) and reports the reads it performed.
1a. **Keep a project ledger with a skeleton before the first workflow, in two files** — the ledger of [parts-guide.md](parts-guide.md) item 3, for a project. Both live in the working folder outside every project. The **contract** (`<Project>.md`) opens with the skeleton, written by the first part after its reads: workflow file list and each file's argument names, directions and types; configuration keys; Object Repository screen and element names; the split into parts, which assigns every workflow file to exactly one part, with each part's source objects, its estimate (below) and the activity kinds it will use. The same part writes an argument-only stub of every file the skeleton lists, so the project builds and every invoke's arguments are checked before its callee is written. Decisions with reasons and source object and line, open questions and the orchestrator's rulings follow it. Later work agrees with these contracts; a change is a decision naming the affected items. The **progress file** (`<Project>-progress.md`) tracks every planned item's written, validated and linked status (not applicable where appropriate), with plans and counts, such as derived elements and why each is needed.

    Read the contract whole before the first project action; assemble the group report from both files at the end, never leave an empty report skeleton as the record of progress.

    **Size parts by the context they fill.** Since every call resends a part's whole context ([parts-guide.md](parts-guide.md) item 8), a part that grows large slows, compacts and degrades the model that runs it, while every split repeats a read set and adds the orchestrator's launches and checks. Estimate each candidate part before planning it: its read set once its reads are done, about 400k tokens, plus its growth per line built times the lines its steps are built from — in a migration its source objects' lines in the rendering the build reads them from, otherwise its steps' genome text; for steps read from the inventory script's dump, the growth is about 350 tokens per dump line in a part that builds UI activities and 200 in one that does not. Plan the fewest parts whose estimates stay under the ceiling — about 750k tokens, or the context at which the host compacts when that comes sooner — and balance them: spread the source objects so the parts' estimates come out about equal, cutting at boundaries few contracts cross.

    **A source object stays in one part.** One part builds every file of a source object, so it reads the object once and reviews every built branch against it in source order. The estimate decides how many source objects a part takes, never whether one is divided. An object whose own estimate passes the ceiling is a part by itself, which authors every file of the object itself and may run past the ceiling and compact.

    **The order of work.** A migration runs these sets of parts in this order, the parts of each set in parallel, so a part that builds starts from finished source facts and target specs instead of carrying their work:
    1. the source-fact tables, one part per component, beside exploration on a reachable application;
    2. the target specs, one part per component, derived with exploration's notes;
    3. on a reachable application, the contract probe ([live-application-guide.md § Contract probe](live-application-guide.md));
    4. the libraries, each after the libraries it depends on ([execution-guide.md § 1.5](execution-guide.md) item 7).

    The work that drives the application — exploration, the contract probe, the live healing pass — runs in one agent at a time, since the application has one owner at a time ([parts-guide.md](parts-guide.md) item 6). A migrated process project's work then runs in this order, within parts and across them — a phase is never a reason for a part of its own:
    1. the skeleton with its stubs, and its configuration and framework surfaces with the once-per-run and end-of-run steps;
    2. the per-item steps, their files linked at the end of each part or wave (item 3a);
    3. on a reachable application, once every project's UI steps are linked, the live healing pass, run by the project's owner because its fixes replace elements through the run's target tool (item 1);
    4. verification, the gate, the framework exits and the acceptance verdicts.

    Parts of one project run one after another, except where they author in parallel under item 1c; independent projects may run in parallel.
1b. **Every part reads by plan (item 6), in the three turns of [parts-guide.md](parts-guide.md) item 4.** Turn 2's discovery covers every activity kind the skeleton lists for the part, with the listing of each package's per-activity doc folder — a class name is not a doc file name — and a search of those docs for the component and type docs they link, which a per-activity doc requires read with it; turn 3 reads the per-activity docs, the docs they link and the shapes that discovery returned. The part makes every mandated read before the first file it governs, those its plan omitted included ([SKILL.md § Read Plans](../SKILL.md)); its report marks those among the reads it performed, so the orchestrator adds them to the later parts' plans, and names every read that missed.

    ```
    Read plan — part B1 (steps 10–11 and the Object Repository, UI)
      Turn 1  whole:    run brief; ledger contract; execution-parts-guide; component genome; owning skill's rule files,
                        cards and UI guides (its two-step reads split across turns 1 and 2); source-migration-guide;
                        offline guide
              headings: source-fact table; selector-translation-guide; pack source and selectors guides; owning skill's catalogs
      Turn 2  sections: source facts § Configuration, § Step 10, § Step 11, § shared, § Deviations;
                        selector-translation-guide and its SAP GUI guide; pack § Composite actions,
                        § Realised at execution, § Component Detection naming, selectors § SAP GUI; catalog sections matching the part's activity kinds
              discovery for the part's activity kinds (skeleton)
      Turn 3  per-activity docs, the docs they link, and shapes; references the turn-2 reads route to
    ```

    Read by section: the source-fact table (configuration, the part's steps, the sections shared by every step, deviations), the framework pack's guides (the constructs the part builds), the owning skill's catalogs. A long ledger contract is a whole read above the single-read limit. An earlier part's workflows are known from the skeleton: open one only to edit or copy it, find the edit point with a search that prints the surrounding lines, and read that region. Another project's contract reaches the part through the brief: a library's packed surface, a shared helper's arguments. A targeted lookup for a detail the source-fact table leaves open (item 6) is not part of the plan: it runs before the file that needs it is written. A source-fact part writes the dumps of all its source objects with one command loop and reads them in one message.
1c. **Authoring in parallel inside one project** — by parts with read plans of their own, which the orchestrator launches from the skeleton's split — runs under five conditions:
    1. **Stubs first.** Parallel authors start once the skeleton and its stubs (item 1a) are written and validate.
    2. **Disjoint files.** An author writes only the files the skeleton assigns it, the files its own steps need beyond them, and its own files in the working folder — its progress file and report, and its link-table rows, target-spec additions and live-checks rows, which the owner merges at the wave's end (item 3a). A file beyond the skeleton — a large source object's step files, a helper only its files call — is named after the source object or step it serves, so no two authors' names meet, and listed in the report with its arguments.
    3. **Shared operations and files stay with the owner** (item 1): the orchestrator, which launches the wave and owns the project until the wave's end has passed (item 3a). An author edits a shared file only where the brief assigns it that file by name, and validates only its own files.
    4. **Contracts change through the owner.** An author changes no declared argument's name, direction or type. It requests the change in its report with the callers it knows; the owner rules on it, naming each caller and its author, and the callee and its callers change only after that ruling, each by its current owner ([parts-guide.md](parts-guide.md) items 2 and 6), and are validated.
    5. **Waves.** The authors started together form a wave; the next wave starts once this one's end (item 3a) has passed.
2. One authoring host serves all agents of a project: every CLI call carries the project directory; a busy or locked host is retried once after a pause; the owner's per-file mutations (validate, link, register) run sequentially inside one shell call per batch, following the owning skill's turn-batching guidance, while parallel authors validate their own files beside them (item 1c).
3. Object Repository linking follows the owning skill's target-attachment guidance (screen first, then elements; never two link commands on one file at once) and the ordering and verification rules in [ui-target-migration-guide.md § UI targets](ui-target-migration-guide.md) — link last, size batches by payload, check the file. The executor only orders the work.
3a. **Link and build at the end of every part and every wave, never once after the last.** A build stops at validation errors before it runs any analyzer rule, and an unset target that a UI activity needs is one: while any file is unlinked, the build reports no analyzer error in any file, so an error in the first files surfaces only once the last is linked, after later files have repeated it and the parts that wrote them have handed them on. A stub holds no UI activity, so once the files written so far are linked the build passes validation and runs the analyzer. Before the next part or wave starts — for a wave, once each of its authors is accepted (item 7) — the project's owner:
    1. merges the authors' link-table rows, target-spec additions and live-checks rows into the project's, enters in the skeleton the files they wrote beyond it, and keeps one of any helpers two authors wrote alike, pointing the other's invokes at it;
    2. registers and links the accepted files with the run's target tool (item 3);
    3. builds the project, sends each error to the owner of its file ([parts-guide.md](parts-guide.md) item 6) for a fix in place, and builds again until the build passes;
    4. checks by hand, against each callee's arguments, the calls the build passes unchecked: a missing In argument (the owning skill's build guidance) and a call that passes its arguments as one dictionary.
4. **Progress is written through** ([parts-guide.md](parts-guide.md) item 3), so a part resumes after a compaction, a pause or in a new session. No signal precedes a compaction, so the progress file stays at most one item behind the work: an item's row is written in the turn its validate result arrives, batched with the next item's first call, never at the end of the part. The file opens with a `Resume` block rewritten with each row: the current part, the last item and its gate result, the next item, the files changed since their last validate, and the work in flight (an Object Repository or link batch, a scratch copy, a host restart owed). Beside the brief, `run-progress.md` lists every part of every project with its state, its report and its read plan, and the next parts in order; the orchestrator updates it at each part boundary. A pause is taken at the next clean boundary: the operation in hand is finished (a link batch recounted in its file, a written file validated), nothing new starts, and the Resume block and the run progress are written. To resume, read the run progress, the brief with its rulings, the ledger contract and the current part's Resume block and rows — a part that starts fresh does not read the progress file. Confirming a compaction summary's work on disk is validating again every file changed since its last validate and recounting a link batch in its file; the read plan a resumed part re-runs includes the owning skill's mandatory reads.
5. The orchestrator alone creates the projects and changes the solution. Before the first part starts, it creates every project and installs the packages its Scaffolding answers name ([execution-guide.md § 1.4](execution-guide.md)), so each part's turn-2 discovery (item 1b) finds the per-activity docs, which a package install writes and the project's creation does not. A library the run builds as a package is installed in each consumer once packed ([execution-guide.md § 1.5](execution-guide.md)), before the first part that calls its activities starts. Creating a project inside the solution folder registers it, so a part's scratch or probe project is created outside that folder. The solution's resources change only after the parts that touch the projects finish.
5a. **A builder deletes nothing**, and the brief and every part's prompt say so: no delete command (`rm`, `git clean` or the shell's own); the one removal allowed is a single file named exactly. Anything else goes to the orchestrator.
6. **One run brief, written before the first part starts** ([parts-guide.md](parts-guide.md) item 2). The orchestrator writes a single brief file in the build's working folder outside every project (the `migration/` folder of [source-migration-guide.md § What the executor records](source-migration-guide.md) when the run is a migration): absolute paths (build folder, working folder, export, local feed), the authoring mode ([execution-guide.md § 2.2](execution-guide.md) step 2, verbatim), the run's behavioural contracts (Object Repository rules, the cross-project Interface, verification verdicts), the source-fact table ([source-migration-guide.md § Migration preflight](source-migration-guide.md) step 4), each component's target spec from that preflight, the link table, each project's Object Repository registry and the run's target tool once it exists ([ui-target-migration-guide.md § UI targets](ui-target-migration-guide.md)), each project's ledger paths, the record-store writes and reads each project's parts own ([transactional-execution-guide.md § Split questions](transactional-execution-guide.md) rule 1), the report path and format, the configuration answers, the libraries' packed surfaces once they exist, the environment workarounds the run finds (CLI environment variables, path quirks), and the numbered **Rulings** section, where every orchestrator decision lands — a contract question between a library and its consumers, a source-fact deviation, an interface change, a guard list. Each part's read plan is written into the run progress (item 4) and lists, in the turns of item 1b: the brief, its ledger contract and source-fact sections, the conventions document the configuration answers name ([execution-guide.md § 1.3](execution-guide.md)), parts-guide.md and this guide whole (the owner rule, progress written through and the report the part owes), the owning skill's mandatory reads for what the part authors (UI reads only for a part that writes UI activities), the migration reads of [SKILL.md § Source Frameworks](../SKILL.md) for what the part writes, never cut to sections, the application notes of the applications a UI part's steps act on ([live-application-guide.md § Exploring](live-application-guide.md)), [live-application-guide.md](live-application-guide.md) whole for a part that drives the application, and the genome and pack sections the part's steps use. A group takes literals, counts, waits, flags and log texts from its steps' source-fact sections before it writes. For a missing detail, use the source guide's targeted lookup (`raw --lines` / `--find` where supported) and record the finding with its source object and line in the ledger. A whole-bot dump is only for a step the table does not cover at all. A skill's post-build context files are not written into a project — they would ship in the package. Reports, mapping files and scratch output go to the paths the brief names, never inside a project folder — a file inside a project ships in its package, and a `migration/` or `reports/` folder found inside a project is moved out before packing.
7. **A part's report** ([parts-guide.md](parts-guide.md) item 5) accounts for each contract per step and per file:
    1. for each step, every source defect the genome states for it ([extracted-genome-guide.md § Source Defects](extracted-genome-guide.md) — the process genome's index, or the step itself) and what was built for each; the step's source log points kept and its waits taken from the source;
    2. for each file, its validate result and its link count, or its link rows where the owner links it;
    3. for each file it authored, its review line, `<file>: reviewed against <source object and lines, or genome steps>; fixes: <list or none>`;
    4. the reads it performed (items 1 and 1b) and the activity kinds its files use, each with its default XAML fetched and its per-activity doc read ([execution-guide.md § 2.2](execution-guide.md) step 2);
    5. the live-checks rows it wrote;
    6. as a project's last part, the verdict of each acceptance criterion of that project ([execution-guide.md § 3.1](execution-guide.md));
    7. the scripts and inline commands the part ran, none of which wrote a workflow.

    The review is a second read, once the file validates, of every built branch against its source in source order, checking each source value of [extracted-genome-guide.md § Source values](extracted-genome-guide.md) the branch builds and each argument or state key it reads or writes. A script that checks literals for presence does not replace it, and a file with no source object of its own, such as a pattern helper, is reviewed against the source steps it stands for, named in its line.

    The mechanical check before a part is accepted covers:
    1. the packed surface with `uip rpa packages inspect`;
    2. the Object Repository identities and element count against the target spec and the Object Repository registry, every element's description and label, and its semantic step only where the user asked for one ([ui-target-migration-guide.md](ui-target-migration-guide.md) rule 2), every element and step the live checks owe a row for ([ui-target-migration-guide.md § Verifying targets](ui-target-migration-guide.md)), reconciling reuse, parametrisation and derived elements with the ledger;
    3. a search of the workflows for literal `idx=` values, and a search of their names and texts, and of the elements' descriptions, for the citations [execution-guide.md § 2.2](execution-guide.md) rules out in each;
    4. the validate result re-run, and the project build of item 3a, for a part that links its own files (per-file validate runs no analyzer rule, the owning skill's build guidance);
    5. a search of the working folder's scripts and of the inline commands the report lists for any that write `.xaml` or `.cs` into a project;
    6. the reads the report lists, compared with the part's read plan in the run progress, and the activity kinds its files use — XAML element names and coded activity calls — compared with the report's list of kinds;
    7. a review line for every file the part authored, and three of the part's built branches compared with what they were built from, chosen among conditions with a case rule, loop bounds and waits.

    A mandated read missing from the reads performed, or a kind missing from the list or listed without both, sends the part back to make the read, re-check every file it wrote against it, validate again what it changes, and report the reads and the changes; a missing review line, or one compared branch that differs from what it was built from, sends it back to redo the review of every file it authored.

## Anti-patterns

1. **Building a large group without a skeleton, a ledger and progress written through.** A compaction then loses the contracts, the decisions and every item the progress file never recorded; a part resumed from the summary instead of its read plan authors without the owning skill's reads, and mandatory reads and source dumps are paid twice (items 1a, 4).
2. **A part reading the build's files whole that it needs by section or not at all** — catalogs, the progress file, an earlier part's workflows, another project's ledger — beside the reads [parts-guide.md](parts-guide.md) anti-pattern 1 names (items 1a, 1b, 6).
