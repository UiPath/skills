# Source Migration Guide — UI targets and test data at execution

Execution of an extracted genome migrates two things the genome body deliberately leaves out: the **UI targets** (selectors) and the **test data** of the source automation. Both live in the source artifacts folder the extraction writes next to the genome ([genome-format-guide.md § Source Artifacts](genome-format-guide.md)). This guide is framework-agnostic; each source guide's *UI Target Locators* and *Test Data* sections say what the source provides, its selectors companion says how each recorded field translates, and [selector-translation-guide.md](selector-translation-guide.md) holds the UiPath-side vocabulary and rules that every translation obeys.

## Rules

1. **Migrate targets from the catalog before anything else.** When `source/targets.json` exists, every UI activity of the built project receives an Object Repository (OR) target derived from the catalog. The placeholder-selector stub pattern is the fallback only when no catalog exists AND no live application is reachable; a live application is captured with the owning skill's target-capture procedure instead.
2. **Every migrated target is inferred and says so.** Its OR element description starts with `INFERRED (<confidence>)` and names the source control. The first run against the real application is a healing pass; accepted fixes go into the OR element in place so every consumer inherits them.
3. **Migrate test data from the data catalog by default.** When `source/test-data.json` exists, the test project's data files (one per test-component folder) are filled from it by a scripted, reviewable mapping from source variables to test-case arguments, never by hand. Generated placeholder rows are a temporary state, not a deliverable.
4. **Account identity migrates, secrets never.** A login user name becomes the name of a credential asset (`<App>_Login_<USER>`) plus the tenant/environment URL recorded for that account; passwords, tokens and secrets are refused by the migration engine and are entered in Orchestrator. One credential asset per source account is declared as a solution resource.
5. **The argument set is frozen during data migration.** Mappings place source values onto the test cases' existing arguments; a value with no argument goes to the project's configuration workflow or argument defaults and is listed as `unmapped`. Source row counts and execution flags replace generated ones.
6. **Build through the owning skill's contract.** Invoke the owning skill for each build group and perform its mandatory reads (its authoring rules, the installed activity package's core guide and per-activity docs). Activity XAML comes from the skill's discovery commands and per-activity docs, never from memory and never from a bespoke template generator whose templates were not derived from those commands. Validate per file and build per project exactly as the skill prescribes; a generator is acceptable only for repetition of activity fragments already confirmed that way.

## UI targets — pipeline

| Step | Output |
|---|---|
| 1. Load the target catalog and the built workflows | list of UI activities per workflow (activity id, type, display name, arguments and variables) |
| 2. Map every UI activity to a catalog control (or to *none*) | for each application card its source window; for each UI activity its source control (or none), activity type, argument substitutions, semantic text, confidence |
| 3. Derive targets | per element: strict selector from the control's attributes (the source guide's selectors companion for the left side, [selector-translation-guide.md](selector-translation-guide.md) for the UiPath side and the rules), optional caption anchor, semantic description, confidence; per window: application/browser selector |
| 4. Create OR screens and elements through the owning skill's Object Repository CLI and target-configuration guidance | one screen per source window, one element per distinct source control (plus substitutions), reused across workflows |
| 5. Link screens then elements into each workflow per the owning skill's target-attachment guidance | linked XAML, placeholder prefixes removed from linked activities |
| 6. Validate every workflow; build; pack | per-workflow report: linked count, created vs reused, confidence, remaining errors |

Mapping rules: every UI activity mapped once, activity ids file-unique; `source/step-map.json` names the source processes of each workflow step, and their dumped steps name the controls; shared widgets (search box, OK, Submit, comment box, menus) reuse one control so the OR holds one element each; literals that the workflow receives as arguments (a person name, a placeholder the source rewrote at run time) become selector variables (`{{Argument}}`) bound to the workflow argument; steps the built workflow has but the source had not (optional pop-up checks, verifications) get no source control, a precise semantic description and low confidence. A **composite source step** (§ Composite interactions) maps to several activities and several elements: the anchor control from the catalog plus the derived elements the source never learned.

## Composite interactions — one source step, several UiPath activities

Test frameworks package multi-step interactions into one parameterised step: type-ahead pick, menu path, option list, find-row-then-act, keystrokes to the focused element. The source guide's composite-actions section names them and dictates the substep wording; this section fixes how execution builds them. **Rule: build the pattern, never the nearest single activity.** Each pattern's naive mapping below validates, runs, and does the wrong thing.

**Rule: a derived element never carries an identifier the source did not record for it.** Its selector is the tag plus the matched text, and the semantic description; nothing else. Lifting a developer identifier (`data-automation-id`, `id`, `name`, `aria-label`) from another catalog control because its name looked related is fabrication, not derivation — and a wrong identifier is worse than none, because it suppresses the text match and the semantic fallback instead of deferring to them.

**"Tag plus the matched text" still has to name a node that owns that text.** The attribute the text goes on is decided by [selector-translation-guide.md](selector-translation-guide.md) rule 5's three-case test, not by habit: form-ish tags (`A`, `BUTTON`, `INPUT`, `LABEL`…) get a synthesised `aaname`; a leaf that owns its own text gets `aaname` plus `isleaf='1'`; a **container gets neither** — on a container the text attribute is `visibleinnertext`, matched exactly, and the tag is the container's real tag. Guessing `tag='DIV'` for a control the source called a button is the same fabrication as guessing its identifier: a command button is a `BUTTON`, and the `DIV` around it carries no name. Where the catalog does not say which node is which, the target is tag-only with the semantic description and owes a live pass (rule 13) — it does not get a plausible-looking attribute to fill the gap.

Before building any UI group of an extracted genome, read the per-control `actions` in `source/targets.json` and the substep wording, classify every UI step against this table, and read the owning skill's control-interaction guidance for the classified controls (option lists, date inputs, tables) as it mandates.

| Pattern | Naive mapping that fails | Build | Derived elements |
|---|---|---|---|
| **Type-ahead pick** — type text, a suggestion list appears, pick the entry matching a caption rule, optional confirm key | type + click "first item" (positional container element); type + Enter without checking what was accepted; **verifying on the option's text leaf**, which also exists in the still-open list and so passes before anything was accepted | 1. Type the value into the field's *acting leaf* — the labelled `INPUT`, never the widget wrapper ([selector-translation-guide.md](selector-translation-guide.md) rule 16) — with key-event input (never set-value: the list only opens on key events). 2. Confirm as the source did (Enter) or pick: the entry is the text leaf of the popup, scoped to the popup that is labelled with the field (`<webctrl data-automation-id='activeListContainer' aria-label='{Label}*' /><webctrl data-automation-id='promptOption' aaname='{0}' />`), caption as a selector variable under the source's criteria (contains / equals / nth). 3. Verify on the acting activity's `VerifyOptions` (`Appears`) against the field's **value display scoped to the field** — the selected chip, pill or selected-option text (`<webctrl tag='LI' visibleinnertext='{Label}*' /><webctrl data-automation-id='selectedItem' aria-label='{0}*' />`) — the source's own verification becomes this acceptance check. The typed text is gone once the prompt accepts, so Type Into's target-less Auto/Expected-text verify does not apply to a prompt. 4. When the source itself had a fallback (Enter failed → click the entry), keep it as a Check with the click in the not-found branch; the verify still belongs on the acting activities | popup entry (scoped to the labelled popup) and value display (scoped to the field) — one pair per widget type, parametrised by field label and value, or one pair per field; low confidence until seen live, `derived from <anchor control>` |
| **Option list** — choose an item by caption rule from a list, dropdown or combo | `SelectItem` on a custom (div/li/span) widget; positional `idx` on the item; verifying on the option text | Probe the control's `items` live (`interact get <ref> items`, owning skill's select-item guidance). Items present → `SelectItem` with the listed value verbatim. Items absent — custom lists expose `selecteditem` but not `items` — → click-to-open the combobox (the acting leaf: `aria-role='combobox'`, found inside the form item pinned by its label), click the option under the list labelled with the field (`<webctrl data-automation-id='menuList' aria-label='{Label}' /><webctrl tag='DIV' aaname='{0}' />`), verify the field's displayed selection (`selectSelectedOption` leaf with `aaname='{0}'`, scoped to the field). A numeric index in the source is positional: keep it as an index on the option element and flag it | option entry (scoped to the labelled list), displayed selection; medium when the source caption is literal, low when variable-bound |
| **Segmented date entry** — the source clicked a date field off-centre (its first segment) and typed the whole date | Type Into on the widget wrapper with the source's click offset; a bare-tag Check afterwards | Target the first segment by the field's label (`<webctrl tag='INPUT' data-automation-id='dateSectionMonth-input' aaname='{Label}' />` — only the first segment carries the label), or scope on the form item and type into each segment (`…Day-input`, `…Year-input`) with the segment's expected text as the verify. Follow the owning skill's date-input guidance for the rendered format, `EmptyFieldMode` None and auto-advance. Verify against the widget's rendered value (a hidden "current value is …" leaf, or the segments) — never a bare `tag='DIV'` | month/day/year segments under the field's form item; medium |
| **Menu / tree path** — `A\|B\|C` from a menu root, levels revealed by hover or click | one click on the root, or a click on the leaf caption anywhere on the page | One click (or hover, per the live probe) per level, each re-resolving its target after the previous level rendered; levels are separate activities, never one target with the leaf text. Each revealed level is usually a *new popup of the same type* (a second `relatedActionsList`), and a label can repeat across groups of one level, so a level entry is scoped to its own popup (the newest one) or to its group header, never matched page-wide by text. The last level gets a verify (the page or dialog the leaf opens). Menu roots that appear in several source windows reuse one element | one element per level (text leaf under its own popup); medium for the root (mapped), low for levels |
| **Table row by content** — find the row whose cell(s) match, then click, read, type or verify in that row | store a row number and index into the table with it; assuming the grid is div-based (or `TABLE`) without looking | Never carry a row integer. Read one cell's attribute list live first: when the driver exposes `tableRow`/`colName`/`rowName` (real `TABLE` markup — many modern grids still are), the row-by-content cell is `<webctrl tag='TD' rowName='{key text}' colName='{caption}*' />` (`colName` is the header's full text; wildcard its tail); when the key text repeats in its column, pin the row container by the discriminating value instead. When they are absent, the row is a container pinned by exact text and the cell its descendant. Alternatively extract the table, filter in code, then act through the pinned row. `Last` = last matching row. Multi-criteria finds and-combine the cell matches. Source "popup rendered as table" (suggestion popups) is an option pick, not a table op | matched cell (anchor), target cell in the same row; medium |
| **Table cell** — act on the cell at (row rule, column caption or number) | absolute `tableRow`/`tableCol` | Column by header caption (`colName='{caption}*'` when exposed, else the header-anchored cell), row by content rule from the preceding find; a literal row number in the source is positional and stays flagged; double-click and follow-up keystroke preserved. A prompt inside a cell (typed value + Enter) is a type-ahead pick inside the cell | header cell, target cell; medium |
| **Read cell / row count / control text** | Get Text on the table element | Get Text or Get Attribute on the row-anchored cell after previewing what it extracts (owning skill's get-text guidance); row count via table extraction or a rows attribute, verified live | as table cell |
| **Keystrokes** — keys sent to the window or the focused element | Keyboard Shortcuts to the browser window / page body; a Delay | Determine the target from the preceding step: the keys go to that element (Type Into text with special-key tokens when they follow typing; Keyboard Shortcuts targeted at the element otherwise). Page scrolling keys are dropped (UiPath scrolls the target into view). A browser refresh becomes the browser navigation activity. Invented shortcuts are forbidden; only keys the source actually sent | none; the target is the preceding step's element |
| **Coordinate click** — click at pointer position or screen x/y | Click with an offset on the page | Identify the intended element from surrounding steps (dismiss a popup, focus the page, an unmapped button) and target it; semantic description; flag `*[Inferred]*` in the report | derived element; low |
| **Set state** — ensure checkbox/radio state | Click | Check/Uncheck with the state (idempotent); radio click plus verify selected | none |
| **Input-method hint** — source switched to key-event input for the fields that follow | ignored | Carry into the affected activities' input mode (key events / hardware, per the owning skill's input-methods guidance); the type-ahead pattern needs it | none |

Every derived element is named `derived from <anchor control> — <pattern>` in its description, labelled `INFERRED (low)` unless the table says medium, and listed in the report under the healing-pass note as the first targets to verify live. The description names which attributes came from the source control; if it has to say an attribute was "taken from" another control, that attribute does not belong in the selector. The source's match criteria carry over unchanged, wildcarded per [selector-translation-guide.md](selector-translation-guide.md) rule 2, and inner text is inherited by every ancestor (rule 5): pin the leaf by tag and class, or flag it for live capture. The first live run must exercise every type-ahead and menu-path step; a step that "passes" by clicking the wrong entry is the failure mode this section exists to prevent, so the verify sub-step of each pattern is mandatory, not optional.

Confidence tiers (**high** / **medium** / **low**) and the targeting-method policy (**fuzzy requires an anchor**; a positional index is strict and never anchored; the semantic fallback is always added) are defined once in [selector-translation-guide.md](selector-translation-guide.md) rule 12; the semantic description every element carries is rule 11. A derived element with no control of its own stays **low**.

Creating and linking mechanics are the owning skill's Object Repository CLI, target-configuration and target-attachment guidance; follow them. With no reachable application the CLI cannot produce a first definition or an anchor at all (`resolve-defaults` and `add-anchor` both take live refs, and there is no `create-definition`) — the shapes and the anchor/fuzzy coupling for that case are in [offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md). Other offline specifics the guidance does not cover: a definition can only be updated once it exists (export one from an activity that already carries a target, then mutate it only through the CLI) — and every field the update call does not overwrite survives from the seed into the new element, so clear the seed's selectors and give each element its own `Guid`; the activity-type option accepts only its own enum values; a single link call with more than about a dozen entries can exceed the shell command-line length — batch; the designer leaves `~<Workflow>.xaml` recovery copies in the project after linking — delete them before packing; analyzer rules such as SecureString public arguments or large position indexes fail `build` and `pack` but not `validate` — decide with the user whether to lower them or pack with the analyzer skipped.

## Verification — a property of the activity, not another activity

Every pattern above owes a verify sub-step. **A verify sub-step is normally not a separate activity.** The UI Automation activities carry post-action verification natively (`VerifyOptions` on Click, Hover, Keyboard Shortcuts and Type Into), and that is where a migration's verification belongs. Reaching for a Check Element / Check App State activity instead is the single largest source of activity-count inflation in a migrated project, and each one drags in a target that has to be guessed, reviewed and healed like any other.

Decide with one question: **does the outcome change what the automation does next?**

| Outcome | Build |
|---|---|
| No — the step simply has to have worked, and not working is a failure | `VerifyOptions` on the activity itself. No extra activity, no extra target for an appearance check that reuses one |
| Yes — the automation genuinely branches, retries or takes another route | a Check activity, whose branches hold the alternative work |

Mapping a source's own verification step:

| Source records | UiPath |
|---|---|
| typed value must be accepted / field must now read X — plain text box | Type Into `VerifyOptions`: **Auto** (target-less — confirms the text landed) or **Expected text** (target-less, wildcards allowed). Neither needs a target at all, so neither needs a migrated element |
| typed value must be accepted — prompt / type-ahead field, where the accepted entry replaces the typed text with a chip or selected option | Type Into `VerifyOptions` with a **target and mode** (`VerifyExecutionTypeIntoOptions` extends `VerifyExecutionOptions`): mode `Appears`, target = the field's value display scoped to the field ([selector-translation-guide.md](selector-translation-guide.md) rule 16). Target-less Auto fails here because the text is gone |
| a confirmation, banner, next page or row must appear after a click | Click `VerifyOptions`, mode `Appears`, target = the thing that appears |
| a spinner, dialog or row must be gone | mode `Disappears` |
| a field or label must change value | mode `TextChanges` |
| the step is a checkpoint with no follow-up behaviour | still `VerifyOptions` — a failed verify raises, which is the checkpoint |
| the source branches on the result (retry, alternate path, optional dialog) | a Check activity — this is control flow, not verification |

Mechanics that decide whether it behaves: `Retry` defaults to **true** and re-runs the activity until the activity's own `Timeout`; the verify `Timeout` (default 10s) is how long each check waits. A verify target is *observed, never acted on*, so it is configured with a neutral activity type (`None`), **not** `CheckElement` — a `CheckElement` type applies the state-attribute rules meant for Check Element itself. Reuse an existing Object Repository element for the observed thing whenever one exists rather than minting a near-duplicate.

Three consequences for a migration that are easy to get wrong:

- **The verify observes the element that shows the outcome, scoped to where the outcome shows.** After a pick, that is the field's value display (chip, pill, selected-option text) under the field's form item — not the option's text leaf, which also lives in the still-open list and makes the check pass before anything was accepted, and not a bare `tag='DIV'`. After a click that changes the page, it is the new page's header or the grid that renders. The verify target is one Object Repository element per widget type (parametrised by the field label and the value) or per field; it is never re-derived per step.
- **A plain text box's acceptance check is target-less; a prompt's is not.** Type Into Auto/Expected-text verification confirms the value landed in a text box with no element at all. A prompt replaces the typed text, so its check is a targeted `Appears` on the value display (table above).
- **The `IfNotExists`-branch idiom is control flow wearing a verification costume.** A Check whose "not found" branch clicks the suggestion is a retry path, and it is legitimate — but the *acceptance* check that follows the click is verification and belongs on the click. Do not let one genuine branch pull every check in the sequence into its own activity.

## Element Scope — attach once, keep the children local

The Element Scope activity (`NElementScope`, Version V5, body an `ActivityAction<Object>` named `ContextTarget`; take the shape from the owning skill's `activities get-default-xaml`) attaches to one element and lets every activity inside it resolve its target relative to that element. Its target is a `TargetAnchorable` like any other; the children's targets carry **no** scope selector of their own. This is the activity-level form of [selector-translation-guide.md](selector-translation-guide.md) rule 14 step 2, and it is the right shape exactly when the acting leaves have no name of their own:

| Situation | Scope target | Children |
|---|---|---|
| Segmented input — a date's month/day/year, a phone's parts — where only the first segment carries the field label | the form item pinned by the label (`<webctrl tag='LI' visibleinnertext='{Label}*' />`) or the widget wrapper *with a per-instance id* | `<webctrl tag='INPUT' data-automation-id='dateSectionDay-input' />` and siblings |
| A div-based combobox or custom control labelled only by `aria-labelledby` | the labelled form item | `<webctrl aria-role='combobox' />`, then the value display for the verify |
| Several actions on one row of a repeated structure (a table row, a card, an inbox item) | the row pinned by its key text (`<webctrl tag='TR' visibleinnertext='*{key}*' />`, or `rowName`) | the cell, button or link by its column or caption |
| A dialog or panel that repeats the page's controls (an OK button in a popup over a page that has one) | the dialog container | the local `OK` |

Do not reach for a scope when the leaf is already named by its label — `<webctrl tag='INPUT' aaname='Location' />` is unique on its own and a scope around it adds one more thing to heal. Never scope on the component-type wrapper shared by every instance, and never on a wrapper pinned by its inner text (that text is the field's current value). The scope element is one Object Repository element like any other; its children are elements of the same screen with local selectors.

## Verifying targets — one element per family against the live driver

A migration's targets are generated from rules, so a wrong rule is wrong hundreds of times. Verify the *rule*, on one live instance per interaction family, before the family is written back:

1. **Capture the screen** that holds the family (`snapshot capture <b-ref>`), with the widget in the state the step needs (list open, value accepted).
2. **Ask the driver for its own shape**: `target-anchorable resolve-defaults` on the acting node with the family's activity type. Compare tag, attributes and anchor with the derived selector; a derivation that disagrees with the driver on which node is acted on is wrong, not "different".
3. **Read the acting node's attribute list** (`get-selector-attributes`) and strike every attribute the derived selector names that the node does not carry. Read the label's, the value display's and the popup entry's lists the same way (rule 16).
4. **Evaluate uniqueness** (`evaluate`, one ref per tag) for the derived selector and for the fixed one — with the popup open for a pick, after the pick for the value display, so the shared-text trap shows.
5. **Probe capability where the pattern depends on it**: `interact get <ref> items` for a list (Select Item or open-and-click), one grid cell for `tableRow`/`colName`/`rowName` (table attributes or text-pinned rows).
6. **Fix the rule, regenerate the family, write back** with `object-repository replace-elements` (keeps the `referenceId`, so the workflow links survive), then re-run steps 2–4 on a second instance of the family.
7. **Record per family**: the driver's default, the shipped shape, the collisions found, and what stays `offline-unverified` because no live instance was reachable.

Families to walk for a typical form-driven application: window scope; labelled text input; prompt / type-ahead (leaf, popup entry, value display); custom list (combobox, option, displayed selection); checkbox / radio; segmented date; command button and icon button; menu root and revealed level; grid header and cell; search box and result link; dialog close and error banner. Stale refs are normal — every capture re-mints them, and a `resolve-defaults` call can invalidate the refs of the capture it read from; re-capture rather than retry.

## Test data — pipeline

| Step | Output |
|---|---|
| 1. Decode the data catalog | recordsets as named rows (schema = layout variables, in column order); process → recordset links |
| 2. Per test-component folder of the test project, decide the mapping | per data file: its source recordset(s) and rows; per argument: the source variable (with a transform when needed), a join, a constant, a lookup into another recordset, or keep the default |
| 3. Check coverage, then migrate | every argument has a rule, credentials refused, rows rewritten, coverage report per file (migrated / kept / missing) |
| 4. Rebuild the project | data files are not compiled, but rebuild once to catch argument drift |

Transforms that recur: organisation-with-manager strings (`Org (Manager)` → org, manager), On/Off → boolean, country → region code, dates normalised, placeholder markers (`^`) → empty, user name → credential asset name and tenant URL.

Report per project: rows and cells migrated, values kept at defaults and why, values the source had but the test case has no argument for (and where they went), source quirks carried over (typos, wrong-field values, historical worker names, stale run dates). Historical run dates and worker names must be refreshed before a run on a live tenant; say so in the report.

## What the executor records (no prescribed file formats)

Mechanics — creating screens and elements, updating definitions, fuzzifying, linking — are the owning skill's Object Repository CLI and target-configuration guidance; read them and use them as they are. The genome skill only requires that, at the end, these facts are recorded and reviewable:

- per UI activity: the source window and control it was derived from (or "none"), the resulting strict/fuzzy selector, anchor and semantic description, the confidence tier, and the OR element it links to — one OR element per distinct source control, reused across workflows;
- per composite source step: the pattern applied (§ Composite interactions), the activities it expanded into, the derived elements created, and the verify sub-step;
- per data file: the source recordset(s) it was filled from and, per argument, whether the value came from the source, stayed at its default, or had no source counterpart; credentials appear as asset names and environments only;
- per workflow: validate result after linking, and any activity still without a target.

How that is scripted (mapping files, registries, validators) is the executor's choice for the run; the reports are the deliverable.

## Anti-patterns

1. Shipping placeholder targets when the source export carries locators.
2. Hand-typing selectors into XAML or definition files; the OR CLI and the derivation rules are the only path.
3. Copying passwords, or dropping the account identity along with them (which loses which role each scenario ran as).
4. Authoring test rows from the genome's defaults when the source has recordsets.
5. Widening a test case's argument set to fit the source layout instead of mapping onto the existing arguments and configuration defaults.
6. Declaring a target "done" without the confidence label and the healing-pass note.
7. Mapping a composite source step to the nearest single activity: type-ahead as type + click-first-entry, a custom list as `SelectItem`, a menu path as one click, a found row as a stored row number.
8. Synthesizing an identifier for a derived element by copying an attribute value from another catalog control.
9. Shipping a fuzzy selector with no anchor; matching inherited inner text on a broad tag, which also hits the ancestor chain; tightening or loosening a source criteria.
10. Letting an exported seed definition's own fields survive into the elements built from it — its selector, its `Guid`.
11. Building a type-ahead or option pick without the verify sub-step; the wrong entry accepted silently is the costliest failure of a migration.
12. Sending keystrokes to the window instead of the element that has focus, or keeping the source's page-scrolling keys.
13. Spending a Check Element / Check App State activity — and a guessed target — on a check the acting activity's own `VerifyOptions` performs (§ Verification). A migrated project with hundreds of Check activities and no `VerifyOptions` has this defect everywhere, not once.
14. Flattening a widget's container and its focusable leaf into one tag, so the selector carries the wrapper's identifier and the leaf's caption and matches neither ([selector-translation-guide.md](selector-translation-guide.md) rule 14).
15. Deriving the window scope per screen. The scope belongs to the application and is authored once; per-screen derivation yields one title wildcard per screen for a host that never changed (rule 9).
16. Reporting migrated definitions as done without verifying one element per interaction family against the live driver (§ Verifying targets), or — offline — without reading them back against [selector-translation-guide.md § Checking a definition](selector-translation-guide.md) and labelling them `offline-unverified`.
17. Verifying a pick against the option's text leaf instead of the field's value display — the leaf also lives in the still-open list, so the check passes before anything was accepted (§ Verification, rule 16).
18. Typing a whole date into a segmented widget's wrapper with the source's click offset, or reaching for a scope around a leaf that its label already names (§ Element Scope).
19. Assuming a grid's markup from the application's name — table attributes present or absent — instead of reading one cell live (rule 8).
