# Source Migration Guide — UI targets and test data at execution

Execution of an extracted genome migrates what the genome body leaves out: the source automation's **UI targets** (selectors) and **test data**. Both come from the export the Source Map names ([genome-format-guide.md § Source Map](genome-format-guide.md)); execution derives its catalogs from that export at build time. This guide is framework-agnostic and owns the execution-time procedure. Source guide § UI Target Locators and § Test Data say what the source provides; its selectors companion says how each recorded field translates; [selector-translation-guide.md](selector-translation-guide.md) owns every UiPath-side selector rule (tags, attributes, matching, scope, anchors, confidence, node identity).

## Migration preflight — derive the catalogs from the export

Source Map names framework, export path and identity, and every step's source objects. Execution turns that into working catalogs once, before the first UI group:

1. Resolve the export and the framework migration pack: the recorded export path, or the paths the user gave to the scaffolding questions ([execution-guide.md § 1.3](execution-guide.md)); confirm the export's identity against the Source Map (manifest, version, process count) and select the pack's framework row ([SKILL.md § Source Frameworks](../SKILL.md)). Report a mismatch and let the user decide; a missing or declined export or pack ends the migration part of the run — live capture where the application is reachable, placeholders otherwise, stated in the report.
2. Run the source guide's inventory commands (its § UI Target Locators and § Test Data name them and the files they write) into the build's working folder `<solution or project>/migration/source/`, never beside the genome.
3. Derive the step map: `scripts/genome-step-map.py <genome.md> --processes <process inventory> --recordsets <recordset list> --out <the same folder>` — one entry per workflow step with its source processes (`{name, id}`) and recordsets, read from the genomes' Source Map tables and the step-2 inventory. The script is framework-agnostic and reads no export; the source guide's script produces the two input files in the shape the step-map docstring states. A warning is a Source Map row that does not resolve: fix the Source Map (an extraction edit) or map the step by hand and record it.
4. **Check the source facts the genome cites, before any group builds on them.** A genome is extracted through a rendering of the source, and a rendering can hide a typed value (a number, a flag stored as text, an option nested under another) or an extraction can paraphrase one — the build then implements the rendering's gap as behaviour, silently. First run the source guide's renderer self-test when it has one; a failing self-test means every reading of that export's values is suspect until the renderer is fixed. Then, per workflow step, read from the step map's source objects every fact of these kinds the step's wording or rules depend on, and record it in a source-fact table (`migration/source/source-facts.md`: step, source object and line, genome says, source says):
   - comparison literals, operators and case rules (contains / equals / starts with, case-sensitive or not, line breaks ignored or not), spelled exactly — spacing and punctuation included;
   - counts, attempts and loop bounds, and whether the loop tests before or after its body;
   - lengths, positions and occurrences in text operations (a cut to 20 characters, the second `|`-field);
   - waits, pauses and timeouts, in the unit the source states;
   - flags that change control flow (continue on error, a do-while, a skip switch).

   Where the genome and the source disagree, the build follows the source for criteria and literals — the translation carries criteria over unchanged ([selector-translation-guide.md](selector-translation-guide.md) rule 2 holds for value comparisons as for selectors) — records each as a genome deviation in the group report, and leaves the genome to an extraction edit. A count or wait that differs from an answered configuration value goes back to the user with both values; the answer is theirs. The table is regenerated with the catalogs and handed to every group with the run brief.
5. **Scrub secrets out of the derived catalogs, as part of preflight.** § Rules rule 4 keeps secrets out of the built automation, but the catalogs are derived from the export and the export holds the secret in more places than its variable table: a recorder writes the typed value into the step's own narrative (`Input "…" into the Password field`), so a step dump and a step map reproduce a password verbatim even when the variable itself was refused. Collect the secret-bearing values the source records (the source guide's § Test Data names where they live), replace every occurrence across the working folder with a mask, and re-run the scrub whenever the catalogs are regenerated. The check is one search of the build folder for the values; it belongs before the first group, not in the final review.
6. "The target catalog", "the data catalog", "the step map" and "the source-fact table" mean these derived files. They are build artifacts: regenerated every run, never edited by hand, never committed as source of truth. A catalog that sat beside the genome is stale by definition and is not read.

## Rules

1. **Migrate targets from the catalog before anything else.** In a migration, every UI activity of the built project receives an Object Repository (OR) target derived from the catalog. The placeholder-selector stub pattern is the fallback only when no export was resolved AND no live application is reachable; a live application is captured with the owning skill's target-capture procedure instead.
2. **Every migrated target is inferred and says so.** Its OR element description starts with `INFERRED (<confidence>)` and names the source control. The first run against the real application is a healing pass; accepted fixes go into the OR element in place so every consumer inherits them. Until the live driver has confirmed a target (§ Verifying targets) it is unverified; without an application every element is labelled `offline-unverified`.
3. **Migrate test data from the data catalog by default.** The test project's data files (one per test-component folder) are filled from it by a scripted, reviewable mapping from source variables to test-case arguments, never by hand. Generated placeholder rows are a temporary state, not a deliverable.
4. **Account identity migrates, secrets never.** Genome-side rule (one credential asset per account, never a secret value): [genome-format-guide.md § Platform Dependencies](genome-format-guide.md). At execution a login user name becomes a credential asset name (`<App>_Login_<USER>`) plus the tenant/environment URL recorded for that account, carried per data row; the migration engine refuses passwords, tokens and secrets — they are entered in Orchestrator. One credential asset per source account is declared as a solution resource. Place the credential read inside the same scope that consumes it — the application card whose sign-in form the value is typed into — rather than at the top of the workflow: the secret it produces is scope-checked by the analyzer, and a read hoisted out of the scope that uses it fails the build. Identifiers that are not secrets — an OAuth application (client) id and directory (tenant) id, a service URL, a mailbox address — become Text assets (or configuration values), one per value, even when the source kept them in its credential vault: a credential asset's second half is a SecureString, and a consumer that needs the plain value must convert it, which the workflow analyzer rejects at build (`ST-SEC-009`).
5. **The argument set is frozen during data migration.** Mappings place source values onto the test cases' existing arguments; a value with no argument goes to the project's configuration workflow or argument defaults and is listed as `unmapped`. Source row counts and execution flags replace generated ones. Never widen a test case's argument set to fit the source layout.
6. **Build through the owning skill.** Contract (mandatory reads, discovery commands, per-activity docs, validate per file and build per project as the skill prescribes): [execution-guide.md § 2.2](execution-guide.md); a generator is acceptable only for repetition of activity fragments already confirmed that way. Create, link and update OR elements through the owning skill's Object Repository CLI, target-configuration and target-attachment guidance; never hand-type selectors into XAML or definition files — the one documented exception is the no-application case in [offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md).

## UI targets — pipeline

| Step | Output |
|---|---|
| 1. Load target catalog and built workflows | UI activities per workflow (activity id, type, display name, arguments, variables). The catalog has two channels and both are targets: the controls the source recorded, and the identities it passed as arguments to a scripting wrapper (a SAP GUI scripting id, a selector fragment) — each such identity is an element of the calling step, exactly like a recorded control |
| 2. Map every UI activity to a catalog control (or *none*) | per application card: source window; per UI activity: source control (or none), activity type, argument substitutions, semantic text, confidence |
| 3. Derive targets | per element: strict selector from control attributes (source guide's selectors companion for the left side, [selector-translation-guide.md](selector-translation-guide.md) for the UiPath side), optional caption anchor, semantic description, confidence; per application: one scope selector (rule 9 there) |
| 3b. Collapse to nodes | identity key of every derived target (§ Object Repository identity); targets sharing a key become one element, recurring widget roles one parametrised element, screens follow the application's states |
| 4. Find or create OR screens and elements through the owning skill's Object Repository CLI | lookup by identity key first; create only when new; one element per node, reused across workflows |
| 5. Link screens then elements into each workflow per the owning skill's target-attachment guidance | linked XAML, placeholder prefixes removed from linked activities |
| 6. Validate every workflow; build; pack | per-workflow report: linked count, created vs reused vs parametrised, confidence, remaining errors |

Mapping rules: every UI activity mapped once, activity ids file-unique; the step map names each workflow step's source processes, whose dumped steps name the controls; shared widgets (search box, OK, Submit, comment box, menus) map to one control (§ Object Repository identity); literals the workflow receives as arguments (a person name, a placeholder the source rewrote at run time) become selector variables (`{{Argument}}`) bound to the workflow argument; steps the built workflow has but the source had not (optional pop-up checks, verifications) get no source control, a precise semantic description and low confidence. A **composite source step** (§ Composite interactions) maps to one invocation of the pattern's helper workflow, whose elements — the catalog's anchor control plus the derived elements the source never learned — exist once.

**Linking is the last thing done to a workflow file, and it is not self-verifying.** Four mechanics decide whether step 5 of the pipeline survives; each one fails quietly:

1. **Link a file only once its content is final.** Linking rewrites the workflow in place, so regenerating that file afterwards silently discards every link it had while the run's own bookkeeping still says "linked". When a generator produces the workflows, make it **idempotent** — activity ids and any per-activity identifiers derived from the file and the activity rather than minted per run — and keep a copy of each file as generated, so a re-run can prove a file is unchanged and leave the linked one alone. Without that, every fix to one workflow costs the linking of all of them.
2. **Verify each link by re-reading the file, never by the command's result.** Batched link calls go through a command line, and a batch past the shell's length limit is truncated while the call still reports success for the part that arrived. Count the references in the file after each batch and compare with what the batch contained; size the batches by payload length rather than entry count.
3. **The authoring host caches workflow files.** A file rewritten on disk after the host has read it is still served from the cache, and the link then fails against the stale copy. Its signature: the link reports that the workflow cannot be loaded, while a validate of the same file reports only the ordinary "target not set" errors — and copying the file to a new path and linking that succeeds, which is the test that confirms it. Before linking a rewritten file, validate it: the unlinked targets' "target not set" errors prove the host is serving the new content, where a cached, already-linked copy would report none. When the host must be reset, stop only the headless Studio process that holds this project — confirm the process's name and that its command line names the project before stopping it; a process id taken from an instance listing can be stale and reused by an unrelated process.
4. **Re-registering does not update a definition.** Find-before-create reuses the element and leaves the stored selector as it was, so a regenerated definition never reaches the store unless it is pushed with the replace command (§ Object Repository identity rule 4). To know which ones moved, keep a fingerprint of what was last pushed per element — selector, anchor and description — and replace exactly the ones that differ.

## Object Repository identity — one element per node

Duplicate elements (same screen, same selector, different name or suffix) come from choosing the wrong unit, not from a registration accident. The failure mode is an element count an order of magnitude above the number of distinct nodes, and it has three causes that compound: keying elements by source window, source control *and* activity type; making one screen per source window; minting one element per field value. Rules that prevent it:

1. **An element is a node on a screen.** Its identity key is the tuple (screen, strict selector, fuzzy selector, anchors, selector variables), normalised (attribute order, quoting, whitespace). The same control clicked in one step and typed into in another is **one** element: the metadata `ActivityType` only tunes the generated selector, it does not fork the element — give it the acting type (Type Into over Click over None) and let every activity use it. Two definitions with one key and different names are one duplicate; reuse the first.
2. **Screens are the application's states, not the source's windows.** The scope selector is the application's, authored once ([selector-translation-guide.md](selector-translation-guide.md) rule 9). A source window is provenance: several source windows that share the scope and the controls collapse into one screen, and controls shared by every page (chrome, search, command bar, dialogs) live on one shared screen so they exist once. Screen names are unique within the application. Name screens after what the user sees (page or dialog), never after source window ids. An Object Repository application is one executable or one browser host: a runtime's own prompts (a security warning, an update prompt) are screens of the application that owns their process, not of the business application they interrupt, and a launcher and a desktop client that are different executables are two applications.
3. **Recurring widget roles are one parametrised element.** A prompt's acting leaf, its popup entry and its value display recur for every field with a different label and value; they are **one element each** with selector variables (`{{FieldLabel}}`, `{{Value}}`), not one element per field. Selector variables bind by name to variables or arguments in scope, so the pattern is built **once as a helper workflow** (`PickPromptValue(FieldLabel, Value)`, `ChooseListOption(FieldLabel, Value)`, `EnterSegmentedDate(FieldLabel, Date)`) that owns the variable names, the retry branch and the verify; every step invokes the helper. A source that used the pattern 150 times yields 150 invocations and three elements, not 450 elements and 150 copies of the sequence.
4. **Find before create.** The owning skill's capture flow looks a screen up by its window selector and an element up by name and description before registering; a migration does the same mechanically: read the existing store (the OR CLI's screen and element listings, or the `.objects` tree) into a map keyed by identity, reuse the `referenceId` of every hit in the link, and create only new keys. A name collision with a different key gets a qualifier from the screen or role (`OK` / `OK (dialog)`); a key collision with a different name is the duplicate and is not created. One registration process at a time — two concurrent runs each create the same keys. After registration, count distinct keys against elements and delete every element whose `referenceId` no workflow references. Write back to an existing element with the OR CLI's **replace** command (keeps the `referenceId`, so workflow links survive); its **create** command on an existing element adds a duplicate and orphans the link. Command syntax: the owning skill's Object Repository guidance, routed from the UIA package guide.
5. **Report the collapse.** The migration report states elements created, reused and parametrised, and lists the helpers with the steps that invoke them; a screen count near the source's window count, or an element count near its control count, signals that steps 1–3 were skipped.

## Source steps that are not UI actions

A source's step vocabulary is wider than "click, type, read". The source guide's step table says what each kind *means* (extraction's job); this table says what execution builds for it. Only the first two rows produce a UI activity with a migrated target — which is why a migrated project has far fewer activities than the source had steps, and why an executor that emits one activity per source step produces a project several times too large.

| Kind of source step | What execution builds |
|---|---|
| Act on a control — click, type, set state | the acting activity, target from the catalog |
| Act through a packaged multi-step interaction | the pattern, not the nearest single activity (§ Composite interactions) |
| Wait for / assert a control is shown, with a timeout | a post-condition of the step before it → that activity's `VerifyOptions`; a Check activity only where the source branched on the outcome (§ Verification) |
| Assert a value — verify, compare | **read the control, then compare what it showed against the expected value.** The trap is mechanical: the source step names the control and the expected value, so a naive translation emits the expected value on both sides of the comparison and ships an assertion that can never fail. The actual side is always read at run time. The expected value and the operator come from the source's condition verbatim, like selector criteria ([selector-translation-guide.md](selector-translation-guide.md) rule 2): an equals is never loosened to a contains, and a recorded control's name is never the expected value — a recorder names a text read after what the screen showed at capture time, a sample, while the value the source compares against sits in its own condition |
| Store / read a value for later steps | a read activity writing the variable the later steps consume; a value that crosses a workflow boundary is an **argument**, not a variable |
| Set a locator's value at run time (placeholder rewriting) | a selector variable bound to the argument, not an activity ([selector-translation-guide.md](selector-translation-guide.md) rule 14 step 2) |
| Label, and the jumps that target it | **structure, not activities**: a forward jump becomes a branch that skips the steps between, a backward jump becomes a loop around them. A label with no jump to it is a comment |
| Comment | the name of the enclosing sequence or annotation — never an activity |
| Engine setting — busy check, scroll-into-view, object timeout, input method | dropped; a timeout becomes the affected activity's timeout and an input-method switch its input mode (§ Composite interactions) |
| A fixed pause with a value — between two steps, after a failed attempt, before a retry | kept at its value: the next activity's delay-before when the pause precedes a UI step, a delay where the wait is for something outside the UI (a file operation settling, a retry back-off). An element wait does not replace it — it waits for an element, not for the settle time the source measured. A pause the rendering shows without a value is read from the source object before it is dropped (§ Migration preflight step 4) |
| A call into a scripting wrapper's verb with an identity argument | the UI activity the verb names, on the element the identity names (target catalog, second channel); never a call into a library of verbs |
| Screenshot / evidence capture | the project's evidence workflow, named by the checkpoint id (§ Result parity) |
| Call another source process | an invoke of the workflow that process became |
| A step the source marked as skipped | dropped, unless the genome's own wording says the migration restores it — then it is built and the restoration is recorded as a deviation |

Two contracts have to be closed at the end of this translation, and both fail silently when they are left open:

- **Every out-argument the genome's Interface declares must be written on every path.** Source variables become arguments, but the step that produced one may sit in a branch, or may have been a store the migration dropped; the argument then ships declared, typed, and never assigned, and the caller reads an empty value from a workflow that validated cleanly. Seed each out-argument at the start and check at the end that every one is assigned somewhere; report the ones with no source counterpart rather than leaving them empty.
- **The source's own variable names are not the argument names.** The genome fixes the argument names; the mapping from source variable to argument is the executor's and is recorded per workflow, so a reader can trace a value back.

## Composite interactions — one source step, several UiPath activities

Test frameworks package multi-step interactions into one parameterised step: type-ahead pick, menu path, option list, find-row-then-act, keystrokes to the focused element. The genome substep carries the interaction contract ([genome-format-guide.md § Workflow](genome-format-guide.md)); the source guide's composite-actions table names the source actions and dictates wording; this section fixes how execution builds them. **Rule: build the pattern, never the nearest single activity.** Each naive mapping below validates, runs, and does the wrong thing: type-ahead as "type, then click the first popup entry", a custom list as a native select, a two-level menu as one click. This is the most expensive class of migration defect, because none of it shows up as an error — the project builds, the run completes, and the automation exercised nothing.

**Derived elements.** The catalog holds only the anchor control (input, menu root, table); the popup entries, menu items, option rows and matched cells the source clicked were never learned and must be derived. A derived element's selector is tag plus matched text plus semantic description — never an identifier the source did not record for it ([selector-translation-guide.md](selector-translation-guide.md) rule 13). Which attribute carries the matched text is rule 5's three-case test there (form-ish tag → synthesised `aaname`; text leaf → `aaname` + `isleaf='1'`; container → `visibleinnertext` matched exactly); the tag is the one the node's role in the pattern implies, never a guessed `DIV` — a derived element has no recorded tag to draw on, so it is the one case where the role's implied tag is the best evidence there is (rule 14). Where the catalog does not say which node is which, the target is tag-only with the semantic description and owes a live pass (rule 13).

Before building any UI group of an extracted genome, read the per-control `actions` in the derived target catalog and the substep wording, classify every UI step against this table, and read the owning skill's control-interaction guidance for the classified controls (option lists, date inputs, tables) as it mandates. Each pattern occurring more than once is built as one helper workflow parametrised by field label and value (§ Object Repository identity rule 3); the steps invoke it. Node roles named below (wrapper, label, form item, acting leaf, value display, popup list, popup entry) and their concrete shapes: [selector-translation-guide.md](selector-translation-guide.md) rule 16.

| Pattern | Naive mapping that fails | Build | Derived elements |
|---|---|---|---|
| **Type-ahead pick** — type text, suggestion list appears, pick the entry matching a caption rule, optional confirm key | type + click "first item" (positional container element); type + Enter without checking what was accepted; **verifying on the option's text leaf**, which also exists in the still-open list and passes before anything was accepted | 1. Type the value into the field's *acting leaf* — the labelled input, never the widget wrapper — with key-event input (never set-value: the list opens only on key events). 2. Confirm as the source did (Enter) or pick: the entry is the popup's text leaf, scoped to the *popup labelled with the field*, caption as a selector variable under the source's criteria (contains / equals / nth). 3. Verify on the acting activity's `VerifyOptions` (`Appears`) against the field's **value display scoped to the field** (§ Verification) — the source's own verification becomes this acceptance check. The typed text is gone once the prompt accepts, so Type Into's target-less Auto/Expected-text verify does not apply to a prompt. 4. When the source itself had a fallback (Enter failed → click the entry), keep it as a Check with the click in the not-found branch; the verify still belongs on the acting activities | popup entry (scoped to the labelled popup) and value display (scoped to the field) — one pair per widget type, parametrised by field label and value, or one pair per field; low confidence until seen live, `derived from <anchor control>` |
| **Option list** — choose an item by caption rule from a list, dropdown or combo | `SelectItem` on a custom (div/li/span) widget; positional `idx` on the item; verifying on the option text | Probe the control's `items` live (the package's element-interaction commands; owning skill's select-item guidance). Items present → `SelectItem` with the listed value verbatim. Items absent (custom lists expose `selecteditem` but not `items`) → click-to-open the combobox (the acting leaf, found inside the form item pinned by its label), click the option under the *list labelled with the field*, verify the field's displayed selection scoped to the field. A numeric index in the source is positional: keep it as an index on the option element and flag it | option entry (scoped to the labelled list), displayed selection; medium when the source caption is literal, low when variable-bound |
| **Segmented date entry** — source clicked a date field off-centre (its first segment) and typed the whole date | Type Into on the widget wrapper with the source's click offset; a bare-tag Check afterwards | Target the first segment by the field's label (only the first segment carries it), or scope on the form item (§ Element Scope) and type into each segment with the segment's expected text as the verify. Follow the owning skill's date-input guidance for the rendered format, `EmptyFieldMode` None and auto-advance. Verify against the widget's rendered value (a hidden "current value is …" leaf, or the segments) — never a bare `tag='DIV'` | month/day/year segments under the field's form item; medium |
| **Menu / tree path** — `A\|B\|C` from a menu root, levels revealed by hover or click | one click on the root, or on the leaf caption anywhere on the page | One click (or hover, per the live probe) per level, each re-resolving its target after the previous level rendered; levels are separate activities, never one target with the leaf text. Each revealed level is usually a *new popup of the same type*, and a label can repeat across groups of one level, so a level entry is scoped to its own popup (the newest one) or to its group header, never matched page-wide by text. The last level gets a verify (the page or dialog the leaf opens). Menu roots that appear in several source windows reuse one element | one element per level (text leaf under its own popup); medium for the root (mapped), low for levels |
| **Table row by content** — find the row whose cell(s) match, then click, read, type or verify in that row | store a row number and index into the table with it; assume the grid's markup without looking | Never carry a row integer. Choose the cell shape per [selector-translation-guide.md](selector-translation-guide.md) rule 8 (read one cell live: table attributes → row-anchored `TD` by `rowName`/`colName`; absent → row container pinned by exact text, cell as its descendant; key text repeated in its column → pin the row by the discriminating value). Alternatively extract the table, filter in code, then act through the pinned row. `Last` = last matching row. Multi-criteria finds and-combine the cell matches. Source "popup rendered as table" (suggestion popups) is an option pick, not a table op | matched cell (anchor), target cell in the same row; medium |
| **Table cell** — act on the cell at (row rule, column caption or number) | absolute `tableRow`/`tableCol` | Column by header caption (`colName='{caption}*'` when exposed, else the header-anchored cell), row by content rule from the preceding find; a literal row number in the source is positional and stays flagged; double-click and follow-up keystroke preserved. A prompt inside a cell (typed value + Enter) is a type-ahead pick inside the cell | header cell, target cell; medium |
| **Read cell / row count / control text** | Get Text on the table element | Get Text or Get Attribute on the row-anchored cell after previewing what it extracts (owning skill's get-text guidance); row count via table extraction or a rows attribute, verified live | as table cell |
| **Keystrokes** — keys sent to the window or the focused element | Keyboard Shortcuts to the browser window / page body; a Delay | Determine the target from the preceding step: the keys go to that element (Type Into text with special-key tokens when they follow typing; Keyboard Shortcuts targeted at the element otherwise). One Keyboard Shortcuts activity per chord the source sent (two chords are two activities, not one); a source bring-to-front before the keys is `ActivateBefore` on the keystroke activity, not a separate window activity; a click on the same element is the fallback when the source had one. Page scrolling keys are dropped (UiPath scrolls the target into view). A browser refresh becomes the browser navigation activity. Invented shortcuts are forbidden; only keys the source actually sent | none; the target is the preceding step's element |
| **Coordinate click** — click at pointer position or screen x/y | Click with an offset on the page | Identify the intended element from surrounding steps (dismiss a popup, focus the page, an unmapped button) and target it; semantic description; flag `*[Inferred]*` in the report | derived element; low |
| **Set state** — ensure checkbox/radio state | Click | Check/Uncheck with the state (idempotent); radio click plus verify selected | none |
| **Input-method hint** — source switched to key-event input for the fields that follow | ignored | Carry into the affected activities' input mode (key events / hardware, per the owning skill's input-methods guidance); the type-ahead pattern needs it | none |

Every derived element is named `derived from <anchor control> — <pattern>` in its description, labelled `INFERRED (low)` unless the table says medium, and listed in the report under the healing-pass note as the first targets to verify live. The description names which attributes came from the source control; if it has to say an attribute was "taken from" another control, that attribute does not belong in the selector. Source match criteria carry over unchanged ([selector-translation-guide.md](selector-translation-guide.md) rule 2); confidence tiers and targeting method (fuzzy requires an anchor, a positional index is strict and never anchored, the semantic fallback is always added) are rule 12 there, the semantic description rule 11 — a derived element with no control of its own stays **low**. The first live run must exercise every type-ahead and menu-path step; a step that "passes" by clicking the wrong entry is the failure mode this section prevents, so the verify sub-step of each pattern is mandatory, not optional.

**Actions without a control** map to target-less activities, not to invented elements: opening a browser at a URL or starting an executable is a Start Process (with the executable, its arguments and working directory) followed by an application card that *attaches* to the resulting window through the Object Repository screen for the reads and closes that follow — offline, a card's launch URL or file path cannot be written into a definition ([offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md)), and the live pass may move the open into the card; a forced close of a process is Kill Process; maximise, activate or close of a window is a Window Operations activity inside a card attached to a window-level screen (a screen with no elements); a desktop screenshot on error is Take Screenshot with no target; "the dialog appears within N seconds" is Check App State on the dialog's captured button or on the window-level screen. Every one of these still carries its window-level scope from the catalog.

With no reachable application the owning skill's CLI cannot produce a first definition or anchor; shapes, seed-and-mutate procedure and anchor/fuzzy coupling for that case: [offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md).

## Verification — a property of the activity, not another activity

Every pattern above owes a verify sub-step. **A verify sub-step is normally not a separate activity.** UI Automation activities carry post-action verification natively (`VerifyOptions` on Click, Hover, Keyboard Shortcuts and Type Into), and that is where a migration's verification belongs. Reaching for a Check Element / Check App State activity instead is the single largest source of activity-count inflation in a migrated project, and each one drags in a target that must be guessed, reviewed and healed like any other. A migrated project whose Check-activity count approaches its Click count, or that has hundreds of Check activities and no `VerifyOptions`, has this defect everywhere, not once.

Decide with one question: **does the outcome change what the automation does next?**

| Outcome | Build |
|---|---|
| No — the step simply has to have worked; not working is a failure | `VerifyOptions` on the activity itself. No extra activity, no extra target for an appearance check that reuses one |
| Yes — the automation genuinely branches, retries or takes another route | a Check activity, whose branches hold the alternative work |

Mapping a source's own verification steps (a source expresses "the value was accepted", "the page arrived", "the field now reads X" as its own check steps; the natural-looking one-Check-per-check translation is almost always wrong — those checks are post-conditions of the step before them):

| Source records | UiPath |
|---|---|
| typed value must be accepted / field must now read X — plain text box | Type Into `VerifyOptions`: **Auto** (target-less — confirms the text landed) or **Expected text** (target-less, wildcards allowed). Neither needs a target, so neither needs a migrated element |
| typed value must be accepted — prompt / type-ahead field, where the accepted entry replaces the typed text with a chip or selected option | Type Into `VerifyOptions` with a **target and mode** (`VerifyExecutionTypeIntoOptions` extends `VerifyExecutionOptions`): mode `Appears`, target = the field's value display scoped to the field ([selector-translation-guide.md](selector-translation-guide.md) rule 16). Target-less Auto fails here because the text is gone |
| a confirmation, banner, next page or row must appear after a click | Click `VerifyOptions`, mode `Appears`, target = the thing that appears |
| a spinner, dialog or row must be gone | mode `Disappears` |
| a field or label must change value | mode `TextChanges` |
| the step is a checkpoint with no follow-up behaviour | still `VerifyOptions` — a failed verify raises, which is the checkpoint |
| the source branches on the result (retry, alternate path, optional dialog) | a Check activity — this is control flow, not verification |

**The genome's checkpoint list is the request for verification.** The UIA package guide tells an author not to add `VerifyOptions` unless the user asks; in a migration the Source Map's Checkpoints row *is* that ask — every checkpoint becomes a `VerifyOptions` (or the read-and-compare below), and nothing else gets one.

**A checkpoint followed by a read has no verify slot of its own.** Get Text and Get Attribute carry no `VerifyOptions`; when the source asserts a control is shown and then reads it (`expect(row).toBeVisible()` then `row.innerText()`), the read is the checkpoint: the read activity targets that element with the source's timeout, its success is the "shown" assertion, its value is logged under the checkpoint id and compared where the source compared. No Check activity is spent on it — a Check is still reserved for a genuine branch.

Mechanics that decide whether it behaves: `Retry` defaults to **true** and re-runs the activity until the activity's own `Timeout`; the verify `Timeout` (default 10s) is how long each check waits. A verify target is *observed, never acted on*, so configure it with a neutral activity type (`None`), **not** `CheckElement` — a `CheckElement` type applies the state-attribute rules meant for Check Element itself. Reuse an existing Object Repository element for the observed thing whenever one exists rather than minting a near-duplicate.

Three consequences a migration gets wrong easily:

- **The verify observes the element that shows the outcome, scoped to where the outcome shows.** After a pick, that is the field's value display under the field's form item — not the option's text leaf, which also lives in the still-open list and makes the check pass before anything was accepted (the shared-text trap, [selector-translation-guide.md](selector-translation-guide.md) rule 16), and not a bare `tag='DIV'`. After a click that changes the page, it is the new page's header or the grid that renders. The verify target is one Object Repository element per widget type (parametrised by field label and value) or per field; it is never re-derived per step.
- **A plain text box's acceptance check is target-less; a prompt's is not.** Type Into Auto/Expected-text verification confirms the value landed in a text box with no element at all. A prompt replaces the typed text, so its check is a targeted `Appears` on the value display (table above).
- **The `IfNotExists`-branch idiom is control flow wearing a verification costume.** A Check whose "not found" branch clicks the suggestion is a legitimate retry path — but the *acceptance* check that follows the click is verification and belongs on the click. Do not let one genuine branch pull every check in the sequence into its own activity.

## Element Scope — attach once, keep the children local

Element Scope (`NElementScope`, Version V5, body an `ActivityAction<Object>` named `ContextTarget`; shape from the owning skill's `activities get-default-xaml`) attaches to one element; every activity inside resolves its target relative to it. Its target is a `TargetAnchorable` like any other; children's targets carry **no** scope selector of their own. This is the activity-level form of [selector-translation-guide.md](selector-translation-guide.md) rule 14 step 2, and the right shape exactly when the acting leaves have no name of their own:

| Situation | Scope target | Children |
|---|---|---|
| Segmented input — a date's month/day/year, a phone's parts — only the first segment carries the field label | form item pinned by the label (`<webctrl tag='LI' visibleinnertext='{Label}*' />`) or widget wrapper *with a per-instance id* | segment inputs by their own segment identifier (e.g. `<webctrl tag='INPUT' data-automation-id='dateSectionDay-input' />` and siblings) |
| Div-based combobox or custom control labelled only by `aria-labelledby` | labelled form item | `<webctrl aria-role='combobox' />`, then the value display for the verify |
| Several actions on one row of a repeated structure (table row, card, inbox item) | row pinned by its key text (`<webctrl tag='TR' visibleinnertext='*{key}*' />`, or `rowName`) | cell, button or link by its column or caption |
| Dialog or panel repeating the page's controls (an OK button in a popup over a page that has one) | dialog container | local `OK` |

Do not reach for a scope when the leaf is already named by its label — `<webctrl tag='INPUT' aaname='Location' />` is unique on its own and a scope around it adds one more thing to heal. Never scope on the component-type wrapper shared by every instance, and never on a wrapper pinned by its inner text (that text is the field's current value). The scope element is one Object Repository element like any other; its children are elements of the same screen with local selectors.

## Verifying targets — one element per family against the live driver

A migration's targets are generated from rules, so a wrong rule is wrong hundreds of times. Verify the *rule*, on one live instance per interaction family, before the family is written back.

**Which of three situations the run is in decides what a verdict can say.** The application the automation will drive is usually *not* reachable from the machine doing the migration — that is the normal case, not a failure, and the run completes without it:

| Situation | What a verdict settles | Label |
|---|---|---|
| The target application itself is reachable | everything: shape, the instance's captions, uniqueness on the real screens | `verified` |
| A **comparable instance** is reachable — another tenant, environment or version of the same product | the *shape* only: which node the driver acts on, which attribute carries the label and which the value, the role identifiers a component framework emits, whether a grid is real table markup, whether a control exposes `items`. These are properties of the product, so they transfer; the target instance's own captions, data, page layout and version drift do not | `shape-verified`, and the report says which instance settled it |
| Nothing is reachable | shape only as far as a definition can be read back on its own (§ below) | `offline-unverified` |

A comparable instance is a **windfall, not a step**: take it when the user has one, and never make the run depend on it. To use it, copy the definition to a scratch file, substitute the selector variables with values present on that screen and the scope with that instance's, and run the validator against the copy — the project's own definitions and scope are never pointed at the other instance. A shape confirmed this way is still owed the healing pass on the real application; what it buys is that the *translation* is no longer the suspect when a target fails there.

Capabilities used below (driver default, attribute listing, selector evaluator, snapshot reload) and what each settles: [selector-translation-guide.md](selector-translation-guide.md) rule 15; their syntax is the UIA package's, routed from its guide. Procedure, for whichever instance is reachable:

1. **Capture the screen** that holds the family (a snapshot of the window), with the widget in the state the step needs (list open, value accepted).
2. **Ask the driver for its own shape**: the driver default for the acting node with the family's activity type. Compare tag, attributes and anchor with the derived selector; a derivation that disagrees with the driver on which node is acted on is wrong, not "different".
3. **Read the acting node's attribute listing** and strike every attribute the derived selector names that the node does not carry. Read the label's, the value display's and the popup entry's listings the same way (rule 16).
4. **Evaluate uniqueness** (the selector evaluator, one ref per tag) for the derived selector and for the fixed one — with the popup open for a pick, after the pick for the value display, so the shared-text trap shows.
5. **Probe capability where the pattern depends on it**: the control's `items` for a list (Select Item or open-and-click), one grid cell's attribute listing for `tableRow`/`colName`/`rowName` (table attributes or text-pinned rows).
6. **Fix the rule, regenerate the family, write back** with the OR CLI's replace command (keeps the `referenceId`, so the workflow links survive), then re-run steps 2–4 on a second instance of the family.
7. **Record per family**: the driver's default, the shipped shape, the collisions found, and which of the three labels above the family carries and why. A UI migration is not reported done before a verdict exists per family — `offline-unverified` is a verdict, an unstated one is not.

Families to walk for a typical form-driven application: window scope; labelled text input; prompt / type-ahead (leaf, popup entry, value display); custom list (combobox, option, displayed selection); checkbox / radio; segmented date; command button and icon button; menu root and revealed level; grid header and cell; search box and result link; dialog close and error banner. Expect to reach only some of them: a family needs a page that shows it in the state the step needs, and reaching such a page read-only is the binding constraint, not the probing. A family left unexercised is recorded as such, and a *partly* exercised one says which part — an editable grid cell whose row and column matched but whose input was never reached is not the same as a cell that was never seen. Drive read-only: open pages, open menus and lists, type into a field to make a popup appear, and cancel out; never submit, save or confirm.

Stale refs are normal — every capture re-mints them, and a driver-default call can invalidate the refs of the capture it read from; re-capture rather than retry.

Application not reachable: read the definitions back against [selector-translation-guide.md § Checking a definition](selector-translation-guide.md) and the offline guide's own checks (a throwaway script for the run is fine when there are hundreds; the skill ships none), fix what fails, and label every element `offline-unverified`. A structural pass proves shape, not that anything matches the screen.

## Result parity — making a UiPath run comparable with the source's

Whether a migrated suite reproduces the source's results is decided by whoever can compare runs — against a fresh source run when the source still executes, or against the last result log the export carries when it does not. That comparison is not the skill's job, nor is verifying the outcome. The skill's job is to make it possible: the built automation asserts at the source's checkpoints under the source's ids, attaches evidence named by those ids, and ships a mapping table saying which UiPath assertion and which artifact stand for each source checkpoint. The table is **static** — derived from the workflows before any run — one per test case, kept with the project (`<build>/migration/parity/<TestCase>.md`):

| # | Source checkpoint | Expected | UiPath assertion | Evidence | Compare |
|---|---|---|---|---|---|
| 12 | step 12 (id 4471) — verify requisition status after submit | `Successfully Completed` | `VerifyOptions` Appears on "Click Submit", target: status cell | `CreateRequisition-12-status.png` attached to the test result; log `[CP 12] status=Successfully Completed` | equals |
| 19 | step 19 (id 4488) — screen capture after the position opened | position page shown | `VerifyOptions` Appears on "Click OK", target: page header | `CreateRequisition-19-position.png` | present |
| — | none | — | page-settle check after every navigation | none | added |

Rules:

1. **Every source checkpoint has a row.** A checkpoint is a source step that asserts something (verify, compare, visible, cell check), a step the source's result log records as a check, or a capture the source took where the state was meant to be inspected; the source guide's § Evidence says which of its step kinds count. Extraction lists them per workflow step in the Source Map's Checkpoints row ([genome-format-guide.md § Source Map](genome-format-guide.md)). No checkpoint list, no parity.
2. **Every row names the UiPath construct that asserts the same thing:** `VerifyOptions` on the acting activity (the normal case), a Check activity where the source branched, a test assertion at the end of the case, or a read-back and compare when a value is checked. A checkpoint with no counterpart is a row marked `not asserted` with the reason; the report counts them.
3. **Evidence per checkpoint, findable by id.** At each checkpoint the built automation attaches a screenshot to the test result through the library's evidence workflow, named `<TestCase>-<CheckpointId>-<label>.png`, and writes one Info log line `[CP <id>] <what>=<observed value>`, so a run's log can be read row by row against the table and against the source's result log, and Test Manager holds the images. A screenshot on failure is the same mechanism with the failing step's id. The attach activity attaches only when the case runs from Orchestrator; a local run logs that it skipped the attachment and the file stays in the project's evidence folder — that is expected, not a defect, and the report says which of the two happened.
4. **The compare rule is the source's own criteria** carried over — equals, contains, present, absent, count — never tightened or loosened.
5. **Assertions the source never had are rows marked `added`** (page-settle checks, pick acceptance the source did not verify). They do not count toward parity; they are listed so the reviewer sees the difference.
6. **Generated, not typed.** Activity display names and log lines carry the checkpoint id, so the table is produced from the workflows by the executor's own script, needs no run, and is regenerated after every change. A table maintained by hand drifts from the project within one edit. The columns above and the counts line (`source checkpoints N, asserted N, not asserted N, added N`) are the schema every generator writes, so tables from different runs and executors read alike; the script lives in the build's `migration/` folder beside the tables it writes.

The completion report states, per test case: source checkpoints, asserted, not asserted (with reasons), added, and where the tables are. It does not claim parity — only a comparison of runs can make that statement, and it belongs to the reviewer who holds a source result.

## Test data — pipeline

| Step | Output |
|---|---|
| 1. Decode the data catalog | recordsets as named rows (schema = layout variables, in column order); process → recordset links |
| 2. Per test-component folder of the test project, decide the mapping | per data file: source recordset(s) and rows; per argument: source variable (with transform when needed), join, constant, lookup into another recordset, or keep the default |
| 3. Check coverage, then migrate | every argument has a rule, credentials refused, rows rewritten, coverage report per file (migrated / kept / missing) |
| 4. Rebuild the project | data files are not compiled; rebuild once to catch argument drift |

Recurring transforms: organisation-with-manager strings (`Org (Manager)` → org, manager), On/Off → boolean, country → region code, dates normalised, placeholder markers (`^`) → empty, user name → credential asset name and tenant URL.

**When the source row is wider than the analyzer's argument cap.** A data-driven test case binds its variation file to its arguments **by name**, so the column set and the argument set are one set: a row of thirty source columns is a case with thirty arguments, and the workflow-analyzer rule that caps arguments (Error severity, so it fails build and pack but not validate) is breached by the data, not by the authoring. The cap is a default best practice written for hand-authored workflows; it is not configurable from the build and pack commands, whose governance-file option is accepted and then ignored. Resolve it in this order, and never by the last two:

1. Drop columns the case never reads — a variation column with no `row:` reference is dead weight, and trimming them is free.
2. Move values that are **environment**, not scenario, into the shared configuration workflow (asset names, tenant URLs) — rule 5's normal route.
3. Still over: accept the finding. Record it as an accepted analyzer error with the reason, build that project with the analyzer step skipped, and list the findings verbatim in the report ([execution-guide.md § 1.5](execution-guide.md) item 1 — decide with the user and record the decision). The analyzer-enabled build is run first so the findings are captured, and the skip covers only that build.
4. **Not** by dropping source data to fit, and **not** by moving per-scenario values into configuration — either one makes the case stop testing what the source tested, which is the whole point of the migration.

Report per project: rows and cells migrated, values kept at defaults and why, source values with no test-case argument (and where they went), source quirks carried over (typos, wrong-field values, historical worker names, stale run dates). Historical run dates and worker names must be refreshed before a run on a live tenant; say so in the report.

## What the executor records (no prescribed file formats)

Mechanics — creating screens and elements, updating definitions, fuzzifying, linking — are the owning skill's Object Repository CLI and target-configuration guidance; read and use them as they are. The genome skill requires only that these facts end up recorded and reviewable:

- per UI activity: source window and control it derives from (or "none"), resulting strict/fuzzy selector, anchor and semantic description, confidence tier, linked OR element — one OR element per distinct node, reused across workflows;
- per composite source step: pattern applied (§ Composite interactions), activities it expanded into, derived elements created, verify sub-step;
- per data file: source recordset(s) it was filled from and, per argument, whether the value came from the source, stayed at its default, or had no source counterpart; credentials appear as asset names and environments only;
- per workflow: validate result after linking, any activity still without a target;
- per interaction family: live verdict (§ Verifying targets) or `offline-unverified`;
- per test case: result parity table (§ Result parity) — source checkpoint, expected value, UiPath assertion, evidence, compare rule — and its counts;
- per source command family: what it was realised as in this build — the activity class, the property encoding the package's per-activity doc prescribed, the analyzer findings accepted — fetched at the version built against ([execution-guide.md § 2.2](execution-guide.md)). This record belongs to the build: a framework pack states the realisation at capability level only (its source guide's "Realised at execution" table) and never copies the class-level record, which is stale on the next package bump.

Scripting (mapping files, registries, validators) is the executor's choice for the run; the reports are the deliverable. One `migration/` folder in the build — the derived `source/` catalogs, the configuration answers, one report per project, the local feed's sources files — keeps them reviewable together and out of every project.

## Anti-patterns

1. Shipping placeholder targets, or authoring test rows from genome defaults, when the Source Map names a reachable export (rules 1, 3).
2. Reading catalogs that sat beside the genome instead of deriving them from the export (§ Migration preflight); a stale copy migrates yesterday's locators.
3. Hand-typing selectors into XAML or definition files; the OR CLI and the derivation rules are the only path (rule 6).
4. Widening a test case's argument set to fit the source layout instead of mapping onto the existing arguments and configuration defaults (rule 5).
5. Declaring a target "done" without confidence label and healing-pass note (rule 2), or reporting migrated definitions done without a per-family verdict (§ Verifying targets).
6. Mapping a composite source step to the nearest single activity — type-ahead as type + click-first-entry, custom list as `SelectItem`, menu path as one click, found row as a stored row number — or building a type-ahead or option pick without the verify sub-step; a wrong entry accepted silently is the costliest migration failure (§ Composite interactions).
7. Sending keystrokes to the window instead of the focused element, or keeping the source's page-scrolling keys (§ Composite interactions, keystrokes row).
8. Spending a Check Element / Check App State activity — and a guessed target — on a check the acting activity's own `VerifyOptions` performs, or verifying a pick against the option's text leaf instead of the field's value display (§ Verification).
9. Typing a whole date into a segmented widget's wrapper with the source's click offset, or scoping around a leaf its label already names (§ Element Scope).
10. Registering one element per source step, source window or activity type, one screen per source window, or one element per field value — and copying a composite pattern's activities into every step instead of one helper workflow (§ Object Repository identity).
11. Reporting a test migration done without the result parity table, or with a hand-typed table; evidence not findable by checkpoint id is not comparable evidence (§ Result parity).
12. Regenerating a workflow after it was linked, or treating a link command's success as proof that the links landed (§ UI targets); re-registering a changed definition with the create command and assuming the store now holds it (§ Object Repository identity rule 4).
13. Emitting one activity per source step — a Check for every wait, an assertion that compares the expected value with itself, an activity for a label or a comment (§ Source steps that are not UI actions).
14. Deriving an activity's XAML from a card snippet or from memory instead of from the default-XAML command *and* the package's per-activity doc — a generator turns one unchecked fragment into hundreds of defects that validate, build and pack ([execution-guide.md § 2.2](execution-guide.md)).
15. Letting a secret reach the working folder because only the variable table was refused while the step text still carries it (§ Migration preflight); shipping a declared out-argument that no path ever writes (§ Source steps that are not UI actions).
16. Dropping source data, or moving per-scenario values into configuration, to get a data-driven test case under the argument cap (§ Test data).
17. Treating a reachable application as a precondition — a run finishes with `offline-unverified` verdicts — or reporting a shape confirmed on a comparable instance as if the target application had confirmed it (§ Verifying targets).
18. Selector-shape mistakes — borrowed identifier on a derived element, fuzzy selector with no anchor, inherited inner text matched on a broad tag, tightened or loosened source criteria, widget wrapper and leaf flattened into one tag, scope derived per screen, grid markup assumed from the application's name — are prohibited where the rule lives: [selector-translation-guide.md](selector-translation-guide.md) rules 2, 5, 8, 9, 12, 13, 14. Copying passwords or dropping account identity: [genome-format-guide.md § Platform Dependencies](genome-format-guide.md). Letting a seed definition's fields survive into offline-built elements: [offline-definition-workarounds-guide.md](offline-definition-workarounds-guide.md).
19. Building a count, a wait, a flag, a case rule or a comparison literal from the genome's wording or a rendering without reading it from the source object — an empty rendering is not an absent value, a paraphrased status text never matches the application's, and a case-insensitive test built as case-sensitive rejects valid input (§ Migration preflight step 4). Building a scripting wrapper's verbs as a library of verbs instead of UI activities on the elements its identities name (§ UI targets pipeline step 1).
