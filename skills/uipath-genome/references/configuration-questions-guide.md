# Configuration Questions Guide — never skipped

Step 1.3 of [execution-guide.md](execution-guide.md): after preflight discovery (1.2), before the target project is resolved (1.4). Bare step and section numbers below are that guide's. `prepare` asks the same questions, as far as the user answers them, and writes the rest into the readiness file ([prepare-guide.md](prepare-guide.md)).


Ask before writing any code, creating any project, or installing any package. This step runs in every execution, including when the genome's Configuration Questions section is the stub line, because the scaffolding questions below do not come from the genome.

Four groups of questions, asked in this order — five in a refactor:

**Genome questions** — every numbered question in the genome's Configuration Questions section but a withdrawn one. Absent only when that section is the stub line. A question with a default per environment is answered for each: the build runs with the value of the environment it builds in, and the open items carry the others.

**Open decisions** — after the genome questions: each open entry of the genome's Open Decisions in the business-outcome tier, and each in the material tier, that no answers file settles nor the user's choice of the SDD's defaults (rule 4a); in a refactor, the Rulings question asks the source defects among them. Options from the entry: what it `builds now:` first, then each `instead:`, none Recommended, since the owner rules. The defaults, an autonomous run's or the user's choice of them, answer none of these: the build follows the genome as written, the entry stays open, and the completion report lists it as unconfirmed, as it does an entry of the run-behaviour or reading tier, which is not asked. An answer is a genome edit (rule 4b). The entry forms: [genome-reading-guide.md § Open Decisions](genome-reading-guide.md).

**Refactor questions** — when the Source Map names a UiPath source, or the request asks to refactor a genome extracted from another framework, after the genome questions: the rulings on each component's source defects, the run modes, the run record and the connections' identities, [refactor-guide.md § Refactor questions](refactor-guide.md). The targets are the genome's Components and Build With rows, and they decide which split and scaffolding questions follow.

**Split questions** — asked once per flow when the genome's Transactional Shape is not the stub, after the genome questions and before any scaffolding question, because the project list depends on every flow's answers: [transactional-execution-guide.md § Split questions](transactional-execution-guide.md).

**Scaffolding questions** — always asked, for every project the genome will create or the split answer materialises (each component of a process genome, each project a split adds, the single test project). They are asked once per owning skill and the answer applies to all its projects; a project gets its own answer only where it differs (an existing project to reuse, another location, the test project's packages), and each such question names the project:

Rules:

1. Group questions by topic (notifications, data sources, behaviour, environment, split, scaffolding).
2. **Write each question in plain words for a user who has not read this skill.** The tables are the decision, not the text to show: say briefly what is being decided and why it matters, explain any term the skill names (a table, file or mode) by what it is, and let each option's description say what the user gets and what it rules out in this run that the user would notice — a local run or a preview it blocks, a resource left for the deploy, a step left to a person. For each question give its real options, two to four, never a filler to make up a count. When the genome carries a default, or discovery produced a value, it is option one with "(Recommended)". Labels 1-5 words; header ≤ 12 characters.
2a. A question that touches the source — an extracted genome's Configuration Question, a ruling on a source defect, a refactor question, a question about the export itself — keeps the question alone on its first line and adds, after a blank line, a `Context:` section: a few labelled bullets with the facts the user needs to answer it, the labels chosen for that question, never a fixed set filled in where it does not fit. Source objects go by the names their author wrote, never by an object id or a line. Labels that often fit, to pick from and add to by what the question means: `Source process:` the source's workflow and step and the genome's step (`"Create Requisition" › "Wait for status", step 4, Submit requisition`); `Used for:` what a value does there; `Source value:` what the source runs with or does; `Also used in:` the other steps using a value; `Intent:` what a defective step evidently meant to do; `Extracted from:` and `Given:` when what the user supplied differs from what the genome was read from; `Affects:` what the answer changes in the build. The genome's Workflow and the Source Map's step table give the steps and their source objects.
2b. Every component, project and step a question or option mentions goes by the name the genome gives it — a component by its Component cell in the Components table, a step by its number and bold name (`step 4, Submit requisition`) — never by its position (`component 2`) or a role several could share (`the processing component`, `the consumer`); a role may follow the name when it helps (`Invoice Extraction, which takes the queue items`).
3. Present with `AskUserQuestion`, at most four per batch; collect a batch before showing the next. The first question, or a line before the first batch when how to answer is not asked, says how many questions the build asks, how many of them the SDD's defaults can take (rule 4a), and how many the files of answers settled (rule 4), so the user sees what is not asked again. When the questions run past three batches, the SDD or the readiness file leaves an item with a default unanswered, or a genome question defaults to the value the source runs with, the first batch is one question, how to answer them, since its answer decides which follow; it is not asked when the request already answers it. Its options: batch by batch; the defaults; the defaults with named overrides; given such an item, the SDD's defaults (rule 4a); given such a genome question, the source's values (rule 3a); and what the user can answer now, the rest written into the readiness file for others, the build then stopping as `prepare` does ([prepare-guide.md](prepare-guide.md)). The defaults option names each default that rules something out (rule 2), so a user who takes them knows what they give up. A choice of the defaults, with or without overrides, is the user's waiver the autonomous-run paragraph below requires. Under `prepare` it is always the first question, with its own options: what the user knows now, the rest left in the file (Recommended); the file only; every question now, with the offer to build once none is left. Each question it asks offers "Leave open", for an answer that sits with someone else. The file only and an autonomous run ask nothing and leave every question open in the file.
3a. **The source's values** answer each genome question whose default is a value the export holds, recorded "(source)". Every other question is asked: one whose default is "not in the export" or marked *[Inferred]*, which the source does not settle; a question between the source's way and another the target offers or requires, whatever its default, since the source never faced that choice; and the refactor, split and scaffolding questions, which shape the target build.
3b. **A question comes before those its answer settles or changes**, and an answer drops each later question it settles: among the scaffolding questions, the Source export and the Framework migration pack first, then the Live application; Source fidelity before Library layout, and Library layout before Library location. The split questions keep their own order.
4. Record answers as a `Configuration Answers` list with a `Scaffolding` group, in the hand-off's README as soon as they exist ([completion-report-guide.md](completion-report-guide.md)); the project-creation step in 1.4 receives the scaffolding answers, and every later build step receives the answers relevant to it. A choice the request makes that no question asks — a semantic step on migrated targets ([selector-translation-guide.md](selector-translation-guide.md) rule 12) — is recorded in the same list, as the request words it, so every part and check reads it from there. A file of answers the user supplies — named in the request, handed over at any batch, the preferences file the genome's `Preferences:` line names (read before the first question), or the SDD and the readiness file beside the genome (rule 4a) — is the user's answer, read when it arrives. For every file of answers: a question it answers is not asked, or not asked again, and is recorded "(from the answers file)"; a decision it states that no question asks is recorded, marked "(from the answers file)", as a rule the build follows; an answer that conflicts with a rule of this skill or the owning skill goes to the user with both statements, never resolved silently, and the list records the user's ruling. Each answer the user did not give in a batch carries its source's label: `(from the SDD)`, `(from the request)` or `(from the refactor answers)` for a decided value (the decided-values table), "(from the answers file)", "(SDD default)" (rule 4a), "(source)" (rule 3a), "(default)" (autonomous runs).
4a. **The SDD and the readiness file beside the genome.** An SDD `uipath-planner` wrote sits beside the genome, `<slug>-sdd.md` (a process genome's `<slug>-solution-sdd.md`), opening on its Action Required section, which it also writes into the SDD a `Designed in:` line links; a genome may have none; `prepare` writes the readiness file, `-readiness.md` in place of `-genome.md`. A component genome with a `Part of:` line reads its process genome's. In either, what follows an item's `Answer` is its answer: an option's letter, a value, `default` for a value item's default, or the person's own words. An item left blank is asked. The SDD tells whoever answers that the build uses each item's default until someone changes it, so how to answer offers the SDD's defaults (rule 3): taken, each blank item with a `Default:` or a `(built now)` option takes it, recorded "(SDD default)", and an open decision so taken keeps the genome as written and stays open, among the report's unconfirmed decisions ([completion-report-guide.md](completion-report-guide.md)); an item with an `Until answered:` line has no default and is asked. An SDD item `prepare` copied into the readiness file keeps its default there. An item `prepare` wrote whose options no longer hold on the machine that builds (another machine, other packages installed) is asked again. Genome edits not yet made are, unless the answer keeps what the genome builds now, which the build records and follows as it stands:
    - the answered or changed items of Business decisions, Material to supply and Preferences, in the SDD or under the readiness file's Decisions still open;
    - the readiness file's Genome edits: each gap ruled on, and each line of Edits for `uipath-planner`, with neither an `Applied` nor a `Not applied:` line.

    The Architecture decisions, Build setup and the configuration values are the build's and stay where they are (rule 4b). Before preflight discovery and any other question ([execution-guide.md § 1.1](execution-guide.md)), name the genome edits not yet made and ask whether `uipath-planner` applies them now, since only the user starts an edit. On a yes, invoke `uipath-planner` with "Apply the answers", the genome path, and the user's request and yes quoted verbatim, then stop; its edit starts the verb the request named again. On a no, and in an autonomous run, stop and name them, since a build past them would build what the answers change. A request that asks for them to be applied is the yes. An item marked `Not applied:` is one that edit could not make: the build follows the genome as written and reports the item ([completion-report-guide.md § Differences from the genome](completion-report-guide.md)).
4b. **An answer to an open decision is a genome edit**, whether an Open decisions question asks it or the refactor questions' Rulings do, and so is the ruling on a genome gap (1.2 step 9); none is when it keeps what the genome builds now (rule 4a). Once the batch holding one is answered, the build offers it as rule 4a offers the edits not yet made, and asks only what is still open when its edit starts the verb again. Every other answer is the build's: one that departs from what the genome states (a Technology per capability answer other than what the component's Target Applications row names; a Source fidelity answer that turns a library workflow the Interface lists into activities where it is called) is built as answered and listed under the report's Differences from the genome, and no genome section changes for it.
5. A default in the genome, a value found by discovery, a stub section, a "(Recommended)" option or a silent user never licenses skipping the question. Only the user answers it, or the user's waiver of an autonomous run (below) — except a question the decided-values table answers, answered from the genome, never asked, and recorded under its source's label; and one whose every other option cannot run what the genome needs (Portable, for a step that drives a desktop application), answered by that need and recorded with the reason.
6. Process genomes: ask the process-level genome questions first, then each component's genome questions in Components order, then the scaffolding questions per owning skill, with the per-project differences after them.
7. The split questions follow their own rules and record their own answer line: [transactional-execution-guide.md § Split questions](transactional-execution-guide.md).
8. **An empty or malformed setting that would change the flow, or fail only after business work has begun, is guarded, not defaulted.** A configuration value marked as a setting and left empty — "not in the export", or by the user's instruction — is built as a setting with an empty value. Where the empty value would silently change what the automation does instead of failing (an end-of-day time that compares as reached, a mode switch that falls to its else branch, a name list matched by containment that matches everything, a folder name that resolves to the drive root), and where a value of a fixed format would fail only where it is first used, after items have been worked (an end time that does not parse as `HH:mm`), the build checks it where the settings load and stops the run naming the setting and its source reference. The guards are listed in the report.

Autonomous runs — only when the questions are waived by the user: in the build request (for example "take the defaults", "run unattended"), or by the answer rule 3 asks for. An SDD's `Execution autonomy` never waives the build's questions: they are asked like any other.

Then take the default for every configuration and scaffolding question — the value the genome records as decided, recorded under its source's label (the decided-values table), otherwise the Recommended option — record "(default)" next to each default answer, ask nothing, and list them in the completion report. The split questions' defaults: [transactional-execution-guide.md § Split questions](transactional-execution-guide.md). Absence of a reply, a long-running session, or a subagent context alone is not authorisation to run autonomously; the build asks and waits. A default an autonomous run takes counts as the answer, but Platform resources is answered None unless the request allows writes to the tenant, since the run would create them in whatever tenant the session is signed in to; the deploy is no default ([execution-guide.md § 3.6](execution-guide.md)).
