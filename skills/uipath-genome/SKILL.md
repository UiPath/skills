# UiPath Genome — document, author, and execute automation blueprints

A genome is a markdown specification of an automation that an AI agent can consume to rebuild it: what it does, the business rules, the data that moves between parts, the platform resources it needs, how to verify it, and which UiPath skill builds each part. Genomes stay thin because the build skills carry the UiPath know-how; a genome describes *what*, the skills know *how*.

> **Read the referenced guide in full before acting.** This file routes; the guides carry the rules. Open the guide for the detected mode and the format guide, and read each whole file — do not grep them or work from memory.

## When to Use This Skill

- User has an existing UiPath project or solution and wants it documented, understood, or prepared for migration ("what does this solution do", "extract a genome", "document this process at high and low level")
- User describes an automation idea and wants a specification before anything is built
- User points at a `*-genome.md` file and wants the automation built from it
- User wants an existing genome updated, split into components, or re-extracted after the source changed

## Mode Detection

Determine the mode from the input, in this order:

1. **A `*-genome.md` path plus build intent** ("build", "execute", "implement", "follow") → **Execute**. Read [execution-guide.md](references/execution-guide.md).
2. **A directory, project file, solution manifest, or another framework's export** (`project.json`, `project.uiproj`, `.uipx`, `.flow`, `.bpmn`, `agent.json`, `Workflow.json`, `caseplan.json`, `uipath.json`; a Worksoft Certify export folder with `Manifest.txt` and `Processes.json`) → **Extract**. Read [extraction-guide.md](references/extraction-guide.md) and the framework's guides (§ Source Frameworks).
3. **A description, idea, SOP, or process narrative** with no source project → **Author**. Read [authoring-guide.md](references/authoring-guide.md).
4. **A `*-genome.md` path plus edit intent** ("update", "add a step", "split", "remove the inferred flags") → **Edit** in place per the edit tables in the authoring guide; re-extract instead when the user says the source changed.

A PDD or SDD, or a request to design a solution and derive tasks, is `uipath-planner`'s job, not a genome. Say so and stop.

Every mode reads [genome-format-guide.md](references/genome-format-guide.md) for content rules and [skill-mapping-guide.md](references/skill-mapping-guide.md) for Build With.

## Source Frameworks

Every framework a genome can be extracted from has a **source guide** (detection, inventory, signals, component → skill mapping, composite actions, UI target locators, test data) and, when it records UI locators, a **selectors guide** (its locator formats and the attribute-by-attribute translation into UiPath targets). **When a guide exists for the framework, read it in full in both modes:** Extract reads the source guide (and runs its inventory script first) to write the genome and a Source Map that names the framework, the export and every step's source objects; Execute reads the Source Map, resolves the export it names, derives the target catalog and the data catalog from the export with the same script, and reads the source guide's § Composite actions and the selectors guide together with [selector-translation-guide.md](references/selector-translation-guide.md) to expand composite steps and build the Object Repository targets. An extracted genome names its framework in the Source Map; that name selects the row and makes the execution a **migration**.

| Framework | Detection | Source guide | Selectors guide | Script |
|---|---|---|---|---|
| UiPath (Studio, Studio Web, Maestro, Agents, API workflows, Coded apps, Functions, Solutions) | `.uipx`, `project.json`, `project.uiproj`, `.xaml`/`.cs`, `.flow`, `.bpmn`, `caseplan.json`, `agent.json`, `Workflow.json`, `uipath.json` | [sources/uipath-source-guide.md](references/sources/uipath-source-guide.md) | none — UiPath targets are carried over, not translated (source guide § UI Target Locators) | — |
| Worksoft Certify (database export) | Folder with `Manifest.txt` (`Certify Version:`), `Processes.json`, `Layouts.json`, `MapObjects.json`, `ComponentActions.json` | [sources/worksoft-certify-source-guide.md](references/sources/worksoft-certify-source-guide.md) | [sources/worksoft-certify-selectors-guide.md](references/sources/worksoft-certify-selectors-guide.md) — web, SAP GUI, UI Automation desktop, Java | `scripts/certify-export-inventory.py` (`profile`, `cards`, `dump`, `targets`, `data`) — run before reading anything; never read `Processes.json` raw |

No row matches → say which framework the files appear to come from and that no guide exists yet; never improvise an extraction. Adding a framework: [sources/source-framework-contract.md](references/sources/source-framework-contract.md) — its guides join this table in the same change.

## Critical Rules

1. **Choose the genome level before writing.** One buildable project produces a component genome. Two or more projects, or a coordinator plus the automations it invokes, produce a process genome with one component genome per project. Never flatten a multi-project solution into one file and never split a single project into a process genome. **Exception — test components:** every test-case group of a process is its own component genome but all of them are folders of one test project `<ProcessName>.Tests`; the process genome states this in a Project layout table, and execution creates that project once. Level rules: [genome-format-guide.md § Two Levels](references/genome-format-guide.md).
2. **Read the source, do not ask about it.** In Extract mode read every non-generated file of every project before writing anything. Never ask the user what the automation does; the artifacts tell you. Ask only when a linked component is missing from disk.
3. **Infer complexity, never ask for it.** Authoring infers it from the description, extraction from source signals, both defaulting to the lower level when ambiguous. Escalate when later evidence demands it.
4. **Replication-grade detail, behavioural wording.** The genome must let a builder recreate the automation without seeing the source: field names, mappings, thresholds, conditions, substeps, and data in/out for every non-trivial step. Activity names, variable names, file paths, and code syntax are banned from the body; they belong only in the Source Map.
5. **Generalize hardcoded values into Configuration Questions.** Every path, URL, address, server, credential, queue, threshold, column name, and application choice becomes a numbered question with the source value as its default.
6. **Every section present, always.** Use the stub lines from the format guide for sections that do not apply. Never omit a section.
7. **One skill per Build With row, from the mapping guide only.** Use only skill names listed in [skill-mapping-guide.md](references/skill-mapping-guide.md). Operate-only skills (queues, assets, connections) go under Platform Dependencies, not Build With.
8. **Preamble and blueprint blockquote are mandatory** in every genome file, and Build With (or Components) precedes Workflow (or Process Map). This is what stops an agent from executing the steps instead of building the automation.
9. **Acceptance criteria are specific and testable.** Each names a concrete input, condition, or output from a workflow step, rule, transformation, or error handler. "Completes successfully" and "handles errors" are banned.
10. **Flag ambiguity, never leave gaps.** Write the best interpretation and append `*[Inferred]*`. Record the uncertainty in the Source Map.
11. **Write immediately, offer edits after.** Write the file(s) to the working directory, then ask "Want to adjust anything?". No previews, no confirmation before writing. Edits are targeted, in place, never a regeneration.
12. **Execution never edits the genome, and never skips the configuration questions.** During Execute the genome is read-only. Before any code is written or any project created, every question in the genome's Configuration Questions section is asked, followed by the scaffolding questions execution always asks for each project — location, target framework, expression language, and which activity packages and versions are installed where the automation will run, pinned or latest. A stub section, a genome default, a discovered value, or a silent user does not waive a question; only an explicit "take the defaults" in the current request does. Skill groups then advance without pausing; every acceptance criterion is assessed at the end.
13. **Extraction writes genomes, and the Source Map is the migration contract.** Recognition data, data rows and process inventories never enter the genome body and are not written beside it either: they are the export's, and execution reads them from the export. What extraction must record, in the Source Map, is everything execution needs to find them again — the framework, the export's root path and identity (version, database, date), and for every workflow step the source objects it was built from with their ids ([genome-format-guide.md § Source Map](references/genome-format-guide.md)). A Source Map that names the export but not the per-step objects has lost the migration.
14. **Execution on an extracted genome is a migration by default.** The Source Map names a framework with a source guide → preflight resolves the export (a scaffolding question with the recorded path as default), derives the target catalog, the data catalog and the step map from it with the source guide's script into the build's working folder, and every UI activity receives an Object Repository target inferred from the catalog, labelled `INFERRED (<confidence>)`, with the first live run as its healing pass. The export absent or declined → live capture where the application is reachable, placeholders otherwise, and the report says so. Inferred means inferred *from the control the element is*: an element the source never learned carries no identifier, only the matched text and a semantic description. Selectors are translated per technology (browser, SAP GUI, UI Automation desktop, Java) with the source's selectors guide and [selector-translation-guide.md](references/selector-translation-guide.md) — never by pattern-matching attribute names. Object Repository entries are created **once per node**, found before created ([source-migration-guide.md § Object Repository identity](references/source-migration-guide.md)). With a data catalog, the test project's data files (one per test-component folder) are filled from it through mapping files. Account user names become credential asset names plus environment per row; secrets are never copied. Procedure: [source-migration-guide.md](references/source-migration-guide.md).
15. **Build through the owning skill, verifiably.** Every build group invokes the skill named in Build With and performs its mandatory reads, including the installed package's per-activity docs; activity XML is never written from memory or from templates that were not derived from the skill's discovery commands. Subagents get the same obligation and report the reads they did.
16. **Composite source actions are patterns, not activities.** Source frameworks bundle multi-step interactions into one parameterised step (type-ahead pick, menu path, option list, find-row-then-act, keystrokes to the focused element). Extraction writes the full interaction contract into the substep (what is typed, how the entry is matched, which key confirms, the path levels, the row rule) per the source guide's composite-actions table; execution expands each into the pattern in [source-migration-guide.md § Composite interactions](references/source-migration-guide.md) with its verify sub-step, never the nearest single activity.
17. **One tag is one node, and a verify sub-step is a property of the activity.** Two defects account for most of the damage a UI migration does, and both look correct on the page. (a) A source catalog lists a widget as one row while the live UI renders it as a nest — wrapper, label, focusable leaf, value display, popup list; merging the wrapper's identifier with the leaf's caption into one tag yields a selector that matches nothing ([selector-translation-guide.md](references/selector-translation-guide.md) rules 14 and 16). Where the catalog cannot say which node owns which attribute, the target ships tag-only with its semantic description and owes a live pass — it never gets a plausible attribute to look finished (rule 13). (b) Verification belongs in `VerifyOptions` on the acting activity, observing the element that *shows the outcome* (the field's selected value, the next page's header) — a separate Check Element / Check App State activity is for a genuine branch only ([source-migration-guide.md § Verification](references/source-migration-guide.md)).
18. **A migrated target is unverified until the live driver has confirmed it, and the skill ships no checker.** With the application reachable, the owning skill's selector tools are the arbiters — `target-anchorable resolve-defaults` for the shape the driver itself would generate, `selector-intelligence get-selector-attributes` for the attributes a node really exposes, `evaluate` for uniqueness — and the executor records the verdict per element family before reporting a UI migration done ([source-migration-guide.md § Verifying targets](references/source-migration-guide.md)). Without the application, every element is labelled `offline-unverified` and the report says so. The mechanically decidable rules are listed in [selector-translation-guide.md § Checking a definition](references/selector-translation-guide.md) so that an executor can script a check for one run when the volume warrants it; the skill does not maintain such a script, because a passing structural check proves shape, not that anything matches the screen, and a checker's rule set drifts from the guide it claims to enforce.

## Workflows

### Extract (project or solution → genome)

1. Detect the source framework and the deployment unit with the source guide's Detection section. A `.uipx` or a folder of several projects is a solution → process genome.
2. Inventory every project; skip generated directories per the source guide.
3. Extract signals file by file with the source guide's signal tables: steps, control flow, error handling, data, targets, invocation edges, triggers, platform resources.
4. Build the call graph per project and the handoff graph across projects.
5. Infer complexity from the signal counts in the extraction guide.
6. Map signals to genome sections per the extraction guide; write the process genome first, then each component genome with `Part of:`, Interface, and Source Map.
7. Complete the Source Map as the migration contract: framework, export root path and identity, one row per workflow step naming its source objects with ids, and the counts the inventory reported (processes, windows, controls, recordsets, rows, credential accounts). Check it resolves: run the source guide's inventory into a scratch folder, then `scripts/genome-step-map.py <genome.md> --processes <inventory> --recordsets <recordsets> --out <scratch>` must map every step without a warning — a warning is a Source Map row whose reference does not resolve against the export. Nothing else is written beside the genome.
8. Write, then offer edits. Common follow-ups: "remove the inferred flags", "drop the Source Map for sharing", "this step is wrong".

Full procedure: [extraction-guide.md](references/extraction-guide.md); framework guides and scripts: § Source Frameworks.

### Author (description → genome)

Receive → choose level → infer complexity → extract → suggest platform capabilities → bounded follow-ups (simple 0-1, medium 1-2, complex 2-3 rounds, all questions of a round in one message) → generate → write → offer edits. Full procedure: [authoring-guide.md](references/authoring-guide.md).

### Execute (genome → automation)

Parse and validate the genome → preflight discovery (login state, host, installed packages and versions per build skill, build location next to the genome) → ask every configuration question: the genome's own, then the scaffolding questions per project (location, target framework, expression language, installed packages and versions, pin or latest) with `AskUserQuestion`, ≤4 per batch — never skipped; only an explicit "take the defaults" in the request makes the run autonomous → resolve one project (component) or one solution with one project per non-test component plus a single test project holding every test component as a folder (process); libraries pack first and consumers install them from a local feed → plan skill groups → build each group by invoking the owning skill with the assembled context and its mandatory reads → when the Source Map names a framework with a source guide, resolve the export and derive the target catalog, data catalog and step map from it into the build's working folder → migrate UI targets from the catalog into the Object Repository, one element per node, reading the framework's selectors guide and § Composite actions (§ Source Frameworks) → migrate test data from the data catalog into the test project's folders (credential assets per account) → wire handoffs → assess every acceptance criterion → for migrated test components, generate the static checkpoint mapping per test case (source checkpoint → UiPath assertion → evidence artifact) → report. Full procedure: [execution-guide.md](references/execution-guide.md); target and data migration: [source-migration-guide.md](references/source-migration-guide.md).

## Anti-patterns

1. **Asking the user what the project does, or which complexity it is.** Read and infer.
2. **Previewing before writing.** Write, then offer edits.
3. **Code in the body.** "Uses ReadPDF", "Calls Main.xaml", `Amount > 10000 AndAlso …`, file paths in Workflow. Translate to behaviour; provenance goes to the Source Map.
4. **Treating Integration Service as an application.** Resolve to Salesforce, ServiceNow, SAP.
5. **Compressing steps to hit a count, or flat one-liners for multi-field operations.** Minimums are floors; substeps carry the detail a builder needs.
6. **Disconnected rules and handlers.** Attach every business rule and error handler to its step.
7. **Retired skill names in Build With** (`uipath-rpa-workflows`, `uipath-coded-workflows`, `uipath-coded-agents`). Use the mapping guide's names; a stale name will not resolve at execution.
8. **Process genome without Handoffs, or component Interface that disagrees with Handoffs.** The handoff table is the contract that makes the components composable.
9. **Stopping between execution groups, or building before configuration answers exist** — including scaffolding a project with the init command's default framework and package versions instead of the ones the user was asked about.
10. **Producing a genome when the user brought a PDD/SDD or asked for a solution design.** That is `uipath-planner`.
11. **Extracting behaviour but not the provenance** — a Source Map without the export's location or without per-step source objects — so that execution cannot find the locators and recordsets the export carried and ships placeholders and invented rows. Its mirror: copying the export's catalogs beside the genome, where they go stale and duplicate what execution reads from the export anyway.
12. **Copying passwords into data files, or collapsing every scenario onto one login.** Account identity per row, secret in a credential asset.
13. **Authoring activity XML from memory or bespoke templates** instead of through the owning skill's discovery commands and package docs.
14. **Naive one-to-one translation of composite source steps**: type-ahead as type-then-click-first-entry, a custom list as a native select, a menu path as one click, a found row as a stored row number. Validates, runs, does the wrong thing.
15. **Inventing an identifier for an element the source never learned** by lifting `id` or `data-automation-id` from a catalog control that looked related. Worse than no identifier: it suppresses the text match and semantic fallback.
16. **Verifying a pick on the option's text instead of the field's value display**, typing a date into a segmented widget's wrapper, or scoping on a component-type wrapper shared by every instance — the widget anatomy in [selector-translation-guide.md](references/selector-translation-guide.md) rule 16 names the node each step uses.
17. **Shipping or maintaining a conformance script in the skill.** The checkable rules are listed in the guide; a run may script them, the skill does not.
18. **One Object Repository element per source step, source window or activity type.** Elements are nodes: the same control clicked and typed into is one element, a control shared by many pages is one element on one screen, a widget role that recurs per field is one parametrised element inside one helper workflow ([source-migration-guide.md § Object Repository identity](references/source-migration-guide.md)).
