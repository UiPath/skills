# Templates — Studio library coded-workflow service

Three files in `Coded Workflow Service/`. Substitute:

- `<Ns>` — namespace, default `<ProjectName>.CodedWorkflowService`
- `<Name>` — PascalCase service name, e.g. `Razor`
- `<servicename>` — the member consumers type, e.g. `razor`

---

## `I<Name>Service.cs`

```csharp
using System;

namespace <Ns>
{
    public interface I<Name>Service
    {
        /// <summary>
        /// One line on what it does, in the caller's terms.
        /// </summary>
        /// <param name="templateKey">What it is, and any constraint worth knowing.</param>
        void AddRazorTemplate(string templateKey, string templateSourceText);

        /// <summary>
        /// Workflows with a single Out argument return it directly.
        /// </summary>
        string PopulateRazorTemplate(
            string templateKey,
            object inputObject,
            Type modelType = null,
            string templateSourceText = null);
    }
}
```

Surface design:

- Name methods for what the caller wants, not the workflow file. `Populate Razor
  Template.xaml` → `PopulateRazorTemplate`.
- Optional workflow arguments become optional parameters with `= null`/defaults.
- XML-doc every member — it is what consumers see on hover, and it is the only
  documentation a package consumer gets.

## `<Name>Service.cs`

```csharp
using System;
using UiPath.CodedWorkflows.Interfaces;

namespace <Ns>
{
    /// <summary>
    /// Exposes this library's workflows to consuming coded workflows as `<servicename>.*`.
    ///
    /// Workflows are invoked through the runtime, never constructed directly: a `new`'d
    /// CodedWorkflow has null services (Log, workflows, system all NRE) because
    /// CodedWorkflowBase.services is only populated by OnWorkflowInitialization when the
    /// runtime hosts the workflow.
    ///
    /// WorkflowRunnerService is generated by the Studio compiler from this project's
    /// workflow files. It resolves the correct target assembly via ILibraryAssemblyProvider,
    /// which is necessary because this class compiles into <Name>.Core.dll while the
    /// generated MapFilePathToActivity_... lives in <Name>.dll.
    /// </summary>
    public class <Name>Service : I<Name>Service
    {
        private readonly WorkflowRunnerService _workflows;

        public <Name>Service(ICodedWorkflowServices services)
        {
            if (services == null) throw new ArgumentNullException(nameof(services));
            _workflows = new WorkflowRunnerService(services);
        }

        public void AddRazorTemplate(string templateKey, string templateSourceText)
        {
            if (string.IsNullOrEmpty(templateKey))
                throw new ArgumentException("templateKey is required.", nameof(templateKey));
            if (string.IsNullOrEmpty(templateSourceText))
                throw new ArgumentException("templateSourceText is required.", nameof(templateSourceText));

            _workflows.Add_Razor_Template(templateKey, templateSourceText);
        }

        public string PopulateRazorTemplate(
            string templateKey,
            object inputObject,
            Type modelType = null,
            string templateSourceText = null)
        {
            if (string.IsNullOrEmpty(templateKey))
                throw new ArgumentException("templateKey is required.", nameof(templateKey));
            if (inputObject == null)
                throw new ArgumentNullException(nameof(inputObject));

            return _workflows.Populate_Razor_Template(
                templateKey, inputObject, modelType, templateSourceText);
        }
    }
}
```

`WorkflowRunnerService` sits in the project's root namespace (e.g.
`Roboyo.Razor.Activities`). If `<Ns>` is nested beneath it, no `using` is needed; otherwise
add one.

Keep the class comment. It is the reason the next person does not "simplify" this into
`new My_Coded_Workflow()` and reintroduce the null-services bug.

## `<Name>Registry.cs`

```csharp
using System;
using System.Activities;
using System.Collections.Generic;
using <Ns>;
using UiPath.CodedWorkflows;

[assembly: CodedWorkflowsServiceRegistry(typeof(<Name>Registry))]

namespace <Ns>
{
    public class <Name>Registry : ICodedWorkflowsServiceRegistry
    {
        internal const string ServiceName = "<servicename>";

        public IEnumerable<string> AutoImportedNamespaces => new string[]
        {
            "<Ns>"
        };

        public IDictionary<string, Type> AutoImportedTypes => new Dictionary<string, Type>
        {
            { ServiceName, typeof(I<Name>Service) }
        };

        public void Register(
            ICodedWorkflowsServiceLocator serviceLocator,
            ActivityContext initialActivityContext)
        {
            serviceLocator.RegisterType<I<Name>Service, <Name>Service>();
        }
    }
}
```

The assembly attribute must sit **after** the `using` directives and **before** the
`namespace` declaration. It is a plain assembly-level attribute — nothing generates it, and
Studio has no UI for it.

## Consumer snippet for the handover

```csharp
// in a coded workflow of a project referencing the published package
<servicename>.AddRazorTemplate("welcome-layout", layoutCshtml);
var html = <servicename>.PopulateRazorTemplate("welcome-body", model);
```

No `using`, no field declaration, no instantiation — `AutoImportedTypes` puts the member
there.
