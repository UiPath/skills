# Genome From SDD Guide — the genome of an agreed SDD

`author` reads this guide when the input is an agreed SDD (`## Planner Handoff` with `Status: ready`): inside `design`, on the turn after the SDD is `ready` when the request asks for the genome or a build ([sdd-writing-guide.md](../design/sdd-writing-guide.md) § Step 5). It also reads it when a request asks for the genome of an agreed SDD or to build one. The SDD decided the architecture; the genome restates it as the coding-agent spec and adds what only the genome holds (replication-grade substeps, composite UI contracts, the configuration questions, numbered acceptance criteria).

## Author from an agreed SDD

1. **Read the SDD whole**, with its Planner Handoff, and for a solution SDD (the root `*-solution-sdd.md`, `Project SDD role: root`) every child SDD it lists. A child SDD given as input (`Project SDD role: child`) resolves to the root its `Solution root SDD` row names: read that root and write the genome for the whole solution from it, saying so in one line ("<CHILD> is part of <ROOT>; writing the solution's genome from the root."). Then stop without writing when any of these holds:
   - **A `draft` SDD** — `Status: draft`, with blocking SME items. Name the blocking items; the genome is written once the SDD is `ready`.
   - **A missing root** — the `Solution root SDD` row names a path that does not exist. Name the path and ask for the root SDD.
   - **A missing or `draft` child** — a child SDD the root lists does not exist, or is not `Status: ready`. Name the child and, for a draft, its blocking SME items; the genome is written once every child is `ready`.
2. **Read `Execution autonomy` from the Planner Handoff.** It decides how the genome is finished:
   - **`autonomous`** — no follow-up rounds ([author-guide.md](author-guide.md) Step 8): every gap is written with `*[Inferred]*`, or carried as a Configuration Question with its default. After the review ([author-guide.md](author-guide.md) Step 10), the edits are offered in the closing summary, and the run does not wait for them.
   - **`interactive`, or no row** — [author-guide.md](author-guide.md) Steps 8 and 10 as written.
3. **The SDD's products and projects are the genome's.** Every resource the SDD's integrated-components tables mark for the build to create (an IXP model, an agent, an API workflow, a function, a custom connector) is a component of its own; a resource that already exists is a Platform Dependency. Its components, counted as this item states, set the level ([author-guide.md](author-guide.md) Step 4) and the Build With / Components rows; Steps 5–7 never re-select a product the SDD placed. Its delivery model holds for every row.
   - **A dispatcher and a performer are ONE component.** Two projects that are the producer and the consumer of one flow — a dispatcher that adds items to a queue and a performer that works them — are one `uipath-rpa` component, never two components. They count as one for the level: an SDD whose only projects are a dispatcher and its performer gets one component genome, never a process genome. They are the split the SDD chose for that flow ([skill-mapping-guide.md](../shared/skill-mapping-guide.md) rule 3), recorded as item 4 states. An RPA Master Project is therefore one `uipath-rpa` component:
      - its flows are the ones [transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 12 finds — a hand-off of the same item to its next stage stays one flow unless a person decides between the stages;
      - each flow's `Decided:` line names the split and, when the SDD names the sub-projects, their chain under the SDD's project names ([transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 8);
      - the process genome's Deployment, when the genome has other components, lists the SDD's project names.

   **An SDD its build skill builds from** ([skill-mapping-guide.md § Build Skills](../shared/skill-mapping-guide.md#build-skills), "Built from the SDD"; a Case Management SDD is one) is one component whose Build With is that skill. Its Interface names that SDD's path, relative to the genome, as the component's build input: `uipath-genome` hands the SDD to the build skill, which builds from it. The genome restates the design as the SDD holds it and never redesigns it. Standalone, it is a component genome named after the SDD — unless its integrations section marks resources the build creates (a new agent, API workflow, function or IXP model). Each such resource is a component of its own, so the genome is then a process genome named after the SDD, the SDD-built component beside them. A solution child is one component of the solution's process genome.
4. **The SDD's decisions are recorded, not reopened.** The split it chose is each flow's `Decided:` line with the SDD section as its source ([transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 8). A single project with no queue is A; a dispatcher and a performer project is B; one project that fills and works its own queue is C. The implementation mode, the package versions and the queue design go into the sections that hold them (Build With rationale, Configuration Questions defaults, a process genome's Deployment), so `uipath-genome` takes them as answered. The delivery model stays in the SDD: the genome names no platform.
4a. **Every business rule carries over with its ID.** Each row of the SDD's Business Rules homes ([business-rules-guide.md § Homes per template](../design/business-rules-guide.md#homes-per-template)) is a Business Rules entry of the component that applies it, under the step it fires in, ending with its ID — `(BR-012)` — so the build and its tests trace it back. A Rules Not Carried row is not carried.
5. **Gaps carry over, marker and all, once.**
   1. **Which.** Every `[SME REVIEW]` or `[DEFAULT]` item of the SDD that touches a genome section, except a default sub-rule 4 makes a Configuration Question or a fact.
   2. **Where and how.** Written once — in the one genome file and section its decision lives in, across a process genome and its components — as `*[Inferred: D<n>]*` followed by the item's text with its marker verbatim: `*[Inferred: D<n>]* (SDD [SME REVIEW]: <note>)`, `*[Inferred: D<n>]* (SDD [DEFAULT]: <note>)`. It is an Open Decisions entry ([genome-questions-guide.md § Open Decisions](../shared/genome-questions-guide.md)). Other sections that depend on it name the genome section that holds it.
   3. **Its id.** An item of the SDD's Action Required keeps its id when the SDD's items all land in one genome file; otherwise it takes the next number in the file it lands in, matched by what it asks ([open-questions-guide.md](../shared/open-questions-guide.md) Writing Rule 1). Any other point takes the next number.
   4. **Values.** An SDD default an operator sets per environment (a host, mailbox, folder, cap, a schedule's time zone) becomes a Configuration Question with that default, never an entry as well. An SDD item of that kind keeps its id as an entry that reads `withdrawn: asked as Configuration Question <n>`, and its mark names the question (`*[Inferred: CQ<n>]* (SDD [SME REVIEW]: <note>)`). A default the design fixed (a timeout, an attempt count) is a fact in its step ([genome-questions-guide.md](../shared/genome-questions-guide.md) § Configuration Questions).
   5. **Left in the SDD.** An item that touches no genome section (an SDD-only deployment or test-environment detail) stays in the SDD. [author-guide.md](author-guide.md) Step 8 asks nothing the SDD already left to an SME.
5a. **Build Assumptions carry over the same way, once each; the strict check fails a row that is carried nowhere.** Every row of the SDD's Build Assumptions table is an Open Decisions entry. It goes in the genome file of the component whose skill the row's Confirmed By names (the process genome's when it spans components). The entry reads: `N. Can {the capability, as the row words it}? (run behaviour; answered by: {Confirmed By skill}, at build, before the steps that rely on it; Builds now: as designed; instead: {If It Does Not Hold}) — SDD Build Assumption A<n>`. Each step the row's Relied On By names carries `*[Inferred: D<n>]*`, naming that entry. The genome never states the capability as a fact.
6. **Apart from the `Genome` handoff row (item 7) and its Action Required section, written again from the genome ([sdd-from-genome-guide.md](../shared/sdd-from-genome-guide.md) item 6), the SDD is never edited.**
   - **An SDD a component is built from** is never written again from the genome, its Action Required included. Its items carry over as item 5 states, each keeping its `D<n>` id.

   A contradiction between the SDD and what the genome needs is named when edits are offered ([author-guide.md](author-guide.md) Step 10). Before offering edits, compare the genome with the SDD — every skill the SDD routes work to is in Build With or Components, every resource it names is in Platform Dependencies, and every error behaviour, split and integration agrees — and fix the genome wherever it disagrees.
7. **Name the genome after the SDD and record it in one handoff.**
   - **A single-product SDD:** `<PROCESS_NAME_KEBAB>-genome.md` beside the SDD.
   - **A solution SDD** (a root `<SOLUTION_NAME_KEBAB>-solution-sdd.md` and its child SDDs): one genome for the whole solution, named after the root — `<SOLUTION_NAME_KEBAB>-genome.md` beside the root SDD. It is a process genome with its component genomes in `<SOLUTION_NAME_KEBAB>-genome/` when Step 4 counts two or more projects, and a component genome otherwise ([genome-format-guide.md § File Naming and Location](../shared/genome-format-guide.md)). Never write one genome per child SDD.

   Write the `Designed in:` line, linking the SDD the genome is named after and carrying its fingerprint — for a solution, `sdd-fingerprint.mjs` run on the root, which covers the root and every child it lists ([genome-format-guide.md § Design Links](../shared/genome-format-guide.md)). Record the genome as `| **Genome** | <path> |`, the last row of that SDD's Planner Handoff table — for a solution, the root SDD's handoff only. The child SDDs are not edited. The strict check of [author-guide.md](author-guide.md) Step 10 runs once the `Designed in:` line is written, so it verifies the fingerprint.
8. **The genome write is a turn boundary.** What follows it: [sdd-writing-guide.md](../design/sdd-writing-guide.md) § Step 5 item 4 when `design` ran; otherwise [SKILL.md](../../SKILL.md) § Chaining.
