# Genome From SDD Guide — the genome of an agreed SDD

`author` reads this guide when the input is an agreed SDD (`## Planner Handoff` with `Status: ready`): inside `design`, on the turn after the SDD is `ready` ([sdd-writing-guide.md](../design/sdd-writing-guide.md) § Step 3), or when a request hands over an agreed SDD. The SDD decided the architecture; the genome restates it as the coding-agent spec and adds what only the genome holds (replication-grade substeps, composite UI contracts, the configuration questions, numbered acceptance criteria).

## Author from an agreed SDD

1. **Read the SDD whole**, with its Planner Handoff, and for a solution SDD (the root `*-solution-sdd.md`, `Project SDD role: root`) every child SDD it lists. A child SDD given as input (`Project SDD role: child`) resolves to the root its `Solution root SDD` row names: read that root and write the genome for the whole solution from it, saying so in one line ("<CHILD> is part of <ROOT>; writing the solution's genome from the root."). Then stop without writing when any of these holds:
   - **A `draft` SDD** — `Status: draft`, with blocking SME items. Name the blocking items; the genome is written once the SDD is `ready`.
   - **A missing root** — the `Solution root SDD` row names a path that does not exist. Name the path and ask for the root SDD.
   - **A missing or `draft` child** — a child SDD the root lists does not exist, or is not `Status: ready`. Name the child and, for a draft, its blocking SME items; the genome is written once every child is `ready`.
2. **Read `Execution autonomy` from the Planner Handoff.** It decides how the genome is finished:
   - **`autonomous`** — no follow-up rounds ([author-guide.md](author-guide.md) Step 6): every gap is written with `*[Inferred]*`, or carried as a Configuration Question with its default. After the review ([author-guide.md](author-guide.md) Step 8), the edits are offered in the closing summary, and the run does not wait for them.
   - **`interactive`, or no row** — [author-guide.md](author-guide.md) Steps 6 and 8 as written.
3. **The SDD's products and projects are the genome's.** Every resource the SDD's integrated-components tables mark for the build to create (an IXP model, an agent, an API workflow, a function, a custom connector) is a component of its own; a resource that already exists is a Platform Dependency. Its project list sets the level ([author-guide.md](author-guide.md) Step 2) and the Build With / Components rows; Steps 3–5 never re-select a product the SDD placed. Its delivery model holds for every row. Two projects that are the producer and the consumer of one flow — a dispatcher that adds items to a queue and a performer that works them — are one `uipath-rpa` component: they are the split the SDD chose for that flow ([skill-mapping-guide.md](../shared/skill-mapping-guide.md) rule 3), recorded as item 4 states, never two components. An RPA Master Project is therefore one `uipath-rpa` component: the flows are the ones [transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 12 finds — a hand-off of the same item to its next stage stays one flow unless a person decides between the stages — and each flow's `Decided:` line names the split and, when the SDD names the sub-projects, their chain in hand-off order under the SDD's project names ([transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 8: `B, one PO — the SDD §10: Dispatcher → DUPerformer → OutputPerformer`), and the process genome's Deployment lists the SDD's project names, so nothing the SDD decided is lost.
   - **A Case Management SDD** (its first section is `## Section 1: Case Definition`) is one component whose Build With is `uipath-maestro-case`. Its Interface names that SDD's path, relative to the genome, as the component's build input: `uipath-genome` hands the SDD to `uipath-maestro-case`, which builds the case from it. The genome restates the case as the SDD designed it and never redesigns it. Standalone, it is a component genome named after the SDD — unless its Section 4 marks resources the build creates (a new agent, API workflow, function or IXP model): each is a component of its own, so the genome is a process genome named after the SDD, the case component beside them. A solution child is one component of the solution's process genome.
4. **The SDD's decisions are recorded, not reopened.** The split it chose is each flow's `Decided:` line with the SDD section as its source ([transactional-shape-guide.md](../shared/transactional-shape-guide.md) rule 8): a single project with no queue is A; a dispatcher and a performer project is B; one project that fills and works its own queue is C. The delivery model goes to Platform Dependencies' lead-in (component genome) or Deployment (process genome); the implementation mode, the package versions and the queue design go into the sections that hold them (Build With rationale, Configuration Questions defaults, a process genome's Deployment), so `uipath-genome` takes them as answered.
5. **Gaps carry over, marker and all, once.** Every `[SME REVIEW]` or `[DEFAULT]` item of the SDD that touches a section is written once — in the one genome file and section its decision lives in, across a process genome and its components — as `*[Inferred]*` followed by the item's text with its marker verbatim — `*[Inferred]* (SDD [SME REVIEW]: <note>)`, `*[Inferred]* (SDD [DEFAULT]: <note>)`. [author-guide.md](author-guide.md) Step 6 asks nothing the SDD already left to an SME. Other sections that depend on it name the genome section that holds it. An item that touches no genome section (an SDD-only deployment or test-environment detail) stays in the SDD. An SDD default an operator sets per environment (a host, mailbox, folder, cap) becomes a Configuration Question with that default; one the design fixed (a timeout, an attempt count) is a fact in its step ([genome-format-guide.md](../shared/genome-format-guide.md) § Configuration Questions).
6. **Apart from the `Genome` handoff row (item 7), the SDD is never edited.** A contradiction between the SDD and what the genome needs is named when edits are offered ([author-guide.md](author-guide.md) Step 8). Before offering edits, compare the genome with the SDD — every skill the SDD routes work to is in Build With or Components, every resource it names is in Platform Dependencies, and every error behaviour, split and integration agrees — and fix the genome wherever it disagrees.
7. **Name the genome after the SDD and record it in one handoff.**
   - **A single-product SDD:** `<PROCESS_NAME_KEBAB>-genome.md` beside the SDD.
   - **A solution SDD** (a root `<SOLUTION_NAME_KEBAB>-solution-sdd.md` and its child SDDs): ONE genome for the whole solution, named after the root — `<SOLUTION_NAME_KEBAB>-genome.md` beside the root SDD. It is a process genome with its component genomes in `<SOLUTION_NAME_KEBAB>-genome/` when Step 2 counts two or more projects, and a component genome otherwise ([genome-format-guide.md § File Naming and Location](../shared/genome-format-guide.md)). Never write one genome per child SDD.

   Write the `Designed in:` line, linking the SDD the genome is named after and carrying its fingerprint — for a solution, `sdd-fingerprint.mjs` run on the root, which covers the root and every child it lists ([genome-format-guide.md § Design Links](../shared/genome-format-guide.md)) — and record the genome as `| **Genome** | <path> |`, the last row of that SDD's Planner Handoff table — for a solution, the ROOT SDD's handoff only; the child SDDs are not edited. The strict check of [author-guide.md](author-guide.md) Step 8 runs once the `Designed in:` line is written, so it verifies the fingerprint.
8. **The genome write is a turn boundary.** What follows it: [sdd-writing-guide.md](../design/sdd-writing-guide.md) § Step 3 item 4 when `design` ran; otherwise [SKILL.md](../../SKILL.md) § Chaining.
