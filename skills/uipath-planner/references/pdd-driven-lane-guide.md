# PDD-driven Lane Guide

When the planner detects an SDD at entry, run Lane A: read the SDD, derive tasks, and hand off to specialists. Lane A starts when input contains `## Planner Handoff` or `<!-- planner-handoff:v1 -->`; either signal suffices. See SKILL.md for the entry guard.

## Step 1 — Read the SDD's Planner Handoff header

The header is near the top: immediately after `## Document History` in per-project SDDs, or section 2 after Solution Overview in solution-overview SDDs.

**Status gate:** `Status: draft` means Phase D is unfinished (missing sections/completeness check or an open architecture-blocking SME item). Do not derive tasks. Tell the user the SDD is unfinished and offer **resume Phase D** (finish sections, resolve blocking SME items, run the superset check, set Status to ready) or **regenerate from the PDD**. Missing Status means `ready` for backward compatibility; note this in the Step 8 summary. Only explicit or legacy-implied `ready` proceeds. A `Blocking = yes` row in a `ready` SDD contradicts its Status; treat it as `draft`.

A ready SDD may contain `## Action Required — SME Review Items` with default-carried rows. Do not refuse it or create tasks for them. For each task whose SDD section is named by an item, append: `Assumption pending SME confirmation: <ITEM> — proceeding with default <DEFAULT>`. List open items in the closing summary.

Read these fields:

| Field | Handling |
|---|---|
| **Status** | Apply the gate above. |
| **Solution root SDD / Solution ID / Project SDD role** | Define scope. `child` resolves the root and uses the Step 3 root algorithm; `root` makes this file's Project Inventory + SDD Index canonical. `Solution ID` must match root and children. |
| **Execution autonomy** | `interactive` → plan-mode review; `autonomous` → emit live tasks directly. |
| **Delivery model** | `cloud` / `automation-suite <version>` / `standalone` / `unspecified`; propagate as a platform constraint into every specialist task prompt. |
| **SDD scope** | `single-product` → one file/task list; `solution` → overview plus per-project SDDs, with tasks spanning all projects. |
| **Project list section** | Location of the unified project list, such as `§10`, `§3 + §7`, or `Project Inventory`. |
| **Tasks file** | Destination for `<process>-tasks.md`; respect Phase D's path. |
| **Build handoff** | Case SDDs carry this instead of `Tasks file`; the case build writes `caseplan.json`. Parse it for provenance; never resolve it to a path. |
| **Generated by** | Use in the summary for provenance. |
| **Generation date** | `YYYY-MM-DD`; show in the summary. |

For missing or malformed fields, default `Execution autonomy` to `interactive`, `Delivery model` to `unspecified` (propagate no constraint), `SDD scope` to `single-product`, infer `Project list section` from the template, and default `Tasks file` to `<sdd-basename-without-sdd>-tasks.md`. For a Case SDD with `Build handoff`, default `Tasks file` silently and do not report it as defaulted. Track every other default in a session-local list; Step 8 surfaces it so the reviewer can correct the SDD. Do not silently swallow defaults.

On resume, an explicit user request for review or interactive handling overrides `Execution autonomy`; do not re-ask.

## Step 2 — Check for an existing tasks.md

If `Tasks file` exists, ask via `AskUserQuestion`:

> A task list already exists at `<tasks-file>`. How should I proceed?
>
> 1. **Continue with the current task list** *(recommended)* — pick up where you left off; checkbox state preserved
> 2. **Regenerate from the SDD** — discard the current task list and rebuild from the SDD; checkbox state lost (or preserved per identity matching, see [plan-and-tasks-format.md → Regenerate logic](plan-and-tasks-format.md#regenerate-logic-pdd-driven-lane-only))

Choice 1: read the existing file, recreate live `TaskCreate` calls with status preserved, and do not re-parse the SDD. Choice 2: parse the SDD, run identity matching against the old file, preserve completed work, write the new file, and emit live tasks; see [plan-and-tasks-format.md](plan-and-tasks-format.md) for regeneration and archive-footer rules. If absent, proceed to Step 3.

## Step 3 — Parse the SDD project list

**Solution scope:** never derive from one file. Run this algorithm:

1. Resolve the root: `Project SDD role: child` → open `Solution root SDD` (fallback: `*-solution-sdd.md` beside the file, else ask the user); `root` or overview file → use it.
2. Read the root's Project Inventory and Per-Project SDD Index.
3. Verify every indexed child exists, has the same `Solution ID`, and is `Status: ready`. If any is missing, mismatched, or `draft`, STOP and ask via `AskUserQuestion`: finish/regenerate the child first *(recommended)*, or derive a partial list with exclusions named explicitly in the plan header.
4. Read each child's detailed architecture from its `Project list section` (nodes, workflows, tools, pages, schemas, integrated components); the overview alone is insufficient.
5. Merge shared resources and cross-project dependencies from the root's Shared Assets & Queues and Cross-Project Data Flow. Create each shared queue/asset/connection once at solution level; order edges build-before-consume.
6. Write exactly one canonical tasks file: the root's `Tasks file`. Never write per-project task files. Put end-to-end testing and packaging last, after all component build and testing tasks.

For `single-product`, read the header's `Project list section`; the project list is canonical and every project goes to the appropriate specialist.

| Template | Project list location |
|---|---|
| RPA single project | §11 Project Structure (workflow inventory) |
| RPA Master Project | §10 Master Project Architecture (sub-project list) + §11 Workflow Inventory per sub-project |
| Flow | §3 Nodes Inventory + §7 Integrated Components |
| BPMN | §4 Activities Inventory + §9 Integrated Components |
| Case | §2: Stages & Tasks + §4: Integrations |
| Agent | §9 Project Structure + §3 Tools |
| Coded App | §10 Project Structure + §9 Integrated Components |
| API Workflow | §10 Project Structure + §5 Connectors |
| Solution overview | Project Inventory + Cross-Project Data Flow |

For Case Management, the case is the project. Read Section 2 for stage/task implementation and Section 4 for external dependencies; do not expect legacy `Project Structure`, `Tasks Grid`, or `Task Type Registry` tables.

Extract per project: name (for the `Identity` tuple), Product (`RPA` / `Flow` / `BPMN` / `Case` / `Agent` / `Coded App` / `API Workflow` / `IXP` / `Function`), subtype (RPA `Process` / `Library` / `Test Automation`), role, framework (`Sequence` / `REFramework` for RPA), input/output queues for Master Project sub-projects, and workflows/nodes/tools/pages/steps.

## Step 4 — Pick the multi-skill pattern

Use [multi-skill-patterns-guide.md](multi-skill-patterns-guide.md):

| SDD shape | Pattern |
|---|---|
| Single RPA project, no deploy hint in §16 | Pattern 1, dropping deploy steps |
| Single RPA project, §16 specifies Orchestrator deploy | Pattern 1 |
| RPA Master Project | Pattern 1 per sub-project, integrated by shared queues; cross-project deploy via `uipath-solution` (single `.uipx`) |
| Flow with §7 Integrated Components referencing unbuilt resources | Pattern 2 |
| Flow with pre-existing §7 components | Pattern 3 |
| BPMN with §9 components referencing unbuilt resources | Pattern 2, substituting `uipath-maestro-bpmn` for `uipath-maestro-flow` |
| BPMN with pre-existing §9 components | Pattern 3, substituting `uipath-maestro-bpmn` |
| Case with §4 integrations referencing unbuilt resources | Build external components first, then `uipath-maestro-case`; keep inline `action`, connector, timer, and child-case details with the Case specialist |
| Case with pre-existing or unresolved portable-intent §4 integrations | Build `uipath-maestro-case` first; unresolved IDs/folders travel as review items for registry discovery |
| Filled “IXP / Document Understanding Models” table | Add one IXP model build + validation task per model via `uipath-ixp`, before its consumer |
| Filled “Coded Functions” table | Add one Function build + validation task per function via `uipath-functions`, before its consumer |
| Agent with RPA tools in §3 Tools | Pattern 5 |
| Coded App | Coded App build + `uipath-solution` deploy + testing when wrapped in `.uipx`; otherwise `uipath-coded-apps` self-deploys |
| API Workflow | API Workflow build + `uipath-solution` publish + testing |
| Solution scope | Compose project patterns in cross-product dependency order |

**Deploy routing is constraint-gated.** Before emitting deploy tasks, check `Delivery model` against [platform-availability-guide.md](platform-availability-guide.md). If Solutions (`.uipx`) is blocked for `standalone`, Automation Suite older than 2.2510, or a user exclusion, replace every `uipath-solution` deploy/publish step above with per-package Orchestrator publish via `uipath-platform`. Apply this also to hand-written SDDs whose §18 Constraint Gate did not rewrite it.

## Step 5 — UI element targeting (only when §9 contains UI applications)

If §9 Application Inventory names web, desktop, or Citrix applications and a `uipath-rpa` workflow interacts with them, ask the following as one batched `AskUserQuestion` call (up to three questions):

> *Question 1 — App type:* What kind of application are we automating?
> 1. Web / browser app
> 2. Desktop app
> 3. Citrix / remote session
>
> *Question 2 — Targeting approach:* How should I handle the UI elements?
> 1. **I build it, you review it** *(recommended)*
> 2. **You indicate each element** in Studio's Selector editor
>
> *Question 3 — App state:* Is the app open on your machine?
> 1. **Yes, it's open and ready**
> 2. **No, I'll open it first** — tell me when ready
> 3. **Skip discovery for now** — scaffold with placeholder selectors

All user-facing questions in any lane must use plain developer language: no internal jargon (`snapshot`, `hand-wire`, `AutomationId`, `selector candidate`, `autonomous capture`, `target configuration`) and no domain/app names in question text. Never add a third Q2 option.

Skip Q1 when §9 explicitly identifies web/desktop/Citrix; skip Q2 only when the user explicitly chose an approach; skip Q3 when the user said the app is running, not open, or discovery should be skipped. Skip the batch for plans without UI automation (pure data-processing, API-only, agent-only, or flow-only). On resumed sessions, resolve Q1 from §9; re-ask session-bound Q2/Q3 when absent from the current conversation. Record answers in the tasks.md header.

## Step 6 — Derive tasks

Walk the project list and emit rows for the selected pattern using [plan-and-tasks-format.md](plan-and-tasks-format.md):

1. Create one task per discrete deliverable (workflow file, Orchestrator queue, asset, etc.).
2. Use stable identity `<skill>:<project>:<subject>` with naming consistent with the SDD.
3. Reference SDD sections explicitly in each skill prompt, e.g. “Implement `Process/CalculateTotal.xaml` per §11 row #3 of `<sdd-path>`. Use exact data field names from §5.”
4. Append the anti-hallucination rule verbatim to every Skill prompt.
5. Use `Blocked-by` edges for leaf resources before consumers, build before testing, and testing before deploy.
6. Add a mandatory testing task per generation skill between generation and deploy tasks.
7. For `automation-suite` or `standalone`, append to every Skill prompt: `Deployment target: <value> — do not introduce products or features unavailable there.` Skip this for `cloud` / `unspecified`.
8. For each task tied to an open SME item, append the assumption line specified in Step 1.

## Step 7 — Write tasks.md

Use [plan-and-tasks-format.md](plan-and-tasks-format.md). Header: Source SDD, SDD scope, Execution autonomy, Generation date, plus UI answers when applicable. Body: task list. On regeneration, append the Archive footer for removed tasks.

## Step 8 — Plan-mode review (interactive autonomy only)

For `Execution autonomy: interactive`, call `EnterPlanMode` with the full tasks.md content and wait for approval. Any response without specific change requests—including “Looks good”, “ok”, “proceed”, “yes”, or a topic change—is approval. Incorporate specific requests and re-present, up to 3 revisions; then proceed with the latest. On approval, call `ExitPlanMode`, then Step 9.

For `autonomous`, skip plan mode and output:

```
Generated <tasks-file>: <N> tasks.
Skills involved: uipath-rpa, uipath-platform, …
Starting execution autonomously.
```

If Step 1 defaulted handoff fields, append:

```
Defaulted handoff fields: Execution autonomy → interactive, Tasks file → <inferred-name>.
Review the SDD's `## Planner Handoff` table and re-run if any of these are wrong.
```

List actual defaulted fields and values. In interactive mode, prepend the same block, when applicable, to the `EnterPlanMode` payload. Include SDD provenance (`Generated by`), generation date, and open SME items in the closing summary.

## Step 9 — Emit live tasks

Emit one `TaskCreate` per task row in row order. After creation, emit `TaskUpdate` calls with `addBlockedBy` for dependencies. Apply Rule G-8: if any `TaskCreate` or `TaskUpdate` fails, log one warning, continue without live tasks, and do not retry. `tasks.md` remains authoritative.

## Step 10 — Hand off

The planner is finished. The main agent reads live tasks with `TaskList` and executes them in dependency order, loading each specialist. As tasks complete, the planner may be invoked on TaskUpdate events or later in the project to refresh tasks.md (`[ ]` → `[~]` → `[x]`). The planner does not observe TaskUpdate events; the main agent's session loop owns synchronization. On the next Lane A entry, re-read the file.

## Lane A budget

| Scenario | `AskUserQuestion` calls |
|---|---|
| First run, no UI apps in §9 | **0** (plan review uses `EnterPlanMode`) |
| First run, UI apps in §9 | **1** (UI batch only if Q1/Q2/Q3 unresolved) |
| Resume with existing tasks.md | **1** (continue/regenerate), plus 0–1 unresolved UI batch |
| Maximum | **2** under any realistic scenario |

This remains within the planner's 5-call Critical Rules budget.
