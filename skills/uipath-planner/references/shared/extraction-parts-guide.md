# Extraction Parts Guide — extraction in parts, through subagents, and resuming

Runs when the extraction guide's sizing (its Step 2b) plans parts. An extraction too large for one context runs in parts. The agent that plans the parts is the **orchestrator**: it fixes the shared decisions, writes the brief, runs the parts through subagents where the host has them, checks each part's return against the disk, and assembles the result. The brief, the ledgers, the read plans and the returns below are what a part, a new agent or a resumed session works from. Extraction's own agent is the orchestrator: besides the work that guide gives it, it reconciles the parts' output and writes the process genome.

## Running in Parts

1. **The orchestrator fixes the shared decisions before fan-out** — every decision two parts would otherwise take differently — and writes them into the brief. § What Extraction Adds rule 3 lists them.
2. **One brief, written before the first part starts,** in the working folder: absolute paths, the shared decisions, the reads, the return contract, the part table with each part's state, and a numbered **Rulings** section. Every orchestrator decision taken during the run takes the next ruling number, is written before the part that builds on it starts, and overrides the brief's text above it; it reaches every later part through the brief, never only through one agent's prompt. A ruling that changes what a running part writes is also sent to that part with its number, and the part applies it to its own files; where the host cannot reach a running part, the orchestrator applies it once the part has returned. Either way the orchestrator edits no file a part still owns (item 6). Every agent is pointed at the brief and the guides instead of receiving the rules inline.
3. **A ledger per part, written through.** Every item assigned to the part carries its state, written in the turn the work lands, and the ledger opens with a `Resume` block naming the next item. A resumed part — after a pause, a compaction or in a new session — reads the brief with its rulings, its ledger and what it has written; it takes from a compaction summary only the work after the last row and confirms it on disk, re-runs its read plan, since a summary carries none of the reads it made, and continues at the next item. A part that ends before finishing returns its unfinished items. Before relaunching or resuming a part, the orchestrator reconciles its ledger with the disk and assigns only unfinished work.
4. **Every part reads by plan, in at most three turns** ([extract-guide.md](../extract/extract-guide.md) § Read Plan). A part run through a subagent starts fresh, never as a fork of the orchestrator or of another part: a fork starts with its parent's whole context and resends it on every turn. The plan is written before the part starts and a subagent's prompt carries it, so the part's first turn needs nothing read before it: every file the part reads, whole or by named sections, with the line count of each whole-read file above the single-read limit, so its ranges go out in turn 1. A read stops at the harness's single-read limit, so a file the plan reads whole above that limit is read as consecutive line ranges in the same turn. Another part's ledger is not read; what a part needs of another part's work reaches it through the brief.
5. **A part returns a verdict, never a retelling, and the return is a claim; the disk is the result.** The return accounts for each item and contract the extraction return contract lists, so it can be checked against the disk. Before accepting a part — a subagent's or one resumed after a compaction — the orchestrator checks it mechanically: the files the return names exist with the counts it gives, and every assigned item appears done or among the unfinished ones. A defect such a check finds goes back to the part that owns it, with the evidence.
6. **What parts share has one owner at a time** — a part or the orchestrator. Ownership passes only once the previous owner has stopped: a subagent that receives a message after its final report resumes and acts again, so before the next part starts on what the previous one owned, the orchestrator confirms that the previous part's agent is idle with no unread message. A fix goes to a part only while no later part has taken its files: the message reopens it, it owns them again, and its new report passes the check of item 5. Once ownership has passed, a note goes to the current owner or into the brief as a ruling (item 2), never to the earlier part. Only the owner edits a shared file and runs a shared operation.
7. **Parts run on the orchestrator's model, at most four at once — unless the Subagents question says otherwise.**
   - **The question.** The extraction asks its Subagents question before the first part starts ([extract-guide.md](../extract/extract-guide.md) Step 1), with these options: the orchestrator's model, at most four parts at once (recommended); a smaller model of the orchestrator's family, at most four parts at once; the smaller model, as many parts at once as § What Extraction Adds lets run in parallel. A request that names the model or the cap answers it.
   - **The model and the cap.** A part's reading becomes the genome's text, which no validate or build checks, and a value misread there is built as behaviour ([extracted-genome-guide.md § Source values](extracted-genome-guide.md)), so the orchestrator's model is the default. Four is the cap because each running part adds its own stream of model calls on the same machine, and its return waits for the orchestrator's check before anything builds on it.
8. **Every agent's context grows only by what it acts on, and stays cached while it waits.** Every turn resends the whole context, so a command's output is paid again on every later turn, and the host's prompt cache lapses after a few idle minutes (five on the Claude API), so the call after a longer pause rewrites the whole context at many times the price of reading it.
   - **Output.** A script the run writes prints one line per failure and a summary line, with the details in a file in the working folder; a listing, search or log longer than about 150 lines goes to a file, and the agent reads the lines it needs.
   - **Waits.** Every call returns within about four minutes, so the next one still finds its context cached. A command that runs longer goes to the background, and so does every part the orchestrator launches. Whoever waits — a part on its command, the orchestrator on its parts — repeats one bounded wait, a shell call that returns when the awaited report or output file exists or after about four minutes (`sh -c 'i=0; until [ -f "<REPORT_PATH>" ] || [ $i -ge 15 ]; do sleep 15; i=$((i+1)); done'`), until the file is there. The call's own time limit is set above that wait: a call past the shell tool's limit is cut off or moved to the background. Ending the turn to await a notice — the part's completion or a file watcher's event — or launching a part in the foreground, leaves the context idle for as long as the part runs, and the call after it rewrites the whole context; a poll rereads the cached context at a small fraction of that price. A part does not wait on an agent it launched to review its own files; the orchestrator launches the review once the part has returned.
   - **Looks.** Every look at the disk the next step needs — a file's arguments, a link count, a folder listing, the lines around an edit point — goes out with the other looks of that step, in one message or one shell chain, never one look per turn.

## What Extraction Adds

1. **One part per component, reading its objects whole.** A component above one part's budget is split along its call graph: each part takes one phase's subtree (the object that runs the phase and what only it calls) and a step range the orchestrator assigns. Every object belongs to exactly one part. A part whose objects call an object another part owns names that part's step and does not describe the object.
2. **Who writes.** A part that owns a whole component writes that component's genome file. The parts of a split component write notes, and the orchestrator writes that component's genome from them. Notes go to the part's notes file in the working folder, in genome wording, so the orchestrator assembles and reconciles instead of rewording: each step of the range with its substeps, Business Rules, Error Handling entries, Acceptance Criteria and Source Map rows, then the facts the component's shared sections need (Interface, Target Applications, Platform Dependencies, open values).
3. **The shared decisions** (§ Running in Parts item 1). The orchestrator runs the source guide's self-test and export-wide commands once, reads the export-wide renderings (an inventory profile) in full and the per-object renderings of the shared components, and writes into the brief:
   - the component list with file names; each part's objects and bytes, with the step range of each part of a split component;
   - each shared component's step numbers and public workflows with their arguments, so callers name them before that component is written;
   - the names of lanes, environments and every platform resource, one credential asset per login account ([genome-format-guide.md § Platform Dependencies](genome-format-guide.md));
   - the questions that are process-wide, asked only in the process genome;
   - the owner of each helper that several components call;
   - each part's finding-id prefix, so ids stay unique within a component's Source Map.

   Parts never rerun an export-wide command. They read the renderings the extraction guide's Step 2b wrote (a UiPath part reads its files), and run the direct read only to verify suspected defects ([defect-verification-guide.md](defect-verification-guide.md)).
4. **The brief** (§ Running in Parts item 2) names, among its absolute paths, the export, the pack, the genome folder and the working folder; its reads are those of rule 6 and its return contract that of rule 8.
5. **The ledger** (§ Running in Parts item 3), in the working folder, lists every assigned object with its state (read, steps written or noted, findings verified), and its `Resume` block names the next object. A part that ends before reading all its objects returns the unread ones. The orchestrator writes them into the Source Map as a `Not read (run cut short)` row with each object's id and flags the steps they feed `*[Inferred]*`; [extract-guide.md § Partial Re-extraction](../extract/extract-guide.md) completes them.
6. **Every part reads by plan, in at most three turns** (§ Running in Parts item 4). Turn 1: the brief, the extraction guide, this guide, the format guide (every section before § Process Genome Sections: a part writes a component genome), the extracted genome guide, the component template and the source guide as the extraction guide's § Source Guides requires; the transactional shape guide when the part's objects show per-item work, and the defect verification guide at the first suspected defect, as [extract-guide.md § Read Plan](../extract/extract-guide.md) opens them. Turn 2: the renderings of all the part's objects, in one message. Turn 3: only the direct reads its findings need and the sections a turn-2 read routes to.
7. **A part verifies its own suspected defects.** It runs both passes of [defect-verification-guide.md](defect-verification-guide.md) itself, since it holds the rendering and the direct read is a targeted lookup, and returns the verdicts. A finding on an object another part owns goes to the orchestrator as a new finding with its line.
8. **Return contract** (§ Running in Parts item 5). A part returns:
   1. the file written — the genome file, or the notes file;
   2. counts: steps, rules, handlers, criteria, test cases;
   3. target applications;
   4. the Configuration Questions written, marked where another component may ask the same;
   5. platform resources, each with the name used;
   6. secrets found, by object and line, never the value;
   7. every verdict on a suspected defect, with the fields [defect-verification-guide.md](defect-verification-guide.md) returns and the behaviour the rebuild follows;
   8. cross-component calls: calling step, callee component and step, data passed, failure behaviour;
   9. transactional signals: per-item constructs with object and line, for the Transactional Shape;
   10. deviations from the brief, and every object left unread.
9. **Checking a return** (§ Running in Parts item 5). Before reconciling, the orchestrator checks each part mechanically: the file exists with the counts returned, every defect has its Source Map row with lines, and every assigned object appears in a Source Map row or in the unread list.

## Reconciliation

Before the extraction guide's Step 6b Source Map check and before edits are offered, the orchestrator works through every item:

1. **Questions.** A question two or more components ask moves to the process genome's Configuration Questions; each component keeps, in its own numbered list, a one-line pointer that names that number, a statement with no question mark: `N. {What it decides}: process genome Configuration Question M.`
2. **Names.** Every platform resource, lane and environment carries the brief's name in every file; each drift is renamed.
3. **Defect index.** The process genome's defect table is built from the returned verdicts ([extracted-genome-guide.md § Source Defects](extracted-genome-guide.md)).
4. **Rebuild follows.** Each defect is re-checked against that section's rule on which behaviour the rebuild follows, from the intent evidence its verdict returned. A wrong mark is corrected at the step and in the index.
5. **Code in bodies.** Search every genome file for selector tags (`<webctrl`, `<wnd`, `<html`, `<ctrl`), activity and command names, file extensions, drive and repository paths, and the source's variable syntax (source guide § Value syntax). A hit inside the Source Map is provenance and stays; so do a selector a test asserts as a value (extraction guide Step 3) and a text the source writes that [genome-format-guide.md § Provenance](genome-format-guide.md) keeps verbatim. Every other hit is translated or moved to the Source Map. Interface descriptions included ([genome-format-guide.md § Interface](genome-format-guide.md)).
6. **Cross-component calls.** Every returned call is a Handoffs row, and the Interfaces of both components agree with it. A helper several components call is described once, in its owner, and each caller names that owner's step.

Then the extraction guide's Step 6b check runs over every file, and its Step 7 offers edits.

## Anti-patterns

1. **A part reading file by file.** Reads in the order files name each other, one per turn; whole reads of what a part needs only by section; another part's ledger; a read plan that gives every part the reads of all parts. Each read is replayed on every later turn of the part (items 3, 4).
