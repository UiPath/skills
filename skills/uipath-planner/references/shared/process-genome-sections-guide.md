# Process Genome Sections Guide

Content rules for the sections only a process genome has, however the genome is produced; a component genome has none of them. The rules every section follows and the sections both levels share: [genome-format-guide.md](genome-format-guide.md).

## Process Map diagrams (process)

One Mermaid component-view diagram (`flowchart TB`), kept under `## Process Map` after the numbered stage list, with no subheading above it. Sequence and order live in the stage list, never in the diagram.
- **Nodes:** the automation's own components and its queues only; no people or outside systems, so no lanes. One node per queue, never a grouped node, drawn as a cylinder `[( )]` with no number. Every component node carries its number from the Components table in brackets.
- **Trigger marks** prefix a component node: ⏰ time trigger, 🔔 queue trigger (a component that consumes a queue), ⚡ event or API trigger (a mail, a file, a connector event or a call to its API endpoint starts it), 👤 started by a person (an attended robot, a form, an app). A component with no mark is invoked by another component; one with several entry points carries the mark of each triggered one. A trigger is *[Inferred]* when the source holds no schedules. A short legend under the diagram names the marks and the arrows; when the Source Map holds an as-is process map ([extracted-genome-guide.md § Source Map](extracted-genome-guide.md)), a line after the legend points to it.
- **Arrows** point the way the data or work travels; never a double-headed arrow, draw two. Solid: a component adds to a queue (component → queue), takes from or reads a queue (queue → component), or calls another component (caller → callee). Dotted: a handoff between components through a file, a mail or a shared store (a Data Fabric entity, a database table) rather than a queue or a call. A queue inside one component (the stages a decided split realises) is drawn in that component's label — `2 InvoiceProcess<br/>Dispatcher → queue → Performer` — never as a loop from the component back to itself.
- **Layout:** wrap node labels with `<br/>` at about 34 characters per line and edge labels at about 26; never put `<br/>` in a subgraph title (a test project's components may share one subgraph). A Mermaid parse success does not catch clipped text: when a renderer (mermaid-cli) is installed, render the diagram and look at it; otherwise keep to the wrap widths above.

Mermaid cannot render BPMN 2.0 itself; when the customer wants a formal model, add a sidecar `<process-slug>-process.bpmn` authored from the Process Map (the `uipath-maestro-bpmn` skill knows the format) and link it from this section.

## Handoffs (process)

One row per edge between components: mechanism, its cell opening with the mechanism's name (queue item; library workflow call, for a library's public workflow run as an activity inside the caller's job; Invoke Process, for a process run inside the caller's job — the caller waits and receives its outputs; start job, for one run as a job of its own — waited for, its outputs returned, or started and left, returning nothing, as the row says; Flow invoke; event; file drop; Action Center task; a shared store one component writes and another reads when asked — a Data Fabric entity, a database table), data schema passed, and what happens when the receiving side fails. An RPA caller reaches a callee the source runs in the caller's own run and session by a library workflow call or an Invoke Process, never by a start job, which runs in a session of its own, possibly on another machine, away from the applications the caller has open. This table is the data contract; component Interface sections must agree with it. When the Transactional Shape's producer and consumer are two phases of one component that form a flow ([transactional-shape-guide.md](transactional-shape-guide.md) rule 12) exchanging items through a store (a database work table, a folder, an in-memory work list the job reads once and then works item by item), add one row for that edge too, marked as intra-component and naming the stages on each side (the sub-projects a `Decided:` line names): it is the data contract the shape cites. Every flow of the Transactional Shape cites the Handoffs row that carries its items. The table follows the Process Map diagram: no rows for people or systems the automation only reads from or acts on (the diagram omits them), a human task a component creates (an Action Center task) keeps its row because it carries a data contract, one row per queue edge naming the queue(s) by name, never "the queues", and one row per call and per file or mail handoff between components.

## Deployment (process)

What holds wherever the automation is deployed, in these bullets, each present, each value the source or the description does not settle classed as [genome-questions-guide.md § Open Decisions](genome-questions-guide.md) classes a point:

- **Packaging and route:** one solution or independent packages, independent packages whenever the delivery model blocks Solutions ([platform-availability-guide.md](platform-availability-guide.md)), with the buildable projects named; a library with the feed it is published to and before its consumers, or with its consumers and the route that delivers it to them, apart from the solution's projects, since it is never one of them; with test components, exactly one test project and one Test Manager test set per test component.
- **Entry points:** each process's entry point, and who or what starts it; how each starts is the Triggers table.
- **Runtime:** Windows, cross-platform or serverless, and unattended or attended, as each component's steps need.
- **Kept out of the logs:** the data a run must not log (a source's private activities and the name keywords that mark them), or none.

The environments themselves — the platform, tenants and folders, robot accounts, machines and their Robot versions, log retention — are not the genome's: each deployment sets them, and the build asks what it needs and hands the rest over in its open items.
