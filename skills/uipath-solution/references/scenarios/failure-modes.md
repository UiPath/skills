# Cross-cutting failure modes

Symptoms that don't fit a single scenario but bite often enough to call out. Use this as triage when you don't yet know which scenario applies.

| Symptom | Likely cause | Fix |
|---|---|---|
| `[1009] <kind> <name>: Invalid argument 'Value'` at deploy | Virtual resource without `value` set ([virtual-resource](virtual-resource.md)) | `deploy config set <file> <name> value <val>` or `deploy config link <file> <name> --name <existing>` |
| Deployment sits in `OperationStatus: Draft` and won't activate | Deploy-time validation rejected a resource; the install never completed | Read the reasons (`Validation:` / `Conflicts:` in the failure's `Instructions` — on every feed, since each deploy waits for its run), fix them with `deploy config set` / `link`, then run the same `deploy run` again with the draft's `--package-version` and `--config-file <file>` — see [A deploy that stops in `Draft`](../pack-and-deploy.md#a-deploy-that-stops-in-draft). `deploy list` shows the row only with the same `--personal-workspace` / `--feed` flag the deploy used |
| `has a pending draft (<key>) for version <v>` from `deploy upgrade` or `deploy run` | An earlier attempt was rejected (`ValidationFailed`, a conflict or scheduling error) and stays behind as a draft that owns the deployment; the live version is untouched | Finish it: re-run the failed `deploy run` with the draft's `--package-version` and a corrected `--config-file`. Or drop it: `deploy upgrade <key> --discard-draft [--version <v>]`, or Delete draft in Orchestrator — see [activate-and-manage](../activate-and-manage.md) |
| `Deploying '<name>' will permanently delete <k> resource(s) along with their data: …` (or `Upgrading …`), `ErrorCode: invalid_argument`, `Data.PermanentDeletionResources` | The update unlinks a queue or bucket that no other folder uses, so Orchestrator deletes it with its data and asks for consent first. Older servers ask instead when a link deletes an installed copy (`deleteInstalledCopy: true`). Nothing was installed; the attempt is kept as a pending draft | Not a config error. With the user's consent, re-run the **same** command with `--acknowledge-permanent-deletion` (on `deploy upgrade` never with `--discard-draft`). To keep the resources: keep them linked (`deploy config link`) or share them into another folder, then re-run; on `deploy upgrade`, `deploy upgrade <draft-key> --discard-draft`. On older servers, `deploy config unlink <file> <resource>` keeps the copy. See [When a deploy would permanently delete resources](../pack-and-deploy.md#when-a-deploy-would-permanently-delete-resources) |
| `deploy run` fails with `Deploying '<name>' would permanently delete the installed copy of <kind> '<name>'… this server does not support keeping the installed copy…`, `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix`, `Data.PermanentDeletionResources` | The `--config-file` links that resource with `deleteInstalledCopy: false` (the default), but the server predates the keep option and asked to confirm deleting the copy. Nothing was installed or acknowledged, even with `--acknowledge-permanent-deletion`; the attempt is kept as a pending draft | Ask the user. To accept the deletion: `deploy config link <file> <resource> --name <existing> --delete-installed-copy`, then re-run with `--acknowledge-permanent-deletion`. To keep the copy: `deploy config unlink <file> <resource>`, then re-run. See [When a deploy would permanently delete resources](../pack-and-deploy.md#when-a-deploy-would-permanently-delete-resources) |
| `deploy run` fails with `'<name>' cannot be kept: it has the same name as the installed copy in the solution folder…` (error `5028`), `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix` | A kept installed copy already holds the name of a link's target in the `--config-file`. Either the link keeps its own copy (`deleteInstalledCopy: false`, the default, also sent for a link without the key) and its target has that copy's name, or another resource of the same kind keeps a copy with that name in the same folder. The second case fires even when this link deletes its own copy. The install was refused before anything ran; the attempt is kept as a pending draft | Delete the copy that holds the name: `deploy config link <file> <resource> --name <existing> --delete-installed-copy` on the link that keeps it. Or link a target with a different name. Then re-run. See [Link to an Existing Orchestrator Resource](../pack-and-deploy.md#link-to-an-existing-orchestrator-resource) |
| `deploy run` fails with `A resource with kind: '<kind>' and name: '<name>' already exists in the same location.` (error `5002`), `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix` | Two names would match in the solution folder (case-insensitive): a link in the `--config-file` keeps a copy with the same name as another resource's name or link name, or two links point at targets with the same name. A resource name set in the `--config-file` that another resource of that kind already uses gets the same refusal. The install was refused before anything ran; the attempt is kept as a pending draft | Link a target with a different name, stop keeping the copy (`deploy config link <file> <resource> --name <existing> --delete-installed-copy`), or choose another resource name, then re-run. See [Link to an Existing Orchestrator Resource](../pack-and-deploy.md#link-to-an-existing-orchestrator-resource) |
| `deploy run` or `deploy upgrade` stops at `ValidationFailed` with `A resource named '<X>' already exists in the solution folder…` | Orchestrator's link name check on upgrade: a resource in the solution folder already has the link target's name. Not every tenant runs it yet | Link a target with a different name (`deploy config link`), or rename or delete `<X>` in Orchestrator, then re-run. The attempt is a normal draft, see [A deploy that stops in `Draft`](../pack-and-deploy.md#a-deploy-that-stops-in-draft) |
| `deploy uninstall` fails: `Message` "...this deployment has uncompleted jobs; --force uninstalls anyway" or "...permanently deletes these resources and their data: ..." (or the 409 form "Deployment '<name>' was not uninstalled: ..."), `Retry: RetryWillNotFix` | Orchestrator wants consent: jobs not in a final state (`Data.JobsNotInFinalState: true`) and/or installed resources replaced by links that the uninstall deletes (`Data.PermanentDeletionResources`) | Ask the user. Only on explicit consent re-run with `--force` (implies `--yes`); otherwise let the jobs finish and re-run without it -- see [When the uninstall is refused](../activate-and-manage.md#when-the-uninstall-is-refused) |
| `deploy uninstall` fails: "...errors that --force cannot get past: [code] text", `Retry: RetryLater` | The Uninstall validation holds an error `--force` does not skip | Never add `--force`. Resolve the named error in Orchestrator, then run `deploy uninstall <name> --yes` again |
| `A deployment with name '<n>' is already in progress` from `deploy run` (`DeploymentAlreadyInProgress`, `Retry: RetryLater`) | The install is keyed on the deployment name, and an earlier deploy or upgrade under `<n>` has not finished — often one whose poll was cut short. The package is there; this is not a publish problem | Wait for the run, following it with `deploy list` **with the same `--personal-workspace` / `--feed` flag**; then update that deployment with `deploy upgrade <deployment-key>`, or re-run with a different `--name` for a separate copy |
| `A deployment named '<n>' already exists for another solution package` from `deploy run` (`NameInUseByAnotherDeployment`) | `<n>` belongs to a deployment of a different package in that feed; the install never re-points a name at another package | Re-run with a different `--name`; `deploy list` with the same feed flag shows which deployment holds the name |
| `Folder already exists` at deploy | `--folder-name` collides with an existing folder under `--parent-folder-path` | Pick a different `--folder-name`, or `solution deploy uninstall <existing>` first |
| Suffix `_N` keeps growing on re-refresh (`_1`, `_2`, `_3`...) | Old CLI version (pre-suffix-amplification fix) | Upgrade `@uipath/cli` to a build that ships the SDK bump (`resource-builder-sdk` ≥ `2025.11.0-alpha3780`); the current refresh is idempotent on cloud key |
| Tool dialog in Studio Web doesn't open for one of two same-name tools | SW UI bug — affects pure-SW solutions too ([same-name-across-folders](same-name-across-folders.md)) | Verified at deploy/runtime — ignore the UI symptom; check the tool resolves correctly via `resources list --source remote` after deploy |
| Refresh imports 0 of N bindings, no warnings | `bindings_v2.json` not at expected path (project root, not nested) | Move file to `<ProjectName>/bindings_v2.json`; `agent validate` regenerates it for agent projects |
| `processKey` collision, or HTTP 409, on `solution publish` | Republishing same name+version | Bump version (`solution pack --version <NEW_VERSION> …`) and publish that; the feed rejects duplicate `name+version` pairs. Never delete the published version to reuse its number unless the user asks — `packages delete --yes` is the only check ([Version Bumping](../pack-and-deploy.md#version-bumping)) |
| `pack` fails and `Message` names no file | `Message` flattens every failed project into one sentence | Read `Data.Projects`: per project `Path`, `Type`, `Result`, `Findings` (`Source`, `ErrorCode`, `FilePath`, `ActivityIdRef`) — [pack-build-guide](../pack-build-guide.md#read-dataprojects-on-a-failed-pack) |
| `pack` exits `0` but governance was not enforced | AutomationOps could not be asked (unreachable, or an external-app login), so the shipped rules or `--governance-file-path` were used; only a stderr warning says so | Keep `--log-level` at `warn`, read stderr or `--log-file` — [Governance does not gate a build](../pack-build-guide.md#governance-does-not-gate-a-build) |
| `pack` / `restore` fails to restore official activity packages with `--exclude-configured-sources` | The flag drops the built-in feeds; most tenant feeds do not mirror UiPath-Official | Pair it with `--nuget-sources-config-path` pointing at a `NuGet.config` with your mirror — [Dependency feeds](../pack-build-guide.md#dependency-feeds) |
| `pack` or `upload` fails `permission_denied`, `authentication_required`, `rate_limited` or `server_error` while resolving bindings; refresh exits `0` with warnings | A Resource Catalog lookup failed (401/403, outage, no login on `pack`). Nothing is created for an unresolved binding | Fix the login or wait for the outage. From CI on an external app: refresh under a user login, commit `resources/`, then pack — [A failed Resource Catalog lookup](../develop-solution.md#a-failed-resource-catalog-lookup-is-not-a-not-found) |
| `Resource key <key> is used by: <file>, <file>` (older CLIs: `Node already added to the graph`) | Two resource files carry one key | Keep the file whose `name` other resource files and the bindings reference, delete the rest, then `uip solution resources refresh`. For `(missing)` or `""` keys the files are different resources: give each its own unique `key` instead of deleting |
| `pack` / `upload` fails with `idp_processor_duplicate_author` or `idp_processor_unprovisioned` (`invalid_argument`) | Two Extract document nodes in a Flow define one processor, or a node names no processor the runtime can resolve | Follow the error's `Instructions`: they differ per node — give a duplicate author a fresh `inputs.processorKey` or mark it read-only, provision an authoring node that has no processor, point a read-only node at the author's key. Never invent a key just to get past pack. The message names the nodes |
| Edited `bindings_v2.json` beside a `.flow` has no effect | Refresh, pack and upload read a Flow's bindings from its `.flow` and ignore the derived `bindings_v2.json` | Edit the `.flow` or use `uip maestro flow nodes configure` — [A Flow's bindings come from its `.flow`](../develop-solution.md#a-flows-bindings-come-from-its-flow) |
| `upload` fails 401/403, `permission_denied` | Not a login problem: the identity's Studio Web access (`StudioWebS2S` for an external app), or a `SolutionId` from another tenant | Do not log in again — [When Studio Web refuses the upload](../develop-solution.md#when-studio-web-refuses-the-upload) |
| `upload` of a `.uis` fails HTTP 500, `Context.ErrorCode: 20039` | A project file name Studio Web rejects (control character or `: * ? " < > |`) | Rename the file, or upload the solution directory, which names it |
| `deploy list --folder-key <key>` returns nothing | The key is the row's own `FolderKey` (the solution folder one level below), or the deployment sits in a subfolder | Pass the key of the row's `FolderPath` folder, or `--folder-path <full path>`; list each subfolder separately — [Step 6](../pack-and-deploy.md#step-6-list-deployments) |
| `deploy status` / `activate` / `uninstall` / `delete` by name fails, `ErrorCode` not `not_found` | A feed could not be searched; the name may be right | Follow `Instructions` (log in again, fix access, or retry later) — [Check Deployment Status](../activate-and-manage.md#step-2-check-deployment-status) |

> See the individual scenario files for setup, root-cause walkthroughs, and verification steps.
