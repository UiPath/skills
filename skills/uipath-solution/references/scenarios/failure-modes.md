# Cross-cutting failure modes

Symptoms that don't fit a single scenario but bite often enough to call out. Use this as triage when you don't yet know which scenario applies.

| Symptom | Likely cause | Fix |
|---|---|---|
| `[1009] <kind> <name>: Invalid argument 'Value'` at deploy | Virtual resource without `value` set ([virtual-resource](virtual-resource.md)) | `deploy config set <file> <name> value <val>` or `deploy config link <file> <name> --name <existing>` |
| Deployment sits in `OperationStatus: Draft` and won't activate | Deploy-time validation rejected a resource; the install never completed | Read the reasons (`Validation:` / `Conflicts:` in the failure's `Instructions` — on every feed, since each deploy waits for its run), fix them with `deploy config set` / `link`, then run the same `deploy run` again with the draft's `--package-version` and `--config-file <file>` — see [A deploy that stops in `Draft`](../pack-and-deploy.md#a-deploy-that-stops-in-draft). `deploy list` shows the row only with the same `--personal-workspace` / `--feed` flag the deploy used |
| `has a pending draft (<key>) for version <v>` from `deploy upgrade` or `deploy run` | An earlier attempt was rejected (`ValidationFailed`, a conflict or scheduling error) and stays behind as a draft that owns the deployment; the live version is untouched | Finish it: re-run the failed `deploy run` with the draft's `--package-version` and a corrected `--config-file`. Or drop it: `deploy upgrade <key> --discard-draft [--version <v>]`, or Delete draft in Orchestrator — see [activate-and-manage](../activate-and-manage.md) |
| `Deploying '<name>' will permanently delete <k> resource(s) along with their data: …` (or `Upgrading …`), `ErrorCode: invalid_argument`, `Data.PermanentDeletionResources` | The update unlinks a queue or bucket that no other folder uses, so Orchestrator deletes it with its data and asks for consent first. Older servers ask instead when a link deletes an installed copy (`deleteInstalledCopy: true`). Nothing was installed; the attempt is kept as a pending draft | Not a config error. With the user's consent, re-run the **same** command with `--acknowledge-permanent-deletion` (on `deploy upgrade` never with `--discard-draft`). To keep the resources: keep them linked (`deploy config link`) or share them into another folder, then re-run; on `deploy upgrade`, `deploy upgrade <draft-key> --discard-draft`. On older servers, `deploy config unlink <file> <resource>` keeps the copy. See [When a deploy would permanently delete resources](../pack-and-deploy.md#when-a-deploy-would-permanently-delete-resources) |
| `deploy run` fails with `Deploying '<name>' would permanently delete the installed copy of <kind> '<name>'… this server does not support keeping the installed copy…`, `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix`, `Data.PermanentDeletionResources` | The `--config-file` links that resource with `deleteInstalledCopy: false` (the default), but the server predates the keep option and asked to confirm deleting the copy. Nothing was installed or acknowledged, even with `--acknowledge-permanent-deletion`; the attempt is kept as a pending draft | Ask the user. To accept the deletion: `deploy config link <file> <resource> --name <existing> --delete-installed-copy`, then re-run with `--acknowledge-permanent-deletion`. To keep the copy: `deploy config unlink <file> <resource>`, then re-run. See [When a deploy would permanently delete resources](../pack-and-deploy.md#when-a-deploy-would-permanently-delete-resources) |
| `deploy run` fails with `'<name>' cannot be kept: it has the same name as the installed copy in the solution folder…` (error `5028`), `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix` | A kept installed copy already holds the name of a link's target in the `--config-file`. Either the link keeps its own copy (`deleteInstalledCopy: false`, the default, also sent for a link without the key) and its target has that copy's name, or another resource of the same kind keeps a copy with that name in the same folder. The second case fires even when this link deletes its own copy. The install was refused before anything ran; no draft | Delete the copy that holds the name: `deploy config link <file> <resource> --name <existing> --delete-installed-copy` on the link that keeps it. Or link a target with a different name. Then re-run. See [Link to an Existing Orchestrator Resource](../pack-and-deploy.md#link-to-an-existing-orchestrator-resource) |
| `deploy run` fails with `A resource with kind: '<kind>' and name: '<name>' already exists in the same location.` (error `5002`), `ErrorCode: invalid_argument`, `Retry: RetryWillNotFix` | Two names would match in the solution folder (case-insensitive): a link in the `--config-file` keeps a copy with the same name as another resource's name or link name, or two links point at targets with the same name. A resource name set in the `--config-file` that another resource of that kind already uses gets the same refusal. The install was refused before anything ran; no draft | Link a target with a different name, stop keeping the copy (`deploy config link <file> <resource> --name <existing> --delete-installed-copy`), or choose another resource name, then re-run. See [Link to an Existing Orchestrator Resource](../pack-and-deploy.md#link-to-an-existing-orchestrator-resource) |
| `deploy run` or `deploy upgrade` stops at `ValidationFailed` with `A resource named '<X>' already exists in the solution folder…` | Orchestrator's link name check on upgrade: a resource in the solution folder already has the link target's name. Not every tenant runs it yet | Link a target with a different name (`deploy config link`), or rename or delete `<X>` in Orchestrator, then re-run. The attempt is a normal draft, see [A deploy that stops in `Draft`](../pack-and-deploy.md#a-deploy-that-stops-in-draft) |
| `deploy uninstall` fails: `Message` "...this deployment has uncompleted jobs; --force uninstalls anyway" or "...permanently deletes these resources and their data: ..." (or the 409 form "Deployment '<name>' was not uninstalled: ..."), `Retry: RetryWillNotFix` | Orchestrator wants consent: jobs not in a final state (`Data.JobsNotInFinalState: true`) and/or installed resources replaced by links that the uninstall deletes (`Data.PermanentDeletionResources`) | Ask the user. Only on explicit consent re-run with `--force` (implies `--yes`); otherwise let the jobs finish and re-run without it -- see [When the uninstall is refused](../activate-and-manage.md#when-the-uninstall-is-refused) |
| `deploy uninstall` fails: "...errors that --force cannot get past: [code] text", `Retry: RetryLater` | The Uninstall validation holds an error `--force` does not skip | Never add `--force`. Resolve the named error in Orchestrator, then run `deploy uninstall <name> --yes` again |
| `Folder already exists` at deploy | `--folder-name` collides with an existing folder under `--parent-folder-path` | Pick a different `--folder-name`, or `solution deploy uninstall <existing>` first |
| Suffix `_N` keeps growing on re-refresh (`_1`, `_2`, `_3`...) | Old CLI version (pre-suffix-amplification fix) | Upgrade `@uipath/cli` to a build that ships the SDK bump (`resource-builder-sdk` ≥ `2025.11.0-alpha3780`); the current refresh is idempotent on cloud key |
| Tool dialog in Studio Web doesn't open for one of two same-name tools | SW UI bug — affects pure-SW solutions too ([same-name-across-folders](same-name-across-folders.md)) | Verified at deploy/runtime — ignore the UI symptom; check the tool resolves correctly via `resources list --source remote` after deploy |
| Refresh imports 0 of N bindings, no warnings | `bindings_v2.json` not at expected path (project root, not nested) | Move file to `<ProjectName>/bindings_v2.json`; `agent validate` regenerates it for agent projects |
| `processKey` collision on `solution publish` | Republishing same name+version | Bump version (`solution pack --version 1.0.1 …`); the feed rejects duplicate `name+version` pairs |

> See the individual scenario files for setup, root-cause walkthroughs, and verification steps.
