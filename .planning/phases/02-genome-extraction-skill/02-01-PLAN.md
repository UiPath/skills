Create `skills/uipath-genome-extraction/references/project-analysis-guide.md` — the file-by-file extraction reference the agent reads when analyzing a UiPath project.

Structure the guide as a sequential analysis pipeline with these sections:

**1. Analysis Pipeline Overview**
Brief intro: the agent follows steps 1-5 in order. Each step produces signals that feed into the extraction-mapping-guide.md tables.

**2. Step 1 — Locate and Read project.json**
What to extract:
- `name` -> genome file name (slugify: "InvoiceProcessing" -> "invoice-processing-genome.md")
- `main` -> entry point file path
- `entryPoints` -> additional entry points (multi-entry-point detection)
- `dependencies` -> package list (keys are package IDs)
- `designOptions.outputType` -> Process vs Library vs TestCase
- `expressionLanguage` -> VB or CSharp (affects how to read expressions)
- `targetFramework` -> Windows or Cross-platform
- `runtimeOptions.isAttended` -> Attended automation flag
- `globalHandler` -> Global error handler file path (if present)

Fallback rule: If project.json not found, scan for .xaml/.cs files directly and flag the genome with `*[Inferred from project signals]*` for any metadata that would have come from project.json.

**3. Step 2 — Build File Inventory**
How to classify files into categories:
- `.xaml` files -> XAML workflows (analyze with Step 3)
- `.cs` files -> Coded workflows (analyze with Step 4) 
- `.cs.json` files -> Coded workflow metadata (arguments, display name)
- `.flow` files -> Maestro flow definitions (analyze with Step 5)

Exclusion rules (from CONTEXT.md locked decision):
- SKIP `.local/` directory entirely (auto-generated)
- SKIP `.objects/` directory entirely (auto-generated)
- SKIP `.codedworkflows/` directory entirely (auto-generated boilerplate)
- Red flag file names to ignore: `CodedWorkflow.cs`, `ConnectionsManager.cs`, `ObjectRepository.cs`, `WorkflowRunnerService.cs`
- `.cs.json` files ARE safe to read (argument definitions, not auto-generated logic)

**4. Step 3 — XAML File Analysis**
For each .xaml file, extract these signals. Structure as a table: Signal | Where in XAML | What It Tells You | Example.

Signals to document:
- Root element (`Sequence`, `Flowchart`, `StateMachine`) -> workflow type
- `xmlns` declarations -> which activity packages are used (for target app detection). Use xmlns only to identify packages, NOT as workflow steps
- Activity elements (e.g., `ui:TypeInto`, `umam:GetNewestEmail`, `p:ReadRange`) -> workflow steps
- `x:Members` with `x:Property` -> arguments (In/Out/InOut direction from PropertyAttributes)
- `If`, `Switch`, `FlowDecision` elements -> business rules / conditional logic
- `TryCatch`, `Retry Scope` elements -> error handling patterns
- `ConnectionId` attributes -> Integration Service connection present (but GUID, not service name — need to cross-reference xmlns namespace)
- `isactr:ConnectorActivity` -> Integration Service connector activity
- Variable definitions in `<Sequence.Variables>` or similar -> data flow
- `InvokeWorkflowFile` with `FileName` attribute -> call graph edges

Critical: SKIP `<sap2010:WorkflowViewState.ViewStateManager>` sections entirely — these are designer layout metadata, not logic.

**5. Step 4 — Coded Workflow Analysis (.cs files)**
For each .cs file, extract these signals. Structure as a table: Signal | Code Pattern | What It Tells You | Example.

Signals to document:
- `[Workflow]` attribute -> workflow entry point
- `[TestCase]` attribute -> test case, not a business workflow
- Service property usage (`system.`, `excel.`, `office365.`, `testing.`) -> target applications
- `connections.*` usage -> Integration Service connections (service name visible in property name)
- `workflows.*` calls -> workflow invocation graph (call graph edges)
- `try/catch` blocks with exception types -> error handling patterns
- C# control flow (`if`, `switch`, `foreach`, `while`) with business-relevant conditions -> business rules
- Method signatures and return types -> data flow

**6. Step 5 — Flow File Analysis (.flow JSON)**
For each .flow file, extract:
- `nodes` array -> workflow steps (each node is a step)
- Node `type` field (e.g., `core.action.script`, `core.action.invoke`) -> step type
- `edges` array -> step ordering (source -> target connections)
- `inputs.script` content in script nodes -> embedded business logic
- Variable definitions -> data flow

**7. Building the Call Graph**
How to construct the workflow step ordering from the entry point:
1. Start from `main` entry point in project.json
2. Follow `InvokeWorkflowFile` in XAML (read `FileName` attribute)
3. Follow `workflows.*` calls in .cs files
4. Order by position in the call chain (depth-first from entry point)
5. Parallel branches (multiple invocations at same level): order by file position in calling workflow
6. No clear entry point: for `outputType: Library`, list all public workflows as independent capabilities. For `outputType: Process`, look for Main.xaml/Main.cs by convention. Flag with `*[Inferred from project signals]*` if none found.

Include a cross-reference note at the bottom: "After analysis, use extraction-mapping-guide.md to map these signals to genome sections."

Do NOT duplicate deep XAML format rules, project.json field definitions, or coded workflow syntax from existing skill references. This guide tells the agent WHAT to extract and WHERE to find it, not HOW the file format works in general.

Create `skills/uipath-genome-extraction/references/extraction-mapping-guide.md` — the signal-to-genome-section mapping reference.

Structure with these sections:

**1. How to Use This Guide**
Brief: After analyzing project files (see project-analysis-guide.md), use these tables to map extracted signals to genome sections. Each table maps signals -> specific genome section content.

**2. Package-to-Target-Application Mapping (-> Target Applications section)**
Table with columns: Package ID | Target Application | Role. Include these rows:
- `UiPath.UIAutomation.Activities` | Desktop/Browser apps | UI interaction
- `UiPath.Excel.Activities` | Excel | Data source/target
- `UiPath.Mail.Activities` | Email (generic) | Input/output
- `UiPath.MicrosoftOffice365.Activities` | Outlook/Office 365 | Email, Calendar, OneDrive
- `UiPath.GSuite.Activities` | Gmail/Google Workspace | Email, Drive, Sheets
- `UiPath.Database.Activities` | Database (SQL) | Data source/target
- `UiPath.WebAPI.Activities` | REST APIs | Integration
- `UiPath.PDF.Activities` | PDF files | Document processing
- `UiPath.Word.Activities` | Microsoft Word | Document generation
- `UiPath.Presentations.Activities` | PowerPoint | Presentation generation
- `UiPath.IntegrationService.Activities` | Integration Service | Connector runtime
- `UiPath.IntelligentOCR.Activities` | Document Understanding | Document AI extraction
- `UiPath.DocumentUnderstanding.ML.Activities` | Document Understanding | ML models
- `UiPath.Cryptography.Activities` | Encryption/Security | Data protection
- `UiPath.Testing.Activities` | Testing framework | Validation
- `UiPath.Persistence.Activities` | Orchestrator queues/assets | Queue management

Note after the table: Applications become configurable in Configuration Questions. Original app becomes the default. Example: project uses `UiPath.MicrosoftOffice365.Activities` -> Target Applications lists "Outlook/Office 365" AND Configuration Questions gets "Which email provider? (source project used: Outlook)".

**3. Platform Feature Detection (-> Target Applications + Configuration Questions sections)**
Table with columns: Signal | Platform Feature | Where to Check | Genome Impact. Include these rows:
- `UiPath.IntelligentOCR.Activities` or `UiPath.DocumentUnderstanding.*` in deps | Document Understanding | project.json | Add to Target Applications
- `UiPath.IntegrationService.Activities` in deps OR `ConnectionId` in XAML OR `connections.*` in .cs | Integration Service | project.json, .xaml, .cs | Add specific service to Target Applications (resolve from xmlns/property name, not generic "Integration Service")
- `UiPath.Persistence.Activities` in deps OR queue activities | Orchestrator Queues | project.json, .xaml | Add to Configuration Questions ("Which Orchestrator queue? (source project used: X)")
- `BuildClient("Orchestrator")` in .cs | Orchestrator API | .cs | Add to Configuration Questions
- `GlobalHandler` in project.json or GlobalHandler.xaml exists | Global error handling | project.json, files | Document in Error Handling section
- `entryPoints` array with multiple entries | Multi-entry-point | project.json | Document all entry points in Workflow section
- `.flow` files present | Maestro orchestration | file listing | Add Maestro to Build With section
- `isAttended: true` or `requiresUserInteraction: true` | Attended automation | project.json | Note in Overview and Configuration Questions

**4. Error Handling Pattern Mapping (-> Error Handling section)**
Table with columns: Source Pattern | XAML Signal | .cs Signal | Genome Description. Include these rows:
- Retry on failure | `<RetryScope>` with `NumberOfRetries` | `for` loop wrapping try/catch | "Retries Nx on [exception type]"
- Catch and log | `<TryCatch>` with `<Catch>` containing `LogMessage` | `catch` with `Log()` | "Logs [error type] and continues"
- Catch and rethrow | `<TryCatch>` with `<Catch>` containing `Rethrow` | `catch` with `throw` | "Escalates [error type] to caller"
- Global handler | `GlobalHandler.xaml` or project.json `globalHandler` | N/A (XAML only) | "Global error handler catches unhandled exceptions"
- Catch specific types | `<Catch x:TypeArguments="s:TimeoutException">` | `catch (TimeoutException)` | "Handles timeout exceptions separately"
- Queue exception | Queue-related exception activities | `system.AddQueueItem` with exception | "Routes failed items to exception queue"

Rule: Always translate to behavioral descriptions, never code-level detail. "Retries 3x on timeout" not "RetryScope with NumberOfRetries=3 for TimeoutException".

**5. Complexity Inference from Project Signals (-> Complexity section)**
Table with columns: Signal | Simple | Medium | Complex. Include these rows:
- Total workflow files (.xaml + .cs) | 1-3 | 4-8 | 9+
- Unique package dependencies | 1-3 | 4-6 | 7+
- Entry points | 1 | 1-2 | 3+
- Integration Service connections | 0 | 0-1 | 2+
- Error handling patterns found | 0-1 | 2-3 | 4+
- Orchestrator features (queues, assets) | None | Optional | Present
- Flow files present | No | No | Yes
- Document Understanding packages | No | Optional | Often

Rule after table: "When ambiguous, default to the lower level (same rule as authoring skill). Complexity determines section depth per the population matrix in SKILL.md."

**6. Generalization Rules (-> Configuration Questions section)**
Rules for converting hardcoded values to Configuration Questions:
1. Every hardcoded path, URL, email address, server name, credential name, queue name, threshold value, column name -> Configuration Question with original value as default
2. Application choices -> configurable (e.g., "Which email provider? (source project used: Outlook)")
3. Credential asset names -> configurable ("Which credential asset? (source project used: MyCredential)")
4. Environment-specific values (server URLs, database connection strings) -> configurable
5. Business-rule thresholds (amounts, counts, dates) -> configurable with original value as default

Format for each question: `N. {Question}? (source project used: {original value})`

**7. Business Rule Extraction (-> Business Rules section)**
How to translate code constructs to natural language:
- `If` / `FlowDecision` conditions -> "If [condition in plain English], then [action]"
- `Switch` cases -> "Route based on [variable]: [case] -> [action], [case] -> [action]"
- VB expressions: translate operators (AndAlso -> "and", OrElse -> "or", `&` -> concatenation). Check `expressionLanguage` in project.json
- C# expressions: translate directly to English
- Rule: Never include programming syntax in the genome. "If amount exceeds $10,000 and category is Premium" not "Amount > 10000 AndAlso Category = \"Premium\""

**8. Acceptance Criteria Derivation (-> Acceptance Criteria section)**
Rules for generating acceptance criteria from the extracted workflow:
- Each criterion describes a functional outcome, not a code-level assertion
- Pattern: "Given [specific input], [specific observable outcome]"
- Derive from: workflow steps (each major step -> at least one criterion), error handling patterns (each pattern -> one criterion), business rules (each rule -> one criterion)
- Ban list: "Uses [activity name]", "Calls [workflow file]", "Reads [variable name]" -- these are code-level, not behavioral
- Good: "Given an invoice PDF, extracts vendor name, amount, and due date"
- Bad: "Uses ReadPDF activity to process InvoiceFile variable"
