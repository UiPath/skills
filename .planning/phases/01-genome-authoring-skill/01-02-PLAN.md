**Body structure** (follow the canonical section order from CONTRIBUTING.md and skill-structure.md):

### 1. Title
`# Genome Authoring`

Brief description (1-2 sentences): "Interview users about their automation ideas and produce structured genome markdown specifications. The agent carries the weight — users describe what they want, the agent fills in the UiPath-specific details."

### 2. When to Use This Skill
Bullet list of activation scenarios:
- User describes an automation idea ("I want to automate invoice processing")
- User asks to create a genome or automation spec
- User says "plan an automation" or "design a workflow"
- User wants to document what an automation should do before building it

### 3. Critical Rules (numbered, highest-priority)

1. **User describes, agent infers.** The user provides a free-form description. The agent infers complexity (simple/medium/complex) from the description. Never ask the user to declare complexity.
2. **Extract first, ask second.** Parse the user's description and extract everything possible (target apps, workflow steps, business rules). Only ask follow-up questions for genuine gaps — not for information already provided.
3. **Follow-up depth scales with complexity.** Simple: 0-1 follow-up rounds. Medium: 1-2 rounds. Complex: 2-3 rounds. After the last round, generate the genome with available information and offer edits. Never let the interview loop indefinitely.
4. **Proactively suggest UiPath features.** When the description mentions PDFs or documents, suggest Document Understanding. When it mentions web forms or desktop apps, suggest UI Automation. When it mentions third-party connectors, suggest Integration Service. When it mentions coordinating multiple automations, suggest Orchestrator queues or Maestro flows. Add these to the genome even if the user didn't mention them.
5. **Every section present, always.** The genome must include all template sections. For simple genomes, sections that don't apply get a stub with guidance (e.g., "No explicit business rules — agent applies standard validation"). Never omit a section entirely.
6. **Acceptance criteria must be specific and testable.** Each criterion references a concrete input, output, or observable behavior from the workflow. Pattern: "Given [specific input], the automation [specific observable outcome]." Ban generic criteria like "step completes successfully" or "errors handled properly."
7. **Write immediately, offer edits after.** Write the genome file to the user's CWD as `{slug}-genome.md` immediately after generating. Then ask "Want to adjust anything?" Do not show a preview or ask for confirmation before writing.
8. **One skill per workflow step in Build With.** Each workflow step maps to exactly one skill. Use [skill-mapping-guide.md](./references/skill-mapping-guide.md) for selection. Orchestration (queues, multi-step flows) is its own step with its own skill reference — not a top-level annotation.

### 4. Workflow (step-by-step interview process)

**Step 1 — Receive description.**
The user provides a free-form description of their automation idea. This can range from a single sentence to multiple paragraphs. Accept whatever they give.

**Step 2 — Infer complexity.**
Analyze the description against these signals:

| Signal | Complexity |
|--------|------------|
| Single sentence/paragraph, one target app, straightforward input-to-output | Simple |
| Multiple systems mentioned, field mappings, business rules, or conditional logic | Medium |
| Multi-phase workflow, error handling requirements, multiple integrations, orchestration needed, human-in-the-loop | Complex |

When ambiguous, default to the lower level. Follow-up questions may reveal higher complexity — escalate if so.

**Step 3 — Extract from description.**
Parse the description and extract:
- Target applications (what systems are involved)
- Workflow steps (what happens in what order)
- Business rules (any validation, conditions, or decision logic mentioned)
- Error scenarios (any failure handling mentioned)
- Input/output data (what goes in, what comes out)

**Step 4 — Identify gaps and suggest features.**
Compare extracted information against the template sections. For each gap:
- If the section is mandatory for this complexity level (see population matrix below), prepare a follow-up question.
- If the user's description implies a UiPath capability they didn't name, note the suggestion.

UiPath feature suggestions to proactively offer:
- PDFs, scanned documents, images of forms -> Document Understanding
- Desktop app interaction, clicking, typing, reading screen -> UI Automation (RPA workflows)
- REST APIs, connectors, third-party services -> Integration Service
- Multiple automations coordinated -> Orchestrator queues, Maestro flows
- Web forms or dashboards for end users -> Coded Apps
- AI/ML or LLM-powered decisions -> Coded Agents

**Step 5 — Ask follow-up questions (if needed).**
Group related gaps into a single set of questions. Ask all at once — do not ask one at a time. State what you already know from the description so the user doesn't repeat themselves.

For simple genomes: skip follow-ups entirely if the description is sufficient, or ask at most 1 round.
For medium genomes: 1-2 rounds maximum.
For complex genomes: 2-3 rounds maximum.

After the final round, proceed to generation regardless of remaining gaps. Fill gaps with reasonable defaults and stub guidance.

**Step 6 — Generate genome.**
Read the genome template from [genome-template.md](./references/genome-template.md). Populate every section according to the template population matrix:

| Section | Simple | Medium | Complex |
|---------|--------|--------|---------|
| Overview | Full (1 paragraph) | Full (2-3 paragraphs) | Full (2-3 paragraphs) |
| Target Applications | Full | Full | Full |
| Configuration Questions | Stub: "Description covers the scope — no additional configuration needed." | Full (3-5 questions) | Full (5+ questions) |
| Workflow | Full (3-5 steps) | Full (5-8 steps) | Full (detailed, 8+ steps) |
| Business Rules | Stub: "No explicit business rules — agent applies standard validation patterns." | Full | Full |
| Error Handling | Stub: "Standard error handling — retry on transient failures, log and skip on permanent errors." | Full | Full |
| Acceptance Criteria | Full (3-4 criteria) | Full (5-7 criteria) | Full (7+ criteria) |
| Build With | Full | Full | Full |
| Complexity | Full | Full | Full |
| Tags | Full | Full | Full |

"Full" means populated with specific content derived from the interview. "Stub" means the section heading is present with a one-line guidance note.

For the **Build With** section: map each major workflow step to a skill using [skill-mapping-guide.md](./references/skill-mapping-guide.md). Include rationale for each choice.

For **Acceptance Criteria**: derive each criterion from a specific workflow step. Use the pattern: "Given [input], the automation [observable outcome]" or "[Specific action] produces [specific result]". Reference the existing genome examples for the expected specificity level (see `.genome_spec/examples/`).

**Step 7 — Write file.**
Write the genome to the user's current working directory as `{slug}-genome.md`. The slug is derived from the automation name: lowercase, hyphens for spaces, no special characters. Example: "Invoice Processing" -> `invoice-processing-genome.md`.

**Step 8 — Offer edits.**
After writing, tell the user the file has been created and ask: "Want to adjust anything?" If they request changes, edit the file in place and confirm.

### 5. Reference Navigation
- **[genome-template.md](./references/genome-template.md)** — Full genome template with all sections. Read this to populate the genome output.
- **[skill-mapping-guide.md](./references/skill-mapping-guide.md)** — Which UiPath skill handles which automation type. Consult when populating the Build With section.

### 6. Anti-patterns

1. **Asking the user to declare complexity.** The agent infers it. Never say "Is this a simple, medium, or complex automation?"
2. **Showing a preview before writing.** Write the file first, then offer edits. No "Here's what I'll generate — look good?" step.
3. **Generic acceptance criteria.** "Completes successfully" and "handles errors" are banned. Every criterion must reference a specific input/output or workflow step.
4. **Omitting sections.** Even if a section doesn't apply, include it with a stub. The template must be complete.
5. **Asking too many questions.** Respect the follow-up limits per complexity level. Extract as much as possible from the initial description. When in doubt, generate with reasonable defaults and offer edits.
6. **Top-level orchestration annotation.** Orchestration is a workflow step like any other, with its own skill in Build With. Do not add a separate "Orchestration" section or top-level note.
7. **Cross-referencing other skills in SKILL.md.** This skill is self-contained. The genome output references build skills, but SKILL.md does not import from or depend on other skill definitions.

The file should be approximately 200-280 lines. Keep it focused — the template and mapping details are in the reference files, not inlined here. SKILL.md contains the workflow, rules, and decision logic.
